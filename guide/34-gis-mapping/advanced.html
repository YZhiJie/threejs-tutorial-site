34.2 进阶应用：地形、影像与矢量数据上屏 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ②⑨ 与 ㉑ 再阅读。

核心概念讲解 ​

接桥：⑯ 的地形是噪声造的，GIS 的地形是高程数据给的 ​

在 ⑯ 大场景 · 地形与 LOD 里，我们用噪声函数造过一片山地：height = fbm(x, z) * amplitude，好看、可控、随便生成。那是视觉地形，本质是一张"看起来很地形"的函数。

GIS 的地形不一样：它是测量结果。每一格高程都对应地球上某个经纬度，来自航测、卫星雷达或实地测量，存成 GeoTIFF 或点云，带坐标系、带精度、带 no-data。你不能"调一个参数让它更高"，只能如实呈现（或者按视觉需要做高度夸张）。

这个差别会改变整条管线的写法：噪声地形可以运行时生成，GIS 地形必须先做数据预处理（重投影、重采样、切片、压缩），再按需加载。这一篇讲的就是从"高程数据"到"可渲染网格"的完整链路。

DEM、DSM、DTM：三张"高度图"的分工 ​

名称全称高度包含什么典型来源适用场景
DEMDigital Elevation Model地面高程（通常指裸地）测绘、SRTM、ASTER地形底图、坡度分析
DSMDigital Surface Model地面 + 建筑 + 植被等一切表面航测、倾斜摄影、激光雷达城市三维、可视域分析
DTMDigital Terrain Model裸地地形（与 DEM 常互换使用）测绘成果工程土方、洪水淹没
CHMCanopy Height Model植被冠层高度 = DSM − DTM林业遥感树高、生物量

做城市白模时，如果拿 DEM 做地面、再把建筑按属性高度立起来，建筑底部可能悬空——因为 DEM 在建筑位置给的是"挖空"的裸地高程，而真实地面被建筑覆盖。更稳的做法是用 DTM 做地面，建筑底面按 DTM 采样并向下延伸一段"基础"，把缝隙埋掉。

GeoTIFF → 高度图 → PlaneGeometry 顶点 ​

GeoTIFF 是"带地理信息的栅格"。它除了像素值，还带 CRS、仿射变换（像素行列 → 经纬度）、no-data 值、以及高程单位。上屏前要处理四件事：

  1. 重投影：把源 CRS 转到城市原点下的局部 ENU，或至少转到 WGS84 / Web Mercator。
  2. 重采样：把任意分辨率采样到 2 的幂网格（如 257×257、513×513），保证结构规整。
  3. 填补 no-data：用邻域插值或最近有效值填坑，否则地形会出现突兀的"洞"。
  4. 换算单位：确认高程是米还是英尺、是椭球高还是 1985 国家高程基准，必要时加减基准差。

高度图的位深也影响观感。8 位只能表示 0~255 个台阶，1000 米的落差每级约 4 米，缓坡上会出现明显的"梯田"；16 位有 65536 级，精度足够城市尺度。因此运行时用的高度图通常是 16 位 PNG、EXR 或原始 Float32 数组，而不是截了图的普通 JPG。

然后才是"顶点位移"：把高度图的一个像素对应到网格的一个顶点，y = (h - baseHeight) * verticalScale。

瓦片金字塔与 LOD：z/x/y 的切分规则 ​

Web 地图把世界切成四叉树：第 z 层有 4^z 个瓦片，编号 x 从左到右、y 从上到下，瓦片大小通常是 256 或 512 像素。任意经纬度都能算出它所在的瓦片：

x = floor((lon + 180) / 360 * 2^z)
y = floor((1 - ln(tan(φ) + 1/cos(φ)) / π) / 2 * 2^z)

每一层的地面分辨率大约是 156543.034 * cos(纬度) / 2^z 米/像素。下表以 256 px 瓦片、北纬 40° 为例：

城市级场景并不会加载所有层级的瓦片，而是按**屏幕空间误差（SSE）**挑一层：当前层级一个像素覆盖的地面米数超过阈值就降级，小于阈值就升级。再叠加视锥剔除与距离排序，通常同时存在的瓦片只有几十到一百多张。

影像贴图与地形贴合 ​

影像瓦片贴到地形上有三个技术点：

  1. UV 对齐：地形网格的 UV 必须和影像瓦片的切片范围严格对应，否则道路会"漂"到山坡上。
  2. 色彩空间：影像是颜色贴图，texture.colorSpace = SRGBColorSpace；高程是数据，必须 NoColorSpace，两者不能混。
  3. 接缝：相邻瓦片边缘的采样要一致，常见做法是让瓦片边缘多采一圈像素（overlap），或者在地形网格外加一圈向下的 skirt（裙边）遮住裂缝。

影像与地形不是"贴上去就完了"：如果地形网格的分辨率低于影像，山脊会被"抹平"，建筑和道路看起来像浮在模型表面。这时要么提高网格分段，要么用法线贴图 / 位移贴图补细节，但都要付出显存与顶点开销。

GeoJSON 到三维：点、线、面的三种落地方式 ​

GeoJSON 是矢量数据的通用交换格式，坐标顺序是 [经度, 纬度]（这一点必须记住，反了就跑到南极）。

几何类型三维落地方式关键参数常见问题
PointSprite / InstancedMesh 小标记 / CSS2D 标注屏幕像素尺寸、聚合阈值近大远小失控、点太多
LineStringLine2 + LineMaterial，或手工生成带状网格线宽（米）、端点样式WebGL 原生 lineWidth 只支持 1 px
PolygonShapeGeometry 填充 / ExtrudeGeometry 挤出挤出高度、洞、底面绕序反了导致法线朝下、洞丢失
MultiPolygon拆成多个 Shape 合并合并粒度、draw call每个 feature 一个 Mesh，draw call 爆炸

面的处理最容易踩坑：GeoJSON 的环有绕序约定（外环逆时针、内环顺时针），但数据质量参差不齐。稳妥做法是统一用 Shape 的 holes 表达内环，并在挤出后检查法线；高度从 properties 里取（例如 height、levels * 3），取不到时给一个区域默认值。

线和面还有两种常见落地方式：道路不要用 WebGL 原生线段（线宽被限制为 1 px），而是沿折线法线方向偏移出左右两条边，拼成一条带宽度的"带状网格"；面则用 ShapeGeometry 做三角剖分填充，或者再挤出成体。两者都要在 ENU 米制坐标里完成，线宽才有真实的米制含义。

建筑白模：LoD1 与 LoD2 ​

级别几何内容数据要求视觉与成本
LoD1底面轮廓 + 高度，挤出成平顶盒子建筑轮廓 + 高度属性便宜、通用，城市级首选
LoD2屋顶形状（坡屋顶、女儿墙）+ 立面拆分CityGML / 精细建模精细，但数据稀缺、制作贵
LoD3门窗、阳台等建筑细节精细测量通常只用于地标单体

城市级大屏绝大多数用 LoD1：轮廓挤出 + 一点屋顶细节 + 材质颜色变化，已经足够识别城市肌理。LoD2 用在少数地标或近景飞行视角里，远看和 LoD1 没有区别。

纠偏与投影在管线中的位置 ​

正确的顺序只有一条：

源数据（任意 CRS）
   → ETL：重投影 / 纠偏 / 统一单位
   → WGS84（数据交换层）
   → 城市原点下的 ENU（渲染层）
   → 生成 BufferGeometry
   → 每帧渲染

要点是转换发生在建几何之前，且只发生一次。不要在渲染循环里逐帧转换，也不要在着色器里做坐标变换。每份数据入库时写清楚 sourceCrs、targetCrs、origin、verticalDatum，验收时用控制点抽样比对，误差超过阈值就不许发布。

分块加载与调度 ​

城市级数据不可能一次性全进显存，需要"按需加载 + 及时释放"：

  • 切块粒度：按瓦片或按街区，块内几何合并 / 实例化，块间独立加载。
  • 优先级：视锥内优先，距离近优先，屏幕占比大优先；预加载下一层级的父瓦片，避免空白。
  • 预算：每帧最多解析 N 个块、上传 M MB 纹理，超出的排队。
  • 释放：离开视锥一段时间后 dispose() 几何与纹理，保留 LRU 缓存。
  • 失败处理：单块 404 不应阻塞整场景，用占位色块或父级低清瓦片兜底。

纹理压缩与显存预算 ​

一张 2048×2048 的 RGBA8 贴图 = 16 MB，加 mipmap 约 21 MB；一百张就是 2 GB，直接爆显存。压缩是必选项：

格式压缩比画质典型用途
KTX2 / Basis ETC1S约 1/8 ~ 1/6中影像底图、颜色贴图
KTX2 / Basis UASTC约 1/4高法线、粗糙度、近景细节
原始 RGBA81×无损小图、调试图

估算公式：

显存 ≈ 宽 × 高 × 4 字节 × 1.33（mipmap）× 数量

显存预算要和 ㉖ GPU 分析与性能预算 一起定：先算"同时可见的瓦片数 × 单瓦片成本"，再反推最大层级与缓存容量。不要先做高清素材、最后才来砍分辨率。

术语解释：

  • DEM / DSM：裸地高程 / 含地表物体的高程。
  • GeoTIFF：带地理参考的栅格文件格式。
  • 瓦片金字塔：多层级四叉树切片，层级越高分辨率越高。
  • SSE：屏幕空间误差，衡量一个瓦片投影到屏幕后的像素误差。
  • LoD1 / LoD2：建筑白模的细节等级，前者是平顶盒子，后者含屋顶与立面。
  • 裙边 skirt：地形网格边缘向下延伸的一圈面，用来遮挡瓦片接缝。

常见坑 ​

  1. 把 GeoTIFF 高程当颜色贴图：高程是数据，必须 NoColorSpace，否则高度会被"调色"，地形整体变形。
  2. 高程单位没核对：源数据是英尺、或高程基准不同，建筑会整片悬空或穿地。
  3. 瓦片接缝裂开：相邻瓦片分辨率 / 采样不一致；用 skirt 或边缘 overlap 兜底。
  4. 每个 GeoJSON feature 一个 Mesh：十万栋楼 = 十万 draw call；必须合并或实例化。
  5. 只按距离切 LOD，不看屏幕占比：细长的远景瓦片被误判为"近"，白白加载高清。

① 高程图 → 顶点位移：重点是"先采样、再写入，最后重算法线"，不要在循环里反复 computeVertexNormals()。

js
const geo = new THREE.PlaneGeometry(EXTENT, EXTENT, seg, seg)
geo.rotateX(-Math.PI / 2) // 平面转到 XZ，Y 轴留给高程

const pos = geo.attributes.position
for (let i = 0; i < pos.count; i++) {
  const x = pos.getX(i)
  const z = pos.getZ(i)
  const u = x / EXTENT + 0.5   // 东西向 0~1
  const v = 0.5 - z / EXTENT   // 南北向：-Z 为北，所以 v=1 在北
  pos.setY(i, sampleHeight(u, v) * exaggeration) // 高度只在 Y 轴夸张
}
pos.needsUpdate = true
geo.computeVertexNormals() // 全部写完后只算一次

双线性采样的意义是：DEM 的像素格通常比网格粗，直接按最近邻取点会让地形出现"台阶"。演示里先把高程缓存成 161×161 的网格，再对任意 UV 做双线性插值，纹理与顶点就都能复用同一份数据。

function lonToTileX(lon, z) {
  return Math.floor((lon + 180) / 360 * 2 ** z)

function latToTileY(lat, z) {
  const rad = lat * DEG
  const m = Math.log(Math.tan(rad) + 1 / Math.cos(rad))
  return Math.floor((1 - m / Math.PI) / 2 * 2 ** z)
}

③ GeoJSON 面 → 挤出建筑：坐标先转 ENU，再用 Shape 挤出。

js
function polygonToBuilding(ring, holes, height) {
  const shape = new THREE.Shape()
  ring.forEach(([lon, lat], i) => {
    const { east, north } = lonLatToLocal(lon, lat)
    if (i === 0) shape.moveTo(east, north)
    else shape.lineTo(east, north)
  })

  // 内环（院落、天井）必须进 holes，否则会被填实
  holes.forEach((hole) => {
    const path = new THREE.Path()
    hole.forEach(([lon, lat], i) => {
      const { east, north } = lonLatToLocal(lon, lat)
      if (i === 0) path.moveTo(east, north)
      else path.lineTo(east, north)
    })
    shape.holes.push(path)
  })

  const geo = new THREE.ExtrudeGeometry(shape, {
    depth: height,
    bevelEnabled: false
  })
  geo.rotateX(-Math.PI / 2) // 挤出方向 +Z 转成世界 +Y，底面落到 y=0
  return geo
}

④ 分块调度骨架：把"加载、上传、释放"收敛到一个队列，避免一帧内同时解析几十个块。

js
const queue = []
const cache = new Map()

function requestChunk(key, priority) {
  if (cache.has(key)) return
  queue.push({ key, priority })
  queue.sort((a, b) => a.priority - b.priority) // 视锥内、距离近的先来
}

function pumpChunkBudget() {
  const budgetMs = 6 // 每帧最多花 6 ms 处理块
  const start = performance.now()
  while (queue.length && performance.now() - start < budgetMs) {
    const task = queue.shift()
    const chunk = buildChunk(task.key) // 解析 GeoJSON / 上传纹理
    scene.add(chunk)
    cache.set(task.key, chunk)
  }
}

⑤ 显存估算：把预算写进 HUD，团队就不会在"为什么手机崩了"上反复猜。

js
function textureBytes(w, h, mip = true) {
  return w * h * 4 * (mip ? 1.33 : 1)
}

function geometryBytes(vertexCount, indexCount) {
  return vertexCount * 32 + indexCount * 4 // pos + normal + uv = 8 个 float32
}

const total = (textureBytes(2048, 2048) + geometryBytes(1e5, 6e5)) / 1024 / 1024
console.log(`单块显存约 ${total.toFixed(1)} MB`)

演示 HUD 里的数字就是按这个公式算的：顶点 32 字节、索引 4 字节、贴图 RGBA8 加 mip 链 1.33 倍。

常见问题解答 ​

Q1：把 GeoTIFF 直接拖进 Three.js 当贴图，地形高度完全不对，怎么办？

先把"数据"和"颜色"分开。GeoTIFF 的高程是标量，不能按 sRGB 颜色解码，读像素时要用数据路径（位深正确、NoColorSpace），而不是让浏览器按图片解码成 8 位 sRGB。其次确认高程范围和单位：很多数据的值域是 0~65535 的整型，需要按比例换算成米；再确认垂直基准，椭球高与 1985 国家高程基准之间可能差几十米。正确流程是离线 ETL：读高程 → 换算单位 → 填补 no-data → 重采样 → 输出 16 位高度图或 Float32 数组 → 运行时只做采样和顶点位移。

Q2：相邻地形瓦片之间出现一条细缝，怎么消掉？

裂缝通常来自两处：边界顶点不共享（两个瓦片各自采样，边缘值不完全一致）和浮点误差。工程上的解法有三层：① 相邻瓦片边缘使用同一套采样规则（同一个高度图、同一插值方式）；② 给每块地形加一圈向下的 skirt，即使有缝也被裙边挡住；③ 在瓦片边界做 1~2 像素的 overlap，让采样有冗余。注意不要用"整体抬高一点点"的方式掩盖，那会让道路与地形脱开。

Q3：GeoJSON 挤出后建筑是"倒扣"的，或者中间的洞被填实了，怎么排查？

先查绕序，再查 holes。Three.js 的 Shape 依赖外环与内环的方向来区分实体和洞，GeoJSON 数据质量参差时，需要统一绕序（外环逆时针、内环顺时针）后再构建。洞必须放进 shape.holes，不能简单地"再画一个环"。最后查旋转方向：ExtrudeGeometry 沿 +Z 挤出，rotateX(-Math.PI / 2) 后 +Z 变成 +Y；如果写成 +Math.PI / 2，建筑会朝地下长。排查时先只渲染一个 feature，把材质设成 DoubleSide 看结构，再换回单面。

Q4：城市级高清影像一加载就爆显存，除了降分辨率还能做什么？

按收益排序：① 用 KTX2 / Basis 压缩，2048 的 RGBA8 从 21 MB 降到几 MB；② 按层级和视锥只加载可见瓦片，别把整座城市一次拉满；③ 限制同时驻留的瓦片数量，用 LRU 释放离开视锥的块；④ 对远景瓦片降采样，屏幕上看不出差别；⑤ 关闭不必要的 mipmap 或改用各向异性过滤的合理档位。最后用显存预算表约束美术规格：先定"同屏最多多少 MB"，再决定单张瓦片的分辨率与压缩格式。
