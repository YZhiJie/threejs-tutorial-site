34.1 基础入门：坐标系、投影与瓦片 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ②⑨ 与 ㉑ 再阅读。

核心概念讲解 ​

接桥：㉑ 的园区坐标是"自己编的"，真实世界得用经纬度 ​

在 ㉑ 大屏与数字孪生 里，我们搭了一个很漂亮的园区：楼群按 (r, c) 排布，坐标是 x = (c - 2) * 25、z = (r - 2) * 25，单位是米，原点在园区中心。那套坐标只对这一个园区有效，换一个园区、换一份 GIS 数据，它立刻失效。

原因很直接：园区坐标是"自己编的"。它只回答"第几排第几列、离中心多少米"，不回答"这栋楼在地球上的哪个位置"。而 GIS 要做的恰恰是后者——把真实世界的经纬度、地形、道路、建筑轮廓搬进三维场景。只要场景里出现了第二份数据（比如一张卫星底图、一条规划红线），"自己编的坐标"就会和它对不上。

这一篇补上的就是这条数据链的第一环：经纬度怎么变成三维里可以用的米制坐标，以及为什么不能随便转。

WGS84、GCJ-02、BD-09：三套坐标，一套地图 ​

国内做地图相关项目，第一课不是投影，而是"你手上这份数据到底是哪套坐标"。

坐标系别名 / 来源数值特征典型来源能否直接叠在国内底图上
WGS84国际通用大地坐标系（EPSG:4326）真实经纬度，GPS 原始输出GPS 设备、部分开源数据、海外数据否，会整体偏移数百米
GCJ-02火星坐标、国测局坐标在 WGS84 上做非线性偏移高德、腾讯、国内互联网底图是（这些底图本身就是 GCJ-02）
BD-09百度坐标在 GCJ-02 上再叠加一次偏移百度地图及其 SDK否，需要先转回 GCJ-02

三套坐标描述的是同一块地，但数值不同。北京地区 WGS84 与 GCJ-02 的差值通常在 500 米上下，方向偏东偏北；不同城市的偏移量并不相同，而且不是简单的平移，所以不能用"统一加一个常数"来纠偏。这也是国内项目里"模型整体偏了 200 米"这类事故的常见根因。

坐标系合规要讲清楚两点：

  1. 在中国境内公开发布的地图产品，底图必须使用依法审核通过的坐标系（通常是 GCJ-02 或经过审核的数据），不能直接把 WGS84 卫星影像当公开底图发布。
  2. 坐标转换只做一次，并且要记录在数据管线里。最怕的是同一条链路里转两次、或者一半数据转了另一半没转——结果是画面里每类要素各偏各的。

正确的心智模型不是"哪个坐标更准"，而是**"数据源与底图必须使用同一套坐标系"**。WGS84 是"真实"，GCJ-02 是"合规"，两者都正确，混用才错误。

从球面到平面：Web Mercator（EPSG:3857） ​

经纬度是球面坐标，三维场景是平面坐标。中间必须做一次投影。

Web Mercator（EPSG:3857，也叫 Pseudo-Mercator）是 Web 地图事实上的标准：

x = R * λ(弧度)
y = R * ln(tan(π/4 + φ(弧度)/2))
R = 6378137 m（WGS84 长半轴，这里按球体使用）

它的特点是：

  • 单位是米，可以直接和三维场景的米制单位对齐；
  • 经纬线在平面上是直线，瓦片切分非常规整；
  • 面积变形严重：高纬度被拉伸，格陵兰看起来和非洲差不多大；
  • 不能用它量测真实距离，尤其在纬度 40° 以上，横向比例被放大了约 1/cos(φ) 倍。

所以 Web Mercator 的定位是"瓦片索引与切片用的公共平面"，不是"测量坐标系"。要在城市尺度做精确量算，应该用局部投影或 ENU 切平面。

坐标 / 投影单位适用尺度典型用途主要陷阱
EPSG:4326（经纬度）度全球数据交换、GPS不能直接当米用
EPSG:3857（Web Mercator）米全球~区域瓦片、底图、粗略定位面积/距离变形
局部 ENU 切平面米城市~园区三维场景、量算远离原点后误差变大
屏幕像素px屏幕UI 标注、拾取与 DPR 相关

局部 ENU 切平面：把经纬度变成米 ​

城市级场景最常用的做法，是在城市中心取一个原点，把经纬度差换算成"东向 / 北向"的米数：

east  = (λ - λ0) * (π/180) * R * cos(φ0)
north = (φ - φ0) * (π/180) * R

其中 λ0、φ0 是原点的经纬度，R = 6378137 m。这个公式假设城市范围足够小，可以把地球表面近似成一个切平面。

Three.js 的坐标约定是 -Z 朝北、+X 朝东、+Y 朝上，所以落进场景时再做一次映射：

x = east
z = -north

这一步看似只是符号，但漏掉它，整个城市会南北翻转，而且从截图上一时半会儿未必看得出来——建筑还在、道路还在，只是方向反了。

局部切平面的误差随距离平方增长。20 km 处地球曲率造成的高差约 31 m，对城市大屏可以忽略；但如果是省级范围，就必须换回购地投影或分带投影，否则边缘会明显"翘起来"。

坐标原点与缩放：1:1 米，还是夸张缩放 ​

三维场景有两种尺度策略：

策略做法优点代价
1:1 米1 单位 = 1 米，建筑 100 m 高就是 100与 GIS 数据天然对齐，量算可信城市太平，视觉冲击弱
夸张缩放高度乘 2~5 倍，平面仍 1:1天际线更抓眼，适合大屏高度数据失真，不能做量算

关键纪律是：平面坐标不要夸张，只夸张高度。平面一旦拉伸，所有经纬度换算、拾取、纠偏都会失效；高度夸张只是视觉参数，不会破坏平面拓扑。演示 terrain-imagery-lab.html 的高程夸张系数就是只作用于 Y 轴。

"每个城市一个原点"是工程上最常见的做法：把原点写进配置（origin: { lon, lat }），所有数据在入库时统一转到这个原点下的 ENU 坐标。这样每个城市都有自己的一套局部米制坐标，互不干扰，也避免全国范围用一个原点导致数值过大。

原点本身要作为元数据管理，不能只存在于某位同事的脑子里。建议在数据文件里同时保留 lon/lat 与 x/z 两套字段，并记录 origin 与 crs，任何一次交付都能复算。

Float32 抖动与浮动原点 ​

GPU 里绝大多数顶点属性是 float32。它的尾数是 23 位，相对精度约 2^-24 ≈ 6e-8。在 100 km 处，绝对分辨率大约是：

100000 m * 6e-8 ≈ 0.006 m

单看数值并不大，但真实画面里的"抖"往往是三件事叠加：顶点坐标绝对值过大导致最低位被吃掉、相机近远裁剪面比例失衡导致深度精度不足、以及阴影/后处理等多次采样放大了误差。表现是远处模型边缘闪烁、Z-fighting、建筑表面出现斑驳的"爬行"纹理。

工程上的解法有优先级：

  1. 浮动原点（floating origin）：把场景整体平移，让相机始终在原点附近。World 坐标不变，只是渲染时减去一个 anchor。
  2. 分块（tiling / chunking）：每个瓦片或街区用自己的局部原点建模，互相之间只差一个平移，GPU 看到的坐标始终很小。
  3. 收紧相机近远裁剪面：near 不要设 0.1，far 不要设几十万，按场景尺度取合理值。
  4. 不要指望 logarithmicDepthBuffer 包治百病：它改善深度分布，但不会修复顶点属性本身的精度损失。

术语解释：

  • 基准面 / 椭球：描述地球形状的数学模型，WGS84 是其中一种。
  • 投影：把球面坐标映射到平面的数学变换，必然产生变形，只是变形类型不同。
  • ENU：East-North-Up，局部东-北-天切平面坐标系。
  • 浮动原点：渲染前把世界整体平移，使相机附近的坐标绝对值保持很小。
  • 纠偏：把数据从一种坐标系转换到另一种，使它与底图对齐。

常见坑 ​

  1. 模型与底图错位几百米：数据是 WGS84，底图是 GCJ-02，两边都没"错"，只是没统一。
  2. 越远越飘：原点选在城市一头，另一头 30 km 外的模型开始抖；应改用浮动原点或分块。
  3. 经纬度顺序写反：GeoJSON 的坐标是 [经度, 纬度]，而很多 API 是 (lat, lon)。反了会跑到南极附近，日志里一眼能看出，但坐标数组里不容易发现。
  4. 把 Web Mercator 当等距：在高德/百度底图上量出来的"米"不是地面真实米，做面积统计会系统性偏大。
  5. 让模型绕世界原点旋转：整座城市绕原点转，越远偏移越大；旋转中心应该用相机 target 或当前街区中心。
  6. 把经纬度差直接当米用：lon - lon0 是角度，0.01 度在赤道约 1113 米、在北纬 40° 只有约 852 米；不做 cos(φ0) 换算，东西向会系统性偏大。

function lonLatToMercator(lon, lat) {
  return {
    x: R * lon * DEG,
    y: R * Math.log(Math.tan(Math.PI / 4 + lat * DEG / 2))
  }
}

// 经纬度 -> 局部 ENU；三个分量同时给出，方便 HUD 与拾取复用
function lonLatToLocal(lon, lat) {
  const east = (lon - ORIGIN.lon) * DEG * R * Math.cos(ORIGIN.lat * DEG)
  const north = (lat - ORIGIN.lat) * DEG * R
  return { east, north, x: east, z: -north } // Three.js 里 -Z 朝北
}

// 局部坐标 -> 经纬度：拾取后回填信息卡要用反向公式
function localToLonLat(x, z) {
  return {
    lon: ORIGIN.lon + x / (DEG * R * Math.cos(ORIGIN.lat * DEG)),
    lat: ORIGIN.lat - z / (DEG * R)
  }
}

② 点击选点：射线拿到地面交点，再反算经纬度。三维里拾取到的永远是米制坐标，必须反算回经纬度才能和业务数据对齐。

js
const raycaster = new THREE.Raycaster()
const pointer = new THREE.Vector2()

renderer.domElement.addEventListener('pointerup', (e) => {
  // 先判断是不是拖拽：移动超过 6px 就不算点击
  if (Math.hypot(e.clientX - downX, e.clientY - downY) > 6) return

  pointer.x = (e.clientX / innerWidth) * 2 - 1
  pointer.y = -(e.clientY / innerHeight) * 2 + 1
  raycaster.setFromCamera(pointer, camera)

  const hit = raycaster.intersectObject(ground, false)[0]
  if (!hit) return

  const ll = localToLonLat(hit.point.x, hit.point.z)
  params.lon = ll.lon
  params.lat = ll.lat
  ctrlLon.updateDisplay() // lil-gui 的滑杆也要同步，否则界面和数据会脱节
  ctrlLat.updateDisplay()
  refresh()
})

演示里的偏移量是固定的模拟值，真实项目必须用权威的坐标转换服务或经过审核的转换库，并且把"源坐标系"写进数据的元信息。

④ 浮动原点的最小实现：世界坐标与渲染坐标分离，渲染坐标每次都由"真实坐标 − anchor"重新算出来，避免累减。

js
// worldPos / worldTarget 是未平移前的真实坐标
function renderFromWorld(worldPos, worldTarget) {
  // 每移动约 1 km 才换一次原点，避免每帧抖动
  const anchor = new THREE.Vector3(
    Math.round(worldPos.x / 1000) * 1000,
    0,
    Math.round(worldPos.z / 1000) * 1000
  )

  world.position.copy(anchor).negate()   // 世界整体反向平移
  camera.position.copy(worldPos).sub(anchor)   // 相机回到小坐标
  controls.target.copy(worldTarget).sub(anchor) // target 同步，否则视角会跳
}

实际项目里还要把光照、雾、标注一起纳入 anchor 的平移，否则会出现"地动了、灯没动"的割裂感。

常见问题解答 ​

Q1：GCJ-02 的偏移能不能用一个固定的经度差、纬度差修回来？

不能。GCJ-02 的偏移是地域相关的非线性变换，不同城市、不同位置的偏移量和方向都不同，用全国统一的常数修正只能让某一块区域"看起来对"，其他区域一样错。工程上的正确做法是：① 在数据入库阶段用权威转换服务统一转到目标坐标系；② 转换结果连同源坐标系一起存进元数据；③ 上线前用已知控制点抽样验收，而不是靠肉眼。另需注意合规：境内公开地图产品应使用审核通过的坐标系与底图。

Q2：模型和底图差了约 200 米，但两边的坐标数值看起来都"合理"，怎么定位？

先查坐标系，而不是查模型。把同一个已知地物（例如一条道路交叉口）在两套数据里的坐标分别打印出来：如果差值在几百米且方向一致，基本就是 WGS84 与 GCJ-02 混用；如果差值随位置变化，则是投影或原点不一致；如果差值是个整齐的整数（比如 1000 米），更可能是某个环节多做了一次平移。定位顺序是"源坐标系 → 转换次数 → 原点 → 单位"，四步走完再怀疑建模。

Q3：局部坐标用 1:1 米，城市看起来像一张纸，能不能直接整体放大？

可以放大，但要区分"平面缩放"和"高度夸张"。整体缩放（把 1 米当 2 米）会同时改变平面距离与建筑高度，所有经纬度换算、拾取、量算都会失真；只夸张高度则只影响视觉。大屏常用做法是平面严格 1:1、高度乘 2~3 倍，再把相机压低做透视夸张，既保住数据可信度，又拿到视觉冲击。

Q4：10 万米外的模型抖动，开 `logarithmicDepthBuffer` 就够了吗？

通常不够。它改善的是深度缓冲的分布，让远近距离的深度精度更均匀，但顶点坐标本身在 float32 下的精度损失依然存在。优先级应该是：先做浮动原点或分块，把渲染坐标压到几千米以内；再收紧相机 near/far；最后才考虑对数深度缓冲。若还要更稳，可以用 DoubleFloat 分段顶点属性或把静态几何预合并到局部原点下。

动手小练习 ​

  1. 打开 crs-lab.html，把偏移开关打开，记录左上角"经纬度"与"局部 ENU"两组数字；再用公式手算一遍 Web Mercator 的 X/Y，确认你算出的值与 HUD 一致（允许 1 米以内的四舍五入误差）。
  2. 把 ORIGIN 改成你所在城市的经纬度，观察同一组经纬度在"局部 ENU"里的数值变化；思考为什么原点必须"每个城市一个"，以及原点写错 1 公里会造成什么。
  3. 在演示里加一个"距离量算"按钮：点击两个点，在世界坐标里算欧氏距离，再和用经纬度算出的球面距离对比，记录城市尺度下的误差，并解释这个误差来自哪里。
