34.3 实战案例：城市级 GIS 场景 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ②⑨ 与 ㉑ 再阅读。

核心概念讲解 ​

接桥：㉑ 的园区做了 3 平方公里，城市级是 300 平方公里 ​

㉑ 大屏 · 园区数字孪生 里，我们的园区大约 3 平方公里：63 栋楼、一个扫描环、几条告警卡片，所有东西都能一次加载完。那套做法放到城市级会立刻失效——面积扩大 100 倍，建筑数量可能从 63 栋变成 30 万栋，数据从"一个 JSON"变成"几百个瓦片 + 十几个图层"，相机从"俯瞰一个园区"变成"从 3 公里飞到 25 公里"。

城市级 GIS 场景不是"把园区放大"，而是换一套组织方式：数据按空间分块、渲染按尺度分级、交互按图层隔离。这一篇把 34.1 的坐标链、34.2 的地形与影像，组装成一个能开关图层、能缩放、能点选建筑的城市级场景，并给出交付验收的检查表。

城市级场景的组装清单 ​

图层数据形态渲染方式来源性能要点
地形DEM 网格 / 高度图单个 PlaneGeometry 顶点位移测绘、公开 DEM网格分段与视距匹配
影像底图瓦片纹理贴在地形或独立平面卫星 / 航拍切片压缩、LRU、mipmap
道路GeoJSON LineString合并带状网格 / Line2导航数据、测绘合并成少数 draw call
建筑白模轮廓 + 高度InstancedMesh 或分块合并城市三维、规划数据分块 + LOD + 实例颜色
POI点要素InstancedMesh / Sprite / HTML 标注业务台账聚合、屏幕空间尺寸
标注 / UIHTML叠加在 canvas 上业务系统pointer-events 分层

这份清单有一个共同原则：每个图层都要能独立开关、独立加载、独立释放。图层不是"场景里的一堆 Mesh"，而是一个有生命周期、有数据源、有可见性状态的对象。后面所有性能与交互问题，都建立在这个边界上。

除了"有什么"，还要决定"谁先画"。不透明图层（地形、白模）先画，半透明与叠加层（路网高亮、选中环、热力）后画，标注与 UI 最后叠加；同一图层内的物体尽量按材质与几何合批，避免在渲染顺序上反复横跳。这些顺序如果一开始不定，后期每加一个特效就会打乱一次，性能问题会以"某次提交后突然变慢"的形式出现。

尺度策略：近处细节、远处瓦片 ​

城市级场景必须按"相机距离"准备多档细节。下面是本演示采用的档位表，可以直接当项目模板：

档位相机距目标可见内容建筑细节目标 draw call目标三角数
近景1~3 km白模 + 屋顶细节 + POI逐栋实例 + 屋顶小件5~20< 100 万
中景3~8 km白模 + 道路 + POI逐栋实例，无屋顶3~10< 200 万
远景8~25 km合并白模 + 影像底图整城合并成一个 Mesh< 5< 50 万

注意最后两列的"目标"。城市级项目的性能管理不是"出问题再优化"，而是先定预算再选实现：先决定远景最多 5 个 draw call，才知道必须把整城合并成一个几何体；先决定近景 100 万三角，才知道建筑不能都用 LoD2。

切换档位时要做三件事：移动相机、切换几何、更新拾取策略。三者必须原子地一起变，否则会出现"相机在远景、但拾取还按近景算"的错位。

三档制适合演示与汇报，真实项目更常用连续的屏幕空间误差（SSE）阈值：每栋建筑、每块地形各自计算"在当前相机下占多少像素"，占得少就降级，占得多就升级。SSE 的好处是尺度连续变化时不会出现"整城突然换一套几何"的跳变，代价是需要给每个对象维护 LOD 状态，并且切换时要避免同一帧内反复升降级（通常加一个滞回区间）。无论用哪种方式，原则都一样：精度跟着屏幕走，而不是跟着数据量走。

相机与拾取：从屏幕点回到经纬度 ​

城市级拾取的完整链路是：

屏幕坐标 → NDC → Raycaster → 命中实例 → instanceId
        → 建筑台账（name / height / x / z）
        → localToLonLat(x, z)
        → 信息卡

这里有两个容易忽略的点：

  1. 拾取只对当前档位有效的几何做。远景是合并白模，没有 instanceId，点击就没有楼栋语义；正确的产品行为是提示"请切换到近景/中景"，而不是随便返回一个结果。
  2. 命中容差要跟随尺度。近景可以按真实几何命中；远景如果还想点中，需要额外的"拾取代理"（比如每个街区一个不可见的盒子），否则小建筑在屏幕上只有几个像素，几乎点不中。

坐标回填必须走与 34.1 相同的 localToLonLat，并且显示时保留 6 位小数——这既是精度，也是"这份数据可信"的视觉信号。

性能策略：分块、实例化、显存、LOD ​

手段解决什么本演示的做法城市级建议

一个可用的经验值：城市级 300 km²、30 万栋 LoD1 建筑，按 500 m 分块约 1200 块；同屏可见 40~80 块；每块合并后 1 个 draw call；加上地形、道路、POI、标注，总 draw call 控制在 100 以内是合理目标。超过这个量级，先怀疑"是不是每栋楼一个 Mesh"。

还有两类成本容易被忽略。一是纹理上传的瞬时尖峰：几十张 2048 瓦片同时进 GPU，主线程会卡住一两百毫秒，表现为"飞行中突然顿一下"，所以必须把上传摊到多帧。二是材质切换：即使 draw call 数量不多，频繁在两种材质之间切换也会打断 GPU 状态，把同材质的物体放在一起渲染（按材质排序）往往比单纯减少对象更有效。

坐标纠偏的验收流程 ​

交付前不要靠"看起来对齐"，按下面五步走：

  1. 源坐标系抽样：从每份数据里随机取 5 个点，用权威服务反查真实经纬度，确认 sourceCrs 标注正确。
  2. 统一转换：所有数据转到 WGS84，再转到城市原点下的 ENU；转换脚本要幂等，重复执行结果一致。
  3. 叠合误差：把建筑轮廓、道路、影像底图叠在一起，抽查 10 个控制点，平面误差控制在 1~3 m（城市级可放宽，但要有书面阈值）。
  4. 高程基准：核对 DEM 的垂直基准与建筑高度基准，抽样检查建筑底面是否贴地，允许下沉 1~2 m 埋入地形，不允许悬空。
  5. 视觉回归：固定 3 个机位（近、中、远）截图，与上一版做 diff；坐标类改动必须在这三张图上都看不出位移。

验收记录要落盘：数据版本、转换参数、控制点误差、验收人。没有记录的"对上了"，下一次换数据就会重新错。这套流程看起来繁琐，但它把"坐标对不对"从主观判断变成了可复核的数据——出了问题能沿着记录回查是哪一批数据、哪一次转换、哪一个原点，而不是整组人对着屏幕猜。

常见交付坑 ​

  1. 多源数据坐标系不一致：建筑是 WGS84、道路是 GCJ-02、底图又是另一套；单看每层都"对"，叠起来全错。
  2. 建筑穿地 / 悬空：地形用了 DSM（含建筑高度），建筑又按属性高度立起，双重计算；或高程基准没统一。
  3. POI 飘在空中：POI 高度固定写死 80 m，而地形在 200 m；应按地形采样高度 + 偏移。
  4. 原点变更没有全链路同步：只改了渲染原点，没改数据转换，整城平移。
  5. 远景合并后无法拾取：交互与 LOD 没有一起设计，产品验收时才被发现。
  6. UI 层挡住拾取：信息卡、图例盖在 canvas 上却没设 pointer-events 规则。

术语解释：

  • 图层（Layer）：一组同源、同生命周期、可独立开关的空间数据。
  • LOD：细节等级，按距离或屏幕误差切换几何精度。
  • 拾取代理（pick proxy）：用于点击检测的简化几何，不参与显示。
  • LRU：最近最少使用缓存策略，用来淘汰离开视锥的资源。
  • 控制点：已知真实坐标的参考点，用于验收坐标精度。

代码示例 ​

对应演示 gis-scene-lab.html：一个 8 km 视窗的程序化城区，地形、道路、建筑白模、POI 四个图层可独立开关，三档缩放切换细节与 draw call，点击建筑显示经纬度、高度与名称。

① 图层管理器：把"可见性"收敛到一个函数。不要在每个 GUI 回调里各自写 if，否则图层组合一多就会互相覆盖。

js
const layers = {
  terrain: terrainMesh,
  roads: roadsMesh,
  buildings: buildingsMesh,
  poi: poiMesh
}

function applyLayers() {
  const level = ZOOM[params.zoom]
  const highOn = params.buildings && level.detail !== 'far'

  layers.terrain.visible = params.terrain
  layers.roads.visible = params.roads
  layers.buildings.visible = highOn
  layers.poi.visible = params.poi && level.detail !== 'far'

  // LOD 相关对象跟随缩放档位，不跟图层开关混在一起
  roofsMesh.visible = highOn && level.detail === 'near'
  lowDetailMesh.visible = params.buildings && level.detail === 'far'
}

常见问题解答 ​

Q1：建筑和底图整体错位约 200 米，但坐标数值都在合理范围内，怎么修？

先确认三件事，顺序不能乱：① 建筑数据的 sourceCrs 是什么，底图用的又是什么；② 转换链里有没有"一半数据转了、一半没转"；③ 渲染原点与数据原点是否一致。200 米这个量级在国内项目里最典型的就是 WGS84 与 GCJ-02 混用，其次才是原点写错。定位方法：取一条道路的交叉口，在底图与建筑数据里各取一个点，打印经纬度和 ENU 坐标，看差值是否随位置变化——固定方向、固定量级通常是坐标系问题；随位置缩放、方向不一致通常是原点或投影问题。修完之后，用本篇的验收流程把控制点误差记录进交付文档。

Q2：缩放后模型边缘抖动、Z-fighting 明显，是什么原因？

抖动通常不是"模型坏了"，而是精度不够。排查顺序：① 相机 near/far 比例是否过大（near=0.1、far=100000 这种配置在城市级非常危险）；② 世界坐标是否动辄十万米级，导致 float32 顶点精度被吃掉；③ 共面物体（道路贴地、选中环贴地）是否做了微小抬高。修复优先级是：先做浮动原点或按街区/瓦片分块，把渲染坐标压到几公里内；再收紧 near/far；最后才考虑 logarithmicDepthBuffer。如果是选中环、道路与地形这种"故意贴面"的物体，给 1~3 cm 的 Y 偏移或用 polygonOffset 比调精度更直接。

Q3：300 平方公里的城市，怎么把帧率稳在 60？

先把预算写死：同屏 draw call < 100、三角数 < 200 万、纹理驻留 < 500 MB。然后按四条线落地：① 建筑按街区合并或实例化，每块最多 1~2 个 draw call；② 纹理瓦片按层级加载，离开视锥的块进 LRU 并 dispose()；③ LOD 按屏幕空间误差切换，远景只保留合并白模；④ 每帧给资源上传设预算（例如 6 ms），避免某一帧突然解析几十个块。最后用 renderer.info 与 GPU 计时器验证，而不是凭感觉。300 km² 并不是"必须全部同屏"，大部分时间你只需要看到十几公里。

Q4：点击建筑经常选不中，或者点到了旁边的楼，怎么提高拾取准确度？

先确认事件链路：信息卡、图例等 HTML 是否设了 pointer-events: none，pointerup 是否被判成了拖拽，NDC 换算是否用了 canvas 的实际尺寸而不是窗口尺寸（有侧边栏或 DPR 时尤其容易错）。再看几何：远景合并白模没有 instanceId，必须切到近/中景或加拾取代理。最后看容差：小建筑在屏幕上只有几个像素，可以用"街区级代理盒 + 二次按距离筛选"的方式提高命中率，或者直接按屏幕坐标做最近要素查询。若同一位置有多个实例，intersectObject 返回数组按距离排序，取第一个即可，但要确认材质没有意外设置 transparent 导致排序异常。
