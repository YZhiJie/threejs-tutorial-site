37.2 进阶应用：表情、口型与动作混合 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ⑮ 与 ⑬，并读过 37.1 的骨骼与蒙皮。

核心概念讲解 ​

接桥：15.3 的 AnimationMixer 会播片段，但数字人要"同时做三件事" ​

在 ⑮ glTF · 动画与状态 的 15.3 里，我们学会了用 AnimationMixer 播放 AnimationClip：一段"挥手"播完，crossFadeTo 到"走路"，action.weight 控制淡入淡出。那条链路的前提是一次主要表演一个片段，片段之间是串行的。

数字人不是这样工作的。一个正在说话的角色，同一秒内至少要同时完成三件事：

  1. 待机层：呼吸、重心微摆、无意识的头部晃动；
  2. 手势层：说到重点时抬手、比划、摊手；
  3. 口型层：按音素时间轴开合嘴巴，同时叠加眨眼。

这三层不是"播完 A 再播 B"，而是并行叠加、各自有权重。如果强行把三层烘成一个长 clip，任何一句台词变化都要重新导出整段动画，完全不可维护。所以 37.2 的核心命题是：把表演拆成可独立驱动的层，再在运行时合成。

维度15.3 的单片段播放37.2 的分层表演
时间轴一条，线性推进多条，各自推进或循环
数据来源资产里的关键帧骨骼动画 + morph 权重 + 程序函数
混合方式crossFadeTo 片段过渡权重叠加、按通道覆盖
变更成本改动画要重导出改台词只需换时间轴
典型故障过渡生硬、脚滑层与层互相打架、口型超前或滞后

Morph Target：用顶点差值做表情，而不是加骨骼 ​

骨骼擅长"大块位移"，不擅长"皮肤表面的细碎起伏"。让嘴角上扬、眉毛下压、脸颊鼓起，用骨骼需要几十根辅助骨，用 morph target 只需要几组顶点差值。

three 的 morph 实现很直接：

js
geometry.morphAttributes.position = [closedAttr, slightAttr, roundAttr, flatAttr, grinAttr]
geometry.morphTargetsRelative = true
  • 每个 BufferAttribute 与基础几何体顶点数相同，存的是每个顶点的位移量；
  • morphTargetsRelative = true 表示存的是"差值"，渲染时用 基础位置 + Σ(权重 × 差值)；
  • mesh.morphTargetInfluences 是长度等于目标数的浮点数组，每帧改它就能改表情；
  • morphTargetDictionary 把名字映射到下标，方便写 influences[dict.grin] = 1。

如果目标是"绝对位置"而不是差值，morphTargetsRelative 要设为 false，此时多个目标同时开启会互相覆盖，而不是叠加。这是导入 blendshape 时最常见的语义坑。

手段数据量擅长不擅长本例用途
骨骼蒙皮每顶点 4 个索引 + 4 个权重大范围弯曲、肢体动作面部细微褶皱身体、头、四肢
Morph Target每个目标一份顶点位移表情、口型、肌肉鼓起大幅旋转、长距离位移嘴型 5 目标
纹理/贴图一张图颜色、法线细节轮廓变化本模块不用

命名：行业里常把 morph target 叫 blendshape（混合形状）。ARKit 定义了 52 个面部 blendshape，Oculus 的 LipSync 用 15 个 viseme，不同厂商的口型集合并不通用。程序化方案的好处是你可以自定义 5 个目标就够用，不必背上 52 个的资产包袱。

表情系统：把脸拆成可组合的开关 ​

口型只是嘴，表情还要管眉、眼、脸颊。工程上不会为"惊讶"单独做一个整脸 morph，而是继续复用基础目标，把它当成几个开关的组合：

表情微开圆扁咧嘴眉毛/眼睛
中性0.3000.05正常
微笑0.2500.30.8眉毛略抬
惊讶0.91.000眉毛上抬、眼睛睁大
思考0.150.20-0.05眉毛内侧下压
说话（A）1.550.10.550.1正常眨眼

组合的好处是"表情强度"可以变成一个全局乘数：params.表情强度 = 1.4 时，所有非中性权重按比例放大，角色立刻显得更外放；调到 0.5 就变成克制、内敛的表达。注意负权重也是合法的，咧嘴 = -0.05 表示嘴角轻微下压，适合"思考"或"为难"。这类细枝末节如果不做，角色会一直保持同一种礼貌微笑，看久了非常假。

另一个常被忽略的是嘴部区域的顶点密度。同样的 5 个目标，如果嘴部只有 50 个顶点，形变会呈多边形块状；把球体分段从 48 提到 96，嘴部能拿到 200 多个顶点，唇线才平滑。代价是顶点数翻倍，所以正确做法不是全头加密，而是在建模阶段让嘴部区域的布线更密——程序化方案里则可以用更高的球体分段，再用 LOD 控制远距离版本。

Viseme：口型不是"张嘴"，是音素的视觉映射 ​

音素（phoneme）是听觉上的最小语音单位，viseme 是视觉上可区分的口型单位。二者不是一一对应：/p/、/b/、/m/ 三个音素在视觉上几乎都是"双唇闭合"，所以它们共享一个 viseme；而同一个 /a/ 在"啊"和"安"里，嘴形也会因为前后音素而提前变形，这叫协同发音（coarticulation）。

本模块把口型简化为七个 viseme：A、E、I、O、U、M、F，每个 viseme 对应 5 个 morph 目标的一组权重。这张表可以直接当"翻译表"用：

Viseme中文拼音（简化）英文音素（简化）嘴形目标权重组合
Aa、an、ang/a/、/ʌ/张大、下巴下沉微开 1.55、扁 0.55
Ee、en、ei/e/、/ɛ/嘴角拉开、开口中等扁 1.0、咧嘴 0.35
Ii、in、ing/iː/、/ɪ/扁而窄、露齿扁 0.82、咧嘴 0.5
Oo、ong、ou/ɔ/、/oʊ/圆唇、向前收圆 1.0、微开 0.55
Uu、ü/uː/、/ʊ/小圆、嘴唇前突圆 0.85、微开 0.22
Mm、b、p 开头/m/、/b/、/p/双唇闭合闭 1.0
Ff、v 开头/f/、/v/上齿咬下唇扁 0.58、微开 0.28

这张表是工程简化，不是语言学教材。真实的 viseme 集合通常会拆成 12 到 15 个，还会区分圆唇的松紧、开口的层级。但对于"观众能对上嘴"的目标，七个已经够用，尤其当角色是风格化大头时。

口型时间轴：从一句话到一条权重曲线 ​

真实 TTS 会返回音素序列与每个音素的起止时间；本模块没有音频，所以用"文字 → 拼音 → viseme 序列 → 固定时长"的 mock 管线，得到一条与真实 TTS 结构相同的时间轴：

js
function buildTimeline(text) {
  const segs = []
  for (const ch of text) {
    if (isPunctuation(ch)) {
      segs.push({ v: 'M', dur: 0.3 })      // 标点 = 闭嘴换气
      continue
    }
    const vs = visemesForChar(ch)           // 一个字拆成 1~3 个 viseme
    for (const v of vs) segs.push({ v, dur: 0.105 })
  }
  let t = 0
  segs.forEach((s) => { s.start = t; t += s.dur; s.end = t })
  return { segs, total: t }
}

有了时间轴，每帧只需要做两件事：找到当前 segment，把它的权重设为目标；然后让实际权重平滑逼近目标，而不是瞬间跳变。

js
const k = 1 - Math.exp(-dt * 20)          // 指数平滑，与帧率无关
weights[i] += (target[i] - weights[i]) * k

这个系数很关键：1 - exp(-dt * 20) 保证 60fps 与 30fps 下的收敛速度一致，不会因为掉帧导致口型节奏变化。20 越大嘴动得越"脆"，越小越"糯"。真人说话的口型过渡通常在 60 到 120 毫秒，对应这个系数的 12 到 25。

还有两个专业细节值得知道：

  • 预判（lead-in）：音频有缓冲与解码延迟，口型应当比音频提前 30 到 80 毫秒启动，而不是等声音出来再张嘴；
  • 协同发音：连续元音之间不该完全回到闭口，否则会出现"机器人打字机"感。用平滑逼近而不是硬切，天然缓解这个问题。

三层动画叠加：待机 / 手势 / 口型 ​

分层的关键是"哪些通道归哪层管"。一个务实的分法：

层驱动对象更新频率混合策略例子
待机层脊柱、肩、颈每帧正弦始终开启，低幅度呼吸、重心摆动
手势层肩、肘、腕事件触发与待机层相加或覆盖抬手、摊手、指方向
口型层嘴部 morph音素时间轴独占嘴部通道A/E/I/O/U/M/F
微表情层眨眼、眉毛、视线随机/事件叠加到面部眨眼、挑眉、看观众

three 没有内置的"动画层"概念，AnimationMixer 的层能力体现在多 action 同时播放 + 各自权重。所以有两种做法：

  1. 资产层：每层是一个 AnimationClip，同时 play()，用 action.weight 调强弱，骨骼通道由 AnimationMixer 的累加器合成；
  2. 程序层：不用 clip，每帧直接写骨骼旋转与 morph 权重，自己控制优先级。

本模块的身体待机与手势属于程序层，口型与表情属于 morph 层。这样避免为了"呼吸"专门做一个 clip，也避免 Mixer 与手动写旋转互相覆盖。

AnimationMixer 的权重与 crossFadeTo ​

如果你确实用 clip 做手势，记住 crossFadeTo 的三个实用点：

js
idle.play()
wave.play()
wave.crossFadeTo(point, 0.25, false)   // 从 wave 淡到 point，0.25 秒
  • crossFadeTo 会同时改两个 action 的权重，不要再手动设 weight，否则过渡曲线会被打乱；
  • 过渡被新的 crossFadeTo 打断时，旧过渡不会自动清理，最好在状态机切走时统一 stop() 或 reset()；
  • warp = true 会调整时间尺度让两段动画"步幅对齐"，适合走路切跑步，不适合说话切手势。

还有一个容易忽略的细节：AnimationMixer 每帧更新的是它认识的属性绑定。如果你同时手动写同一个骨骼的 rotation，Mixer 会在下一帧把它覆盖回去。混用两种驱动方式时，给通道划清归属，比调权重更重要。

眨眼与视线：微表情让角色"活" ​

一个完全不眨眼的数字人，三秒内就会让人出戏。眨眼成本极低，收益极高：

  • 间隔随机：2 到 6 秒一次，避免节拍器式规律；
  • 时长：单次 120 到 200 毫秒，闭眼过程比睁眼略快；
  • 偶发连眨：连续两次，模拟疲劳或紧张；
  • 视线微动：瞳孔在眼眶内做 1 到 3 度的随机偏移，比整颗头转动更自然；
  • 头部微动：幅度控制在 3 到 6 度，超过 10 度就会显得"摇头晃脑"。

实现上不需要 morph，直接缩放眼球组的 Y 轴即可：

js
const p = 1 - blinkPhase / 0.18
const squash = 1 - Math.sin(p * Math.PI) * 0.93
eyeGroup.scale.y = squash

用 sin 曲线而不是线性，闭眼与睁眼才有加速与减速，不会像卷帘门。

性能预算：morph 与骨骼各自花在哪 ​

  • 蒙皮：每个顶点 4 次矩阵乘加，成本与顶点数、骨骼数相关；顶点数翻倍，成本翻倍。
  • Morph：每个受影响的顶点、每个目标都要一次加权累加。5 个目标 × 6000 顶点就是 3 万次顶点运算，听起来不多，但同时开着 52 个 ARKit 目标就是 31 万次。
  • CPU 端更新：每帧写 morphTargetInfluences 很便宜，真正的成本在 GPU 顶点阶段；不要每帧重建 morph attribute。
  • 内存：每个 morph 目标占一份 顶点数 × 3 × 4 字节。6000 顶点 × 5 目标约 360KB，可接受；52 目标就是 3.7MB，移动端要谨慎。

代码示例 ​

第一段，构造嘴部 morph。核心是给每个顶点算一个"离嘴多近"的衰减，再按目标写位移：

js
for (let i = 0; i < count; i++) {
  const x = base[i * 3]
  const y = base[i * 3 + 1]
  const z = base[i * 3 + 2]
  if (z <= 0.35) continue                 // 只处理脸前侧
  const dx = x / 0.34
  const dy = (y + 0.32) / 0.21
  const d2 = dx * dx + dy * dy
  if (d2 < 1) falloff[i] = Math.pow(1 - d2, 1.2)
}

第二段，把 viseme 映射成权重。注意 A 的"微开"给到 1.55，超过 1 的 influence 是合法的，它会把差值外推，得到比默认更大的开口：

js
const VISEME_WEIGHTS = {
  A: { closed: 0, slight: 1.55, round: 0.10, flat: 0.55, grin: 0.10 },
  E: { closed: 0, slight: 0.32, round: 0, flat: 1.0, grin: 0.35 },
  M: { closed: 1.0, slight: 0, round: 0, flat: 0, grin: 0 },
  F: { closed: 0.18, slight: 0.28, round: 0, flat: 0.58, grin: 0 }
}

第三段，三层叠加的写法。口型层直接覆盖嘴部权重，眨眼层缩放眼睛，待机层写脊柱与头部：

js
// 口型层：按时间轴取目标，再平滑
const viseme = currentSegment(playTime).v
const target = VISEME_WEIGHTS[viseme]
for (let i = 0; i < 5; i++) {
  const name = MORPH_NAMES[i]
  mouthWeights[i] += (target[name] * amplitude - mouthWeights[i]) * k
  headMesh.morphTargetInfluences[i] = mouthWeights[i]
}

// 待机层：呼吸与轻微摆头
spine.rotation.x = Math.sin(t * 1.1) * 0.018
head.rotation.y = Math.sin(t * 0.45) * 0.06

// 微表情层：随机眨眼
blinkWait -= dt
if (blinkWait <= 0) { blinkPhase = 0.18; blinkWait = 2.6 + Math.random() * 3.2 }

常见问题解答 ​

Q1：为什么口型看起来比字幕"慢半拍"？

两个原因。第一，权重平滑本身有延迟，k = 1 - exp(-dt * 20) 需要一个时间常数才收敛，如果字幕按字符瞬间出现，视觉上就会觉得嘴跟不上。第二，真实音频有缓冲延迟，而 mock 时间轴从 0 开始，缺少 lead-in。解决方向是让口型时间轴比字幕提前 30 到 80 毫秒启动，并把平滑系数提高到 18 到 25，而不是简单地把整条时间轴加速。

Q2：多个 morph target 同时开启，权重需要归一化吗？

morph 与蒙皮不同，不要求归一化。骨骼蒙皮的权重和必须是 1，否则顶点会缩放；morph 是位移叠加，权重和大于 1 只是"表情更夸张"，小于 1 是"表情更淡"。本例故意让 A 的微开到 1.55，就是为了做出更大的开口。需要注意的反而是目标之间的冲突：闭与微开同时给高权重，嘴唇会互相抵消，看起来像抖动。

Q3：为什么加了 `morphAttributes` 之后，`morphTargetInfluences` 是 undefined？

因为 Mesh 只在构造时扫描几何体的 morph 属性。属性是在 Mesh 创建之后才挂上去的，字典与影响数组就不会自动生成。解决方式是手动调用一次 mesh.updateMorphTargets()，或者先给几何体加好 morph 再 new Mesh。本例采用后者，顺序是"几何体 → morph 属性 → Mesh"。

Q4：中文和英文能共用同一套 viseme 吗？

可以共用"口型集合"，但不能共用"映射规则"。中文的韵母与英文的元音在听感上并不重合，例如汉语拼音的 ü 更接近 U，而英语的 /ʌ/ 更接近 A。务实做法是保留 A/E/I/O/U/M/F 这套视觉槽位，分别写中文拼音映射表与英文音素映射表，两者输出同一组权重。不要把音素直接当索引塞进 morph 数组。

Q5：说话时手势和口型会不会互相覆盖？

只要通道不重叠就不会。手势层只写肩、肘、腕的旋转，口型层只写嘴部 morph，待机层只写脊柱与头的微小旋转。真正会冲突的是"两个层都想写同一个骨骼"，例如待机层想摆头、手势层也想摆头。工程上的解法是给每个通道指定唯一所有者，或者明确规定"上层权重覆盖下层"，而不是两边都写一半。

  1. 把 VISEME_WEIGHTS 里的 A 从"微开 1.55、扁 0.55"改成"圆 1.2、微开 0.9"，播放同一句话，对比"啊"与"哦"的观感差异，记录哪个参数最容易让嘴形失真。
