37.1 基础入门：骨骼、蒙皮与程序化人形 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ⑮ 与 ⑬ 再阅读。

核心概念讲解 ​

接桥：15.2 的 glTF 骨骼是"美术给的"，我们先用代码造一副 ​

在 ⑮ glTF 资产管线 的 15.2 里，我们打开一个带骨骼的 .glb，看到的是这样一条链路：DCC 软件里由美术摆好骨架、刷好权重、导出 glTF，three 只负责把 SkinnedMesh、Skeleton、AnimationClip 装载进来，然后 AnimationMixer 按时间播放。那条链路的关键词是资产：骨架长什么样、每个顶点听哪几根骨头的话，都是别人已经决定好的。

本篇把方向反过来：骨架由代码创建，权重由公式计算，动画由参数驱动。不加载任何模型、图片或音频，整副人形完全由 Bone、CapsuleGeometry 和几行权重计算现场生成。这样做不是为了替代美术，而是为了把 15.2 里被 .glb 封装起来的三件事拆开给你看：

  1. 骨骼层级到底是一棵什么树；
  2. skinIndex / skinWeight 这两个属性到底存了什么；
  3. 逆绑定矩阵为什么必须和绑定姿态配套。

先看一张对照表，建立"资产骨骼"和"程序化骨骼"的边界感：

维度资产骨骼（15.2 的 glTF）程序化骨骼（本篇）
骨架来源DCC 建模、导出代码逐根 new THREE.Bone()
权重来源美术刷权重，或自动蒙皮按关节距离写公式
迭代方式改模型 → 重新导出 → 重新加载改参数 → 刷新页面
精度上限可以做到影视级受公式与几何体限制，适合风格化
调试成本需要 DCC 与导出链可直接打印属性、画 SkeletonHelper
适用场景写实角色、面部捕捉、复杂服装风格化吉祥物、加载动画、教学演示、原型验证

所以正确的期待是：程序化人形擅长"可控、可解释、零资产"，不擅长"写实"。当你要做一个 20 厘米高的客服小人，或者要在面试里解释蒙皮原理，它非常合适；当你要做一部写实短片，还是回到 15.2 的资产管线。

Bone 层级：一副骨架就是一棵 Transform 树 ​

THREE.Bone 继承自 Object3D，它没有任何"骨骼专属"的魔法，唯一特殊的地方是它可以被 Skeleton 收集、被 SkinnedMesh 引用。因此理解骨骼的第一步，是把它当成普通的父子变换：子骨骼的 position 是相对父骨骼的，父骨骼一转，整条子链跟着转。

本篇的示例骨架一共 17 根，分成四条链：

  • 中轴：hips → spine → chest → neck → head
  • 左臂：chest → shoulderL → elbowL → wristL
  • 右臂：chest → shoulderR → elbowR → wristR
  • 双腿：hips → hipL → kneeL → ankleL，右侧同理

用代码创建时只需要三行核心逻辑：

js
function makeBone(name, x, y, z, parent) {
  const bone = new THREE.Bone()
  bone.name = name
  bone.position.set(x, y, z)
  if (parent) parent.add(bone)
  return bone
}

const hips = makeBone('hips', 0, 0.95, 0)
const spine = makeBone('spine', 0, 0.28, 0, hips)
const chest = makeBone('chest', 0, 0.28, 0, spine)

注意 shoulderL 的父级是 chest 而不是 neck：手臂挂在胸腔上，头挂在脖子上，这是人体结构决定的。层级一旦搭错，抬肩会带着头一起动，或者点头会拽动双手，调试时会非常痛苦。经验规则是先把中轴搭对，再挂四肢，最后挂手指与道具。

关节父级主要职责常见错误
hips无（根）全身位移与重心把根骨骼放在脚底，导致旋转时人绕脚转
spine / chesthips / spine躯干弯曲、呼吸脊柱过长，弯腰时腹部穿插
neck / headchest / neck点头、转头、视线头骨原点不在颈部，转头变成"甩头"
shoulderchest抬臂、耸肩肩点太靠内，抬手夹住躯干
elbowshoulder屈肘前臂长度与网格不一致，弯曲处断裂
hip / kneehips / hip迈步、下蹲膝盖旋转轴与腿的朝向不匹配

Skeleton 与 SkinnedMesh：骨骼是线，蒙皮才是皮 ​

只有骨骼时，屏幕上什么都看不到，因为 Bone 没有几何体。Skeleton 是骨骼的"花名册"：它持有一个有序的 bones 数组，以及每个骨骼的 boneInverses。SkinnedMesh 则是"会变形的网格"：它在普通 Mesh 的基础上，多存了 skinIndex 与 skinWeight 两个顶点属性，并在渲染时把顶点交给 GPU 蒙皮。

最小绑定流程如下：

js
const skinned = new THREE.SkinnedMesh(mergedGeometry, material)
skinned.frustumCulled = false
skinned.add(hips)                   // 根骨骼挂到网格下
scene.add(skinned)
scene.updateMatrixWorld(true)       // 先算世界矩阵
const skeleton = new THREE.Skeleton(boneList)
skinned.bind(skeleton)

bind() 做两件事：记录当前的 bindMatrix，并让 Skeleton 计算逆绑定矩阵。这里最容易忽略的是 scene.updateMatrixWorld(true)：如果骨骼的世界矩阵还没更新，逆绑定矩阵会按错误的世界变换计算，最终表现为"模型一加载就扭曲"。很多"绑定后模型炸开"的问题，根因就是绑定时机，而不是权重。

角色存什么什么时候用到
Bone局部位置、旋转、缩放每帧被动画或代码改写
Skeleton骨骼数组、逆绑定矩阵上传给 GPU 的骨骼纹理/矩阵
SkinnedMesh几何体 + skinIndex/skinWeight渲染时执行蒙皮
bindMatrix绑定时刻网格的世界矩阵把顶点送进骨骼空间再送回来

skinIndex / skinWeight：每个顶点最多 4 个骨骼影响 ​

three 的蒙皮属性是固定四槽的：

  • skinIndex：Uint16BufferAttribute，itemSize = 4，每槽存一个骨骼在 Skeleton.bones 里的下标；
  • skinWeight：Float32BufferAttribute，itemSize = 4，每槽存对应权重。

一个顶点如果只想听一根骨头，就写 [骨骼下标, 0, 0, 0] 与 [1, 0, 0, 0]；如果想让肘部平滑过渡，就写两根骨头、权重 0.6 / 0.4。权重必须是归一化的，也就是四个分量之和等于 1。three 的着色器不会自动帮你归一化，权重和写成 0.5，顶点就会被"缩"向原点；权重和为 2，顶点会被"拉"到两倍远。

js
const skinIndex = new Uint16Array(count * 4)
const skinWeight = new Float32Array(count * 4)

// 一个顶点受两根骨骼影响
skinIndex[i * 4 + 0] = boneIndex.shoulderL
skinIndex[i * 4 + 1] = boneIndex.elbowL
skinWeight[i * 4 + 0] = 0.7
skinWeight[i * 4 + 1] = 0.3

四槽不是"人体只有四根骨头"，而是GPU 的预算。移动端为了控制顶点着色器成本，通常就锁死在 4；影视级角色会用 8 甚至更多，代价是多 pass 或自定义着色器。对风格化数字人，四根足够，因为大部分顶点只需要一到两根。

绑定姿态与逆绑定矩阵：bind pose 为什么不能随便换 ​

把蒙皮公式写出来，很多疑惑会立刻消失：

text
蒙皮后顶点 = Σ ( 权重_i × 骨骼世界矩阵_i × 逆绑定矩阵_i × 绑定姿态顶点 )

逆绑定矩阵 的作用，是把"绑定姿态下的模型空间顶点"转换到第 i 根骨骼的局部空间。这样当骨骼从绑定姿态旋转到新姿态时，顶点就会被"带着走"。因此：

  • 绑定姿态是合同：网格建在什么姿势，逆绑定矩阵就必须按那个姿势算；
  • 如果你在 A-pose 下建网格，却拿 T-pose 的骨骼去 bind，公式里的"合同"对不上，肩膀和腋下会立刻歪掉；
  • 绑定之后再去改骨骼的初始旋转，不会自动更新逆绑定矩阵，模型会保持旧姿势或直接扭曲。

在程序化人形里，我们干脆让网格和骨骼都在同一个"T 形/直臂"姿势下创建，然后一次性 bind，从此只改关节旋转，不再动骨骼的初始位置。

用 CapsuleGeometry 拼一副最小骨架 ​

程序化人形的最低成本做法，是用胶囊体拼四肢、球体拼头、胶囊体拼躯干，然后按关节位置写权重。胶囊的两端是半圆，关节处天然重叠，弯曲时不会露出硬边，特别适合低多边形风格。

关键不是几何体，而是权重函数。示例里用了两种策略：

  1. 躯干用"帐篷函数"：以 hips / spine / chest 三个高度为中心，按顶点到中心的距离给权重，三个权重相加后归一化；
  2. 四肢用"轴向过渡"：沿手臂的 X 轴或腿的 Y 轴，计算顶点离关节的比例，在关节附近用 smoothstep 做 0.5 到 1.0 的混合。
js
function torsoWeights(p) {
  const out = []
  const tent = (name, centerY, radius) => {
    const w = Math.max(0, 1 - Math.abs(p.y - centerY) / radius)
    if (w > 0.001) out.push([boneIndex[name], w])
  }
  tent('hips', 0.95, 0.32)
  tent('spine', 1.23, 0.32)
  tent('chest', 1.51, 0.32)
  return out
}

这段代码的特点是"可解释"：想让腰部更软，就把 radius 调大；想让手臂更硬，就把过渡区间压窄。它不如图形学里的热扩散自动蒙皮精确，但对一个 3000 顶点的风格化角色已经足够，而且改起来不用回 DCC。

几何体合并时要注意属性一致：所有子几何都必须有 position / normal / uv / color / skinIndex / skinWeight，并且索引状态一致，否则 mergeGeometries 会返回 null。示例里每个零件都补了顶点色，合并后一个 SkinnedMesh 就能有分区配色，避免十几个 draw call。

SkeletonHelper：把看不见的骨骼画出来 ​

SkeletonHelper 会用线段把骨骼的父子关系画出来，是排查"网格和骨骼对不对齐"的第一工具：

js
const helper = new THREE.SkeletonHelper(skinned)
helper.material.depthTest = false
helper.material.color.set(0x22d3ee)
scene.add(helper)

depthTest = false 让骨骼线穿透身体显示，方便观察内部关节。如果线在身体外面、网格却在原地不动，通常说明 bind() 没执行、权重全给了根骨骼，或者 skinIndex 与 Skeleton.bones 的顺序不一致。演示里的"错误权重"模式就是刻意制造这种视觉冲突：网格被钉在绑定姿态，骨骼线却在弯曲。

姿态 pose 与动画 animation 的区别 ​

这是初学者最容易混淆的一对概念：

  • pose（姿态）：某一瞬间所有关节的旋转/位移值，是一组静态数字；
  • animation（动画）：随时间变化的曲线，AnimationClip 存关键帧，AnimationMixer 每帧采样后写到 pose 上；
  • 物理/程序动画：连曲线都没有，每帧根据速度、碰撞或正弦函数直接算 pose。

本篇演示里的关节滑块改的是 pose，所以拖动时模型会停在那个姿势；打开"呼吸微动"后，spine 的旋转由 Math.sin(t) 驱动，这才变成了最小的 animation。37.2 会把这条线延伸到 AnimationMixer 与多层混合。

概念数据形态谁在改典型用途
Pose一组关节变换代码、Mixer、IK当前帧的最终姿势
AnimationClip关键帧曲线美术/程序导出走路、挥手、说话
Mixer播放器每帧采样多段动画混合与过渡
程序动画函数输出正弦、噪声、物理呼吸、待机、视线跟随

常见坑：四条最容易踩的线 ​

  1. 权重和为 0 或未归一化：顶点会被压到原点或拉飞。写权重时最后一定做一次 sum 归一化，并对"全零"顶点给一个兜底骨骼。
  2. 骨骼缩放污染：给 Bone 设置非均匀 scale，子骨骼与蒙皮矩阵都会被拉斜，弯曲时出现剪切。骨骼只建议改旋转，缩放交给网格或父级 Group。
  3. skinIndex 越界或顺序错位：Skeleton 的 bones 数组顺序必须与写入时的下标一致；动态增删骨骼后要重建 Skeleton 并重新 bind。
  4. 绑定姿态不一致：网格是直臂，骨骼是垂臂，bind() 之后怎么调都别扭。要么统一姿势，要么在 bind 前先把骨骼摆到网格的姿势。

第一步，骨架只搭结构，不碰网格：

js
const hips = makeBone('hips', 0, 0.95, 0)
const spine = makeBone('spine', 0, 0.28, 0, hips)
const chest = makeBone('chest', 0, 0.28, 0, spine)
const shoulderL = makeBone('shoulderL', 0.30, 0.04, 0, chest)
const elbowL = makeBone('elbowL', 0.32, 0, 0, shoulderL)

第二步，每个零件合并前先写权重。这里用 addPart 统一处理颜色、索引与归一化，避免每个几何体各写一遍：

js
function addPart(geometry, matrix, hex, weightFn) {
  geometry.applyMatrix4(matrix)
  geometry.clearGroups()

  const pos = geometry.attributes.position
  const index = new Uint16Array(pos.count * 4)
  const weight = new Float32Array(pos.count * 4)
  const v = new THREE.Vector3()

  for (let i = 0; i < pos.count; i++) {
    v.fromBufferAttribute(pos, i)
    const infs = weightFn(v)
    let sum = 0
    for (let k = 0; k < 4; k++) {
      if (!infs[k]) continue
      index[i * 4 + k] = infs[k][0]
      weight[i * 4 + k] = infs[k][1]
      sum += infs[k][1]
    }
    if (sum > 0) {
      for (let k = 0; k < 4; k++) weight[i * 4 + k] /= sum
    } else {
      index[i * 4] = 0
      weight[i * 4] = 1
    }
  }

  geometry.setAttribute('skinIndex', new THREE.Uint16BufferAttribute(index, 4))
  geometry.setAttribute('skinWeight', new THREE.Float32BufferAttribute(weight, 4))
}

第三步，绑定。注意顺序：先 add 根骨骼，再更新世界矩阵，最后 bind：

js
const mesh = new THREE.SkinnedMesh(merged, material)
mesh.add(hips)
scene.add(mesh)
scene.updateMatrixWorld(true)
mesh.bind(new THREE.Skeleton(bones))

第四步，用 GUI 直接写 pose。演示里的错误模式只是把 skinIndex 全指向 hips、权重全给 1，就能看到"网格不跟骨骼走"的经典故障：

js
const wrongIndex = new THREE.Uint16BufferAttribute(new Uint16Array(count * 4), 4)
const wrongWeight = new THREE.Float32BufferAttribute(
  new Float32Array(count * 4).fill(1), 4
)

换成错误属性后记得把 needsUpdate 置为 true，否则 GPU 缓冲不会重新上传。真实项目里更隐蔽的错误是"只改了一半顶点"，那会看到肢体被无限拉长，而不是整块不动。

常见问题解答 ​

Q1：我明明改了骨骼旋转，网格却完全不动，为什么？

按可能性从高到低排查四处：第一，skinWeight 是不是全给了根骨骼，根骨骼不动，网格自然不动；第二，bind() 有没有执行，没绑定的话 SkinnedMesh 会按普通网格渲染；第三，Skeleton 的 bones 顺序是否与 skinIndex 对得上，错位时顶点会被别的骨骼带跑；第四，改的是不是 Bone 的 rotation，而不是某个同名 Group。演示里的"错误权重"开关就是第一种情况的可复现版本。

Q2：每个顶点一定要 4 个权重吗？能不能只给 1 个？

可以。属性是四槽，不代表必须写满。刚性零件只写一槽 [bone, 0, 0, 0] 与 [1, 0, 0, 0] 就够了，多余槽留 0。只有关节过渡区才需要两根甚至三根骨骼混合。四槽是上限，不是义务；权重写满反而增加无意义的矩阵乘加。

Q3：程序化人形能直接用于生产吗？

看目标。风格化吉祥物、加载页、语音助手、教学演示完全可以，因为这些场景要的是"可控、轻量、无资产"。写实角色、复杂服装、面部捕捉不适合，公式权重很难覆盖肌肉与布料的细节。务实的做法是混合：程序化骨架做原型与调试可视化，最终资产仍由 15.2 的管线产出。

Q4：SkeletonHelper 的线为什么和模型错位？

先看绑定姿态。SkeletonHelper 画的是骨骼当前世界位置，网格则按"绑定姿态 + 蒙皮矩阵"变形；如果两者在静止状态就已经错位，说明 bind() 时的姿势与建网格时的姿势不一致。其次是根骨骼的父级：把根骨骼挂到场景而不是网格下，网格的 bindMatrix 会按另一个坐标系记录，表现同样会错位。

Q5：为什么手臂弯曲时肘部会"塌陷"或出现糖纸一样的拧转？

这是线性混合蒙皮的固有缺陷。弯曲角度越大，过渡区的顶点越会被两根骨骼"平均"到内侧，体积就丢失了。缓解手段有三类：把过渡区收窄、在肘部加一根辅助骨骼、或者用 dual quaternion 蒙皮。风格化角色通常靠"胶囊关节重叠"掩盖这个问题，比堆权重更便宜。

动手小练习 ​

  1. 给骨架加一根 toe 骨骼（ankle 的子级），把脚掌前段的权重从 ankle 分一半给它，再给 toe 加一个滑块。观察脚趾弯曲时鞋底是否还贴地，思考为什么脚部通常需要两根骨骼。
  2. 把躯干权重函数里的 radius 从 0.32 改成 0.18，重新加载后弯腰，对比腰部过渡是变硬还是变软；再把归一化那一步注释掉，观察顶点如何被"拉飞"，记录两种现象的差别。
  3. 给演示加一个"只改右前臂权重"的错误模式：让右前臂的顶点一半听 hips、一半听 wristR，弯曲肘部时截图。解释为什么这种"半对半错"比"全错"更像真实的线上事故。
