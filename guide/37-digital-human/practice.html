37.3 实战案例：可对话的数字人 ​

前置提示：本篇属于行业纵深内容，建议先完成 37.1 与 37.2，并了解 ㉕ 的容错与监控思路。

核心概念讲解 ​

接桥：㉕ 的容错在数字人场景更残酷——嘴型对不上，观众立刻出戏 ​

㉕ 线上监控与容错 讲的是"出错时系统怎么活下去"：超时重试、降级、兜底文案、错误上报。那套方法的前提是——错误是可以被"功能层面"掩盖的，用户最多觉得"这次慢了一点"。

数字人把难度提高了一档：错误是表演层面的，观众不需要懂技术就能看出来。嘴型比声音慢半拍、说完了嘴还张着、思考状态卡死、字幕和语音各说各话，任何一个都会瞬间摧毁"这是一个会说话的人"的错觉。所以本篇要做的不是"接一个 TTS 就完事"，而是把 25 的容错原则翻译成表演语言：

维度25 的通用容错37.3 的表演容错
失败表现接口报错、超时、返回空嘴不动、嘴乱动、状态卡住、字幕不同步
用户感知功能不可用角色"不像活的"
兜底手段重试、缓存、静态文案字幕 + 默认口型 + 主动回 idle
监控指标成功率、P95 延迟口型-字幕偏移、状态停留时长、掉帧率
最难处理的部分成功"看起来成功了，但表演是错的"

一句话总结：25 关心"有没有结果"，37.3 关心"结果像不像真的"。

架构分层：渲染 / 表演 / 对话 / 降级 ​

把数字人拆成四层，边界清楚之后，每一层都可以单独替换或降级：

层职责输入输出本模块实现
渲染层场景、相机、灯光、材质骨骼与 morph 权重画面three 场景 + 程序化人形
表演层姿态、口型、眨眼、手势状态与时间轴骨骼旋转 / morph 值状态机 + 平滑权重
对话层意图、回复文本、TTS用户输入文本 + 音素时间轴mock TTS
降级层无 WebGL、TTS 失败、低端机错误与能力探测字幕 / 静态形象 / 低配模式降级面板 + 兜底口型

数据流是单向的：对话层产出"说什么、说多久"，表演层把它翻译成"嘴怎么动、手怎么摆"，渲染层只负责画。反向只有一种情况：用户打断，从 UI 直接通知对话层取消，再由对话层把"回到 idle"传给表演层。不要让渲染层去读对话层的内部变量，否则状态会越缠越乱。

对话状态机：idle / listening / thinking / speaking ​

四个状态足够表达一次完整对话：

状态进入动作停留时间允许转出表演特征
idle手势归位、嘴闭合无限用户开始说话 → listening呼吸、眨眼、轻微摆头
listening显示用户字幕、麦克风高亮1 到 2 秒超时 → thinking，打断 → idle头微侧、单手轻抬
thinking显示思考提示0.8 到 1.5 秒TTS 返回 → speaking，失败 → speaking（兜底）头微仰、手靠近面部
speaking启动口型时间轴等于音频时长播完 → idle，打断 → idle口型 + 手势 + 字幕逐字出现

三个工程约束必须写进状态机，而不是靠"应该不会发生"：

  1. 每个状态都有超时。listening 最多 3 秒，thinking 最多 5 秒，超时一律回 idle 并给出提示。没有超时的状态机是线上事故的温床。
  2. 转出时清理副作用。离开 speaking 必须停口型、清字幕定时器、把手势淡出；离开 thinking 必须撤销"手贴脸"的姿势。
  3. 打断是最高优先级。打断不是"把状态设成 idle"这么简单，还要让口型立刻回到闭合、让字幕停止增长、让未完成的 TTS 结果被丢弃。
js
function setState(next) {
  machine.state = next
  machine.phase = 0
  machine.segIndex = 0
  stateEl.textContent = next
  stateEl.className = 'badge ' + next
}

状态机本身只有这几行，真正的工作量在"进入/离开每个状态时做什么"。把这些副作用写成 enterState 与 exitState 两个函数，比在 update 里堆 if 更容易维护。

mock TTS：把"生成"与"播放"拆开 ​

本模块没有音频，但接口形状要和真实 TTS 一致，否则以后替换时会牵一发动全身。理想接口只暴露两件事：

js
const result = await tts.synthesize(text)
// result = { text, phonemes: [{ v: 'M', dur: 0.1 }, ...], total: 2.4 }

tts.speak(result)   // 真实实现里返回音频与播放事件；mock 里只推进时间

为什么强调这个形状？因为口型驱动需要的不是波形，而是音素序列与时长。真实 TTS 通常提供 word/phoneme timing；如果只有音频没有时间戳，就得自己做强制对齐（forced alignment），复杂度会高一个量级。先把"时间轴"这层抽象出来，动画代码就不用关心底层是 Web Speech、云端 TTS 还是本地模型。

mock 的实现就是把 37.2 的 buildTimeline 包一层，返回同样的结构，再加上一个可控的"失败开关"：

js
function synthesize(text) {
  if (params.模拟TTS失败) throw new Error('TTS offline')
  return buildTimeline(text)
}

失败开关不是玩具，它让你能在演示与测试里稳定复现"最糟糕的情况"，而不是等线上真的挂掉才发现兜底路径没写。

口型驱动与字幕同步：只允许一个时钟 ​

数字人最容易出现的 bug 是"字幕和嘴不同步"，根因通常是两个时钟：字幕用 setTimeout 逐字追加，口型用 requestAnimationFrame 推进，两套时间基准在掉帧、切后台、调速时必然漂移。

正确做法是只维护一个 replyTime，字幕与口型都从它派生：

js
machine.replyTime += dt * params.语速
const progress = Math.min(1, machine.replyTime / timeline.total)
const visible = Math.floor(progress * REPLY_TEXT.length)
bubble.textContent = REPLY_TEXT.slice(0, visible)

口型则用同一个 replyTime 去查当前 segment。这样无论帧率如何波动、语速怎么调，字幕与嘴型永远处在同一条时间轴上。暂停时只要不再累加 replyTime，两者会一起停。

还有一个细节：字幕按字符数均分时间并不等于按音素时间。中文字符与音素的时长并不一一对应，严格同步应该用"每个字符对应的首段 viseme 的起始时间"来决定它何时出现。本模块为了可读性做了均分简化，但只要你把 visible 的计算改成"查找第一个 start <= replyTime 的字符下标"，就能得到更精确的对齐。

说话手势与结束回到 idle ​

说话时的手势要遵守三条经验：

  • 频率：1.5 到 2.5 秒一次，不要每句话都抬手；
  • 幅度：抬到胸口即可，超过肩膀会变成"演讲"；
  • 收尾：句子结束时手势要"衰减"，而不是戛然停住。

实现上用一个正弦包络就够了，不需要额外的动画片段。句末回到 idle 时，把所有骨骼目标角度设为待机值，再通过指数平滑过渡回去，观众看到的是"放松下来"，而不是"突然复位"。

js
const g = Math.sin(elapsed * 1.8)
const up = Math.max(0, g)
P.shRz = 0.22 + up * 0.35
P.elRx = -0.5 - up * 0.55

打断的处理则要"快"：状态立刻回 idle，口型目标设为闭合，字幕停止增长，并在气泡里给出明确反馈。打断后不要继续播放未完成的句子，否则用户会觉得自己按了个假按钮。

错误兜底：TTS 失败时也要"像在说话" ​

兜底不是"什么都不做"，而是用最低成本维持表演的完整性：

失败类型表现兜底策略观众感受
TTS 请求失败无音频、无时间轴全文字幕 + 默认微张口型循环像在看字幕版，仍是一个"人"
TTS 超时思考状态过久2 秒后切兜底，不无限等不被卡死
时间轴为空嘴不动、字幕不动按字数生成简化节奏至少嘴在动
音频解码失败有声但无时长用字幕估算时长大致同步
WebGL 不可用画面全黑静态形象 + 文字回复功能仍在

关键点是：兜底口型不能是"完全不动"。哪怕只是让嘴巴以 0.4 的微开权重做低频开合，观众也会认为角色在"说话"。完全静止的脸会被立刻判定为"卡了"。

与 UI 的联动：字幕气泡 ​

字幕气泡不是简单的 textContent 赋值，它承担三件事：

  1. 逐字出现：跟随 replyTime，让阅读节奏与说话节奏一致；
  2. 长度控制：超过两行要截断或滚动，不能把气泡撑到盖住整张脸；
  3. 可访问性：给气泡加 aria-live="polite"，读屏用户能听到回复；同时保留完整的文字副本，而不是只渲染可见部分。

演示里的气泡在说话结束后停留 1.2 秒再淡出，这个"留白"很重要：说完立刻消失会让观众来不及读最后一句。

可访问性与降级：没有 WebGL 也要能对话 ​

数字人站点经常被用在客服、展厅、教学场景，设备能力参差不齐。建议准备三档：

档位触发条件呈现
完整档WebGL2 + 设备像素比正常3D 人形 + 口型 + 手势 + 字幕
轻量档低端机、掉帧持续超标降采样、减少 morph 目标、关闭手势
文本档无 WebGL 或用户开启减少动效静态形象 + 字幕 + 键盘操作

降级不是"砍功能"，而是"保住核心信息"。对数字人来说，核心信息是回复内容与对话节奏，3D 只是表达方式。把这一点想清楚，降级方案就不会显得可怜。

性能与掉帧：低端机上先保口型 ​

掉帧时最该保的是口型与字幕的同步，最该先砍的是手势与阴影。实践顺序：

  1. 把 pixelRatio 限制到 1.5 甚至 1；
  2. 关闭手势层与头部微动，只保留口型与眨眼；
  3. 减少 morph 目标（只保留闭、微开、圆、扁四个）；
  4. 降低头部球体分段，或换成低模头；
  5. 必要时把渲染循环降到 30fps，但字幕与口型的时间基准仍按真实时间推进。

千万不要用"降低时间推进速度"来对抗掉帧，那会让说话变慢、字幕变慢，比掉帧更出戏。

代码示例 ​

第一段，主循环里只做"推进时间 + 驱动表演"，状态转换集中在 updateDialogue：

js
function updateDialogue(dt) {
  if (machine.state === 'idle') return
  machine.phase += dt

  if (machine.state === 'listening' && machine.phase > 1.5) {
    setState('thinking')
    return
  }
  if (machine.state === 'thinking' && machine.phase > 1.25) {
    startSpeaking()
    return
  }
  if (machine.state === 'speaking') {
    machine.replyTime += dt * params.语速
    if (machine.replyTime >= timeline.total) finishSpeaking()
  }
}

第二段，口型与字幕共用 replyTime，并让权重平滑收敛：

js
const progress = Math.min(1, machine.replyTime / timeline.total)
bubbleEl.textContent = REPLY_TEXT.slice(0, Math.floor(progress * REPLY_TEXT.length))

const target = VISEME_WEIGHTS[currentViseme()]
const k = 1 - Math.exp(-dt * 15)
for (let i = 0; i < MORPH_NAMES.length; i++) {
  const name = MORPH_NAMES[i]
  weights[i] += (target[name] * params.表情强度 - weights[i]) * k
  headMesh.morphTargetInfluences[i] = weights[i]
}

第三段，打断要同时清理三层：

js
function interrupt() {
  if (machine.state === 'idle') return
  machine.replyTime = 0
  setState('idle')
  bubbleEl.textContent = '（已打断，回到 idle）'
  bubbleEl.classList.add('show')
  machine.bubbleHold = 1.0
}

第四段，TTS 失败时走另一条分支：字幕一次性显示全文，口型用固定的默认节奏，时长由兜底常量控制，结束后同样回 idle：

js
if (machine.fallback) {
  bubbleEl.textContent = REPLY_TEXT
  target = { closed: 0.15, slight: 0.42 + Math.sin(t * 7) * 0.16 }
  if (machine.replyTime > machine.fallbackTotal) finishSpeaking()
}

整套代码没有一行音频，但状态、时间轴、口型、字幕、兜底都在位。替换成真实 TTS 时，只需要把 timeline 换成后端返回的音素时间轴，表演层不用动。

常见问题解答 ​

Q1：口型和声音不同步，应该调哪里？

先确认是不是"两个时钟"。如果字幕用定时器、口型用帧循环，调速或掉帧时必然漂移，正确做法是只维护一个 replyTime，两者都从它派生。其次看音频延迟：真实 TTS 的音频往往比时间轴晚 30 到 80 毫秒开始，口型应该按音频的起始时间做 lead-in，而不是从请求发出时就开始。最后看平滑系数，k = 1 - exp(-dt * 20) 在掉帧时依然稳定，但如果你用了固定 0.2 这种与帧率相关的系数，30fps 和 60fps 的表现会完全不同。

Q2：低端机掉帧，应该先砍什么？

先砍不影响"说话"的东西：阴影、后期、手势、头部微动。再降 pixelRatio 与几何分段。口型与字幕务必保留，因为它们是"这是一个会说话的人"的核心证据。如果仍然不够，把渲染降到 30fps，但时间轴仍按真实时间推进，这样画面会略卡，嘴型与字幕不会错位。最忌讳的是"帧率低就把 dt 乘小一点"，那会让整个表演慢放。

Q3：为什么对话结束后角色还保持抬手的姿势？

状态机切到了 idle，但骨骼目标没有归位。进入 idle 时要把所有关节目标设为待机值（肩下垂、肘微屈、头回正），再让平滑函数把当前值收回去。如果只改状态、不改目标，角色会停在最后一个手势上，看起来像"被按了暂停"。同理，离开 speaking 时要把口型目标设回闭合，否则嘴会一直张着。

Q4：模拟 TTS 失败时，为什么还要让嘴动？

因为观众判断"是否卡住"看的是表演是否还在继续，而不是有没有声音。完全静止的脸会被判定为崩溃，而"字幕 + 轻微开合"至少维持了"它在表达"的错觉。兜底口型不需要与文字精确对应，只要节奏稳定、幅度克制，就足以撑过故障窗口。等真实 TTS 恢复后再切回正常时间轴即可。

Q5：能不能直接接浏览器的 SpeechSynthesis？

可以，但要注意两个限制：SpeechSynthesis 的 onboundary 事件在不同浏览器上粒度差异很大，中文尤其不稳定，拿不到可靠的音素时间；而且它只提供"词/句"级别的回调，做精细口型仍然要自己估算时长。务实的方案是先用它做"有没有声音"的验证，再用后端 TTS 的音素时间戳替换口型驱动，接口形状保持成本篇的 synthesize 返回结构。

动手小练习 ​

  1. 给状态机加一个 error 状态：TTS 抛错时先进入 error 显示 1 秒提示，再自动回 idle。要求所有转出路径都清理口型与手势，并用 console.time 记录每个状态的停留时长。
  2. 把字幕的出现方式从"按字符均分"改成"按 segment 的起始时间"，让每个字在它对应的第一个 viseme 开始时出现；对比两种方式在语速 0.6 与 1.8 下的观感。
  3. 在演示里加一个"口型偏移"滑块（-200ms 到 +200ms），专门用来模拟音频延迟。记录偏移多少毫秒时你会觉得"嘴在抢拍"或"嘴在追声音"，并解释为什么负偏移比正偏移更难被容忍。
