36.3 实战案例：低代码配置台 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ② 与 ㉟ 再阅读。

核心概念讲解 ​

接桥：㉝ 的"一套场景多端交付"需要一个不写代码的配置入口 ​

㉝ 跨端与框架广度 解决的是"同一套场景怎么在 Web、小程序、XR 上交付"：几何可以降级、贴图可以换规格、渲染管线可以替换。做到那一步，代码层面的多端能力已经有了，但下一个问题马上出现：谁来改场景？

运营想换主推产品的摆放位置，市场想把主色从青色改成橙色，客户成功想给某个客户关掉阴影。这些人不该改代码，也不该学会 Three.js。你需要一个入口：填表单、看预览、点发布。这个入口就是低代码配置台。它不是"给开发者用的可视化编辑器"（那是 ㉟），而是"给非开发者用的配置界面"。

低代码台的五层结构 ​

层次职责输入输出
Schema 层定义有哪些字段、类型、范围、默认值业务规则字段描述表
表单层把字段描述渲染成控件字段描述表用户输入
DSL 层把输入组装成场景配置字段值JSON
运行时层校验、构建、预览、发布DSL场景与版本
版本层草稿、发布、回滚、审计快照可追溯的版本

这条链路和 36.1、36.2 完全对齐：表单只是"生成 DSL 的一种方式"，DSL 仍然要过校验，运行时仍然要原子替换，版本仍然要能回滚。低代码台没有发明新的运行时，它只是把"写 JSON"换成了"填表单"。

表单驱动：字段由 schema 生成，不手写控件 ​

低代码台最容易腐化的地方，是"每加一个字段就手写一段 HTML"。加十个字段就有十段重复的标签、校验、取值、回显代码，最后没人敢删。正确做法是字段即数据：

js
const FIELDS = [
  { key: 'sceneType', label: '场景类型', type: 'select', options: [['campus', '园区'], ['gallery', '展厅']] },
  { key: 'fov', label: '相机 FOV', type: 'range', min: 25, max: 85, step: 1, unit: '°' },
  { key: 'light', label: '光照强度', type: 'range', min: 0, max: 3, step: 0.05 },
  { key: 'color', label: '主材质颜色', type: 'color' },
  { key: 'rotate', label: '自动旋转', type: 'checkbox' }
]

渲染器只认 type，不认具体字段：

js
function renderField(field) {
  if (field.type === 'select') return makeSelect(field)
  if (field.type === 'range') return makeRange(field)
  if (field.type === 'color') return makeColor(field)
  if (field.type === 'checkbox') return makeCheckbox(field)
  throw new Error('未注册的控件类型：' + field.type)
}

这样做有四个直接收益：新增字段只改一行 schema；校验规则和表单共用同一份描述；文档可以从 schema 自动生成；控件类型可以按端替换（Web 用原生控件，小程序用原生组件）。演示页 lowcode-builder-lab.html 的表单就是这样生成的，页面上没有任何一个硬编码的 <input>。

表单与 DSL 的双向同步 ​

"双向同步"听起来简单，做起来最容易出环：表单变化触发 DSL 更新，DSL 更新又触发表单回填，回填又触发一次 change，最后死循环或光标乱跳。三种常见方案：

方案做法优点风险
生成式表单是唯一来源，每次变化重新生成整份 DSL简单、状态少用户手改 DSL 会被覆盖
补丁式DSL 是唯一来源，表单变化只 patch 对应字段保留手改内容需要路径写回与类型转换
混合式表单主导常规字段，DSL 编辑走"应用"按钮兼顾两者需要明确当前来源

演示页用的是混合式：改表单时整份重新生成，点"从 JSON 应用"时反向解析并回填表单。这个方案适合字段少、结构稳定的场景。字段多、且允许手写 DSL 的项目，建议用补丁式：

js
function setByPath(target, path, value) {
  const keys = path.split('.')
  let cursor = target
  for (let i = 0; i < keys.length - 1; i++) {
    const key = keys[i]
    if (cursor[key] === undefined) cursor[key] = {}
    cursor = cursor[key]
  }
  cursor[keys[keys.length - 1]] = value
}

无论哪种方案，都要有一个 syncing 标志位，在程序化写控件时跳过事件回调；并且用值比较而不是"事件次数"来判断是否真的变化。否则一次滑块拖动会触发几十次重建。

预览区：防抖、原子替换、和生产同一条管线 ​

预览区不是"另一套渲染代码"，它必须和生产运行时共用同一份校验器与构建器。很多线上事故的根因是"预览能跑、线上报错"，因为预览用了简化版校验，或者预览的构建器没处理某种类型。

三个工程细节：

  • 防抖：滑块拖动时每 150~300 毫秒才重建一次，避免每像素都建几何；
  • 原子替换：先构建到临时组，成功后再替换，失败保留上一版；
  • 性能预算：预览时统计节点数、材质数、预计 draw call，超过阈值就提示，而不是等发布后才在低端机卡顿。

预览还要明确"它不代表最终画质"。阴影分辨率、后处理、DPR 在不同端不同，预览只需要保证结构正确：物体在不在、颜色对不对、相机构图合不合理。画质细节交给真机验证。

草稿、发布与回滚 ​

三个概念必须分开：

  • 草稿：编辑中的状态，可以自动保存、可以脏、可以频繁变化；
  • 发布：一次不可变的快照，带版本号、哈希、发布人、发布时间；
  • 回滚：把线上指向某个历史快照，通常只需要改一个指针。

最小的发布流程：

  1. 校验当前 DSL（结构 + 语义 + 业务预算）；
  2. 计算影响面（对象数、材质数、新增资产、相机变化）；
  3. 生成版本号与内容哈希，写入审计日志；
  4. 线上原子替换，保留 lastGood；
  5. 观察指标，异常则回滚到上一版。

回滚的目标要明确：是"回滚到上一版"还是"回滚到任意历史版本"。前者只需要保留一个前指针，后者需要完整的版本列表。演示页实现的是前者：发布两次后，点"回滚上一版"会恢复到上一次发布的表单与场景。真实项目建议保留完整版本列表，但默认按钮只做"上一版"，减少误操作。

发布前校验与"影响面提示" ​

低代码台最需要的一个能力，是在点"发布"之前告诉作者"这次改动会影响什么"。影响面不需要精确到字节，能给出量级就够了：

js
function computeImpact(prev, next) {
  const prevProps = prev.objects.filter((o) => o.role === 'prop').length
  const nextProps = next.objects.filter((o) => o.role === 'prop').length
  return {
    props: prevProps + ' → ' + nextProps,
    materials: prev.materials.length + ' → ' + next.materials.length,
    fov: prev.camera.fov + ' → ' + next.camera.fov,
    addedAssets: next.assets.filter((id) => !prev.assets.includes(id))
  }
}

提示的措辞要面向非技术用户："物体从 6 个变成 9 个，相机会拉近，预计绘制调用增加 3 次"。如果新增了资产，还要提示"该资产尚未上传，发布后可能显示为占位材质"。这类提示能把大量"发布后才发现"的问题提前到发布前。

配置与代码的边界：什么该配置化，什么不该 ​

这是低代码台最重要的一张表。配置化不是越多越好，越界的配置会变成"一门没人会写的编程语言"。

适合配置化不适合配置化
物体布局、变换、层级自定义着色器算法
相机机位、FOV、目标点物理模拟与碰撞求解
灯光类型、强度、颜色复杂交互状态机
材质颜色、金属度、粗糙度网络请求与鉴权逻辑
文案、标签、跳转链接安全策略与权限判断
动画类型与速度参数性能关键的每帧循环
功能开关、灰度比例配置 schema 本身
资产 id 与多端映射资产上传与转码流程

一条实用的判断规则：如果一项改动需要评审"渲染是否正确"，它更可能是代码；如果只是"摆放与外观"，它可以是配置。 另一条规则：配置应该描述"是什么"，而不是"怎么算"。当你发现自己在配置里写条件分支、循环、表达式求值，说明已经越界了，应该把它收回到一个受控类型或插件里。

团队协作与权限（简要） ​

不展开后端，只说前端需要知道的边界：

  • 角色：查看者（只能预览）、编辑者（能改草稿）、发布者（能发布）、管理员（能改 schema 与权限）；
  • 并发：草稿用 revision 做乐观锁，保存时带上"我基于哪个版本改的"，落后就提示合并，而不是静默覆盖；
  • 环境：开发、预发、生产三套配置，发布是"从预发提升到生产"，不是直接改生产；
  • 审计：每次发布记录人、时间、版本、哈希、影响面摘要，回滚也记录。

低代码台让"不改代码的人"获得了改场景的能力，同时也让"一次误操作影响全量用户"变得更容易。权限与审计不是锦上添花，是这个能力的刹车。

术语解释 ​

术语含义在本篇里的落点
Schema 驱动表单控件类型、范围、默认值都由字段描述生成不手写 <input>
草稿编辑中的可变状态，可自动保存允许频繁变化
发布版本一次不可变快照，带版本号与内容哈希回滚的目标
影响面一次改动波及的对象数、材质数、资产与相机变化发布前的提示
乐观锁保存时带上基于的版本号，冲突则提示合并多人协作防覆盖
快照某一时刻配置的完整副本审计与回滚的依据

三个常见坑 ​

  1. 预览与线上双实现。 预览用自己的简化构建器，线上用正式构建器，结果是"预览正常、线上黑屏"。解决办法只有一条：共用同一份校验与构建代码，预览只换容器，不换逻辑。
  2. 表单字段爆炸。 所有字段平铺，用户找不到重点。用分组、折叠、搜索与"常用字段"来解决，而不是继续加字段。
  3. 发布没有回滚目标。 只存了"当前配置"，没存历史快照，出事时只能手改。发布即快照，回滚才有落点。

常见问题解答 ​

Q1：配置化之后性能反而变差了，问题通常出在哪？

先查三处。第一，材质是否逐对象创建：配置里每个对象都内联颜色，构建时每个对象一份 MeshStandardMaterial，draw call 与着色器编译次数都会上升；应该按 materialId 缓存复用。第二，是否每次表单变化都全量重建：滑块每动一下建一次几何，GC 和显存都会抖；应该防抖，并对纯属性变化走差量。第三，配置是否变相引入了更重的效果：从"固定一盏平行光"变成"每个物体一个点光源"，这不是配置化的错，是配置暴露了不该开的预算。配置化本身只增加一点解析与校验开销，通常远小于一次重建的成本。

Q2：表单字段越加越多，怎么控制？

四个手段，按成本从低到高：给字段加分组与折叠，默认只展示"常用"；给字段加 advanced 标记，收进"更多设置"；把强相关字段合并成一个复合控件（例如"相机预设"替代 FOV、位置、目标三个字段）；把长尾能力从表单里移出去，交给 DSL 或插件。根本的解法是收敛场景类型：如果每加一个场景就加十个字段，说明应该把差异做成"场景模板 + 少量参数"，而不是继续堆字段。

Q3：怎么判断一个能力该不该配置化？

问三个问题：改动是否只影响"摆放与外观"？是否能用有限类型与参数表达？出错时是否能通过校验提前发现？三个都是"是"，就适合配置化。只要有一个是"否"，就应该留在代码里。典型不该配置化的：着色器算法、物理、复杂交互状态机、鉴权与安全策略、性能关键循环。把这些问题塞进配置，短期省了发版，长期会得到一门只有一个人会写、没有类型、没有测试、无法重构的"配置语言"。

Q4：低代码台要不要支持自定义组件或插件？

可以，但要走"代码发布"而不是"配置下发"。自定义组件本质上是新增一种节点类型，它需要构建器、属性面板、校验规则和资源声明，这一整套应该随代码版本发布、经过评审与测试。配置里只引用已经注册的类型与 assetId。这样既保留了扩展性，又不会让远端配置获得执行任意代码的能力。插件注册表还可以带版本号与能力声明，运行时按能力过滤，保证旧端不会收到它不认识的类型。

Q5：团队协作与权限最小要做到什么程度？

最小可用集是四件事：角色区分（查看/编辑/发布）、草稿乐观锁（防止两人互相覆盖）、发布快照与回滚、审计日志（谁在什么时候发了什么）。再往上才是审批流、环境隔离、字段级权限。不要一开始就做复杂 RBAC，先把"发布是快照、回滚有目标、改动有记录"做扎实，这三件事能挡住绝大多数事故。

动手小练习 ​

  1. 给演示页加一个"雾效浓度"字段：在 FIELDS 里加一条 range，在 makeDsl 里写进 scene.fog.near，确认表单、DSL、预览三处同步变化，且不需要改任何控件代码。
  2. 把演示页的"回滚上一版"扩展成"回滚到任意历史版本"：维护版本列表与当前指针，点击某个版本时恢复它的表单与 DSL。思考回滚后"草稿"应该处于什么状态。
  3. 为发布流程补一张检查单：校验通过、资产齐全、预算未超、影响面已确认、审计已记录。挑其中两项写成可执行的检查函数，并说明失败时按钮应该如何禁用或提示。
