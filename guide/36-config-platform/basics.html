36.1 基础入门：场景配置 DSL 与运行时解释器 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ② 与 ㉟ 再阅读。

核心概念讲解 ​

接桥：㉟ 导出的 JSON 只是"存档"，还不是"配置" ​

在 ㉟ 场景编辑器 里，我们做了一件很痛快的事：把轨道控制器、变换手柄、属性面板拼成一个可视化编辑器，用户拖一拖、转一转，最后点"导出"，得到一份 JSON。那份 JSON 已经很小，也能把当时的画面原样还原回来，看起来已经很像"配置"了。

但它还不是。35.2 导出的是一份按编辑器需要裁剪过的快照：id 由编辑器顺序分配，颜色内联在每个节点里，没有材质表；nodes 里只有可编辑物体，没有相机、灯光、动画与资源引用。它能回答"那一刻场景长什么样"，却回答不了下面这些问题：

  • 这个对象叫什么？是"主楼"还是自动编号的 box-7？
  • 换一台设备、换一个屏幕，position 要不要按比例缩放？
  • 两个对象共用同一份材质，改一处颜色要不要改两处？
  • 这份数据是哪个版本？旧字段升级后还能不能读？
  • 发布前能不能自动检查"材质引用不存在"？

所以本篇要做的，是把"存档"再往前推一步，变成可运维的配置。区别可以用一张表说清：

维度编辑器导出的存档可运维的配置
命名顺序分配的 id / 自动编号语义化 id，如 tower-a、main-light
坐标多数是绝对世界坐标相对父节点 + 显式层级
引用颜色内联，没有材质表按 id 引用，单点修改
默认值全量写出，冗余字段多只写与默认值不同的部分
版本只有 version，没有迁移链version 字段 + 迁移函数
校验导入时只做基础合法性检查schema、引用、数值范围、环检测
变更粒度整份替换可 diff、可增量、可回滚
远端下发不适合支持灰度、开关、热更新

一句话：存档负责"还原"，配置负责"运行、协作和演进"。把它展开成四个关键字就是：语义化（稳定 id 与明确单位）、可版本化（version 与迁移链）、可复用（材质与资产按 id 引用）、可远端下发（体积可控、可校验、可灰度）。㉟ 解决"人怎么摆"，本篇解决"摆完怎么变成可运维的数据"。

配置语言的四条设计原则 ​

场景配置本质上是一门很小的领域语言（DSL，Domain Specific Language）。它不需要图灵完备，反而应该刻意"能力有限"。四条原则决定了它能不能长期活下去。

① 节点类型有限且封闭。 只允许 scene、camera、light、object、material、animation 这几类节点。类型集合稳定，解释器才能为每种类型写一个构建器，也才能在编辑器里生成对应的表单。类型一旦无限扩张，配置就会变成"另一套代码"。

② 只写数据，不写行为。 配置里不能出现函数、回调、eval 字符串、着色器源码。原因不是"JSON 不支持"，而是四件更实际的事：

  • 无法跨语言、跨端传输：小程序、服务端、编辑器都要读同一份数据；
  • 无法静态校验：一段字符串里的逻辑，schema 看不见；
  • 无法 diff 与审计：函数体变化只能整段替换；
  • 安全风险：远端下发的配置若可执行，等于把后门送进页面。

行为应该由类型 + 参数表达。例如"让信标绕 Y 轴转"写成 { "type": "spin", "axis": "y", "speed": 0.8 }，由解释器里的动画构建器实现，而不是在配置里塞一个 () => mesh.rotation.y += 0.01。

③ 引用而不是拷贝。 材质、资产、父节点都用 id 引用。拷贝会让"改一处、漏一处"变成常态；引用则保证单一事实来源，也让 diff 变小。引用的代价是要做存在性校验和环检测，这两件事恰好是 36.2 的重点。

④ 层级而不是全量世界坐标。 物体挂在父节点下，position 相对父级。这样移动一个组，整组子节点跟着走；换端调整整体布局时，只改根节点即可。代价是解释器必须先建节点、再挂父子，顺序不能错。

还有一条容易被忽略的边界：配置里不能塞 GPU 资源本身。贴图的像素、模型的二进制、编译后的着色器程序，都不该出现在 JSON 里。配置只写 assetId，由运行时的资源表去加载和缓存。把 base64 贴图塞进配置，短期省事，长期会让配置体积、加载时间和 diff 全部失控。

一份最小 DSL：六类节点 ​

先看一份完整但足够小的例子。它描述一个"园区里有一根发光信标"的场景：

json
{
  "version": 1,
  "scene": {
    "background": "#0b0e14",
    "fog": { "color": "#0b0e14", "near": 16, "far": 44 }
  },
  "camera": {
    "fov": 45,
    "position": [10, 8, 13],
    "target": [0, 1.5, 0]
  },
  "materials": [
    { "id": "stone", "color": "#94a3b8", "metalness": 0.1, "roughness": 0.8 },
    { "id": "glass", "color": "#38bdf8", "metalness": 0.85, "roughness": 0.16 }
  ],
  "objects": [
    { "id": "ground", "type": "plane", "scale": [30, 1, 30], "rotation": [-1.5708, 0, 0], "material": "stone" },
    { "id": "tower", "type": "box", "position": [0, 2, 0], "scale": [1.4, 4, 1.4], "material": "glass" },
    { "id": "beacon", "type": "torus", "position": [0, 4.4, 0], "scale": [1.1, 1.1, 1.1], "material": "glass" }
  ],
  "lights": [
    { "type": "hemisphere", "sky": "#7dd3fc", "ground": "#0f172a", "intensity": 0.6 },
    { "type": "directional", "position": [6, 10, 4], "intensity": 2.2, "shadow": true }
  ],
  "animations": [
    { "target": "beacon", "type": "spin", "axis": "y", "speed": 0.8 }
  ]
}

六类节点的职责如下：

节点关键字段语义常见错误
scenebackground、fog全局环境，不含任何对象把对象塞进 scene
camerafov、position、target观察方式，单位统一为米与弧度同时写 lookAt 和 target
materialid、color、metalness、roughness可复用的外观描述每个对象内联一份
objectid、type、position、scale、material、parent几何 + 变换 + 引用用自动编号当稳定 id
lighttype、intensity、color、shadow光照意图强度不设上限，越界后画面全白
animationtarget、type、axis、speed对某个 id 的持续行为目标不存在或拼错

设计 DSL 时，单位与默认值必须写进规范，不能只活在解释器代码里。本篇约定：长度用米，旋转用弧度，intensity 为无量纲倍率，未写的 position 默认为 [0, 0, 0]，未写的 scale 默认为 [1, 1, 1]。这些默认值一旦公开，就变成了契约，后续不能随便改；要改只能走版本迁移。

解释器：解析、校验、构建、挂载、销毁 ​

配置本身不会变成画面，中间必须有一层解释器。它的职责可以拆成五个阶段：

阶段输入输出失败时怎么办
解析 parse字符串内存对象报语法错误与字符位置，保留上一版
校验 validate内存对象合法对象或错误列表拒绝构建，路径式报错
构建 build合法对象 + 资源临时节点组回滚到上一版，清理半成品
挂载 mount临时节点组正在运行的场景原子替换，旧组延后销毁
销毁 dispose旧节点组释放后的显存兜底遍历，记录泄漏告警

解析只是 JSON.parse，不要用 eval，也不要自己写解析器。解析失败时要给出字符位置，方便编辑器把光标放到出错行。校验是下一篇的主角，本篇只需要知道它发生在构建之前。构建是把每个节点翻译成 Three.js 对象，顺序是"先建全部节点、再挂父子、最后加灯光与动画"。挂载建议先构建到一个临时 Group，确认没有异常后再替换场景中的旧组。销毁必须显式遍历 geometry、material、贴图并调用 dispose，否则每次热更新都会漏一点显存。

这五个阶段串起来，解释器就有了一个稳定的"外壳"：

js
function loadConfig(text) {
  const data = parse(text)          // 1. 解析
  const errors = validate(data)     // 2. 校验
  if (errors.length) return { ok: false, errors }
  const next = build(data)          // 3. 构建到临时组
  mount(next)                       // 4. 原子替换
  dispose(previous)                 // 5. 销毁旧组
  return { ok: true, data }
}

真实项目里，构建可能是异步的：模型要下载、贴图要解码。这时把"构建"拆成"预加载资源"和"创建节点"两段，预加载失败就不要进入挂载阶段。

构建器注册表：类型到工厂的映射 ​

解释器不应该写一长串 if (type === 'box') ... else if (type === 'sphere') ...。更好的做法是注册表：类型名对应一个工厂函数，新增类型只加一条注册，不改主流程。

js
const builders = new Map()

builders.set('box', (node, ctx) => {
  const geometry = new THREE.BoxGeometry(1, 1, 1)
  return new THREE.Mesh(geometry, ctx.material(node.material))
})

builders.set('terrain', (node, ctx) => {
  const geometry = makeTerrain(node.size ?? 18)
  return new THREE.Mesh(geometry, ctx.material(node.material))
})

function createNode(node, ctx) {
  const factory = builders.get(node.type)
  if (!factory) throw configError('/objects/' + node.id + '/type', 'registered type', node.type)
  return factory(node, ctx)
}

注册表有三个额外好处：能力可枚举（UI 可以直接列出"这个平台支持哪些类型"）、可替换（Web 与小程序可以注册不同的实现）、可测试（每个工厂单独测，不必拉起整个解释器）。当业务方说"我要一个自定义的地形类型"，你只需要加一条注册，而不是改解释器的核心。

资源引用：assetId 到加载器表 ​

配置里写 assetId，运行时用一张表把它解析成加载器：

js
const assets = {
  'tex:grid': () => new THREE.TextureLoader().loadAsync('/assets/grid.png'),
  'model:crystal': () => new GLTFLoader().loadAsync('/assets/crystal.glb')
}

async function preload(spec) {
  const ids = spec.assets ?? []
  const loaded = await Promise.all(ids.map((id) => {
    const loader = assets[id]
    if (!loader) throw configError('/assets', 'known assetId', id)
    return loader()
  }))
  return new Map(ids.map((id, i) => [id, loaded[i]]))
}

资源表让"配置"与"资产"解耦：同一份配置在 Web 上可以解析到 2048 贴图，在小游戏上解析到 512 贴图，配置本身不需要改。它也天然支持缓存与引用计数：两个对象引用同一个 assetId，只加载一次。

路径式错误定位：从"报错"到"指路" ​

配置解释器最没用的错误信息是 Error: invalid config。最有用的错误信息长这样：

js
{
  path: '/objects/3/material',
  expected: 'existing material id',
  actual: 'gold',
  message: '引用了不存在的材质'
}

路径式报错的价值在于：编辑器可以按路径选中对应节点，CLI 可以按路径做批量修复，CI 可以把错误聚合成报告。实现上只需要在构建和校验时携带"当前位置"：

js
function fail(path, expected, actual, message) {
  const error = new Error(message)
  error.path = path
  error.expected = expected
  error.actual = actual
  throw error
}

路径的写法要统一：对象用 /objects/3，属性用 /objects/3/material，数组下标直接用数字。不要混用 objects[3].material 与 /objects/3/material 两种风格，否则工具链要写两套解析。

热更新的前提：幂等重建 ​

很多团队第一次做热更新，会写出这样的代码：收到新配置就 scene.add(newGroup)，却忘了移除旧组。结果是每更新一次，场景里就多叠一层，帧率逐次下降。

热更新成立的前提是幂等重建：同一份配置执行两次，结果与执行一次完全相同。要做到这一点，需要三条纪律：

  1. 每次重建都从空的临时组开始，不复用上一版的节点；
  2. 所有资源引用都可重复获取，加载器带缓存，重复调用不产生第二份纹理；
  3. 旧组必须销毁，包括几何、材质、贴图、事件监听与动画循环。

演示页 schema-lab.html 就是按这个顺序做的：点"应用"后先解析，再校验，通过后构建到一个新组，挂载时替换旧组，最后遍历销毁。校验失败时直接返回，右侧场景保持上一版，这样用户改配置时不会"越改越黑"。

术语解释 ​

术语含义在本篇里的落点
DSL面向某个领域的受限语言，只描述该领域的概念场景 DSL 只允许六类节点
Schema描述"配置长什么样"的数据，含类型、必填、范围、默认值驱动校验与表单
解释器把配置翻译成运行时对象的程序解析 → 校验 → 构建 → 挂载 → 销毁
构建器类型到对象工厂的映射，负责翻译单个节点type 对应一个工厂函数
assetId资源引用的稳定标识，由资源表解析成实际加载器贴图、模型不内联进配置
幂等重建同一份配置执行两次，结果与执行一次相同热更新不叠层、不漏资源

三个常见坑 ​

  1. 把编辑器自动编号当配置 id。 编号在 id 冲突时会被重新分配，配置 diff 全是噪声，引用也会断。正确做法是让人或工具赋予语义化 id，并在保存时保持稳定。
  2. 相对坐标与绝对坐标混用。 父节点一移动，子节点位置就飞了。规范里必须明确 position 相对父级，根节点才相对世界；编辑器导出时要显式转成相对坐标。
  3. 材质逐对象内联。 20 个对象各建一份 MeshStandardMaterial，draw call 和着色器编译次数都会上去。配置层用 material 引用，构建层做材质缓存。

① 一个最小的解释器骨架：

js
async function applyConfig(text, ctx) {
  let data
  try {
    data = JSON.parse(text)
  } catch (error) {
    return { ok: false, stage: 'parse', message: error.message, at: error.offset }
  }

  const errors = validate(data, ctx.capabilities)
  if (errors.length) return { ok: false, stage: 'validate', errors }

  await preload(data.assets ?? [])
  const next = buildGroup(data, ctx)
  swapGroup(next)
  return { ok: true, data }
}

② 构建器只负责"翻译一个节点"：

js
const builders = {
  box: (node, ctx) => new THREE.Mesh(
    new THREE.BoxGeometry(1, 1, 1),
    ctx.material(node.material)
  ),
  sphere: (node, ctx) => new THREE.Mesh(
    new THREE.SphereGeometry(0.6, 32, 24),
    ctx.material(node.material)
  )
}

③ 挂载与销毁要成对出现：

js
function swapGroup(next) {
  const old = current
  current = next
  scene.add(next)
  if (old) {
    scene.remove(old)
    old.traverse((obj) => {
      obj.geometry?.dispose()
      const materials = Array.isArray(obj.material) ? obj.material : [obj.material]
      materials.forEach((m) => m?.dispose())
    })
  }
}

演示页里的"应用"按钮就是这三步的可视化版本。建议先点一个示例，再故意把 /camera/fov 改成字符串 "45"，观察右侧场景保持不变、错误路径被选中；改回数字后再点一次，场景立刻恢复。

常见问题解答 ​

Q1：㉟ 已经能导出 JSON 了，为什么不能直接拿它当运行时配置？

因为它记录的是"编辑器内部状态"，不是"场景意图"。三个硬伤：第一，id 由编辑器顺序分配，导入冲突时还可能重新编号，diff 和引用都不稳定；第二，坐标是绝对世界坐标，换一个屏幕比例或整体布局就要重算；第三，颜色内联且没有材质表与默认值，改一处颜色要改多处。存档的目标是"还原当时那一帧"，配置的目标是"让多个人、多台设备、多个版本持续运行同一份意图"。两者的字段长得像，契约完全不同。

Q2：DSL 里能不能写 Shader、表达式或回调函数？

不要。配置只描述"类型 + 参数"，把行为留给解释器。允许字符串形式的表达式会带来四个问题：无法静态校验、无法安全地远端下发、无法做 diff、跨端执行环境不一致。自定义着色器应该做成一种受控类型，例如 material.type = "water" 加上几个参数，由注册表里的构建器加载固定的 shader；而不是把 GLSL 源码塞进 JSON。若确实需要可编程能力，应该走"插件/扩展包"的代码发布流程，而不是配置下发。

Q3：模型和贴图怎么放进配置？直接写 URL 可以吗？

可以写 URL，但更推荐写 assetId。URL 把存储位置耦合进了配置：换 CDN、加签名、做多端规格切换时都要改配置。assetId 则通过运行时的资源表解析，不同端可以映射到不同规格。无论哪种方式，都不要把 base64 内联：它会让配置体积膨胀十倍以上，破坏 diff，也让加载无法并行。资源表还要处理失败兜底：贴图失败退到纯色材质，模型失败退到占位几何体，并上报一条可诊断的错误。

Q4：每次改配置都全量重建，会不会很卡？

小场景不会，几十个节点的重建在毫秒级；大场景会。优化的顺序不是"一上来就做增量更新"，而是先确认三件事：构建是否在临时组里完成、旧资源是否释放、重建是否被防抖到用户停止输入之后。这三件事做好，再考虑差量更新。差量更新的前提是稳定 id 与"配置到运行时对象"的映射表，只能替换发生变化的节点；它更省，但也更容易出状态残留，适合在 36.2 里讨论清楚后再上。

动手小练习 ​

  1. 打开 schema-lab.html，把 camera.fov 改成字符串 "45"，记录错误路径与提示；再改成 999，观察数值范围校验是否生效。最后改回 45，确认场景恢复。
  2. 给园区示例增加一个 parent 层级：把 beacon 挂到 tower 下，调整它的 position 让视觉位置不变。思考为什么"改父节点位置"能让子节点跟着走，以及导出时该如何把绝对坐标转成相对坐标。
  3. 自己写一个 30 行的解释器：只支持 box、sphere 两种类型和 directional 一种灯光，要求错误信息带 /objects/下标/字段 路径，并且第二次应用同一份配置时场景节点数量不增加。
