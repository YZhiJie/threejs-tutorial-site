36.2 进阶应用：校验、版本与热更新 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ② 与 ㉟ 再阅读。

核心概念讲解 ​

接桥：㉕ 的容错是"运行时兜底"，配置层的容错要更早——在加载前 ​

在 ㉕ 线上监控与容错 里，我们设计了一架降级阶梯：帧率不足就降 DPR、关泛光、关阴影，最后退到静态图。那套机制解决的是"场景本身跑不动"的问题，它的所有判断都发生在渲染已经开始之后。

配置错误不是这类问题。它会在更早的地方炸掉：objects[2].material 指向一个不存在的材质，构建器拿到 undefined 后 new THREE.Mesh(geometry, undefined)，Three.js 回退到默认材质，画面看起来"好像还行"，但颜色全错；父子关系成环，构建时无限递归，页面直接卡死；camera.fov 是字符串，PerspectiveCamera 拿到 "45"，投影矩阵算出一堆 NaN，屏幕一片漆黑。这些错误不会给你降级的机会，因为它们连一个合法的场景都没建出来。

所以配置层的容错必须提前到加载之前：先在数据层把错误拦住，再让运行时只处理合法输入。㉕ 的兜底是"跑不动时怎么退"，本篇的兜底是"跑之前先证明它能跑"。

校验的三层：语法、结构、语义 ​

很多团队把"校验"等同于"能 JSON.parse 就算通过"，这只覆盖了第一层。完整的校验至少有三层：

层次检查什么典型错误成本
语法 parse是不是合法 JSON少一个逗号、多一个尾逗号极低，JSON.parse
结构 schema类型、必填、枚举、范围fov 是字符串、缺 material、type 拼错低，遍历一遍
语义 semantic引用是否存在、父子是否成环、能力是否满足悬空材质、循环父子、纹理超过设备上限中，需要建索引

三层之外还有一层"业务约束"，通常不算通用校验，但同样要拦：节点总数上限、材质数量上限、单个场景的包体预算、是否允许使用实时阴影。这些规则因项目而异，最好也写成声明式数据，而不是散落在业务代码里。

一个实用的顺序是：先语法、再结构、最后语义。语法失败直接返回，不要试图修复；结构失败可以给出默认值或夹取；语义失败必须拒绝，因为"引用的东西不存在"没有安全的默认值。

手写校验器：不引依赖也能做 ​

JSON Schema 生态很成熟，但很多 3D 项目并不想为了校验引入一个几十 KB 的运行时库。好消息是：场景 DSL 的规则通常很窄，手写一个够用的校验器只需要几十行。关键是把规则写成数据，而不是写成 if 分支：

js
const objectSchema = {
  id: { type: 'string', required: true },
  type: { type: 'enum', values: ['box', 'sphere', 'torus'], required: true },
  position: { type: 'vec3', default: [0, 0, 0] },
  rotation: { type: 'vec3', default: [0, 0, 0] },
  scale: { type: 'vec3', default: [1, 1, 1] },
  material: { type: 'ref', table: 'materials', required: true }
}

有了这份规则表，校验循环就非常薄：

js
function checkObject(node, index, ctx) {
  const path = '/objects/' + index
  const errors = []

  for (const [key, rule] of Object.entries(objectSchema)) {
    const value = node[key]
    if (value === undefined) {
      if (rule.required) {
        errors.push({ path: path + '/' + key, expected: rule.type, actual: 'missing' })
      } else if (rule.default !== undefined) {
        node[key] = clone(rule.default)
      }
      continue
    }
    if (rule.type === 'string' && typeof value !== 'string') {
      errors.push({ path: path + '/' + key, expected: 'string', actual: value })
    }
    if (rule.type === 'enum' && !rule.values.includes(value)) {
      errors.push({ path: path + '/' + key, expected: rule.values.join(' | '), actual: value })
    }
    if (rule.type === 'vec3' && !isVec3(value)) {
      errors.push({ path: path + '/' + key, expected: 'vec3', actual: value })
    }
    if (rule.type === 'ref' && !ctx.tables[rule.table].has(value)) {
      errors.push({ path: path + '/' + key, expected: 'existing id', actual: value })
    }
  }
  return errors
}

这份规则表还有额外收益：同一份 schema 可以驱动低代码表单。字段类型决定控件类型，enum 变成下拉框，vec3 变成三个数字输入，ref 变成材质选择器。36.3 的表单生成就是从这里长出来的。规则只写一次，校验、表单、文档三处共用。

什么时候该引 JSON Schema 库？当规则复杂到需要 oneOf、条件依赖、递归结构、跨文件 $ref 时。那时手写会迅速变成"重新发明 JSON Schema"，不如直接用成熟实现，并接受它的包体与错误信息风格。

严格与宽松：默认值、夹取与"不猜" ​

校验器通常要支持两种模式：

行为严格模式宽松模式
缺必填字段报错可用默认值则补，否则报错
数值越界报错夹到合法区间并记录"已修正"
类型错误报错报错，不自动转换
悬空引用报错报错，不猜最近似项
循环父子报错报错，不做拓扑重排

宽松模式的设计原则是：只修"有确定答案"的问题，绝不猜用户的意图。缺 fov 可以补 45，因为默认值是规范的一部分；fov 写成 "45" 不能自动转数字，因为无法判断这是手误还是上游序列化错误；材质写成 gold 而表里只有 golden，更不能自动匹配，猜错一次可能让整个场景的颜色含义都变掉。

无论哪种模式，宽松修正都必须留下记录。演示页里把这类结果标成 FIX 而不是静默通过，就是为了让作者知道"这份配置不是原样运行的"。生产环境还应该把修正条数上报：修正率突然升高，往往意味着上游表单或迁移函数出了问题。

版本与迁移：把字段改名变成可执行的历史 ​

配置一旦发出去，字段名就变成了契约。想改 mat 为 material、把 pos 改为 position，不能直接改代码然后祈祷旧数据不存在。正确做法是给配置加 version，并维护一条单向迁移链：

js
const CURRENT = 2

const migrations = {
  1: (data) => ({
    version: 2,
    scene: data.scene,
    camera: data.camera,
    objects: (data.objects ?? []).map((item) => ({
      ...item,
      material: item.mat ?? item.material,
      position: item.pos ?? item.position
    }))
  })
}

function migrate(data) {
  let config = data
  while (config.version < CURRENT) {
    const step = migrations[config.version]
    if (!step) throw new Error('缺少 v' + config.version + ' 的迁移函数')
    config = step(config)
  }
  return config
}

四条纪律决定了迁移函数能不能长期维护：

  1. 纯函数：输入输出都是普通对象，不改原对象、不读全局状态、不发网络请求；
  2. 只向前：每次只升一个版本，链式调用，绝不写"v1 直接跳到 v3"的特例；
  3. 幂等：同一份 v1 数据迁移两次，结果一致；重复执行不会叠加字段；
  4. 先迁移再校验：校验器只认当前版本，不写"兼容 v1"的分支。

迁移链要配测试夹具：每个历史版本留一份真实配置作为 fixture，CI 里跑"全部旧版本都能迁移到当前版本并通过校验"。这比事后在线上修数据便宜得多。

配置级开关与灰度 ​

19.4 生产监控与灰度发布 讲的是代码版本的灰度。配置化之后，可以再加一层配置级灰度：同一份代码，不同场景、不同用户分桶拿到不同配置。

json
{
  "version": 2,
  "features": {
    "shadows": true,
    "bloom": false,
    "maxDpr": 1.5
  }
}

三个要点：

  • 默认值必须安全：远端没下发、字段缺失、解析失败时，一律回退到保守默认值，而不是"全开"；
  • 开关在构建期生效：不要在每帧里读开关，否则既浪费又会让画面在帧间闪烁；需要动态关闭的开关（如 Bloom）应该走运行时的 enabled 属性，而不是重建整个场景；
  • 分桶键要稳定：按 sceneId、用户哈希或设备分层下发，保证同一用户同一场景始终拿到同一版本，避免刷新一次换一个画面。

配置级灰度的价值是"不发版也能试错"：新材质方案先给 5% 的场景，看 P95 帧时间与纹理成功率，再逐步放量。回滚也只需要把配置指回上一版，不需要重新构建代码。

热更新的原子性：先建后换，失败保留上一版 ​

热更新最危险的不是"更新失败"，而是"更新到一半失败"，留下一个半新半旧、资源泄漏、状态错乱的场景。原子性可以用一段结构化的流程保证：

步骤动作失败处理
1拉取配置，记录 revision保持当前配置
2解析 + 迁移 + 校验丢弃，保留上一版
3预加载新增资产丢弃，保留上一版
4构建到临时 Group销毁半成品，保留上一版
5替换场景中的旧组替换后再销毁旧组
6首帧渲染后确认异常则回滚到 lastGood

代码骨架大致是这样：

js
async function hotUpdate(text, revision) {
  if (revision < currentRevision) return { ignored: true }
  const parsed = JSON.parse(text)
  const migrated = migrate(parsed)
  const errors = validate(migrated)
  if (errors.length) return { ok: false, errors }

  const next = await buildIsolated(migrated)
  const previous = activeGroup
  activeGroup = next.group
  scene.add(next.group)
  scene.remove(previous)
  disposeGroup(previous)
  currentRevision = revision
  lastGood = migrated
  return { ok: true }
}

两个容易漏掉的细节：revision 单调递增，防止晚到的旧响应覆盖新配置；销毁旧组放在挂载之后，保证任何时刻场景里都有一份可渲染的内容，不会出现"黑一帧"。

差量更新与全量重建：按规模选策略 ​

全量重建差量更新
实现复杂度低高，需要稳定 id 与映射表
适合规模几十到一两百节点数百到数千节点
状态影响交互状态（选中、相机）可能重置可保留大部分运行时状态
资源释放统一销毁，简单需精确引用计数，易漏
失败风险低中高，易出现"删了但没重建"

经验规则：节点少于 100 个，全量重建，代码简单、行为可预测；超过 500 个，再考虑差量。中间地带做混合：结构变化（增删对象、改父子）走全量，纯属性变化（颜色、强度、位置）走差量。无论哪种，都要保留"一键全量重建"作为兜底，出问题时能回到确定状态。

差量更新必须解决三个问题：新增节点的插入位置、删除节点的资源释放、父子关系变化时的重新挂载。最稳妥的做法是按 id 建两张表（旧、新），先处理删除，再处理新增，最后处理更新；父节点变化单独走"先 detach 再 attach"，不要试图在原地改层级。

配置体积与加载策略 ​

配置是会被下载、缓存、比对的，所以要像对待代码一样对待它的体积：

  • 按场景拆分，不要把所有场景塞进一个 JSON；首屏只加载当前场景；
  • 开启 gzip / brotli，文本配置压缩率通常很高；
  • 禁止内联 base64，贴图和模型走 assetId + CDN；
  • 子场景懒加载，进入某个区域或点击某个标签时再拉取；
  • 带版本哈希的 URL，让 CDN 长期缓存；开关类配置用 no-store，保证及时生效。

一份中等复杂度的场景配置通常在几十 KB 量级。如果发现单个配置超过 500KB，先别优化解析速度，先查是不是把资产或重复数据塞进去了。

审计日志：谁在什么时候改了什么 ​

配置一旦能改线上画面，就必须能追责与回溯。最小审计记录包含：

json
{
  "at": "2026-11-04T10:32:18Z",
  "actor": "editor@team",
  "action": "publish",
  "sceneId": "campus",
  "fromVersion": 3,
  "toVersion": 4,
  "configHash": "sha256:9f2c...",
  "summary": "objects +2, camera.fov 42 -> 48",
  "ticket": "OPS-118"
}

日志要追加写、不可改，并保存配置快照或内容哈希。这样"回滚到上一版"才有确切的目标，"这个改动是谁发的"才有答案。configHash 还能做去重：内容相同的配置不重复构建，直接复用当前场景。

术语解释 ​

术语含义为什么重要
迁移函数把旧版本配置升到下一版本的纯函数字段改名不破坏历史数据

宽松模式对"有确定答案"的缺失与越界做补全，并记录降低人工编辑的摩擦，但不掩盖类型错误

三个常见坑 ​

  1. 只在客户端校验。 保存接口收到什么就存什么，等运行时才发现错误，已经晚了。正确做法是服务端复用同一份 schema 做入库校验，客户端只做即时反馈。
  2. 宽松模式静默改数据。 自动补默认值不记录，用户看到的画面和配置文本对不上。必须把 FIX 项回显，并上报修正率。
  3. 热更新没有 revision。 两个请求乱序返回，旧配置覆盖新配置，用户刷新后才"自己好了"。每次下发带单调 revision，客户端只接受更新的那个。

② 引用与环检测：

js
function checkCycles(objects) {
  const byId = new Map(objects.map((o) => [o.id, o]))
  const errors = []
  objects.forEach((o, i) => {
    const seen = new Set([o.id])
    let cursor = o.parent
    while (cursor) {
      if (seen.has(cursor)) {
        errors.push({ path: '/objects/' + i + '/parent', expected: 'acyclic', actual: cursor })
        break
      }
      seen.add(cursor)
      cursor = byId.get(cursor)?.parent
    }
  })
  return errors
}

③ 原子提交：先挂后销：

js
function commit(nextGroup) {
  const previous = activeGroup
  activeGroup = nextGroup
  scene.add(nextGroup)
  if (previous) {
    scene.remove(previous)
    disposeGroup(previous)
  }
}

常见问题解答 ​

Q1：手写校验器与直接用 JSON Schema 库，怎么选？

看规则复杂度与团队约束。规则只有类型、必填、枚举、范围、引用这五类，手写更划算：没有额外依赖、错误信息可以带业务路径、能顺手补默认值、还能和表单生成共用一份 schema。规则出现条件依赖、递归结构、跨文件引用时，JSON Schema 库更合适，因为手写会变成重新实现规范。折中方案是"手写语义校验（引用、环、能力），结构校验用库"，两者都返回统一格式的错误列表。

Q2：宽松模式能不能直接上线？

可以，但要满足三个条件：默认值写进规范并在文档里公开；每一项自动修正都回显给作者并上报；修正率超过阈值时告警。宽松模式适合"人手编辑"的入口，因为人最容易漏字段；不适合"机器生成"的入口，因为机器生成的数据出错通常意味着上游有 bug，静默修复会掩盖它。最危险的做法是"宽松模式 + 不记录"，那等于让线上运行的配置与仓库里的文本不是同一份。

Q3：热更新会不会打断用户正在进行的交互？

取决于更新粒度。全量重建会重置选中状态、相机位置和材质动画，用户正在拖拽时更新会明显"跳一下"。三个缓解手段：更新前判断是否处于交互中，是则延后到空闲；差量更新只替换变化的节点，保留相机与选中；对相机、选中 id 等状态做"更新前快照、更新后恢复"。另外，热更新应该只在配置真正变化时触发，用 configHash 去重，避免同一份配置反复重建。

Q4：配置版本与代码版本怎么对齐？

让它们独立演进，但在构建时做一次兼容检查。代码声明"我支持的 schema 版本范围"，配置声明自己的 version；启动时若配置版本高于代码支持范围，拒绝加载并提示升级，而不是"试着跑一下"。配置迁移函数跟代码一起发版，旧配置在读取时迁移到当前版本。埋点里同时记录 appVersion 与 configVersion，排查时才能区分"是代码改坏了"还是"配置改坏了"。
