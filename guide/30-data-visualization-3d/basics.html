30.1 基础入门：3D 图表的语法与数据映射 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑨⑩ 再学习本篇。

核心概念讲解 ​

接桥：㉑ 的大屏很震撼，但柱子高度到底代表什么？ ​

在 ㉑ 大屏与数字孪生 里，我们搭起了一套"底图层 + 标注层 + 特效层 + UI 层"的架构，楼群起伏、扫描环扩散、告警闪烁，画面确实很有冲击力。但那套系统解决的是"把空间画出来"，不是"把数据讲清楚"。

退一步看那块大屏：如果一根柱子比另一根高两倍，它代表的数值是不是也正好两倍？如果柱子没有从 0 开始，如果相机俯角让近处的矮柱挡住了远处的高柱，如果颜色只是随手挑的渐变——那这根柱子就只是"看起来像数据"，读者无法从画面里得到可验证的结论。

这一篇补上缺失的那一环：图表语法（chart grammar）。它不关心园区有多像、特效有多炫，只关心一件事——数据里的每个维度，到底被映射到了屏幕上的哪条视觉通道，这条通道的刻度是否诚实。㉑ 负责把世界建出来，㉚ 负责让世界说人话。

3D 图表只有三种基本形态 ​

不管业务多复杂，3D 数据图表最终几乎都会落回三种形态。先把它们的"语法"记住，再谈风格：

形态主要编码最擅长回答最容易翻车的地方
3D 柱状高度 = 数值，x/z 平面 = 类别谁大谁小、排名、同比不从 0 起算、近处柱子遮挡远处、透视缩短
3D 散点三个位置轴各放一个维度，颜色/大小补维度相关关系、聚类、离群点三轴含义不清、点云互相遮挡、缺少参考网格
曲面高度图高度 = 网格上的数值，颜色辅助整体趋势、波峰波谷、空间分布单点读数困难、网格过密导致噪点、背面被遮

这三种形态不是"三种皮肤"，而是三种不同的句子结构：柱状在比较离散个体，散点在寻找变量之间的关系，曲面在描述一个连续场。选错形态，后面调再久也只是把一句话说错得更漂亮。

数据维度到视觉通道：先决定"用哪个通道说话" ​

一张图表能承载的维度有限。把数据字段翻译成视觉通道时，先问"这个通道的精度够不够"：

视觉通道常见编码读数精度适合表达
位置（x / y / z）类别轴、数值轴最高精确比较、排序
长度 / 高度柱高、线段长很高连续数值、排名
面积 / 体积气泡大小、立方体中等数量级差异、辅助维度
色相分类色板低离散类别、分组
明度 / 饱和度连续色板中等有序数值、强度
透明度淡化、聚焦低次要信息、上下文
形状 / 图标点、方块、模型低类别提醒、状态

一条实用的优先级：位置 > 长度 > 面积 > 颜色 > 形状。能用高度表达的，就别只靠颜色；能用一个轴表达的，就别硬塞进三个轴。3D 给了你第三个位置轴，但它也同时带来了透视、遮挡和相机依赖，不是免费的午餐。

量化刻度与 0 基线 ​

2D 柱状图有一条铁律：柱子必须从 0 开始。因为读者比较的是柱子的长度，而长度只有在同一把尺子、同一个起点上才有意义。

3D 柱状图同样如此，而且更危险。透视会让远处的柱子变短，相机俯角会让高柱的顶部"缩"进去；如果柱子的起点还悬浮在半空，读者根本无法用眼睛判断"高两倍"是不是"值两倍"。所以 3D 柱状至少要满足三件事：

  1. 统一的 0 平面：所有柱子从同一个 y=0 的基面长出来，基线可以画成一块半透明地板或网格；
  2. 统一的刻度：所有柱子共用同一个高度归一化比例，不能每根柱子各自缩放；
  3. 可读的参照：给出刻度线、数值标签或网格间距，让读者能把高度换算回数值。

如果数据里存在极端离群值，把所有柱子压成一条线，正确的做法不是"把基线抬高"，而是分面、对数刻度或截断并明确标注。任何改变起点的操作，都必须让读者看见。

遮挡、透视与"3D 饼图为什么是反模式" ​

3D 饼图是数据可视化里最经典的错误示范。原因不是"不好看"，而是它同时破坏了三种读数：

  • 角度被透视压缩：正对相机的扇区看起来更宽，背面的扇区被压扁，读者感知到的角度和真实占比不再成正比；
  • 面积被倾斜扭曲：饼图的本质是"角度 = 占比"，一旦把圆盘放倒，角度就变成了椭圆上的弧长，肉眼几乎无法比较；
  • 扇区被自身遮挡：靠近观察者的扇区会盖住后面的扇区，重要的那一块可能恰好被挡住。

同样的道理也适用于 3D 柱状：前排的高柱会挡住后排的矮柱；相机稍微一转，原来的"第一名"就被遮住了。解决办法不是"让柱子透明"，而是：

  • 按数值排序后再排布，把高的放后排或外侧；
  • 拉开间距，降低柱体密度；
  • 提供"正交视角"按钮，一键回到正面读数；
  • 关键结论始终在 HTML 图例或指标卡里重复一遍，不依赖 3D 画面单独承担。

术语解释：

  • 图表语法 chart grammar：把数据维度映射到视觉通道的一套规则，决定"什么数据用什么形状、位置、颜色表达"。
  • 视觉通道 visual channel：位置、长度、面积、颜色、透明度、形状等可被眼睛读出的视觉属性。
  • 0 基线 zero baseline：柱状/面积类图表的共同起点。起点不为 0 时，长度不再与数值成正比。
  • 数据墨水比 data-ink ratio：有效信息占画面元素的比例。装饰越多，比例越低，图表越难读。

色板：分类色、连续色、发散色 ​

颜色在数据可视化里不是装饰，是第四个可选通道。它有三类基本用法，和 ㉔ 色彩空间与线性工作流 里的链路直接相关：

色板类型编码什么典型例子使用要点
分类色无序的离散类别六个品类、八个区域色相彼此可辨，最多 8 色左右；超过就分组
连续色有序的数值大小销售额高低、温度明度或色相单向递进，避免"彩虹色"
发散色围绕中点向两侧偏离同比增长/下降、偏差中点用中性色，两端用对立色相，明确方向

三个常见错误：用彩虹渐变表达连续数值（读者无法判断哪端更大）；用分类色表达有序数据（颜色顺序没有含义）；只用颜色区分类别（色弱读者无法分辨）。最后一条的解法是颜色 + 形状/标签双编码，颜色只是加速识别的辅助。

还有一条和 ㉔ 直接衔接的工程细节：色板里的十六进制值默认按 sRGB 解释，new THREE.Color('#22d3ee') 会把它解码到线性工作空间再参与光照与混合。如果你从设计工具里拿到的是线性色值，要显式指定色彩空间，否则颜色会悄悄偏掉一档。3D 图表通常在 MeshBasicMaterial 或顶点色上直接显示颜色，链路比 PBR 场景短，但"颜色贴图要解码、输出要编码"的规则不变。

标注与图例：让 3D 图表"能被读" ​

3D 图表最容易被忽略的是"读数的最后一公里"：

  • 轴与单位：至少标出类别轴、数值轴和单位（万元、百分比、家）。没有单位的柱状图只是几何体；
  • 图例：颜色代表什么，必须有一份图例。图例用 HTML 覆盖层最清晰，不要用 3D 文字；
  • 数值标签：只在关键点位显示，不要每根柱子都挂一个牌子，否则画面会变成标签森林；
  • 交互提示：hover 或点击时再显示精确值，把"精确读数"交给交互，而不是塞进静态画面。

在 Three.js 里，标签通常有三种实现：CSS2DRenderer 把 DOM 贴到 3D 坐标上，文字最清晰但节点多了会拖慢帧率；Sprite 把文字画进纹理，脱离 DOM 但一张标签一次 draw call；实例化标牌把 N 个标签合成一次绘制，适合千级标注。选型原则和 ㉑ 大屏标注 一致：少量关键标签用 CSS2D，海量标签用实例化。

可读性优先：一张图只回答一个问题 ​

3D 数据可视化最容易犯的错，是把"能放进去的维度"当成"应该放进去的维度"。一张图同时表达销量、增长、门店数、客单价、同比、环比，最后每个维度都只表达了一半。

更稳的做法是：

  1. 先写一句问题："哪个区域的销售额最高？"；
  2. 只保留回答这个问题需要的维度；
  3. 选一个最擅长该问题的形态；
  4. 把其余维度放进筛选器、hover 详情或第二张图。

3D 的价值在于"空间关系"和"沉浸感"，不在于"塞进更多字段"。如果一张 2D 图表能回答得更好，就大胆用 2D；3D 应该是被问题选中的，而不是被风格选中的。

三个常见坑 ​

  1. 高度不归一化：每根柱子按自己的最大值缩放，视觉上"差不多高"，实际上差了三倍。所有柱子必须共用同一个比例尺。
  2. 用颜色当唯一编码：色板一换，结论就变了；色弱读者直接读不出。颜色要配标签、形状或位置。
  3. 相机一动，刻度就失真：透视让近大远小，没有基线和网格时，读者会把"近"当成"高"。至少提供正面视角和 0 基线。

对应演示 chart-mapping-lab.html：同一份"月份 × 品类"的销售数据，用柱状、散点、曲面三种形态呈现，右上角可切换色板与基线显示。下面拆出四个关键片段。

① 一份数据，三种视图共用：先把原始表格生成好，再做聚合，避免每种形态各自 mock 一套数据：

js
const MONTHS = ['1月', '2月', '3月', '4月', '5月', '6月',
  '7月', '8月', '9月', '10月', '11月', '12月']
const CATEGORIES = ['手机', '电脑', '家电', '服饰', '美妆', '食品']

const matrix = CATEGORIES.map(() => new Array(MONTHS.length).fill(0))
const rows = []
for (let m = 0; m < MONTHS.length; m++) {
  for (let c = 0; c < CATEGORIES.length; c++) {
    const sales = mockSales(m, c)          // 本地 mock，不依赖接口
    matrix[c][m] = sales                   // 曲面用这张矩阵
    rows.push({ month: m, category: c, sales }) // 散点用这批明细
  }
}

// 柱状用"按月聚合"的结果
const monthlyTotal = MONTHS.map((_, m) =>
  CATEGORIES.reduce((sum, __, c) => sum + matrix[c][m], 0))
const maxMonthly = Math.max(...monthlyTotal)

② 3D 柱状：高度从 0 起算，所有柱子共用比例尺。柱子用 InstancedMesh，位置固定在 x 轴，y 方向缩放即高度，position.y = h / 2 保证底面贴住 0 平面：

js
const bars = new THREE.InstancedMesh(boxGeometry, barMaterial, MONTHS.length)
const dummy = new THREE.Object3D()

const heights = monthlyTotal.map(v => 0.25 + (v / maxMonthly) * 8.2)

MONTHS.forEach((_, i) => {
  const h = heights[i]
  dummy.position.set((i - 5.5) * 1.32, h / 2, 0) // 底面在 y = 0
  dummy.scale.set(1, h, 1)                       // 高度编码数值
  dummy.updateMatrix()
  bars.setMatrixAt(i, dummy.matrix)
})
bars.instanceMatrix.needsUpdate = true

③ 色板映射：分类 / 连续 / 发散，一个函数收敛。注意发散色要先算均值与最大偏离，才能把"中点"放在 0.5：

js
function colorFor(value, max, index) {
  if (params.palette === 'categorical') {
    return new THREE.Color(PALETTES.categorical[index % 8])
  }
  if (params.palette === 'continuous') {
    return sampleRamp('continuous', value / max) // 0 → 1
  }
  const t = 0.5 + (value - meanMonthly) / (2 * maxDev)
  return sampleRamp('diverging', t)              // 0.5 = 均值
}

常见问题解答 ​

Q1：有了 2D 图表，为什么还要用 3D？什么情况下 3D 真的更好？

3D 真正有价值的场景只有三类：① 数据本身有三个空间维度，例如地理坐标加数值、楼层加能耗、设备位置加状态；② 需要空间关系，例如散点在三维空间中聚成簇，2D 投影会把不同深度的点压在一起；③ 展示与沉浸，例如大屏、展厅、汇报场景，视觉记忆点比精确读数更重要。

如果问题只是"谁最高、谁最低"，2D 柱状图永远更快、更准。判断标准不是"3D 好不好看"，而是"第三个维度是不是问题的一部分"。不是，就别加。

Q2：柱子之间差距很小，3D 里几乎看不出高低，怎么办？

先检查是不是被透视吃掉了差异：把相机切到接近正面的视角，或者打开 0 基线与网格再读。仍然看不清，说明这个差异不适合用高度表达，可以考虑：① 改排序，把要比较的对象放在一起；② 用差值/增长率而不是绝对值，让差异被放大；③ 用对数刻度并明确标注；④ 直接在 HTML 指标卡里给出精确数字，3D 只负责"大趋势"。

不要用"截断基线"或"让柱子从非 0 开始"来放大差异，那会让读者读出不存在的倍数关系。

Q3：分类色板到底能放几种颜色？超过 8 类怎么办？

经验上限是 6 到 8 种。超过之后，相邻色相开始难以区分，色弱读者更吃力。超过 8 类的常见解法：① 把长尾类别合并成"其他"，图例里注明；② 分组后用"组内色相 + 明度变化"表达；③ 换成位置轴（小多图、分面），让类别落在不同面板上；④ 交互筛选，一次只显示一组。

另外，分类色必须配合标签或形状，不能只靠颜色。颜色是加速识别的，不是唯一证据。

Q4：3D 饼图为什么被认为是反模式？我就想做个立体的不行吗？

"立体"可以做，但不要用它承担读数。3D 饼图同时破坏了角度、面积和可见性：倾斜让扇区角度被透视压缩，遮挡让部分扇区看不见，读者无法比较占比。把它当装饰、把真实占比放在旁边的小型 2D 条形图或图例里，问题就不大；把它当主图表，读者一定会读出错误结论。

同样的风险适用于所有"倾斜后靠面积/角度编码"的图表：3D 环形图、3D 漏斗图、3D 仪表盘。它们的问题是语法层面的，不是配色或光照能救的。

动手小练习 ​

  1. 打开 chart-mapping-lab.html，把形态切到柱状，记录三种色板下你对"最高月份"的判断速度；再切到曲面，思考为什么曲面更适合看"哪几个月整体走高"，却不适合报出"三月比二月高多少"。
  2. 给柱状图增加一个"从非 0 起算"的开关（例如基线抬到最小值的 80%），截两张图对比，说明读者会因此产生什么误读；然后恢复 0 基线并解释恢复的理由。
  3. 自己造一组 12 个类别的数据，分别用 8 色分类板和 12 色分类板渲染，找出第一组"看起来几乎一样"的两种颜色，并给出至少两种替代编码方案（标签、形状、分面）。
