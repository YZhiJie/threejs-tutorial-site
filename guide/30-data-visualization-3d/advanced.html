30.2 进阶应用：大规模数据、交互与标注 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑨⑩ 再学习本篇。

核心概念讲解 ​

接桥：⑰ 的 GPGPU 粒子把十万点画出来了，但没告诉你点到哪去了 ​

在 ⑰ 粒子与 GPU 计算 里，我们用 Points 和 GPGPU 把十万级粒子送上了屏幕：位置在顶点着色器里算，颜色随速度渐变，画面像一条发光的河流。那套技术的目标是"让十万个点动起来"。

数据可视化要的是另一件事：每个点是有身份的。它是哪个城市、哪一天的订单、哪台设备；它的数值是多少；用户指着它时，系统要能回答"这一点代表什么"。粒子可以无名，数据点不能。

这一篇就在 ⑰ 的渲染能力上加三样东西：拾取（知道鼠标指到了哪个点）、标注（把点的身份和数值显示出来）、聚合（点太多时，用统计单位替代个体）。渲染只是入口，交互和读数才是图表。

十万级散点：Points 与 InstancedMesh 的取舍 ​

先把两种主力方案摆在一起。它们共享同一批数据，但"每个点在 GPU 里长什么样"完全不同：

维度PointsInstancedMesh
每个点的几何一个屏幕/世界空间的点精灵一份完整几何（盒子、四面体、模型）
draw call1 次1 次（所有实例合并）
顶点开销极低，1 个顶点几何顶点数 × 实例数
光照与体积不支持，只有颜色与大小支持标准材质、阴影、法线
每点差异位置、颜色、大小位置、旋转、缩放、颜色
拾取Raycaster 的 Points.thresholdinstanceId，天然带索引
典型上限几十万到百万几万到十几万（看几何复杂度）

选择标准很直接：要"点云"还是要"物体"。如果每个数据点只需要颜色和位置，Points 是成本最低的方案；如果点需要体积、朝向、光照，或者要点上长出一根柱子，InstancedMesh 更合适。十万个四面体大约 40 万三角面，十万个球体就会直接把帧率打穿——几何复杂度是 InstancedMesh 的隐形上限。

术语解释：draw call 是 CPU 向 GPU 提交的一次绘制命令。实例化的意义是把 N 次提交压成 1 次；但"1 次 draw call"不等于"没有成本"，顶点着色器仍要处理 N 份几何。

数据怎么进 GPU：bufferAttribute 更新 vs 着色器取数 ​

十万个点的位置、颜色、数值，最终都要变成 GPU 能读的缓冲。两条路线：

  1. CPU 算好，写进 BufferAttribute：初始化时 setAttribute，数据变化时改数组并设 needsUpdate = true。简单、可控，适合静态数据或低频更新。
  2. GPU 自己取数：把数据放进纹理（DataTexture / FloatTexture），在顶点着色器里按索引采样；或者把"时间、筛选、缩放"作为 uniform，位置在着色器里现算。适合高频动画与 GPGPU。

关键纪律是不要每帧重建几何。new BufferGeometry()、new Float32Array()、重新 setAttribute 都会带来分配与上传开销；正确做法是初始化时分配最大容量，之后只改前 N 个元素或改 uniform：

js
const positions = new Float32Array(MAX * 3) // 一次分配，反复复用
geometry.setAttribute('position', new THREE.BufferAttribute(positions, 3))
geometry.setDrawRange(0, count)             // 数据量切换只改绘制范围

setDrawRange 对 Points 和 Line 这类非索引几何特别有效：缓冲仍是十万点，但只画前一万个。数据量切换因此变成一次常数级操作，而不是重建整条几何。

如果数据会频繁变化，给属性加上动态用法，提醒驱动不要按静态缓冲优化：

js
positionAttribute.setUsage(THREE.DynamicDrawUsage)
positionAttribute.needsUpdate = true

对于"筛选后只显示一部分点"的场景，还有第三种更省事的做法：不做物理删除，只改绘制范围或用一个 visible 标记属性，在着色器里把不可见的点缩到 0 或丢弃。这样筛选不会触发几何重建，切换也更快。

拾取：Raycaster 对 InstancedMesh 的 instanceId ​

InstancedMesh 的射线拾取结果里带一个 instanceId，它就是数据数组的下标——这是实例化最被低估的礼物：

js
const hit = raycaster.intersectObject(instancedMesh)[0]
if (hit) {
  const index = hit.instanceId      // 直接对应第几个数据点
  selected = index
}

Points 没有 instanceId，Raycaster 用 threshold 判断"射线离点多近算命中"。阈值太小点不中，太大又会误选邻近的点；而且十万点的射线检测要逐点算距离，频繁 hover 时开销不可忽视。

工程上常见的两条优化：

  • 节流：hover 不需要每帧都算，pointermove 后每 100 到 150 毫秒拾取一次即可；
  • 粗筛：先把鼠标射线投到地面平面，得到世界坐标，再在地面网格里查最近的候选点；或者按屏幕空间做一次线性扫描，只保留半径内的点。

本演示用的是"射线 → 地面 → 最近点"的方案：先把屏幕坐标反投影到 y=0 的地面，再在数据里找水平距离最近的点。它不追求像素级精确，但稳定、可解释，也不会因为点的前后遮挡而反复跳变。

hover 高亮与 tooltip：一个标签，而不是一万个 ​

hover 的反馈由两部分组成：高亮（让用户知道指到了谁）和 tooltip（告诉用户它是谁）。

高亮的实现：InstancedMesh 可以临时改 instanceColor，但十万实例每帧改色会触发整块颜色缓冲上传，代价不小。更轻的做法是放一个独立的标记物体——一个发光小球、一个圆环、一个十字线——移动到命中点，不碰实例缓冲。Points 同理，用标记物体比改顶点色便宜。

tooltip 的实现有两种主流路线：

方案做法优点代价
CSS2DRenderer每个标注一个 CSS2DObject，自动跟随 3D 坐标文字清晰、可写富文本DOM 节点多时拖慢帧率；永远盖在画面上
单个 DOM tooltip把 3D 点投影成屏幕坐标，手动定位一个 div只占一个节点，样式自由需要自己处理投影、边界与遮挡

十万点不可能挂十万个 CSS2DObject。正确姿势是只维护一个 tooltip：命中时把世界坐标 project(camera) 成 NDC，再换算成像素坐标，设置 transform 定位。这样 DOM 成本恒定，和点数无关。

筛选与动画过渡：位置插值而不是"瞬移" ​

筛选器改变数据子集时，如果点直接消失或瞬移，读者会失去空间记忆。更友好的做法是插值：每个点保留当前位置与目标位置，每帧用指数逼近推进：

js
const k = 1 - Math.exp(-dt * 9)   // 与帧率无关的平滑系数
current.x += (target.x - current.x) * k

要点有三：

  • 插值系数必须用 dt，否则 120Hz 屏幕上动画会快一倍；
  • 只对可见子集做插值，隐藏的点不必计算；
  • 动画收敛后停止写缓冲，不要永远每帧上传十万个位置。

如果数据量真的到了十万级、又需要频繁筛选，把插值搬进顶点着色器更划算：给每个点两份位置（起点/终点）和一个 uProgress，GPU 自己混合，CPU 每帧只更新一个 uniform。

LOD 与聚合：点太多时，用统计单位替代个体 ​

十万个点在远景下会变成一坨噪声：每个点只有一两个像素，颜色互相叠加，读者既看不出密度，也看不出结构。这时需要聚合（aggregation）：

  • 网格聚合：把地面划分成固定大小的格子，统计每格的点数、均值、最大值；用格柱的高度或颜色表达统计量。
  • 六边形分箱（hexbin）：用六边形代替正方形，减少方向偏差，视觉上更均匀，是地图类密度的常用方案。
  • 屏幕空间聚合：按像素或固定屏幕网格聚合，缩放时聚合粒度随相机变化，更接近"看到什么就统计什么"。

聚合不是"性能优化"的同义词，它同时是可读性优化：从"十万个个体"退到"几百个统计单元"，读者终于能看见分布的形状。代价是丢失个体信息，所以通常要配合"放大后回到原始点"的 LOD 策略：

视角表达目的
远景 / 全局聚合格柱或热力看整体分布与密度
中景抽样点 + 聚合兼顾结构与细节
近景原始点 + tooltip看个体与精确值

把三种方案放在同一张表里，取舍会更清楚：

方案拾取样式自由度性能成本适合的场景
PointsRaycaster 的 threshold，无实例索引只有点大小与颜色，无光照体积1 次 draw call，每点 1 个顶点十万级以上的纯点云、密度与分布
InstancedMesh命中的 instanceId 直接对应数据下标有体积、朝向、光照、法线1 次 draw call，顶点数 × 实例数万级、需要"物体感"或每点不同形状
聚合命中格柱，返回统计值而非个体格柱形状、高度、颜色几十到几百个实例，成本最低远景密度、全局趋势、数据量过大时

本演示把"聚合开关"做成手动切换，便于对比同一批数据在两种表达下的差异；真实项目里通常由相机距离或缩放级别自动触发。

时间维度的动画：时间轴 + 插值 ​

数据可视化里的"时间"有两种完全不同的东西：

  • 数据刷新时间：接口每隔几秒推来新数据，图表要更新——这是"版本变化"，不是动画；
  • 数据时间维度：例如十二个月的销售额，时间轴拖动时点在时间上移动——这是"沿时间轴插值"。

后者的标准做法是预计算关键帧：把每个时间点的位置、颜色、大小算好，存成多份缓冲；播放时按 t 在两帧之间插值。CPU 插值适合几万点，GPU 插值（把两帧存进纹理，着色器 mix）适合十万级以上。不要在拖动时间轴时重新请求接口或重建几何——那会让时间轴变成"卡顿轴"。

术语解释：

  • instanceId：InstancedMesh 射线命中结果里的实例序号，直接对应第几个数据。
  • 聚合 aggregation：把大量个体按空间单元合并成统计值，用更少的视觉元素表达分布。
  • LOD：按距离或缩放级别切换表达精度；在数据可视化里，它常常表现为"聚合 ↔ 原始点"的切换。
  • updateRange / 局部上传：只把缓冲中变化的那一段传给 GPU，避免整块重传；不同版本 API 名称略有差异，思路一致。

三个常见坑 ​

  1. 每帧对十万实例做射线拾取：hover 一移动就全量 intersectObject，CPU 直接打满。拾取要节流，能用索引就不要线性扫描。
  2. 筛选时重建几何：每次筛选 new BufferGeometry，GC 和上传一起拖慢。改用 setDrawRange、可见标记或着色器筛选。
  3. 给每个点挂 DOM 标签：一万个 CSS2DObject 会让浏览器布局崩溃。标签只留关键点，其余交给 hover。

代码示例 ​

对应演示 scatter-scale-lab.html：十万个本地 mock 点，可在 1 万 / 5 万 / 10 万之间切换，可在 Points 与 InstancedMesh 之间切换，可开启网格聚合，hover 时显示最近点的信息。下面按"数据 → 两种表达 → 聚合 → 拾取"拆解。

① 一次生成，两套表达共用同一批缓冲。位置数组只保留一份，颜色用 64 级 LUT 预计算，避免每个点都做颜色插值：

js
const MAX = 100000
const positions = new Float32Array(MAX * 3)

for (let i = 0; i < MAX; i++) {
  const k = i % CENTERS.length
  const angle = rand() * Math.PI * 2
  const radius = Math.pow(rand(), 0.55) * 15
  positions[i * 3] = CENTERS[k][0] + Math.cos(angle) * radius
  positions[i * 3 + 1] = 0.35 + Math.pow(rand(), 1.5) * 9
  positions[i * 3 + 2] = CENTERS[k][1] + Math.sin(angle) * radius
}

③ InstancedMesh：矩阵一次写好，切换只改 count。几何用低面数的四面体，十万实例也只有四十万三角面：

const inst = new THREE.InstancedMesh(
  new THREE.TetrahedronGeometry(0.32, 0),
  new THREE.MeshStandardMaterial({ roughness: 0.55, metalness: 0.15 }),
  MAX
)

const dummy = new THREE.Object3D()
for (let i = 0; i < MAX; i++) {
  dummy.position.set(
    positions[i * 3],
    positions[i * 3 + 1],
    positions[i * 3 + 2]
  )
  dummy.rotation.set(rand() * Math.PI, rand() * Math.PI, 0)
  dummy.updateMatrix()
  inst.setMatrixAt(i, dummy.matrix)
}
inst.instanceMatrix.needsUpdate = true

④ 网格聚合：Map 分箱 → 一个格柱 InstancedMesh。格子中心固定，高度用 log10(n) 压缩，避免大格子把画面顶穿：

js
function rebuildBins(count) {
  const map = new Map()
  for (let i = 0; i < count; i++) {
    const bx = Math.floor(positions[i * 3] / BIN_SIZE)
    const bz = Math.floor(positions[i * 3 + 2] / BIN_SIZE)
    const key = (bx + 300) * 1000 + (bz + 300)   // 数字键比字符串快
    const bin = map.get(key) || { bx, bz, n: 0 }
    bin.n++
    map.set(key, bin)
  }

  let i = 0
  map.forEach((bin) => {
    const h = 0.35 + Math.log10(bin.n + 1) * 2.5
    dummy.position.set((bin.bx + 0.5) * BIN_SIZE, h / 2, (bin.bz + 0.5) * BIN_SIZE)
    dummy.scale.set(1, h, 1)
    dummy.updateMatrix()
    binMesh.setMatrixAt(i++, dummy.matrix)
  })
  binMesh.count = i
  binMesh.instanceMatrix.needsUpdate = true
}

⑤ 拾取：射线打到地面，再找最近点，并按 120ms 节流。这样 hover 不会每帧扫描十万点：

js
const groundPlane = new THREE.Plane(new THREE.Vector3(0, 1, 0), 0)
const hitWorld = new THREE.Vector3()

function pickNearest() {
  raycaster.setFromCamera(pointer, camera)
  if (!raycaster.ray.intersectPlane(groundPlane, hitWorld)) return

  let best = -1
  let bestDist = Infinity
  for (let i = 0; i < count; i++) {
    const dx = positions[i * 3] - hitWorld.x
    const dz = positions[i * 3 + 2] - hitWorld.z
    const d = dx * dx + dz * dz
    if (d < bestDist) {
      bestDist = d
      best = i
    }
  }
  // 命中后：marker 移到点位置，单个 tooltip 用 project 后的屏幕坐标定位
}

常见问题解答 ​

Q1：十万个点用 InstancedMesh 只有 30 帧，换成 Points 就流畅了，是不是 InstancedMesh 不行？

不是"不行"，是"几何太贵"。InstancedMesh 的成本约等于"单个几何的顶点数 × 实例数"：十万个球体可能是几千万三角面，十万个四面体只有四十万。先看几何面数，再决定要不要用实例化。

如果必须保留体积感，可以：① 用面数极低的几何（四面体、八面体、广告牌）；② 远处切回 Points，近处才用实例；③ 用 LOD 分档；④ 减少实例数量，靠聚合表达密度。先量后调，别凭感觉换方案。

Q2：hover 时用 Raycaster 拾取十万点很卡，有没有更快的办法？

三条思路按成本排序：① 节流，hover 每 100 到 150 毫秒算一次；② 粗筛，先把射线投到地面或用一个稀疏网格索引缩小候选范围；③ GPU 拾取，把点渲染到一张离屏纹理，用像素颜色编码索引，鼠标位置读一个像素即可。

本演示用的是"射线 → 地面 → 最近点"的粗筛，加上 120ms 节流。它不依赖额外渲染目标，代码量小，适合十万级；百万级再考虑 GPU 拾取。

Q3：聚合之后，鼠标 hover 还要显示原始点吗？

聚合视图下，hover 的语义应该跟着变：读者看到的是"格柱"，就应该返回"这一格有多少点、均值多少、范围多少"，而不是硬塞一个原始点。否则视觉单位和数据单位对不上，读者会以为格柱就是某一个点。

如果确实需要原始点，提供"放大后自动切回原始点"的 LOD，并在 UI 上标明当前处于哪种表达。聚合和原始点不是同一张图上的两层，而是两个精度档位。

Q4：时间轴动画用 CPU 插值还是着色器插值？

看数据量和更新频率。几万点、关键帧不多时，CPU 插值简单可控，调试也方便；十万点以上、需要 60fps 连续播放时，把两份关键帧位置存进纹理，顶点着色器里 mix 更划算，CPU 每帧只更新一个进度 uniform。

无论哪种，都建议预计算关键帧，不要在播放过程中请求数据或重建几何。时间轴卡顿的根源通常不是插值算法，而是每帧都在做分配、上传或网络请求。

动手小练习 ​

  1. 把 scatter-scale-lab.html 的聚合格子从正方形改成六边形排布（提示：用两个错位的网格近似，或直接画六棱柱），对比同一批数据下两种聚合的视觉均匀度。
  2. 给 InstancedMesh 模式加一个"按簇高亮"的筛选：选中某个簇后，其余实例颜色降到 20% 亮度，观察颜色缓冲更新的开销，并尝试改成着色器方案。
  3. 实现一个最简单的 GPU 拾取：把十万点的索引编码成颜色渲染到离屏纹理，鼠标移动时读取对应像素，比较它与"射线 → 地面 → 最近点"方案的反应速度与准确度。
