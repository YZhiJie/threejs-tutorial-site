30.3 实战案例：可交互 3D 数据看板 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑨⑩ 再学习本篇。

核心概念讲解 ​

接桥：㉑ 的园区大屏缺一块"能下钻的图" ​

在 ㉑ 大屏 · 园区数字孪生 里，告警卡片可以点、相机可以飞、扫描环一直在转，但如果你把镜头拉远看，会发现那块大屏其实只有"空间"和"状态"，没有"数据结论"：楼栋高低是随机的，告警数量是 mock 的，没有人能从那块屏上回答"本月哪个区域卖得最好、为什么"。

这一篇补的正是这块拼图：一块能下钻的图。它不再回答"楼在哪"，而是回答"哪个区域、哪项指标、多少、排第几、明细是什么"。3D 在这里退居为图表的载体，数据、交互、标注、降级才是主角。

看板的三块拼图 ​

一个可交互 3D 数据看板，稳定结构通常只有三块：

区域职责推荐技术注意点
图表区柱状比较大小、散点观察关系Three.js InstancedMesh + Points编码诚实、0 基线、标签克制
指标卡 / 侧栏汇总、明细、单位、更新时间纯 HTML + CSS，盖在 canvas 上pointer-events 分层，别挡住拖拽
筛选器切换指标、区域、时间范围HTML 按钮 / 下拉 / lil-gui一次只改一个维度，更新要平滑

最大的一条原则和 ㉑ 相同：3D 只负责"图形"，文字与数字交给 HTML。指标卡的排版、单位、对齐、滚动，HTML 一天能做完的事，用 3D 文字做要一周，还更模糊。

指标卡的信息层级：先结论，后细节 ​

指标卡不是把数据全部列出来，而是按"结论 → 对比 → 明细"三层组织：第一层放当前最重要的大数字，配单位与变化；第二层放对比信息，例如最高区域、最低区域、与上期的差异；第三层放选中区域的明细，包括订单、门店、客单价与排名。

视觉上，第一层字号最大、颜色最亮；明细层用小字号、低对比，避免抢走结论。3D 图表负责"形状与分布"，指标卡负责"数字与判断"，两者不要重复表达同一件事：如果柱状图已经说清排名，侧栏就不必再画一遍条形图，只需给出精确值。

指标卡还要显示数据更新时间，并标明数据是否过期；接口失败时保留上一次成功值，比直接清空更安全，也更符合"看板是长期挂在大屏上"的真实使用方式。

一份数据、两处呈现：选中状态是唯一真相 ​

柱状图和散点图各自有坐标，但它们必须共享同一个选中状态：

数据层（regions + 当前指标）
   │  selectedIndex / metric
   ├─→ 柱状：实例颜色高亮 + 标签加粗
   ├─→ 散点：命中点变金色 + 定位球
   └─→ 侧栏：明细卡切到该区域

如果每个视图各自维护一份 selected，就会出现"柱状高亮了华东，散点却高亮华南"的经典 bug。正确做法是把 selected 放在数据层，所有视图只读它、只通过 selectRegion(i) 改它。这样以后加第三张图、加一个表格，联动逻辑都不用重写。

同样地，指标切换也只改数据层里的 params.metric，柱高、颜色、标签、侧栏 KPI 全部由它派生。不要在每个组件里各写一份"当前指标"。

点击柱子下钻：从 instanceId 到明细 ​

点击下钻的链路很短，但有两个容易忽略的细节：

  1. 区分"点击"与"拖拽"。OrbitControls 也会监听 pointerdown/up，用户拖拽旋转后松手，浏览器仍可能触发一次 click。稳妥做法是记录按下与抬起的屏幕距离，超过 5 到 8 像素就判定为拖拽，不执行选中。
  2. instanceId 就是数据下标。Raycaster.intersectObject(bars) 命中的结果里，instanceId 直接对应第几根柱子；拿到它之后，用同一个下标去查数据、更新侧栏、改散点颜色即可，不需要再按位置反查。
js
renderer.domElement.addEventListener('pointerdown', (e) => {
  downX = e.clientX
  downY = e.clientY
})

renderer.domElement.addEventListener('pointerup', (e) => {
  if (Math.hypot(e.clientX - downX, e.clientY - downY) > 6) return
  pointer.x = (e.clientX / innerWidth) * 2 - 1
  pointer.y = -(e.clientY / innerHeight) * 2 + 1
  raycaster.setFromCamera(pointer, camera)
  const hit = raycaster.intersectObject(bars)[0]
  selectRegion(hit ? hit.instanceId : -1)
})

selectRegion(-1) 表示"点空白处取消选中"。不要忽略这个分支，否则用户点空白后高亮还留在旧柱子上，会以为数据没刷新。

相机控制器冲突：谁听谁的 ​

看板里最容易打架的是相机控制：

  • 图表区要能拖拽旋转、滚轮缩放；
  • 侧栏要能滚动、能点按钮；
  • 点击柱子要能下钻，但旋转拖拽不能误触发。

解决办法不是"禁用某一方"，而是分层：

  1. HTML 侧栏是独立元素，天然拦截自己的事件，pointer-events: auto；图表区 canvas 继续接收 OrbitControls。
  2. 点击判定用"按下到抬起的距离阈值"，把拖拽和点击分开。
  3. 如果点击后需要相机飞向某个区域，先 controls.enabled = false，飞行结束再打开；用户中途拖拽则立即打断飞行并交还控制权——这条沿用 ㉑ 的 flyTo 思路。
  4. 如果侧栏里也放了 lil-gui，注意它的根节点默认在右上角，会与侧栏重叠；通过 CSS 把 GUI 移到左下角，或干脆把筛选器全部收进侧栏，减少两个浮层的交互冲突。

更隐蔽的一条：CSS2DRenderer 的 DOM 层默认 pointer-events: none，它不会挡住拖拽，但也意味着标签本身不可点击。如果标签需要点击，给具体标签开 pointer-events: auto，并处理它和 canvas 的事件优先级。

筛选器驱动数据更新：更新不是重建 ​

筛选器一改，最差的实现是"清空场景、重新创建所有物体"。看板里的数据量通常不大（几十到几百个区域），但每次重建都会带来三笔开销：几何分配、GPU 上传、标签节点重建。

更好的做法是只改数值，不改结构：

  • 柱子数量固定，实例矩阵只改 scale.y 与 position.y；
  • 颜色只改 instanceColor，一次 needsUpdate；
  • 标签文本只改 textContent，位置每帧跟着柱高走；
  • 散点只改 position 属性的 y 分量，needsUpdate = true。

高度切换加一段指数插值，读起来会"长上去"而不是"跳一下"：

js
const k = 1 - Math.exp(-dt * 9)
current[i] += (target[i] - current[i]) * k

注意：插值只在数值变化时进行，稳定后要停止上传矩阵，否则每帧都在传一份没变化的数据。

数据接口的 mock 与刷新节流 ​

真实看板的数据来自接口或 WebSocket，本地开发用 mock 即可。关键是把数据入口收敛成一个函数，和 ㉑ 的 pushAlarm 一样：

js
function refreshData() {
  if (refreshing) return
  if (performance.now() - lastRefreshAt < 900) {
    note.textContent = '刷新过快 · 已触发 900ms 节流'
    return
  }
  // 请求 mock 接口 -> mutateData() -> computeTargets() -> paintAll()
}

三个工程要点：

  1. 节流而不是防抖：用户连点刷新按钮时，保留第一次请求，后续在窗口内直接忽略，并给出可见提示。
  2. 丢弃过期响应：如果接口返回慢，用户又切了指标，旧响应回来时不能覆盖新状态。给每次请求一个序号，只接受最新序号的结果。
  3. 区分"刷新"与"时间动画"：刷新是数据版本变化，时间动画是同一份数据沿时间轴插值。两者混在一起，会出现"拖时间轴也在发请求"的浪费。

如果确实需要每秒刷新，尽量做到：只更新变化的部分、不要重建几何、不要每帧重新计算颜色 LUT、把 DOM 文本更新合并到一次 requestAnimationFrame。每秒一次 × 一千个标签，足以让浏览器主线程喘不过气。

可访问性与降级 ​

3D 看板不是所有人都能看见：

  • 无 WebGL：检测 canvas.getContext('webgl2') || canvas.getContext('webgl')，失败时退回 2D 表格。信息不丢失，只是失去空间编码。
  • 颜色不是唯一编码：柱状配数值标签，散点配 tooltip，选中状态同时用颜色和标签加粗表达。
  • 键盘与读屏：侧栏是原生 HTML 按钮和文本，天然可聚焦、可朗读；3D canvas 本身对读屏不友好，关键结论必须在 DOM 里有一份。
  • 减少动态效果：监听 prefers-reduced-motion，关闭自动旋转和高度动画，直接呈现终值。
  • 对比度与字号：深色看板上，明细文字至少 12px；避免低对比的灰字落在深蓝背景上，关键数字用高对比色突出。

术语解释：

  • 下钻 drill-down：从汇总层进入明细层，例如从"区域销售额"点进"区域订单明细"。
  • 联动 brushing & linking：一个视图的选中状态驱动其他视图高亮，所有视图共享同一份选择。
  • 节流 throttle：在固定时间窗口内只允许一次操作生效，常用于刷新与 hover 拾取。
  • 降级 graceful degradation：能力缺失时退回可用但较弱的实现，而不是直接报错或白屏。

三个常见坑 ​

  1. 侧栏容器整体拦截事件：面板设了 pointer-events: auto，结果盖住的区域拖不动相机。只给需要交互的子元素开 auto，容器保持 none。
  2. 刷新时重建标签：每次刷新都 innerHTML = '' 再重建，滚动位置和焦点丢失，节点数量还会抖动。改为更新文本。
  3. 选中状态在刷新后丢失：数据更新后 selected 还指向旧下标，或直接重置为 -1。刷新后按区域 id 重新定位选中项，比按下标更稳。

② 柱状与散点：共用同一份高度与同一套颜色。柱高与散点 y 都来自 targetHeights，选中颜色统一走 paintAll：

js
function computeTargets() {
  const max = metricMax()
  metricValues().forEach((v, i) => {
    targetHeights[i] = 0.35 + (v / max) * 8.2   // 统一比例尺，0 起算
  })
}

function paintAll() {
  const max = metricMax()
  metricValues().forEach((v, i) => {
    bars.setColorAt(i, i === selected
      ? new THREE.Color(0xfbbf24)
      : rampColor(v / max))
    labels[i].div.classList.toggle('active', i === selected)
  })
  if (bars.instanceColor) bars.instanceColor.needsUpdate = true
}

③ 点击下钻：距离阈值 + instanceId。拖拽超过 6px 不算点击，命中后统一走 selectRegion：

⑤ 刷新节流与过期响应。演示里用 420ms 的 mock 延迟模拟网络，900ms 内重复点击只提示、不发请求：

js
function refreshData() {
  if (refreshing) return
  if (performance.now() - lastRefreshAt < 900) {
    noteEl.textContent = '刷新过快 · 已触发 900ms 节流'
    return
  }
  lastRefreshAt = performance.now()
  refreshing = true
  setTimeout(() => {
    mutateData()
    computeTargets()
    paintAll()
    updatePanel()
    stampTime()
    refreshing = false
  }, 420)
}

常见问题解答 ​

Q1：图表文字被 3D 物体遮挡怎么办？

分两种情况。柱子标签被别的柱子挡住：优先用 CSS2DRenderer，它永远盖在画面上，但会失去深度关系；如果必须保留遮挡，就在每帧做一次射线检测，命中的标签降低透明度或隐藏——代价是每个标签一次射线，数量要控制在几十个以内。

tooltip 被物体挡住：tooltip 是 DOM，天然在 canvas 之上，不会被 3D 遮挡；真正的问题是它可能遮住它标注的点，解决方法是偏移（向上 140%）、翻转（靠近屏幕边缘时改变方向）、或加一条指向线。不要试图用 3D 文字做 tooltip，清晰度和排版都不划算。

Q2：数据每秒刷新导致卡顿，怎么排查和优化？

先定位卡在哪：用 Performance 面板看主线程，如果 setMatrixAt + needsUpdate 占大头，是每帧全量上传；如果大量时间在 DOM，是标签或侧栏重建；如果 GPU 时间高，是 draw call 或三角面。

优化顺序：① 只更新变化的数据，不要每秒重建几何与标签；② 给刷新加节流，合并短时间内的多次推送；③ 把颜色 LUT、字符串格式化等计算移出每帧循环；④ 文本更新合并到一次 requestAnimationFrame；⑤ 数据量真的很大时，把插值与筛选搬进着色器。每秒刷新本身不是问题，"每秒做一次全量重建"才是。

Q3：看板要同时支持鼠标、触摸和键盘，交互怎么设计？

鼠标与触摸共用 Pointer Events，天然统一；关键是触摸下的点击判定阈值要更宽（手指抖动比鼠标大），拖拽旋转与点击下钻仍用距离阈值区分。键盘方面，把指标切换、刷新、区域选择做成原生 button，用 Tab 聚焦、Enter 触发；3D 画布本身不可聚焦，所以关键操作必须在侧栏有一份等价入口。

另外给 canvas 加一个 aria-label 说明"这是可视化图表，详细数据见右侧面板"，让读屏用户知道去哪里找信息。

Q4：为什么点击空白处要取消选中，而不是保持上一次选择？

保持选择会让"当前高亮"和"当前查看"两个状态混在一起：用户点了空白，以为已经取消，侧栏却还显示上一个区域。取消选中是最小惊讶原则——画面上的高亮、散点的定位球、侧栏的明细应该同时消失或同时出现。

如果业务上确实需要"固定选中"，把它做成显式操作：点击空白不取消，侧栏加一个"取消选择"按钮，或把选中状态显示成可关闭的标签。状态要可见，才不会被误解。
