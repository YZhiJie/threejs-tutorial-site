29.3 实战案例：程序化城市生成器 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑯ 与 29.1、29.2 再学习本篇。

核心概念讲解 ​

接桥：⑯ 的万级实例城市是"复制粘贴"，这次让城市自己长出来 ​

在 ⑯ 大场景 · 万级实例城市 里，我们用 InstancedMesh 把一万栋楼塞进了一次 draw call，又用街区分块让视锥剔除真正生效。那座城市跑得很稳，但它的每一栋楼都是同一种盒子按规则循环摆放：位置按行列算，高度随机，颜色随机，没有任何"城市结构"。

它回答的是"怎么画得快"，没有回答"怎么长得像一座城"。真正的城市有地块划分、退台、街道、路灯、绿化、地标，还有一套"同一块地必须长出同一座城"的可复现要求。

这一篇把 29.1 的几何生成与 29.2 的模块拼装组装成一条完整流水线：参数进，城市出。重点有三件事——流水线怎么拆、随机怎么可复现、预算怎么守住。

流水线：从参数到一座城 ​

程序化城市不是一个巨大的函数，而是七个可单独替换的阶段：

阶段输入输出关键决策
① 地块划分城市尺寸、地块尺寸、密度地块列表（中心点、空/占）网格 + 抖动，保留街区感
② 建筑体块地块、风格、最高层数楼块列表（位置、尺寸、颜色）覆盖率高、退台、屋顶类型
③ 街道与路灯地块网格合并路带 + 实例化路灯路带合并成 1 个 Mesh
④ 绿化与地标空地块、中心点实例化树冠/树干 + 独立地标空地块才有绿化
⑤ 合并与实例化全部列表少量 draw call 的场景按"动不动"分层
⑥ 参数面板GUI / JSON参数对象每个参数都能重建
⑦ 导出与再生成参数 + seed配置 JSON / 同一座城确定性

这条流水线的每一段都只依赖上一段的数据，不直接操作 Three.js 对象。这样做的好处是：想换一种屋顶，只改②；想换绿化规则，只改④；想导出配置，参数对象本来就在。

地块划分：网格是骨架，抖动是皮肤 ​

城市的第一层结构是地块。最省事的做法是把城市切成 n × n 的网格，每个格子的中心放一栋楼：

js
const n = Math.max(6, Math.floor(118 / lotSize))
const half = n * lotSize / 2

for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) {
    const cx = (i - (n - 1) / 2) * lotSize + (rand() - 0.5) * lotSize * 0.22
    const cz = (j - (n - 1) / 2) * lotSize + (rand() - 0.5) * lotSize * 0.22
  }
}

纯网格看起来像 Excel 表格：楼距完全一致，街道笔直得不真实。加一点格内抖动（上面 0.22 那一项）就能破掉这种机械感。抖动幅度要小于半格，否则相邻地块的楼会互相穿插。城市里适度的"不整齐"恰恰是真实感的来源。

地块的第二个决策是占用概率。density 控制每个格子是否放楼，剩下的格子留空，后面用来种树。这一步同时决定了建筑数量与绿化数量，是最直观的"密度"旋钮。

确定性：同一 seed 必须同一座城 ​

程序化生成里最容易翻车的一条要求：给同一个 seed 和同一组参数，必须得到逐字节相同的城市。否则美术调好的"第 42 号城"下次打开就没了，验收、截图、bug 复现全部失效。

实现确定性只需要遵守三条：

  1. 不用 Math.random()，用带种子的 PRNG。
  2. 随机调用顺序固定。同一串随机数，先取高度再取宽度，和反过来取，得到的是两座城。
  3. 不依赖时间、屏幕尺寸、设备像素比等环境量。
js
function mulberry32(seed) {
  let a = seed >>> 0
  return function () {
    a = (a + 0x6D2B79F5) >>> 0
    let t = Math.imul(a ^ (a >>> 15), 1 | a)
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296
  }
}

const rand = mulberry32(seed)
const height = 8 + Math.floor(rand() * 20)   // ① 先取高度
const width = 6 + rand() * 2                 // ② 再取宽度

一个隐蔽的陷阱：循环顺序变了，城市也会变。把 for i 和 for j 交换，随机序列的消费顺序就变了，所有楼都换位置。这不是 bug，但必须写进注释，否则重构时"顺手优化"一下循环，整座城就面目全非。

配置本身也要带版本号。生成器升级、规则微调后，旧 seed 必然长出不同的城；在 JSON 里写明 version: "29.3"，至少能回答"这是哪一版生成器的城"。

建筑体块：高度、覆盖率、退台、屋顶 ​

体块阶段的核心是"用最少的参数造出可辨识的风格"：

参数现代低层高密度
基准层数3 + 随机1 + 随机（≤4）7 + 随机
覆盖率0.58 ~ 0.800.70 ~ 0.900.80 ~ 0.95
退台高楼有概率退台无无
屋顶平顶约 6 成坡顶平顶

退台（setback） 是高层建筑最便宜的风格信号：把一栋楼拆成"下段全宽 + 上段缩窄"，视觉上立刻从"盒子"变成"塔"。实现只是往楼块列表里多推一个盒子：

js
const lowerH = totalH * 0.6
const upperH = totalH - lowerH
blocks.push({ x: cx, z: cz, y: lowerH / 2, w, h: lowerH, d, color })
blocks.push({
  x: cx, z: cz, y: lowerH + upperH / 2,
  w: w * 0.66, h: upperH, d: d * 0.66, color
})

屋顶同理：低层用四棱锥（ConeGeometry 四分段旋转 45°）做成坡顶，高层保持平顶。不同屋顶类型要分到不同 InstancedMesh，因为几何体不同；同一类型内部再统一批量。

街道与路灯：合并成"一条路" ​

街道是典型的"永远不动、数量不小"的静态几何，正确做法是合并：

js
const roadParts = []
for (let i = 0; i <= n; i++) {
  const p = (i - n / 2) * lotSize
  const gx = boxGeo.clone().scale(1.9, 0.08, n * lotSize + lotSize * 0.6)
  gx.translate(p, 0.04, 0)
  roadParts.push(gx)
  const gz = boxGeo.clone().scale(n * lotSize + lotSize * 0.6, 0.08, 1.9)
  gz.translate(0, 0.04, p)
  roadParts.push(gz)
}
const roads = new THREE.Mesh(mergeGeometries(roadParts, false), roadMat)

一个城市几十条路带，合并后只占 1 次 draw call。注意合并后不能再单独移动某条路——这正好符合"街道永远不动"的前提。

路灯则相反：数量多、彼此相同、但位置要单独算，适合两组实例化（灯杆 + 灯头，因为材质不同）。灯头用自发光材质，夜里能形成一串光点，成本只有 1 次 draw call。

窗格：最容易被忽略的预算炸弹 ​

窗格是城市"像不像"的关键细节，也是最容易把预算吃光的模块。一个楼块按"8 层 × 3 列 × 前后两面"就是 48 个窗实例，200 栋楼就是近万个实例。它们可以是 1 次 draw call，但三角形总量会明显上升，生成时的矩阵计算也会变慢。

三条控制手段：

  1. 按楼块尺寸算行列，而不是全城统一——矮楼少开窗，高楼多开窗。
  2. 设总实例预算（演示里是 14000），超出就停止添加。宁可远景少细节，也不要让主线程卡住。
  3. 窗格只铺两个立面，不做四面；斜视角下差别很小，成本却减半。

合并与实例化：按"可动性"分层，而不是按数量 ​

整座城市的输出策略可以固化成一张表：

层实现理由
楼块、屋顶、窗格、灯杆、灯头、树冠、树干各一个 InstancedMesh同构、静态、数量大
街道合并成 1 个 Mesh永远不动，且形状各异
地标2~5 个独立 Mesh唯一、可能需要交互或换材质
地面1 个独立 Mesh全局一层，不需要合并

最终 draw call 大致是"实例组数量 + 合并组数量 + 地标"，通常十几到二十几次；而建筑数可以是几百甚至上千。这就是程序化城市能跑起来的原因：不是几何变少了，而是提交次数被压住了。

统计与预算：让数字说话 ​

演示的 HUD 同时显示四组数字：

读数来源用途
建筑数生成器自计判断密度与规模是否合理
体块数楼块列表长度退台会让它大于建筑数
三角数renderer.info.render.trianglesGPU 压力
draw callsrenderer.info.render.callsCPU 提交压力

注意 renderer.info 是每帧重置的，要在 render() 之后读，否则拿到的是上一帧或零。做性能门禁时，建议把"建筑数 / draw calls / 三角数"三者一起记录，单看任何一个都会误判。

导出 JSON：把城市变成一份可复现的输入 ​

程序化城市的最终交付物往往不是模型，而是配置：

json
{
  "version": "29.3",
  "seed": 2029,
  "density": 0.62,
  "maxFloors": 22,
  "lotSize": 9,
  "style": "现代",
  "stats": { "buildings": 128, "blocks": 171 }
}

stats 只是给人看的快照，重新生成时会被忽略；真正决定城市的只有前六个字段。回读配置时必须做范围校验与钳制：密度限制在 0.15~0.95、层数限制在 2~40、地块尺寸限制在 6~16，避免一份手改的 JSON 把城市生成到浏览器卡死。

配置还能做差量对比：两份 JSON 只有 seed 不同，城市应该完全不同；只有 density 不同，街道网格与地标位置应当保持一致（因为地块划分的随机序列前半段没变）。如果发现"只改了密度，地标却跑了"，说明随机调用顺序被某个分支打乱了——这是确定性调试里最有效的一条线索。

常见问题解答 ​

Q1：生成 5 万栋楼直接卡死，页面几十秒没响应，怎么办？

先拆问题：卡的是生成还是渲染。若是生成卡，说明主线程在跑几十万次矩阵与随机计算，同步阻塞了渲染与交互；若是渲染卡，通常是窗格与三角数爆炸。处置顺序：① 给建筑数与窗格数设硬预算（例如建筑 ≤ 2000、窗格 ≤ 20000）；② 窗格只铺两个立面，远景楼干脆不铺；③ 超过预算的楼群用"低模盒子"代替整套模块；④ 把生成放进 Web Worker，只把矩阵数组回传主线程；⑤ 分块生成（按街区流式追加），不要一口气建完。五万栋楼在浏览器里并非不可能，但必须"先预算、再实例化、再分块"，而不是把循环开大。

Q2：同一个 seed，刷新页面后城市变了？

按发生概率排查：① 某个分支里用了 Math.random()（比如屋顶随机、颜色随机漏改）；② 随机调用顺序被条件分支改变——某个 if 里少取了一次随机数，后面整条序列就错位；③ 生成依赖了 innerWidth、devicePixelRatio 或时间戳；④ 用了 Set / Map 遍历顺序参与生成（不同引擎的插入顺序实现可能有差异）。最稳的验证方式是：把生成结果的关键数值（建筑数、首个楼的坐标、地标高度）算成哈希，两个环境比对哈希。

Q3：城市建筑都摆好了，但街道和楼互相穿插？

地块抖动幅度太大或楼块覆盖率超过 1 就会穿插。检查两件事：抖动是否小于半格（演示用 0.22 倍地块尺寸），楼块宽度是否小于地块尺寸。街道本身是沿地块边界铺的，楼块中心落在格内、宽度不超过格宽，就不会压到路带。若追求"楼贴路边"的效果，应该缩小楼块并偏向一侧，而不是把楼放大到压住道路。

Q4：改了密度，为什么地标位置也跟着变了？

因为地标位置是从同一条随机流里取的。如果地块循环里"占用判定"和"楼体参数"共用一条流，密度一变，每个格子的随机消耗数量就变，后续所有随机值都会移位。想保持地标稳定，有两种做法：① 地标位置用独立种子（mulberry32(seed + 991)）单独算；② 先固定地标格，再用另一条流为每个地块生成参数。原则是：不同语义的随机，尽量分不同流。

术语解释：

  • 确定性生成 deterministic generation：相同输入必得相同输出，与时间、设备、调用次数无关。
  • 伪随机数生成器 PRNG：由种子决定序列的算法，mulberry32 是常用的 32 位实现。
  • 退台 setback：高层建筑上段缩进，形成阶梯轮廓。
  • 实例预算 instance budget：对窗格、绿化等实例数量的硬上限，防止生成与渲染失控。
  • 流式生成 streaming generation：分块、分批构建，避免一次性阻塞主线程。
  • 配置驱动 config-driven：以 JSON 参数而非硬编码决定生成结果，便于复现与分享。

动手小练习 ​

  1. 固定 seed 与其它参数，只把 density 从 0.3 调到 0.9，观察建筑数、三角数与 draw call 的变化曲线，找出本机上"帧率开始下降"的临界密度。
  2. 修改配置 JSON 里的 style 为"低层"，再手动把 maxFloors 改成 40，观察生成结果是否被风格规则压制；想一想参数之间应该谁覆盖谁。
  3. 给生成器加一条"地标独立种子"规则（mulberry32(seed + 991)），验证改密度时地标位置是否保持不变，并记录修改前后的差异。
