31.2 进阶应用：WebGPURenderer 与 WGSL 管线 ​

前置提示：本篇属于战略前瞻内容，不纳入阶段考核；建议先完成基础模块 ④、⑬ 与 ⑯ 再阅读。

一句话定调：本篇不纳入考核，了解即可；先把概念看懂，再决定要不要在项目里动手。

核心概念讲解 ​

接桥：⑬ 的 EffectComposer 是 WebGL 时代的产物，WebGPU 里有另一套后处理 ​

在 ⑬ 后处理管线 里，我们搭过一条标准的 EffectComposer：RenderPass 把场景画进 RenderTarget，UnrealBloomPass 做泛光，OutputPass 负责色调映射与输出编码。那套结构非常清晰，也是 WebGL 时代最成熟的方案。

但它有两个时代烙印：每一环都默认操作 WebGLRenderTarget，每一环的着色器都是 GLSL。到了 WebGPU，WebGLRenderTarget 与 GLSL Pass 都不再是底层事实，EffectComposer 自然也不能直接复用。Three.js 为 WebGPU 准备了另一套 PostProcessing 节点式管线，它和 TSL 一起在 ㉜ 里展开；本篇只先把"渲染器"和"原始管线"这两层讲清楚。

换句话说：本篇负责换引擎，㉜ 负责写后处理。先把 WebGPURenderer 跑起来，再谈效果链。

three/webgpu 入口：一个构建，两套后端 ​

Three.js 的 WebGPU 能力不在默认的 three.module.js 里，而在单独的入口：

js
import * as THREE from 'three/webgpu'

const renderer = new THREE.WebGPURenderer({ antialias: true })
await renderer.init()

three/webgpu 这个入口同时导出两样东西：

  • 渲染器与后端：WebGPURenderer、WebGPUBackend、WebGLBackend；
  • 节点材质系统：NodeMaterial、MeshStandardNodeMaterial 等，以及 TSL 相关节点。

它不包含 WebGLRenderer。也就是说，three/webgpu 是"用 WebGPU 方式渲染 Three 场景"的入口，而不是"再包一层 WebGLRenderer"。

工程上建议在 WebGPU 项目里统一从 three/webgpu 导入 Three 的对象，避免同一个页面里同时加载 three.module.js 与 three.webgpu.js 两份核心代码。OrbitControls、lil-gui 这类 addon 仍然从 three/addons/ 导入，它们通过 importmap 解析到 three，与主模块共存不会影响使用——但要意识到，这确实是两份模块实例，做 instanceof 判断时要留个心眼。

await renderer.init()：WebGPU 的异步首帧 ​

WebGLRenderer 的构造是同步的：new 完就能 render。WebGPURenderer 不一样，它要先拿到 adapter、device，再编译管线，因此初始化是异步的：

js
const renderer = new THREE.WebGPURenderer({
  antialias: true,
  forceWebGL: false
})

renderer.setSize(innerWidth, innerHeight)
renderer.setPixelRatio(Math.min(devicePixelRatio, 2))
await renderer.init()

document.getElementById('app').appendChild(renderer.domElement)

这里有几个容易踩的点：

  • init() 之前不要渲染。虽然 render() 内部也可能触发初始化，但显式 await 能让错误在可控的位置被捕获，也让首帧时机可预测。
  • init() 可能失败。设备申请被拒绝、驱动异常、WebGPU 被策略关闭，都可能让 Promise 拒绝。必须包在 try / catch 里，并准备回退。
  • 首帧前有一段空白。异步初始化意味着 canvas 挂上去到第一帧之间有几毫秒到几百毫秒的空档。产品上要放 loading 或骨架，而不是让用户盯着黑屏。
  • 页面隐藏时不要阻塞初始化。如果标签页在后台，rAF 会被暂停，但 init() 仍可能完成；此时不要依赖"首帧已渲染"做业务判断。

初始化完成后，renderer.backend.isWebGPUBackend 会告诉你实际走的是哪条路径。这个字段比"浏览器的 UA"可靠得多，埋点时应该优先记录它。

自动回退与 forceWebGL：同一个 API，两套后端 ​

WebGPURenderer 内置了回退逻辑：当 navigator.gpu 不存在或 requestAdapter 失败时，它会自动实例化 WebGLBackend，并打印一条警告：

WebGPURenderer: WebGPU is not available, running under WebGL2 backend.

这意味着同一份场景代码可以在两条后端上跑，业务层不需要写两套 Scene。如果你明确想用 WebGL2 做对照，构造时传 forceWebGL: true：

js
const renderer = new THREE.WebGPURenderer({ antialias: true, forceWebGL: true })
await renderer.init()

forceWebGL 是构造参数，不是运行时属性。想从 WebGPU 切到 WebGL2，只能销毁旧 renderer、重建新 renderer。这也是"热切换"必须做资源重建的根本原因，31.3 会展开。

自动回退和强制回退的差别只在"意图"：

路径触发条件适用场景
自动回退浏览器没有 WebGPU 或设备申请失败线上兜底，保证可用
forceWebGL: true开发者主动指定对照测试、兼容性验证、降级开关
真正 WebGPUadapter + device 都成功新项目默认路径

NodeMaterial 体系：WebGPU 的材质抽象 ​

WebGPU 不能直接吃 GLSL，所以 Three.js 用 NodeMaterial 表达"材质由什么节点组成"。你可以把它理解成"用节点图代替着色器字符串"：颜色、粗糙度、法线、位置都可以是节点，节点之间可以组合、复用、被后处理读取。

对大多数项目来说，不需要手写节点。WebGPURenderer 会把内置材质（MeshStandardMaterial、MeshPhysicalMaterial 等）自动转换成对应的 NodeMaterial：

js
const material = new THREE.MeshStandardMaterial({
  color: 0x7cc4ff,
  metalness: 0.85,
  roughness: 0.2
})

上面这段代码在 WebGLRenderer 和 WebGPURenderer 下都能工作。转换由 NodeMaterial.fromMaterial() 完成，它会把原材质的属性复制到节点材质上，原材质本身不被破坏。所以"用了 WebGPU 就必须全部改成 NodeMaterial"是误解，标准材质可以继续用。

真正需要 NodeMaterial / TSL 的场景是：

  • 自定义程序化纹理、程序化位移；
  • 需要复用材质片段（比如把噪声节点接到多个材质）；
  • 需要写 WebGPU 后处理；
  • 需要 compute shader 参与渲染。

TSL 的语法细节留给 ㉜，本篇只记住一个边界：能用标准材质解决的，就不要为了"WebGPU"三个字去手写节点。

原始管线与 bind group：一段最小 WGSL 讲清楚 ​

术语解释：

  • shader module：WGSL 源码编译后的模块，一个模块可以同时包含 vertex / fragment / compute 入口。
  • render pipeline：把着色器入口、顶点布局、图元类型、混合与深度状态烘焙成的不可变对象。
  • bind group：按 @group / @binding 槽位打包的资源集合，管线布局决定它能绑什么。
  • uniform buffer 对齐：WGSL uniform 地址空间的结构体对齐与大小规则，写错会读到位移错误的数据。

如果你要写原生 WebGPU，必须理解三样东西：shader module、render pipeline、bind group。下面这段最小 WGSL 只画一个三角形：

wgsl
struct VSOut {
  @builtin(position) position: vec4f,
  @location(0) color: vec3f,
};

@vertex
fn vs(@builtin(vertex_index) index: u32) -> VSOut {
  var positions = array<vec2f, 3>(
    vec2f(-0.56, -0.48),
    vec2f(0.56, -0.48),
    vec2f(0.0, 0.56)
  );
  var colors = array<vec3f, 3>(
    vec3f(0.96, 0.42, 0.28),
    vec3f(0.13, 0.83, 0.87),
    vec3f(0.70, 0.52, 0.98)
  );

  var out: VSOut;
  out.position = vec4f(positions[index], 0.0, 1.0);
  out.color = colors[index];
  return out;
}

@fragment
fn fs(in: VSOut) -> @location(0) vec4f {
  return vec4f(in.color, 1.0);
}

逐项解释：

  • @vertex / @fragment：入口标记。管线描述里用 entryPoint: 'vs' 与 'fs' 指定。
  • @builtin(position)：顶点阶段写出的裁剪空间坐标（vec4f(x, y, z, w)）；到了片元阶段，同名内建变量变成帧缓冲像素坐标。它不是"世界坐标"，也不负责投影，投影矩阵要自己乘。
  • @location(0)：顶点属性或插值变量的槽位，必须与管线里的 shaderLocation 对应。
  • array<vec2f, 3>：WGSL 的固定长度数组，这里用它代替顶点缓冲，演示最小闭环。

对应的管线与绑定：

js
const module = device.createShaderModule({ code: wgsl })

const pipeline = device.createRenderPipeline({
  layout: 'auto',
  vertex: { module, entryPoint: 'vs' },
  fragment: {
    module,
    entryPoint: 'fs',
    targets: [{ format }]
  },
  primitive: { topology: 'triangle-list' }
})

const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [{ binding: 0, resource: { buffer: uniformBuffer } }]
})

layout: 'auto' 让管线自己推导 bind group 布局；生产代码更推荐显式 layout，这样资源槽位在编译期就能被验证。targets: [{ format }] 要与 canvas 的 getPreferredCanvasFormat() 一致，否则会得到验证错误。

顶点缓冲布局：arrayStride 与 shaderLocation 必须对齐 ​

真实项目不会把顶点写死在着色器里，而是从顶点缓冲读。布局描述必须和 WGSL 的 @location 一一对应：

js
const vertexLayout = {
  arrayStride: 20,
  attributes: [
    { shaderLocation: 0, offset: 0, format: 'float32x3' },
    { shaderLocation: 1, offset: 12, format: 'float32x2' }
  ]
}
wgsl
struct VSIn {
  @location(0) position: vec3f,
  @location(1) uv: vec2f,
};

@vertex
fn vs(input: VSIn) -> @builtin(position) vec4f {
  return vec4f(input.position, 1.0);
}

arrayStride 是每个顶点占多少字节。position 是 3 个 float（12 字节）+ uv 是 2 个 float（8 字节），所以 stride 是 20。如果写成 16，第二个顶点的 uv 就会错位，画面会出现"三角形被撕裂"的经典症状。这类错误通常不会在业务代码里报错，而是在管线验证或渲染结果里才暴露。

uniform buffer 对齐：为什么 vec3f 最好别单独放 ​

WGSL 的 uniform 地址空间有严格对齐规则：vec3f 的对齐是 16 字节，f32 是 4 字节，结构体整体大小要向上取整到 16 的倍数。一个常见的坑是：

wgsl
struct Uniforms {
  color: vec3f,   // 占 12 字节，但对齐到 16
  scale: f32,     // 可能被塞进 padding，读到的值不对
};

更稳的写法是显式补齐，或者把标量打包进 vec4f：

wgsl
struct Uniforms {
  color: vec4f,
  params: vec4f,
};

动态 uniform 还有一条额外规则：minUniformBufferOffsetAlignment 通常是 256 字节，多个对象共享一个大 uniform buffer 时，每个对象的偏移必须按这个值对齐。这不是"浪费空间"，而是 GPU 读取 uniform 的硬件约束。

WGSL 与 GLSL 的差异：不是换个语法那么简单 ​

如果你写过 GLSL，初看 WGSL 会觉得"只是换了个写法"。真正动手时会发现差异比想象中多：

维度GLSL / ESSLWGSL
入口函数固定 main()，阶段由上下文决定@vertex / @fragment / @compute 显式标注，可任意命名
资源绑定uniform / sampler2D 由驱动自动分配@group(n) @binding(m) 显式声明，对应 bind group
全局变量可以写全局 uniform、varying模块级变量必须带地址空间与访问模式
类型转换有较多隐式转换基本要求显式转换，f32 / i32 / u32 区分严格
纹理采样texture2D()textureSample()，纹理与采样器分开
计算着色器无原生入口，需要片段着色器伪装@compute @workgroup_size(...) 一等公民
调试编译错误信息因驱动而异getCompilationInfo() 可拿到结构化的错误行号

最反直觉的一条是资源绑定：GLSL 里写一个 uniform sampler2D map，驱动会替你找位置；WGSL 里必须写清它在哪个 group、哪个 binding，管线创建时还要给出布局。这份"麻烦"换来的是可预测性：资源槽位在编译期就能验证，不会在运行时悄悄绑错。

初始化时序：把错误挡在首帧之前 ​

WebGPURenderer 的启动不是"new 完就能画"，而是一条有明确阶段的时序：

new WebGPURenderer
   → setSize / setPixelRatio / toneMapping
   → await init()            // 申请 adapter + device，编译内部管线
   → 挂载 canvas
   → setAnimationLoop(...)   // 首帧

每个阶段都可能出问题，也应该有对应的处理：

阶段可能的失败处理方式
构造参数非法、环境不支持捕获异常，回退 WebGL2
init()设备申请失败、驱动异常捕获 Promise 拒绝，记录原因
首帧材质编译失败、纹理格式不支持监听控制台与 device.lost，降级画质
运行中设备丢失、页面隐藏停止循环、重建后端或提示刷新

一个实用技巧：在 init() 外面套一层超时 Promise，超过阈值就判定"启动失败"，直接走 WebGL2。这样即使用户环境里 requestAdapter 卡住，页面也不会一直停在 loading。

三个常见坑 ​

  1. 同时引入两份 Three。在 WebGPU 项目里既 import * as THREE from 'three'，又 import { WebGPURenderer } from 'three/webgpu'，会产生两份核心模块。多数情况下能跑，但 instanceof、材质转换和常量的行为可能出现细微差异。建议 WebGPU 项目统一从 three/webgpu 导入对象。
  2. 在 init() 之前读取 renderer.backend。未初始化时后端可能还没确定，读到的 isWebGPUBackend 不可靠。所有依赖后端的 UI 与埋点，都应该放在 await init() 之后。
  3. 把 WebGL 的后处理直接搬过来。EffectComposer、UnrealBloomPass 这些类绑定的是 WebGLRenderTarget 与 GLSL，搬到 WebGPU 后通常会黑屏或只渲染第一环。后处理必须使用 WebGPU 体系，或先不接后处理。

WebGL 概念 → WebGPU 概念对照表 ​

WebGL 概念WebGPU 对应关键差异
全局状态 + useProgramGPURenderPipeline管线不可变，创建时一次性烘焙状态
bindTexture / uniform*GPUBindGroup资源分组显式绑定，受管线布局约束
ShaderMaterial / GLSLNodeMaterial / WGSLGLSL 不能直接复用，需要改写
WebGLRenderTargetGPUTexture + GPURenderTarget资源生命周期要自己管理
renderer.render(scene, camera)render pass + drawThree 已封装，原生需要命令编码
同步 getExtensionadapter.features特性是设备申请的一部分
上下文丢失事件device.lost设备丢失需要重建 device 与资源
EffectComposer + PassPostProcessing + TSL 节点后处理实现体系完全不同

这张表不是要求你背下来，而是让你在排查问题时知道"该去哪一层找"。例如"后处理没效果"先看是不是把 WebGL 的 Pass 拿到了 WebGPU 管线里；"纹理是黑的"先看 bind group 的槽位和采样器有没有绑对。

什么时候该写原生 WebGPU，什么时候留在 Three ​

需求建议原因
常规 3D 场景、PBR 材质留在 ThreeWebGPURenderer 已覆盖，改动最小
自定义材质、程序化纹理留在 Three + TSLNodeMaterial 能表达，且能跨后端
重度 compute（粒子、排序、图像处理）可写原生 WebGPUcompute pipeline 需要显式控制
极致性能、Render Bundle可写原生 WebGPUThree 的封装有额外抽象成本
已有 WebGL 后处理链先评估，不要硬迁EffectComposer 与 WebGPU 体系不同
需要 WebGL 兼容兜底留在 Three自动回退是 Three 提供的，原生要自己写

一个实用的判断标准：如果你需要直接控制 command encoder、bind group 布局或 compute dispatch，写原生；否则交给 Three。Three 的 WebGPURenderer 不是"过渡方案"，它已经是新项目的正式选项。

还有一个常被忽略的中间地带：用 Three 渲染主场景，只在某个局部写原生 WebGPU。例如主场景继续用 WebGPURenderer，而粒子模拟单独用一个 compute pipeline 算出 storage buffer，再把结果交给 Three 的 Points 或 InstancedMesh 显示。这种"混合模式"往往比全量重写更现实，也更容易回滚——它把原生代码限制在一个模块里，不污染整条渲染链。

代码示例 ​

对应演示 webgpu-renderer-lab.html，核心只有四步：

① 用 three/webgpu 入口创建渲染器：

js
import * as THREE from 'three/webgpu'
import { OrbitControls } from 'three/addons/controls/OrbitControls.js'

const renderer = new THREE.WebGPURenderer({ antialias: true })
renderer.setSize(innerWidth, innerHeight)
renderer.setPixelRatio(Math.min(devicePixelRatio, 2))
renderer.toneMapping = THREE.ACESFilmicToneMapping
await renderer.init()

② 程序化环境贴图，不加载外部图片：

js
const canvas = document.createElement('canvas')
canvas.width = 1024
canvas.height = 512
const ctx = canvas.getContext('2d')
// 画天空渐变、太阳光斑与冷色补光
const tex = new THREE.CanvasTexture(canvas)
tex.mapping = THREE.EquirectangularReflectionMapping
tex.colorSpace = THREE.SRGBColorSpace

scene.environment = tex
scene.environmentIntensity = 1.15

EquirectangularReflectionMapping 告诉材质"这是一张经纬展开的环境图"，渲染器会自动做 PMREM 预过滤，金属球才能得到模糊合理的反射，而不是一张贴图直接糊在表面。

③ 标准材质直接可用，不需要手写节点：

js
const sphere = new THREE.Mesh(
  new THREE.SphereGeometry(0.62, 64, 48),
  new THREE.MeshStandardMaterial({
    color: 0xffffff,
    metalness: 1,
    roughness: 0.06
  })
)

④ 切换 forceWebGL 时重建渲染器：

js
async function rebuild(forceWebGL) {
  renderer.setAnimationLoop(null)
  renderer.dispose()
  renderer.domElement.remove()

  renderer = new THREE.WebGPURenderer({ antialias: true, forceWebGL })
  await renderer.init()
  document.getElementById('app').appendChild(renderer.domElement)
}

演示里 info 卡会显示 renderer.backend.isWebGPUBackend 的结果。如果浏览器不支持 WebGPU，即使不勾选 forceWebGL，卡片也会显示"已回退 WebGL2"，画面仍然正常。

常见问题解答 ​

Q1：`await renderer.init()` 之前调用 `render()` 会怎样？

可能什么都不显示，也可能在内部触发初始化后补上首帧，行为不应被业务依赖。正确做法是显式 await init()，把失败捕获在处理链里，再启动渲染循环。这样首帧时机可预测，错误也能落到具体的 UI 提示上，而不是控制台里一条没人看的警告。

Q2：自动回退和 `forceWebGL` 有什么区别？

自动回退是"WebGPU 不可用时被动落到 WebGL2"，开发者不需要做额外判断；forceWebGL 是"主动要求使用 WebGL2"，常用于对照测试或用户手动降级。两者最终都走 WebGLBackend，但埋点时要区分：前者是能力不足，后者是产品选择，失败原因完全不同。

Q3：我写的 GLSL 材质能在 WebGPU 下直接用吗？

不能直接复用。ShaderMaterial 里的 GLSL 不会被自动翻译成 WGSL。可行路径有三条：改用标准材质 + 参数调节；改用 NodeMaterial / TSL 重写；或者在原生 WebGPU 里手写 WGSL 管线。工作量取决于着色器复杂度，通常这是迁移中最大的一块成本，需要单独评估。

Q4：为什么 WebGPU 不能用 `EffectComposer`？

EffectComposer 依赖 WebGLRenderTarget 与 GLSL Pass，这两个前提在 WebGPU 下不成立。WebGPU 使用 PostProcessing 与节点式 Pass，写法与 ⑬ 完全不同。不要把 WebGL 的后处理代码直接搬到 WebGPU 渲染器上，症状通常是全黑、只显示第一环，或者控制台出现 RenderTarget 相关错误。

Q5：NodeMaterial 和 TSL 是什么关系？

NodeMaterial 是"材质"，TSL 是"用来描述节点图的语法"。可以类比：NodeMaterial 是菜谱的结构，TSL 是写菜谱的语言。本篇只需要知道标准材质会被自动转换；具体怎么用 TSL 写噪声、位移、后处理，放在 ㉜ 展开。

动手小练习 ​

  1. 把演示里的金属球换成 MeshPhysicalMaterial，加上 clearcoat 与 iridescence，对比 WebGPU 与 WebGL2 后端的高光差异，记录哪些属性在两条路径上表现一致、哪些有细微差别。
  2. 给 WebGPURenderer 加一段"初始化超时"逻辑：超过 1.2 秒未完成就回退到 forceWebGL，并在 info 卡显示耗时。思考超时值应该由什么决定。
  3. 用本篇的最小 WGSL 三角形为基础，把顶点位置改成通过顶点缓冲传入（arrayStride 设为 20，包含 position 与 uv），观察 stride 写错时画面会怎样。
