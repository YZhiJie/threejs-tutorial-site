31.1 基础入门：WebGPU 是什么与能力探测 ​

前置提示：本篇属于战略前瞻内容，不纳入阶段考核；建议先完成基础模块 ④ 与 ⑯ 再阅读。

核心概念讲解 ​

接桥：4.1 的 WebGLRenderer 已经用了十年，新后端换掉了什么 ​

在 ④ 渲染器 · 渲染循环 里，我们写下了最熟悉的三行：new THREE.WebGLRenderer()、setSize()、setAnimationLoop()。这三行背后是浏览器用了十多年的 WebGL：一套从 OpenGL ES 继承来的全局状态机，bindTexture、useProgram、enable 一个个开关地设，画完一帧再把状态留给下一帧。

这套接口足够稳定，也足够"老"。它把很多本可以并行的工作变成同步调用，把资源绑定藏在驱动里自动推断，把 GPU 通用计算挡在门外。WebGPU 要做的不是"把 WebGL 变快一点"，而是换一套更接近现代显卡（Vulkan / Metal / Direct3D 12）的显式接口：管线是对象、绑定是显式的、计算是一等公民、初始化是异步的。

先给一句让人安心的话：WebGL 不会一夜消失，WebGPU 与 WebGL 会长期共存。本篇属于战略前瞻，不纳入阶段考核，了解即可；已有 WebGL 项目不需要为了"追新"而重写。

WebGPU 的定位：更少的驱动开销，更多的显式控制 ​

把 WebGPU 想象成"浏览器里的现代图形 API"，而不是"WebGL 3.0"。它的核心变化有四个：

  1. 管线对象（Pipeline）：把着色器、顶点布局、混合、深度测试等一整套状态预先烘焙成一个不可变的管线对象。绘制时只绑定管线，不再逐次修改全局状态。驱动因此可以提前编译、提前验证，减少每帧的 CPU 开销。
  2. 显式绑定（Bind Group）：纹理、采样器、uniform 不再是"设了就生效"的全局状态，而是打包成 bind group，由管线布局约束。资源什么时候可见、以什么顺序可见，全部写在代码里。
  3. 计算着色器（Compute Shader）：WebGPU 原生支持 compute pass，可以把粒子模拟、后处理、数据排序搬上 GPU。WebGL 时代要靠"渲染到纹理 + 片段着色器伪装"的 GPGPU 技巧，在 WebGPU 里是正式能力。
  4. 异步初始化：requestAdapter、requestDevice、createShaderModule 的编译信息都是 Promise 或异步查询。页面要接受"先拿到设备，再开始渲染"的新节奏。

代价是代码更长、概念更多。WebGL 里十行能画出来的东西，原生 WebGPU 可能要六十行。所以 Three.js 的价值反而更大：它把管线、绑定、资源生命周期重新封装成 WebGPURenderer，让业务代码仍然写 Mesh、Material、Scene。

WebGL 与 WebGPU 的差异表 ​

维度WebGL / WebGLRendererWebGPU / WebGPURenderer
状态模型全局状态机，逐个设置开关不可变管线对象，预先烘焙状态
资源绑定隐式绑定，驱动自动推断显式 bind group + 管线布局
初始化同步创建上下文requestAdapter / requestDevice 异步
着色器语言GLSL / ESSLWGSL
计算能力无原生 compute，需要伪装原生 compute pass
多线程受限于上下文与主线程命令编码可分摊，支持多队列概念
错误模型多为静默错误，靠扩展调试验证错误、设备丢失、编译信息可查询
生态成熟度十年积累，兼容性最好新标准，浏览器与工具仍在完善

术语解释：

  • 管线 pipeline：一整套"顶点怎么进、图元怎么装配、片元怎么写"的不可变配置。
  • bind group：一组按槽位绑定的 GPU 资源（uniform buffer、纹理、采样器）。
  • WGSL：WebGPU Shading Language，WebGPU 的官方着色器语言，语法接近 Rust。
  • adapter / device：adapter 代表一块可用 GPU 的抽象，device 是从 adapter 申请到的逻辑设备，后续资源都挂在 device 上。

浏览器支持现状：能跑，但别假设人人都能跑 ​

截至 2026 年，桌面端的主流情况是：

浏览器支持情况实践建议
Chrome / Edge（桌面）稳定支持，默认开启可作为 WebGPU 首选验证环境
Safari（macOS / iOS）已逐步支持，版本与系统差异较大必须做运行时探测，不要只看 UA
Firefox（桌面）持续跟进，部分版本需开关视为"可能可用"，保留回退
移动端 Chrome部分 GPU / 机型支持按机型与驱动差异做白名单或探测
老旧浏览器 / 内嵌 WebView多数不支持直接走 WebGL2 或静态兜底

这张表只能给方向，不能给结论。唯一可靠的支持判断是运行时 navigator.gpu 探测，而不是浏览器名称、版本号或用户代理。因为即使是同一版本 Chrome，在远程桌面、虚拟机、禁用硬件加速的环境里也可能拿不到适配器。

能力探测：navigator.gpu 的三段式 ​

探测分三步，每一步都可能失败，也都应该有对应的降级：

js
async function probeWebGPU() {
  if (!navigator.gpu) return { ok: false, reason: 'no navigator.gpu' }

  const adapter = await navigator.gpu.requestAdapter({
    powerPreference: 'high-performance'
  })
  if (!adapter) return { ok: false, reason: 'no adapter' }

  const limits = adapter.limits
  const features = Array.from(adapter.features)

  try {
    const device = await adapter.requestDevice()
    device.destroy()
    return { ok: true, adapter, limits, features }
  } catch (err) {
    return { ok: false, reason: 'requestDevice failed: ' + err.message }
  }
}

三个返回值对应三种产品决策：

  • navigator.gpu 不存在：浏览器根本不认识这套 API，直接走 WebGL2；
  • adapter 为 null：浏览器认识，但当前环境没有可用 GPU（虚拟机、远程桌面、驱动黑名单），走 WebGL2；
  • device 创建失败：适配器在，但设备申请被拒绝或驱动异常，仍然走 WebGL2。

注意 requestAdapter() 本身也可能抛异常（例如被权限策略阻止），所以要包在 try / catch 里。探测函数永远不应该让页面白屏，最差也要返回一个"不可用"的结论。

adapter 信息与 limits：知道自己在谁的机器上跑 ​

拿到 adapter 之后，可以做两件对工程很有用的事：

js
const info = adapter.info || {}
console.log(info.vendor, info.architecture, info.device, info.description)

console.log({
  maxTextureDimension2D: adapter.limits.maxTextureDimension2D,
  maxComputeWorkgroupSizeX: adapter.limits.maxComputeWorkgroupSizeX,
  maxComputeInvocationsPerWorkgroup: adapter.limits.maxComputeInvocationsPerWorkgroup,
  maxStorageBufferBindingSize: adapter.limits.maxStorageBufferBindingSize,
  maxBufferSize: adapter.limits.maxBufferSize
})

adapter.info 在不同浏览器上返回的字段并不一致，有的只给 vendor 和 architecture，有的会出于隐私原因留空。不要把它当成精确的设备指纹，把它当成"分维度上报的一个字段"即可。

limits 才是真正影响代码能不能跑的东西。例如：

limit影响什么典型决策
maxTextureDimension2D单张 2D 纹理的最大边长超过就降采样或分块
maxComputeWorkgroupSizeX计算着色器一个工作组的大小决定粒子 / 后处理的 tile 尺寸
maxStorageBufferBindingSize单个 storage buffer 的上限决定大数据能否一次性上传
maxBufferSize单个 buffer 的上限决定几何合并的上限
maxBindGroups一次绘制能绑多少组资源决定材质与后处理链的复杂度

真正的工程做法是：在申请 device 时只提高真正需要的 limit，而不是照着最大值全要一遍。要得越多，失败概率越高：

js
const device = await adapter.requestDevice({
  requiredFeatures: [],
  requiredLimits: {
    maxTextureDimension2D: Math.min(4096, adapter.limits.maxTextureDimension2D)
  }
})

适配器信息与降级策略 ​

降级不是一个 if，而是一条链：

navigator.gpu 存在？
   ├─ 否 → WebGL2 → 静态图
   └─ 是 → requestAdapter
            ├─ null → WebGL2 → 静态图
            └─ adapter → requestDevice
                         ├─ 失败 → WebGL2 → 静态图
                         └─ 成功 → 按 features / limits 决定画质档位

这条链和 ㉕ 线上监控与容错 的降级阶梯是同一套思路：先保可用，再保画质。WebGPU 只是多了一个"后端"维度，而不是把旧阶梯作废。

还有一个容易忽略的点：探测本身要限时。requestAdapter() 在极端环境下可能长时间不返回。首屏不能等它，应该给它设一个 300~800ms 的兜底计时器，超时就先按 WebGL 启动，探测结果回来再决定要不要热切换。

"是否值得现在迁移"的判断表 ​

场景建议理由
全新项目、目标用户以桌面 Chrome / Edge 为主可以优先试水 WebGPU新代码没有历史包袱，收益最直接
已有 WebGL 项目、画面与性能都达标继续 WebGL，保持观察迁移收益有限，风险与测试成本更高
重度自定义 GLSL 材质先不动，单独评估GLSL 不会自动变成 WGSL，这是主要成本
需要 GPU 计算（粒子、物理、图像处理）值得试点 WebGPU原生 compute 是 WebGL 难以替代的能力
移动端 / 内嵌 WebView 为主继续 WebGL2，做能力探测驱动与机型差异大，回退路径必须完整
政企内网、老旧设备继续 WebGL2兼容性优先，不要为了新 API 牺牲可用性

一句话总结：WebGPU 是"新项目的新选项"，不是"旧项目的必修课"。本篇不纳入考核，读完之后你只需要知道它是什么、怎么探测、什么时候值得用，就已经够了。

WebGPU 与 WebGL 的关系：分叉，而不是替换 ​

很多文章把 WebGPU 写成"WebGL 的继任者"，这个说法容易制造焦虑，也不准确。更贴切的描述是分叉：

  • 两者共享同一块 GPU，只是用不同的接口去驱动它；
  • 两者会在很长一段时间里共存，浏览器没有"到某天关掉 WebGL"的时间表；
  • Three.js 用两套入口分别封装它们，而不是让一套代码只能在一条后端上跑；
  • 对业务来说，真正要维护的是"场景与资产"，不是"API 的名字"。

所以看到"WebGPU 来了"时，正确的反应不是"我的项目要死了"，而是"我多了一个可选后端"。如果你的项目画面稳定、性能达标、目标设备以兼容性为先，那么继续用 WebGL 是完全合理的选择。反之，如果新项目需要 compute、需要更低的主线程开销、目标用户以新版桌面浏览器为主，那么 WebGPU 值得一试。

判断"要不要现在动"时，可以用三个问题自查：

  1. 我的用户里，WebGPU 可用比例是否足够高？（看埋点，不看感觉）
  2. 我的项目是否重度依赖自定义 GLSL 或 WebGL 专属后处理？（是则成本高）
  3. 我是否能接受两套后端并行测试一段时间？（不能则先别切）

三个问题里有两个答案是"否"，就应该继续观望。技术选型的成熟标志，是知道什么时候不用新技术。

三个常见坑 ​

  1. 用 UA 判断 WebGPU 支持。navigator.userAgent 包含浏览器名，但不包含 GPU、驱动、硬件加速状态。同一版本 Chrome 在虚拟机里可能拿不到 adapter。正确做法永远是运行时探测 navigator.gpu，UA 只用于报表分组。
  2. 把探测放在首屏关键路径上。requestAdapter() 在异常环境下可能长时间不返回，导致页面一直转圈。应该给探测加超时，先用 WebGL2 出画面，探测结果回来再决定是否升级后端。
  3. 把 WebGPU 当成性能银弹。它降低的是 CPU 侧的驱动开销，不改变像素填充、带宽、几何复杂度的成本。如果瓶颈在 overdraw 或纹理带宽，换后端不会让帧率凭空翻倍，该做的性能优化一项都不会少。

迁移成本到底有多大 ​

很多焦虑来自一个误解：以为上 WebGPU 就要把 Three.js 代码全部重写。实际不是。

  • 如果项目用的是 MeshStandardMaterial、Scene、OrbitControls 这些标准对象，WebGPURenderer 可以接手大部分场景，业务代码改动很小；
  • 真正的成本在自定义着色器：ShaderMaterial 的 GLSL、onBeforeCompile 注入的代码、手写的后处理 Pass，这些需要改写成 TSL / NodeMaterial 或原生 WGSL；
  • 第二块成本在后处理：EffectComposer 是 WebGL 时代的实现，WebGPU 有另一套 PostProcessing；
  • 第三块成本在测试：两套后端都要跑回归，不能只测一条路径。

所以正确的迁移姿势是"新项目试水、旧项目保留回退、自定义着色器单独评估"，而不是"全站重写"。迁移成本可控，前提是你没有把 GLSL 写死到每一个角落。

代码示例 ​

对应演示 capability-lab.html。它的加载顺序就是本篇的探测链：

① 先探测，不创建渲染器：

js
const adapter = navigator.gpu
  ? await navigator.gpu.requestAdapter({ powerPreference: 'high-performance' })
  : null

const supported = !!adapter

② 用同一个场景，准备两套后端：

js
import * as THREE from 'three/webgpu'

const renderer = new THREE.WebGPURenderer({ antialias: true })
await renderer.init()

renderer.setSize(innerWidth, innerHeight)
renderer.setPixelRatio(Math.min(devicePixelRatio, 2))

③ 查看实际后端，而不是"以为"：

js
const isWebGPU = renderer.backend.isWebGPUBackend
document.getElementById('backend').textContent =
  isWebGPU ? 'WebGPU 原生' : 'WebGL2 后端'

④ 强制 WebGL2 做对照：

js
const renderer2 = new THREE.WebGPURenderer({ antialias: true, forceWebGL: true })
await renderer2.init()

forceWebGL 在构造时决定后端，不能运行时修改；要切换只能销毁旧 renderer、重建新 renderer。这正是 31.3 要讨论的"热切换"的难点之一。

演示里还画了一个金属环、一个发光核心和一块地面。你可以切换后端观察画面：绝大多数情况下两者几乎一致，差异更多出现在首帧耗时、着色器编译日志和后处理支持上，而不是"颜色突然变了"。

常见问题解答 ​

Q1：浏览器不支持 WebGPU，页面会不会白屏？

只要按本篇的探测链写就不会。关键是不要"先 new 一个 WebGPURenderer 再说"，而是先判断 navigator.gpu、再 requestAdapter、再 requestDevice，任何一步失败都回退到 WebGL2。Three.js 的 WebGPURenderer 本身也内置了回退：没有 WebGPU 时会自动使用 WebGL2 后端，控制台会打印一条警告。页面层面再加一层提示文案，用户不会看到黑屏。

Q2：WebGPU 一定比 WebGL 快吗？

不一定。WebGPU 的主要优势是更低的 CPU 驱动开销和原生计算能力，在 draw call 密集、需要 compute、需要显式资源管理的场景更明显。如果是简单的几个模型、瓶颈在像素填充或带宽，换后端未必有肉眼可见的帧率提升。正确做法是先用 profiler 找瓶颈，再决定是否值得迁移，而不是把"换 API"当成性能银弹。

Q3：手机上能用 WebGPU 吗？

部分机型可以，但差异很大：Chrome Android 在部分 GPU / 驱动上已支持，iOS 要看 Safari 版本与系统版本，内嵌 WebView 往往更保守。工程上不要按"移动端一律不支持"写死，也不要按"移动端一定支持"假设，统一用运行时探测 + WebGL2 回退。移动端还要额外关注功耗与发热，WebGPU 的低开销不等于低能耗。

Q4：我已有的 WebGL 项目需要立刻迁移吗？

不需要。本篇明确不纳入考核，也不建议为了迁移而迁移。判断标准只有三个：新项目是否有明确收益、是否重度依赖自定义 GLSL、目标设备是否覆盖足够多的 WebGPU 用户。三者都不成立时，继续用 WebGLRenderer 是更稳的选择。WebGL 生态成熟、调试工具完善，这些本身就是价值。

Q5：`requestAdapter` 返回 null，是代码写错了吗？

通常不是。常见原因是虚拟机 / 远程桌面没有暴露 GPU、浏览器禁用了硬件加速、驱动被列入黑名单，或者页面不在安全上下文（HTTPS / localhost）。先换一台物理机、开启硬件加速、确认地址栏是安全连接，再检查代码。把 null 当成一个正常分支处理，而不是异常。

动手小练习 ​

  1. 打开 capability-lab.html，记录你当前设备的 adapter.info、maxTextureDimension2D 与 maxComputeWorkgroupSizeX，再在另一台设备（或关闭硬件加速的浏览器）上重复一次，比较两次的结论差异。
  2. 把探测函数改成"限时 500ms"的版本：超时就先按 WebGL2 启动，探测结果回来后再更新界面上的结论。思考为什么首屏不应该等待 GPU 探测。
  3. 在演示里连续切换三次后端，记录每次的首帧耗时（可以用 performance.now() 打点），并解释为什么 forceWebGL 不能像普通开关一样在运行时直接改。
