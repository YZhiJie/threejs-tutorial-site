31.3 实战案例：可热切换的渲染后端 ​

前置提示：本篇属于战略前瞻内容，不纳入阶段考核；建议先完成基础模块 ④、⑬ 与 ㉕ 再阅读。

一句话定调：本篇不纳入考核，了解即可；热切换是工程能力，不是"必须立刻上线"的任务。

核心概念讲解 ​

接桥：㉕ 的降级阶梯里没有"换后端"这一级 ​

在 ㉕ 线上监控与容错 里，我们设计了一架七档降级阶梯：降像素比、关泛光、关阴影、关反射、关粒子，最后停在一张静态图上。那架阶梯解决的是"同一套渲染路径内部，怎么按预算砍功能"。

但它默认了一个前提：渲染路径本身不变。而 WebGPU 的到来，第一次让"换一条渲染路径"成为可选项。它不属于阶梯里的某一档，而是阶梯旁边的另一条分支：

同一套场景
   ├─ 后端 A：WebGPU（新设备、新项目、compute 需求）
   └─ 后端 B：WebGL2（兼容兜底、旧设备、旧后处理）

这一篇要做的，不是"把 WebGL 全换成 WebGPU"，而是把"后端选择"变成一个可探测、可切换、可回退、可上报的工程能力。它的目标和 ㉕ 一致：让用户在任何设备上都看到能用的画面，同时把决策过程留下证据。

把后端抽象成 createRenderer() ​

术语解释：

  • 能力探测（capability probe）：运行时询问浏览器与 GPU "你能不能跑 WebGPU、能跑多大"，而不是靠 UA 猜测。
  • 特性开关（feature flag）：用配置或远程开关决定某个用户是否尝试新后端，便于灰度与回滚。
  • 冒烟测试（smoke test）：在正式切换前用极小负载渲染一两帧，确认管线真的能工作。
  • 热切换（hot swap）：不刷新页面的前提下，从一套渲染后端原子地换到另一套。

最忌讳的写法，是在业务代码里到处写 if (navigator.gpu)。正确做法是把后端收敛到一个工厂函数，返回一套统一接口：

js
async function createRenderer(options = {}) {
  const preferWebGPU = options.preferWebGPU !== false
  const probe = await probeWebGPU({ timeout: 900 })

  if (preferWebGPU && probe.ok) {
    try {
      const renderer = new WebGPURenderer({ antialias: true })
      await renderer.init()
      return {
        renderer,
        backend: renderer.backend.isWebGPUBackend ? 'webgpu' : 'webgl2',
        reason: renderer.backend.isWebGPUBackend ? null : 'webgpu-init-fallback',
        adapter: probe.adapterInfo
      }
    } catch (err) {
      // 继续往下走 WebGL2
    }
  }

  const renderer = new WebGLRenderer({ antialias: true })
  return {
    renderer,
    backend: 'webgl2',
    reason: probe.reason || 'prefer-webgl',
    adapter: probe.adapterInfo
  }
}

统一接口至少应包含：

方法 / 字段作用
backend'webgpu' / 'webgl2'，埋点与 UI 的唯一真相
renderer底层渲染器，供场景渲染
reason为什么落到这个后端，方便排障
resize(w, h, dpr)统一尺寸与像素比处理
dispose()销毁后端，释放 canvas 与 GPU 资源
createPostFX()按后端返回对应的后处理实现
onLost(cb)统一的设备 / 上下文丢失回调

注意 createRenderer() 是异步的。这会把"启动流程"从同步变成异步，业务代码必须接受这个事实：先拿到后端，再创建场景，或者先创建场景、等后端就绪再挂载。两种顺序都可以，关键是不要在半初始化状态下开始渲染。

统一接口的价值不在于"少写几个 if"，而在于把后端差异挡在业务层之外。业务代码只应该看到 backend.resize()、backend.createPostFX()、backend.onLost()，而不应该看到 isWebGPUBackend。这样可以保证：

  • 加第三套后端（例如未来的 WebGL1 兜底）时，业务代码不用改；
  • 埋点字段统一，不会出现有的模块记 webgpu、有的模块记 WebGPU；
  • 热切换时，业务层只需要替换一个对象，而不是到处改引用。

一个最小的生命周期用法像这样：

js
const backend = await createRenderer({ preferWebGPU: true })

backend.resize(innerWidth, innerHeight, Math.min(devicePixelRatio, 2))
backend.onLost((reason) => {
  report('renderer-lost', reason)
  showStaticFallback()
})

renderer.render(scene, camera)

两套后端的差异点：别假设它们完全等价 ​

WebGPURenderer 让"同一套 Scene 代码"跑在两条后端上，但渲染路径之外的东西并不等价。工程上必须逐项确认：

维度WebGL2 后端WebGPU 后端迁移影响
后处理EffectComposer + PassPostProcessing + TSL 节点需要两套实现，或先只保留 WebGL 后处理
着色器注入onBeforeCompile 改 GLSLNodeMaterial / TSL自定义材质需要改写
上下文丢失webglcontextlost / restoreddevice.lost，没有自动恢复恢复策略不同，必须各自实现
性能计数EXT_disjoint_timer_query（可选）timestamp-query（可选特性）两套采样口径，报表要标注后端
抗锯齿上下文级 sample bufferMSAA 配置 + 后处理 AAforceWebGL 需重建 renderer
纹理格式扩展决定特性决定压缩纹理资产要分别验证
首帧成本同步建上下文，较快异步申请设备，可能较慢首屏策略必须不同

最容易被低估的是后处理。如果项目有一长串 Bloom、SSAO、景深、调色 Pass，WebGPU 路径不是"换个渲染器就自动生效"，而是要重写整条链。实践中的稳妥策略是：先让 WebGPU 跑基础渲染，后处理仍走 WebGL 分支；等基础路径稳定，再逐条迁移后处理。

首帧策略：先用 WebGL 保首屏，再热切换 ​

WebGPU 的初始化是异步的，而用户对首屏的耐心通常只有一两秒。让首屏等 requestAdapter + requestDevice + 管线编译，是不划算的。

推荐的首帧策略分四步：

  1. 立即用 WebGL2 启动：同步建上下文，几十毫秒内出画面，用户先看到内容；
  2. 后台探测 WebGPU：用带超时的 probeWebGPU()，不阻塞主渲染循环；
  3. 离屏预构建 WebGPU 后端：创建第二个 canvas，await renderer.init()，渲染一到两帧做冒烟测试；
  4. 空闲时原子切换：等预构建成功、且当前没有交互（没有拖拽、没有动画关键帧），再交换 canvas、销毁旧后端。
js
async function warmSwitch() {
  const probe = await probeWebGPU({ timeout: 900 })
  if (!probe.ok) return report('webgpu-probe-failed', probe.reason)

  const next = new WebGPURenderer({ antialias: true })
  await next.init()
  next.setSize(2, 2)
  next.render(scene, camera)
  await new Promise((resolve) => requestAnimationFrame(resolve))

  swapBackend(next)   // 交换 canvas、重建后处理、销毁旧 renderer
}

这段代码是示意，真实项目要按你自己的初始化流程调整。核心思想是**"先保证有画面，再追求更好的后端"**：WebGPU 是增强项，不是首屏的前置条件。即使探测失败，用户也只是继续用 WebGL2，体验不受影响。

另外给热切换设一个"重试上限"：一次会话最多尝试两次，失败后不再反复申请设备。反复探测会带来额外的驱动开销，也可能让低端设备在后台持续发热，得不偿失。

还有一个产品层面的细节：热切换会发生在一瞬间，画面可能有 1~2 帧的闪烁。可以在切换前显示一个极轻的遮罩，或者把切换安排在场景静止时。不要在主视觉动画的高潮切后端，那会让用户以为"卡了一下"。

切换时的资源重建：哪些能复用，哪些必须重来 ​

这是热切换最容易翻车的地方。原则是：CPU 侧的数据可以复用，GPU 侧的资源必须按后端重建。

资源能否复用说明
Scene / Group / Mesh可以只是对象树，和后端无关
几何体的 BufferAttribute可以CPU 数组可复用；GPU buffer 由新后端重新上传
MeshStandardMaterial 参数可以WebGPU 会自动转换成 NodeMaterial
自定义 ShaderMaterial不可以GLSL 需要改写，不能直接跨后端
WebGLRenderTarget不可以WebGPU 使用不同的纹理 / 渲染目标实现
EffectComposer 链不可以必须换成 WebGPU 的 PostProcessing
Canvas / 上下文不可以每个后端有自己的 canvas 与上下文
性能计数器不可以两套 API，口径不同

实践中最稳的重建顺序是：

js
function swapBackend(next) {
  const old = current
  old.renderer.setAnimationLoop(null)

  // 1. 先停旧循环，避免切换过程中继续提交命令
  // 2. 挂新 canvas，重建控制器与后处理
  // 3. 把 scene / camera 交给新 renderer
  // 4. 销毁旧 renderer 与后端专属资源
  old.renderer.dispose()
  old.renderer.domElement.remove()
}

不要在新后端还没准备好时销毁旧后端。热切换的目标是"无缝"，不是"先拆再装"。如果新后端的冒烟测试失败，就直接放弃切换、保留旧路径，并记录失败原因。

埋点：把"后端选择"变成可分析的数据 ​

一次后端决策至少应该产生一条会话级事件，字段建议如下：

js
report({
  event: 'renderer_backend',
  backend: 'webgpu',
  reason: null,
  requested: 'webgpu',
  adapterVendor: info.vendor || 'unknown',
  adapterArchitecture: info.architecture || 'unknown',
  probeMs: 312,
  firstFrameMs: 480,
  switchedAt: 2400,
  deviceMemoryGB: navigator.deviceMemory || null
})

几个纪律，和 ㉕ 的遥测体系一致：

  • 一个会话只报一次主事件，不要每帧上报；
  • 失败也要报：no-navigator-gpu、no-adapter、request-device-failed、init-timeout、smoke-test-failed 这些原因比"成功"更有价值；
  • 切换耗时单独记：probeMs 与 firstFrameMs 能回答"热切换到底值不值"；
  • 区分主动与被动：forceWebGL 是用户 / 产品选择，自动回退是能力不足，两者的告警策略不同；
  • 后端字段要带到所有性能报表里：同一帧率数字在 WebGPU 与 WebGL2 下不可直接对比。

如果只在成功路径上报，你会得到一个"WebGPU 覆盖率 90%"的漂亮数字，却不知道剩下 10% 是设备不支持、驱动失败，还是用户手动关掉了硬件加速。

面向未来的迁移路径 ​

不要做"大爆炸式迁移"。一条风险可控的路径是：

阶段做什么验收标准
阶段 0 · 观察只加能力探测与埋点，不改渲染路径知道用户设备里 WebGPU 的真实占比
阶段 1 · 新项目试水新项目默认 WebGPURenderer，保留回退新项目在两条后端上都能跑
阶段 2 · 功能开关老项目加 ?backend=webgpu 或远程开关内部用户可切换，收集问题
阶段 3 · 模块迁移一个模块一个模块迁移（先简单场景）每个模块都有独立回滚
阶段 4 · 默认切换满足条件的用户默认 WebGPU回退率、崩溃率、帧率均达标

这条路径的核心是每一步都能回滚。迁移成本可控的前提，是你没有把"后端"写死进业务逻辑，也没有把 GLSL 散布到每个材质里。

失败原因分类：让"回退"有名字 ​

热切换失败时，最容易犯的错是只上报一句"fallback"。给每种失败一个稳定的枚举值，排障效率会完全不同：

reason含义产品动作
no-navigator-gpu浏览器没有 navigator.gpu继续 WebGL2，不提示
no-adapter有 API，但拿不到适配器记录环境，继续 WebGL2
request-device-failed设备申请被拒绝记录驱动，继续 WebGL2
init-timeout初始化超过阈值放弃本次切换，重试有上限
smoke-test-failed预渲染验证失败回滚，保留旧后端
user-forced-webgl用户或产品主动选择不算故障，单独统计
device-lost运行中设备丢失提示刷新或降级静态图

同一张报表里，"用户主动关掉 WebGPU"和"设备申请失败"必须分开。否则你会把产品决策误判成兼容性故障，进而做出错误的优化方向。

还有一条和首帧相关的经验：页面在后台时不要做热切换。浏览器会暂停后台标签页的 rAF，但 requestAdapter、init() 仍可能完成；此时切换 canvas，用户切回来看到的可能是一帧未完成的画面。稳妥做法是监听 visibilitychange，只在页面可见且连续渲染两帧后再执行切换。

三个常见坑 ​

  1. 切换时忘了停旧循环。旧 setAnimationLoop 还在跑，新旧两个 renderer 同时操作 canvas，画面会闪、会黑，甚至触发上下文错误。必须先 setAnimationLoop(null)，再销毁。
  2. 复用后端专属资源。WebGLRenderTarget、EffectComposer、ShaderMaterial 都不能跨后端。切换时应该重建，而不是把旧对象直接赋给新渲染器。"看起来能跑"不代表状态正确，可能只是还没到触发错误的那一帧。
  3. 把 forceWebGL 记成失败。用户手动降级是预期行为，不是异常。埋点里要区分 requested 与 actual，否则回退率会被高估，后续的兼容性投入也会被带偏。

原生 WGSL 最小三角形：完整代码 ​

最后给一份不依赖 Three.js 的最小闭环，用来理解"后端到底在做什么"。它和 raw-wgsl-lab.html 是同一套逻辑：

js
const canvas = document.getElementById('gpu-canvas')
const adapter = await navigator.gpu.requestAdapter()
const device = await adapter.requestDevice()
const context = canvas.getContext('webgpu')
const format = navigator.gpu.getPreferredCanvasFormat()

context.configure({ device, format, alphaMode: 'opaque' })

const wgsl = `
struct VSOut {
  @builtin(position) position: vec4f,
  @location(0) color: vec3f,
};

@vertex
fn vs(@builtin(vertex_index) index: u32) -> VSOut {
  var positions = array<vec2f, 3>(
    vec2f(-0.56, -0.48),
    vec2f(0.56, -0.48),
    vec2f(0.0, 0.56)
  );
  var colors = array<vec3f, 3>(
    vec3f(0.96, 0.42, 0.28),
    vec3f(0.13, 0.83, 0.87),
    vec3f(0.70, 0.52, 0.98)
  );

  var out: VSOut;
  out.position = vec4f(positions[index], 0.0, 1.0);
  out.color = colors[index];
  return out;
}

@fragment
fn fs(in: VSOut) -> @location(0) vec4f {
  return vec4f(in.color, 1.0);
}
`

const module = device.createShaderModule({ code: wgsl })
const pipeline = device.createRenderPipeline({
  layout: 'auto',
  vertex: { module, entryPoint: 'vs' },
  fragment: {
    module,
    entryPoint: 'fs',
    targets: [{ format }]
  },
  primitive: { topology: 'triangle-list' }
})

function frame() {
  const encoder = device.createCommandEncoder()
  const pass = encoder.beginRenderPass({
    colorAttachments: [{
      view: context.getCurrentTexture().createView(),
      clearValue: { r: 0.043, g: 0.055, b: 0.078, a: 1 },
      loadOp: 'clear',
      storeOp: 'store'
    }]
  })
  pass.setPipeline(pipeline)
  pass.draw(3)
  pass.end()
  device.queue.submit([encoder.finish()])
  requestAnimationFrame(frame)
}

frame()

这份代码不到一百行，却包含了原生 WebGPU 的全部关键步骤：申请适配器、申请设备、配置画布、写 WGSL、建管线、编码命令、提交队列。看懂它，再看 WebGPURenderer 的封装，就不会觉得"WebGPU 很玄"。

常见问题解答 ​

Q1：WebGPU 下我的自定义 GLSL 材质怎么办？

有三条路，按成本从低到高：第一，改用标准材质 + 参数调节，大多数"自定义"其实只是想要某种高光或渐变；第二，用 NodeMaterial / TSL 重写，保留节点化表达，同时兼容两条后端；第三，在原生 WebGPU 里手写 WGSL，适合极端定制。不要指望 GLSL 被自动翻译，这是迁移中必须单独评估的成本，也是"迁移成本可控"里最不可控的一块。

Q2：移动端支持情况怎么样？

部分机型已支持，但差异很大：Chrome Android 取决于 GPU 与驱动，iOS 取决于 Safari 与系统版本，内嵌 WebView 更保守。工程上统一用运行时探测 + WebGL2 回退，不要按 UA 写死。移动端还要额外关注发热与耗电，WebGPU 的低 CPU 开销不代表低功耗，长时间高负载仍可能降频。

Q3：热切换后画面变黑或材质丢失，先查什么？

按顺序查四件事：① 是否在旧 renderer 上继续提交命令；② 是否忘记重建后处理与 RenderTarget；③ 是否把 ShaderMaterial 直接带到了 WebGPU 后端；④ 是否在 init() 完成前就调用了 render()。最常见的是第 ② 和第 ③ 项：后处理链与自定义着色器是后端强相关的，不能跨后端复用。

Q4：两套后处理要维护两份代码吗？

短期看是，长期可以用"统一能力接口 + 两套实现"收敛：业务层只调用 createPostFX().bloom(strength)，内部按后端选择 EffectComposer 或 PostProcessing。如果后处理不是核心卖点，更稳的策略是"WebGPU 路径先不接后处理"，把复杂度留到第二阶段，避免首屏就背上两套链路的维护成本。

Q5：首屏一定要等 WebGPU 探测完吗？

不要。首屏应该先用 WebGL2 立即出画面，WebGPU 探测放到后台，成功后再热切换。探测要带超时（300~900ms），超时就放弃本次切换。用户感知的是"页面打开了"，而不是"后端是哪一个"；把后端选择放在首屏关键路径上，是拿体验换一个用户看不见的指标。

动手小练习 ​

  1. 给 createRenderer() 加一个 preferWebGPU 开关，分别测试"优先 WebGPU"和"强制 WebGL2"两条路径，记录 reason 字段在每种情况下的取值。
  2. 实现一个最小热切换：先用 WebGL2 渲染，1 秒后在后台创建 WebGPURenderer，成功后交换 canvas。故意让 init() 失败一次，确认页面仍保留 WebGL2 画面。
