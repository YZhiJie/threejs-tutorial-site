26.1 基础入门：CPU 与 GPU 帧时间拆解 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ④ 与 ⑯ 再学习本篇。

核心概念讲解 ​

接桥：16.1 只看到了"卡"，没看到是谁在拖后腿 ​

在 ⑯ 大场景 · 性能读数 里，我们学会了看 renderer.info：draw calls、triangles、geometries/textures 三组读数，配合 Stats 面板，能判断"是物体太多、几何太重，还是纹理太占显存"。

但那套读数回答的是**"场景有多复杂"，不是"这一帧的 16.6ms 被谁花掉了"**。同样 300 次 draw call，有的项目跑满 60fps，有的项目卡成幻灯片——差别藏在帧内部：主线程在算矩阵，GPU 在重复着色同一个像素，或者两者都没吃饱、时间全耗在驱动排队上。

本篇把镜头推进到一帧内部，把那条 16.6ms 的时间线拆成 CPU 与 GPU 两段，并给出可复现的基线采集方法。这是后面 26.2（GPU 侧的 overdraw 与带宽）和 26.3（治理工作台）的地基。

一帧的两条时间线 ​

浏览器渲染一帧，粗略有五个阶段：输入处理 → requestAnimationFrame 回调（我们的 Three.js 代码）→ 样式/布局 → 绘制与合成 → 上屏。其中与我们直接相关的只有中间两段，而且它们分别落在两个不同的处理器上：

CPU（主线程）GPU（显卡）
干什么执行 JS、更新场景、提交绘制命令、上传 uniform执行顶点着色器、光栅化、片元着色器、混合、写 framebuffer
谁在等谁提交完就返回，不等 GPU 画完收到命令队列后按序执行
典型耗时来源draw call 提交、材质/着色器切换、矩阵更新、GC顶点数量、片元数量（overdraw）、纹理采样、带宽
怎么读performance.now() 掐表、Performance 面板 Main 火焰图时间查询扩展、Spector.js、GPU 面板、或"帧间隔 − JS"估算

关键认知：renderer.render() 返回时，GPU 很可能连一个三角形都还没画完。WebGL 的命令是异步提交的，CPU 只是把命令塞进队列。因此"render() 只花了 3ms"完全不能证明"这一帧很便宜"——它只证明了 CPU 提交便宜。

术语解释：帧时间（frame time） 是相邻两次画面更新的间隔，单位毫秒；帧率（FPS） 是它的倒数（1000/帧时间）。60fps 对应 16.6ms。习惯上我们盯帧时间，因为它是"预算"这种可加减的量，而 FPS 是非线性的。

CPU 侧：每一次"说话"都要付费 ​

CPU 侧的成本可以归成四类，按出现频率从高到低排：

成本项触发时机量级感受直接证据
draw call 提交每个可见 Mesh / InstancedMesh 一次单次几十微秒，上千次就是十几毫秒renderer.info.render.calls 暴涨
材质 / 着色器切换相邻物体材质不同、需要换 program 或重新绑纹理切换越碎越贵，状态切换是"隐形税"把材质合并后帧时间下降
矩阵更新每帧 updateMatrixWorld、逐物体改 transform上万物体会明显吃掉主线程Performance 面板里 updateMatrixWorld 长条
GC 与业务 JS每帧 new Vector3 / 字符串拼接 / 闭包偶发 5~20ms 尖峰，平均帧率看不出来Performance 面板 GC 条、帧时间峰值

一个常见误区是"CPU 很快，随便算"。实际上主线程还要处理页面滚动、输入、Vue/React 更新、定时器——3D 代码只是排队的一员。CPU 侧的优化目标不是"算得更快"，而是"每帧少做重复的事"：能缓存的世界矩阵别重算，能共享的材质别克隆，能批量提交的别逐个提交。

GPU 侧：顶点账 + 片元账 + 带宽账 ​

GPU 侧的成本更像"工厂流水线"，分三段：

  1. 顶点处理：每个顶点跑一次顶点着色器，还要做裁剪、组装三角形。三角形越多、顶点属性越宽（位置/法线/切线/UV/骨骼权重），这一段的压力越大。
  2. 光栅化与片元处理：每个被三角形覆盖的像素跑一次片元着色器。这是最容易被低估的一段——它和屏幕分辨率、overdraw（同一像素被画几次）、着色器复杂度直接相关，而且是平方级放大。
  3. 带宽与写回：采样纹理、读写 render target、混合、MSAA resolve、上屏。纹理越大、mipmap 越不规整、pass 越多，带宽越吃紧。移动端 GPU 是统一内存架构，带宽和功耗往往是第一瓶颈，而不是算力。

术语解释：

  • Overdraw（过度绘制）：同一个屏幕像素在一帧里被不同的三角形覆盖并着色多次。半透明物体、粒子、后处理全屏 pass 都会抬高 overdraw。
  • 带宽（bandwidth）：GPU 每帧从显存读写的字节数。片元着色器每采样一次纹理就产生一次读；每个全屏 pass 都要把整张图读一遍再写一遍。
  • 片元（fragment）：光栅化后、进入片元着色器之前的一个"候选像素"。它最终可能被深度测试丢弃，但着色往往已经发生了（早期深度测试能救一部分，但不是所有 GPU、所有着色器都享受这个优化）。

renderer.info：能读到什么，读不到什么 ​

renderer.info 是渲染器在 CPU 侧维护的计数器，读完不用装任何库：

js
const info = renderer.info
info.render.calls        // 本帧提交的 draw call 次数
info.render.triangles    // 本帧提交的三角形总数
info.render.points       // 点图元数量
info.render.lines        // 线段图元数量
info.memory.geometries   // 显存中的几何体缓冲份数
info.memory.textures     // 显存中的纹理份数
info.programs            // 已编译的着色器程序数量

必须同时记住它的三个边界：

  • 它是提交计数，不是执行结果。calls 统计的是 CPU 发出了多少次绘制命令，GPU 有没有画完、画了多少像素，它一概不知。
  • render.* 每次 renderer.render() 会自动清零（info.autoReset 默认为 true）。多 pass 场景要设 autoReset = false 并每帧手动 info.reset()，否则只能读到最后一个 pass 的数字。
  • 它没有时间字段。想知道 GPU 花了多少毫秒，得靠时间查询扩展或外部工具，不能指望 renderer.info。

THREE.Timer：delta 与 fps 的正确读法 ​

r186 起 THREE.Clock 已弃用，官方推荐 THREE.Timer。它有两个好处：一是基于 performance.now()，精度稳定；二是 connect(document) 后会跟随页面可见性暂停，切后台回来不会给出一个巨大的 delta：

js
const timer = new THREE.Timer()
timer.connect(document)

renderer.setAnimationLoop(() => {
  timer.update()                 // 每帧第一件事：推进计时器
  const dt = timer.getDelta()    // 距上一帧的秒数，用于动画
  const elapsed = timer.getElapsed()

  // 用 dt 做与帧率无关的动画
  mesh.rotation.y += dt * 0.8

  renderer.render(scene, camera)
})

注意两个纪律：

  • getDelta() 返回秒，不是毫秒。想要"当前帧率"应该是 1 / dt，但它只是瞬时值，抖动极大；稳定的 FPS 应该用"窗口内帧数 / 窗口时长"统计（本模块演示就是这么做的）。
  • dt 一定要截断上限，例如 Math.min(timer.getDelta(), 0.05)。切后台、系统卡顿、打断点都会让 dt 跳到几秒，直接乘进动画就是"瞬移"。

为什么 JS 帧与 GPU 帧会"错位" ​

真实管线是三级流水：JS 生产命令 → 驱动队列 → GPU 消费命令。同一时刻，CPU 可能已经在准备第 N+1 帧，而 GPU 还在画第 N 帧甚至第 N-1 帧。由此产生三个现象：

  1. render() 很快但画面仍卡：CPU 提交完了，GPU 还在排队。这时 renderer.info 的数字很漂亮，帧间隔却很大。
  2. 读数忽高忽低：驱动队列的长度会随负载波动，同一场景连续采样，帧间隔的方差可能比均值更有信息量。
  3. 测量"GPU 时间"没有直接 API：WebGL 不暴露每帧 GPU 耗时（除非用 EXT_disjoint_timer_query_webgl2 这类扩展）。工程上常用的近似是：
text
估算 GPU 时间 ≈ 帧间隔 − CPU 侧耗时

这个估算在 GPU 成为瓶颈时有效（帧间隔被 GPU 拉长）；但在垂直同步下，空载时帧间隔本来就是 16.6ms（显示器刷新节奏），减去 3ms JS 会得到"13ms GPU"的假象。所以它只能做相对比较：同一台机器、同一场景，开负载前后对比，而不是绝对值。

一句话：CPU 时间是"我花了多久说"，GPU 时间是"你花了多久做"。两者相加不等于帧时间，因为它们是流水线并行，不是串行。

常见误判：降 DPR 没用，可能根本不是像素瓶颈 ​

调优时最常犯的错，是拿一个"万能药"乱试。下面这张表把现象、真实原因和验证手段对应起来：

你做的动作没有改善，说明瓶颈在下一步验证
降低 setPixelRatioCPU 提交 / draw call / JS 逻辑看 calls 是否上千；把物体合并后再测
加了 InstancedMesh片元 / overdraw / 带宽关掉半透明与后处理，看帧时间是否下降
关掉阴影几何量 / 顶点处理 / JS看 triangles 是否百万级；看主线程火焰图
关掉后处理纹理带宽 / 显存不足看 memory.textures；换小纹理复测
换更小的模型材质切换 / 着色器编译 / GC看首次帧是否特别长；看 programs 数量

判断顺序建议固定为：先看 calls（CPU 提交）→ 再看 triangles（顶点）→ 再看分辨率与 overdraw（片元）→ 最后看纹理与带宽。这个顺序与"改动成本"一致：合并/实例化最容易，改美术资源最贵。

基线采集：让数字可复现 ​

性能数字最怕"每次都不一样"。一套最小可用的采集纪律：

项要求
场景固定模型、固定灯光、固定后处理开关（建议先全关）
相机固定位置与朝向；自动旋转要么关掉，要么固定角速度
预热先跑 2 秒，避开着色器编译、纹理首次上传、JIT 预热
采样500ms 一个窗口，连续采 3 个窗口取中位数
环境同一浏览器、同一设备、同电源模式；关 DevTools 录制
记录同时记 JS 均值、帧间隔均值、峰值、calls、triangles、DPR

只有基线稳定，"优化前 22ms、优化后 12ms"才是一句可信的话；否则你测到的可能只是后台更新、风扇转速或者电量策略。

代码示例 ​

对应演示 frame-budget-lab.html，核心是"同一场景、三种可叠加负载、两个读数"。下面按四段拆开。

① 三类负载，各自独立可开关：

js
// CPU 负载：每帧做大量矩阵与向量运算
function burnCpu(count) {
  for (let i = 0; i < count; i++) {
    cpuMat.makeRotationY(i * 0.0013)
    cpuVec.set(1, i * 0.0002, 2).applyMatrix4(cpuMat).normalize()
  }
}

// Draw call 负载：400 个独立 Mesh，visible 一切换就多 400 次提交
callGroup.visible = params.drawLoad

// GPU 负载：挂在相机上的全屏重着色面，只改采样循环次数
gpuMat.uniforms.uIter.value = params.gpuLoad ? params.gpuIterations : 1

三类负载必须错开验证，否则你永远不知道改善来自哪一项。演示里的 GPU 负载面挂在相机下、位于场景后方，只负责"背景像素"的片元着色，不遮挡主体——这样视觉变化小，读数变化大。

② 掐表：JS 段与帧间隔：

js
let frameStamp = performance.now()

renderer.setAnimationLoop(() => {
  timer.update()
  const frameStart = performance.now()

  // ... 负载与场景更新 ...
  controls.update()
  renderer.render(scene, camera)

  const jsMs = performance.now() - frameStart   // CPU 侧：脚本 + 提交
  const now = performance.now()
  samples.js += jsMs
  samples.interval += now - frameStamp          // 帧间隔：包含 GPU 与等待
  samples.frames++
  frameStamp = now
})

注意 frameStart 放在循环最开始、jsMs 取在 render() 返回之后：这样 JS 段包含"业务逻辑 + 场景更新 + 提交"，帧间隔则包含 GPU 执行与垂直同步等待。

③ 估算 GPU 段并做窗口平均：

js
const avgJs = samples.js / samples.frames
const avgInterval = samples.interval / samples.frames
const gpuEst = Math.max(0, avgInterval - avgJs)

每 600ms 刷新一次，避免数字跳动到无法阅读。不要用单帧数据：单帧的 performance.now() 精度、调度抖动、驱动队列长度都会让结果失真。

④ 两行条形图：基线 vs 当前：

js
// 空载时持续刷新基线；一旦叠加负载，基线冻结，当前值开始偏离
if (!params.cpuLoad && !params.drawLoad && !params.gpuLoad) {
  baseline.js = avgJs
  baseline.gpu = gpuEst
}

条形图以 16.6ms 为红线，把"JS 段"和"GPU 估算段"堆叠起来。开 CPU 负载时，青色段先变长；开 draw call 负载时，青色段也会变长（提交是 CPU 干的）；只有开 GPU 负载时，洋红段才会明显变长。三种负载各自的"指纹"，就是本篇要建立的直觉。

常见问题解答 ​

Q1：为什么 `renderer.render()` 只要 3ms，画面还是掉帧？

因为 render() 只统计 CPU 提交命令的时间，GPU 是异步执行的。3ms 提交完之后，GPU 可能还要 25ms 才画完这一帧，帧间隔自然被拉长。判断方法：看"帧间隔 − JS"是否明显变大；或用 Spector.js 抓一帧，看每个 draw call 的 GPU 耗时；也可以临时把分辨率降到 0.5 倍，如果帧率明显回升，瓶颈就在片元侧。千万不要用 render() 的耗时当作"这一帧的总成本"。

Q2：空载时估算 GPU 也有十几毫秒，是显卡太差吗？

多半是垂直同步。60Hz 屏幕下，即使 GPU 只用了 2ms，浏览器也会等到下一个刷新周期才上屏，帧间隔仍是 16.6ms；用"帧间隔 − JS"减出来自然是十几毫秒。这不是 GPU 慢，而是"等待显示器"。正确的用法是看相对变化：开 GPU 负载前后，估算值是否从 13ms 涨到 30ms；而不是看绝对值是否小于某个阈值。真要测绝对值，用 EXT_disjoint_timer_query_webgl2 或 Spector.js。

Q3：有没有办法拿到真实的 GPU 帧时间？

三条路：① EXT_disjoint_timer_query_webgl2——WebGL2 的时间查询扩展，可以括住一段绘制并异步读回纳秒级耗时，但部分浏览器/驱动出于安全与功耗考虑会禁用，必须做降级；② Spector.js——浏览器插件，抓一帧的完整命令流，逐 draw call 看状态、纹理、耗时，是定位"哪个物体最贵"的利器；③ Chrome DevTools 的 GPU 面板 / Performance 面板的 GPU 轨道——能看到合成、光栅化、纹理上传的大致分布。三者都拿不到时，就用本篇的"帧间隔 − JS"做相对比较，够用。

Q4：同一个页面，我的机器 60fps，同事的机器 30fps，是谁的问题？

先排除四个环境差异：① DPR——同事可能是 2x/3x 屏，像素量是你的 4~9 倍，片元成本按平方涨；② 浏览器与合成器——Safari 与 Chrome 的合成策略、色彩管理不同；③ 电源模式——笔记本省电模式会锁 GPU 频率；④ 后台标签页/其他占用——浏览器会降频 rAF。让同事打开演示页的读数面板，对比 triangles、calls 与分辨率；如果结构量一致但帧时间差一倍，基本就是像素量或 GPU 档次的差异。真机验收要按"目标用户最弱设备"来定，而不是开发机。

动手小练习 ​

  1. 只开 CPU 负载，把迭代次数从 4000 逐步拉到 120000，记录"JS 段"与"帧间隔"的曲线。找出 JS 段刚好超过 16.6ms 的那个点，解释此时为什么帧率会突然从 60 掉到 30（提示：垂直同步是整倍数跳变）。
  2. 同时打开 draw call 负载与 GPU 负载，再逐个关闭，观察条形图里"青色段"和"洋红段"各自如何变化。用一句话总结：怎么仅凭这两个读数判断该优化 CPU 还是 GPU。
  3. 把 renderer.setPixelRatio 从 1.75 改成 1 和 0.5，各测一次空载与 GPU 负载下的帧时间。记录"降 DPR 对 GPU 负载有效、对 draw call 负载几乎无效"的证据，并写进你的项目性能笔记。
