26.3 实战案例：性能治理工作台 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑯ 再学习本篇。

核心概念讲解 ​

接桥：把 ⑯ 的万级实例城市做成可诊断的标本 ​

在 ⑯ 大场景 · 万级实例城市 里，我们用 InstancedMesh + 分块剔除把上万栋楼塞进了一个 60fps 的城市。那是一个结果——它证明"这样做能跑"；但它没有回答"如果不用 Instancing，会差多少、差在哪一项"。

诊断需要对照组。本篇搭一个性能治理工作台：同一堆 1000 个盒子，用三条实现路径分别渲染——

路径draw calls几何显存典型来源
每个物体一个独立 Mesh1000共享 1 份几何体（很小）新手直写循环 scene.add(new Mesh(...))
InstancedMesh11 份几何体 + 每实例矩阵/颜色批量同构物体
合并几何（mergeGeometries）11000 份顶点数据压进一个缓冲静态装饰、地形碎片

三条路径画面几乎一样，账本完全不同。工作台的价值不是告诉你"用 Instancing"，而是让你在看到数字差距的那一刻，真正理解"draw call 是 CPU 的通话费、显存是 GPU 的地皮费"这两件事彼此独立。

先做减法：三条路径的成本结构 ​

① 独立 Mesh（坏实现）

每帧 CPU 要做三件事：遍历 1000 个对象、更新世界矩阵、为每个对象发一次 draw call。draw call 的固定开销（校验状态、绑定 VAO、提交 uniform、驱动排队）在桌面端约几十微秒，在移动端更贵。1000 次就是 5~15ms——光"说话"就花掉了半帧预算。

它的好处是逐个可控：每个物体能独立做动画、独立换材质、独立剔除。所以它并非永远错：物体数量在几百以内、或每个物体都需要独立逻辑时，独立 Mesh 的可维护性更高。

② InstancedMesh（批量同构的最优解）

一次提交画 N 份，实例差异走两块 per-instance 缓冲：instanceMatrix（每个实例 64 B）与 instanceColor（每个实例 12 B）。1000 个实例的额外显存约 76 KB，几乎可以忽略。GPU 在顶点着色器里按实例序号取矩阵，顶点数并不减少——省的是 CPU 提交，不是几何处理。

它的代价：所有实例共享一份几何体与一个材质，无法逐实例换材质/换贴图；视锥剔除是整体级的（要么全画、要么全不画）；每实例属性更新需要 needsUpdate，动态实例每帧上传整块缓冲。

③ 合并几何（静态场景的省事方案）

mergeGeometries 把 1000 个盒子的顶点（位置、法线、UV）烘焙进一个大 BufferGeometry，只提交一次。代价是顶点数据实打实地复制了 1000 份，显存从一份变成一千份；而且合并后无法再单独控制任何一个盒子（要动一个就得重建整块缓冲）。

一句话选型：要动 → Instancing；不动 → 合并；数量少或要独立逻辑 → 独立 Mesh。 三者不是"先进取代落后"，而是三种成本结构的选择。

真实项目里没有"单选"，只有配比 ​

工作台把三条路径做成互斥开关，是为了让差异看得清楚；真实项目里通常是混着用：

分层实现理由风险
近景主角、可交互物体独立 Mesh 或少量 InstancedMesh需要逐物体拾取、逐物体材质/动画数量一多就回到 1000 calls
中景同构物体（树、路灯、路人）按空间分块的 InstancedMesh1 次提交 + 分块后可剔除分块太多又会把 calls 拉回几百
远景静态装饰（楼群、围墙）合并几何一次提交画完，几乎零 CPU显存变大、无法单独修改
超远背景天空盒 / 贴图公告板只用几个三角形视差穿帮

配比的原则是"按可动性分层，而不是按数量分层"：会动的东西归实例化或独立对象，不会动的东西尽早烘焙合并。一个万级实例城市的典型配比是：2~3 个 InstancedMesh 分块负责楼群、1 个合并几何负责地面碎块、几十个独立 Mesh 负责可交互道具——总 calls 控制在 100 以内，而不是 10000。

双读数：结构量与实测帧时间 ​

治理工作台同时显示两组读数，缺一不可：

读数来源性质用途
draw calls / triangles / 几何字节renderer.info + 自己算结构量，与设备无关做 CI 硬门禁、横向对比实现
FPS / 帧时间 / 峰值rAF 间隔采样体验量，与设备强相关判断用户是否真的感受到卡

只看结构量会陷入"数字好看但用户还卡"；只看帧时间会陷入"换台机器就复现不了"。结构量负责"是否退化"，帧时间负责"是否够用"。

还有一条采样纪律常被忽略：切换实现后必须重置采样窗口。旧的 500ms 窗口里还混着上一模式的帧，直接平均会把两组数据搅在一起。工作台的做法是切模式时把"帧计数、帧时间累计、窗口起点"全部清零，等新窗口攒够 700ms 再出数——否则你会看到"切到 InstancedMesh 后 FPS 只涨了一半"这种假象。

几何字节要自己算，因为 renderer.info.memory 只给份数不给字节：

js
function geomBytes(g) {
  let bytes = g.index ? g.index.array.byteLength : 0
  for (const key in g.attributes) bytes += g.attributes[key].array.byteLength
  return bytes
}

// InstancedMesh 还要加上每实例缓冲
const instBytes = geomBytes(boxGeo)
  + mesh.instanceMatrix.array.byteLength
  + (mesh.instanceColor ? mesh.instanceColor.array.byteLength : 0)

性能治理 SOP：五步闭环 ​

性能治理最怕"边猜边改"。把它固化成五步，每次只动一个变量：

步骤做什么产出工具
① 测基线固定场景/相机/后处理，预热 2s，采 3 个 500ms 窗口取中位数一张基线表26.1 的采集纪律
② 定位维度按 calls → triangles → 片元/overdraw → 带宽/显存 的顺序排除一句"瓶颈在 X"renderer.info + 26.2 的热力图
③ 单项改造一次只改一项：合并、实例化、降 DPR、关一个 Pass一个可回滚的提交版本控制
④ 回归对照同机同场景复测，对比基线表；同时看峰值帧时间改造前后对照表工作台三条路径
⑤ 固化门禁把结构量写成断言，进 CI；帧时间做趋势告警一条自动化红线20.2 的 Playwright

这套 SOP 的关键在 ② 和 ③：先证明瓶颈在哪，再动手；一次只动一个变量，才知道收益归谁。工作台的三条路径就是 ③ 的"单项改造"演示——除了实现方式，其他一切不变。

读表：三组读数组合各自说明什么 ​

工作台的三项读数会组合出不同的"病情"，每一种对应不同的动作：

组合判断第一个动作
calls 高、triangles 低CPU 提交通道堵了实例化 / 合并 / 分块
calls 低、triangles 高顶点阶段吃紧换低模、LOD、减少分段数
两者都低、FPS 仍低片元 / 带宽 / 后处理降 DPR、查 overdraw、数 Pass
calls 正常、显存飙升纹理或大缓冲查 info.memory、上 KTX2
FPS 均值好看、峰值很高GC / 着色器编译 / 纹理上传看 Performance 火焰图找尖峰

这张表的用法是"先看两列结构量，再看体验量"：结构量解释"为什么慢"，体验量解释"慢到什么程度"。两者一致时，优化方向明确；不一致时（比如结构量都很漂亮但用户喊卡），问题通常在片元、带宽或主线程 JS，需要回到 26.1 的时间线拆解。

把读数固化成 CI 断言 ​

呼应 ⑳ 测试与质量：结构量在软件渲染（SwiftShader）下依然准确，最适合做硬门禁：

js
// Playwright 里读页面暴露的读数，做结构断言
const info = await page.evaluate(() => ({
  calls: window.__renderInfo.render.calls,
  tris: window.__renderInfo.render.triangles,
  textures: window.__renderInfo.memory.textures
}))

expect(info.calls).toBeLessThan(500)     // 中端机 draw call 红线
expect(info.tris).toBeLessThan(1_000_000)
expect(info.textures).toBeLessThan(80)

三条纪律：① 门禁卡结构量，不卡绝对帧时间（CI 虚机没有 GPU，帧时间不可比）；② 阈值按"目标设备最弱一档"的 70%~80% 定；③ 每次构建把 calls / tris / 纹理数 记进趋势库，"连续三次上涨 20%"告警，比单次超线更早发现问题。

落地检查：把对照实验搬进真实项目 ​

工作台是实验室，真实项目要做的是把结论变成纪律。交付前至少过三关：

  1. 可动性清单：把所有物体分成"会动 / 不会动"两列。会动的走 InstancedMesh 或独立 Mesh，不会动的在构建期合并。清单落进 README，新人加物体时照表执行，避免"随手 new Mesh 又加了一千个 calls"。
  2. 分块检查：每个 InstancedMesh 的包围球是否覆盖整个场景？如果是，它就永远无法被剔除。按街区/楼层拆成多个实例对象，让相机转开时能整块跳过。
  3. 纹理登记表：每张大纹理登记尺寸、格式、是否 KTX2、是否有 mipmap。4096 的未压缩图一张就 89MB，十张就是 890MB——这张表能在美术交付前拦住显存炸弹。

三关都过之后，再把结构量写进 CI 门禁，性能才从"事后救火"变成"事前约束"。

代码示例 ​

对应演示 drawcall-budget-lab.html，1000 个盒子、三条路径、三项读数。

① 位置只算一次，三条路径共用：

js
const COLS = 32
const dummy = new THREE.Object3D()

function place(i) {
  const col = i % COLS
  const row = Math.floor(i / COLS)
  dummy.position.set(
    (col - (COLS - 1) / 2) * 0.95,
    0.42,
    (row - (COLS - 1) / 2) * 0.95
  )
  dummy.rotation.set(0, (i % 5) * 0.12, 0)
  dummy.updateMatrix()
}

三条路径读同一张"位置表"，保证对照公平——差异只能来自实现方式。

② 独立 Mesh：1000 次提交：

js
function buildMeshMode(count) {
  const group = new THREE.Group()
  for (let i = 0; i < count; i++) {
    place(i)
    const m = new THREE.Mesh(BOX, SHARED_MAT)
    m.position.copy(dummy.position)
    m.rotation.copy(dummy.rotation)
    m.frustumCulled = false // 让 calls 恒定为 count，方便横向比较
    group.add(m)
  }
  return group
}

frustumCulled = false 是为了让读数干净：相机一转、部分盒子出画，draw call 就会掉到 700 多，对照就失去意义。真实项目里当然要保留剔除，但做基准测试时要控制变量。

③ InstancedMesh：1 次提交 + 两块实例缓冲：

js
function buildInstancedMode(count) {
  const mesh = new THREE.InstancedMesh(BOX, SHARED_MAT, count)
  mesh.frustumCulled = false
  for (let i = 0; i < count; i++) {
    place(i)
    mesh.setMatrixAt(i, dummy.matrix)
    mesh.setColorAt(i, color.setHSL(0.56 + (i % 40) / 200, 0.62, 0.6))
  }
  mesh.instanceMatrix.needsUpdate = true
  if (mesh.instanceColor) mesh.instanceColor.needsUpdate = true
  return mesh
}

④ 合并几何：1 次提交 + 大缓冲：

js
function buildMergedMode(count) {
  const parts = []
  for (let i = 0; i < count; i++) {
    place(i)
    const g = BOX.clone()
    g.applyMatrix4(dummy.matrix)   // 把世界矩阵烘焙进顶点
    parts.push(g)
  }
  const merged = mergeGeometries(parts)
  parts.forEach(p => p.dispose())   // 中间克隆立即释放
  merged.computeVertexNormals()
  return new THREE.Mesh(merged, SHARED_MAT)
}

合并完成后一定要释放中间的 parts：不释放的话，JS 侧还挂着一千份几何体数据，info.memory.geometries 也不会下降，看起来像是"合并反而更占内存"。

⑤ 读数：切模式时保留各路径的最近一次成绩：

js
statsByMode[currentKey] = {
  calls: String(info.render.calls),
  mem: fmtBytes(currentMem),
  fps: Math.round(fps) + ' / ' + ms.toFixed(1) + 'ms'
}
refreshTable()   // 三行表格：当前行高亮，其余保留上次读数

只显示"当前"没有比较意义；保留每条路径的最近读数，才能横向看出"省了多少 calls、花了多少显存、换回多少帧"。表格还有一个隐藏作用：它是回归对照的锚点——优化前先截一张表，改完再截一张，两张表放在 PR 描述里，"省了 999 次提交、多花 76KB"就是最有说服力的验收证据。

常见问题解答 ​

Q1：为什么我用了 InstancedMesh，反而比独立 Mesh 还慢？

四个常见原因：① 实例太少——20 个物体做实例化，省的 19 次提交还不够抵消 needsUpdate 与实例缓冲上传的成本，收益为负；② 每帧改实例矩阵——每帧 setMatrixAt + needsUpdate 会把整块实例缓冲重新上传，1000 个实例就是 64KB/帧的额外带宽，而独立 Mesh 只改变换矩阵；③ 材质/着色器不兼容——InstancedMesh 要求材质支持实例化属性，自定义 ShaderMaterial 忘记处理 instanceMatrix 会退化成普通绘制甚至报错；④ 视锥剔除失效——一个 InstancedMesh 只有一个包围球，它覆盖整个场景，相机随便转都不会被剔除，结果"总是全画"，反而不如独立 Mesh 能剔掉一半。对策：按空间分块成多个 InstancedMesh，或手动收窄 boundingSphere。

Q2：合并几何明明只提交一次，为什么显存反而最大？

因为合并不共享顶点。1000 个盒子合并后，顶点缓冲里真的躺着 1000 份盒子的顶点数据（每份约 900 B），总计约 0.9MB；而独立 Mesh 模式里 1000 个 Mesh 共用同一个 BoxGeometry，显存里只有一份。所以三条路径的账本是：独立 Mesh 的代价在 CPU 提交，合并的代价在 显存与顶点处理，InstancedMesh 则用几十 KB 的实例缓冲换掉一千次提交，是三者中性价比最高的一档。合并适合"静态、只画一次、顶点数不大"的装饰物；如果几何体本身很重（几十万顶点），合并会把显存和顶点带宽一起放大，不如实例化。

Q3：移动端 GPU 和桌面差在哪，为什么同样的读数体验完全不同？

三点结构性差异：① 统一内存架构——移动端 CPU/GPU 共享内存与带宽，后处理链、大纹理采样会直接抢走 CPU 的带宽，桌面端有独立显存；② 瓦片式渲染（TBR）——移动 GPU 先把屏幕分块、在片上缓存里完成着色，overdraw 的代价被"每瓦片"放大，全屏半透明与多 Pass 比桌面更致命；③ 功耗与降频——手机跑满 2 分钟后会因发热降频，前 10 秒的 60fps 不代表稳定 60fps。所以移动端验收要看：draw calls 控制在 500 内、避免大面积透明、后处理不超过 2 段、纹理尽量 KTX2，并且要连续跑 3 分钟看是否掉帧。桌面端的数字只能作为参考上限。

Q4：工作台里三种实现的 triangles 为什么完全一样？

因为三角形数量由几何本身决定，三种实现都画 1000 个盒子（每个 12 个三角形），总数恒为 12000。Instancing 与合并省的只是"提交次数"和"缓冲布局"，不减少顶点与三角形。这恰好说明一个重要分工：calls 归 CPU、triangles 归顶点阶段、overdraw/带宽 归片元阶段，三者要分开治理。想降低 triangles，只能换低模、做 LOD 或剔除——那是 16.2 的课题。

Q5：合并几何之后，想单独移动其中一个盒子怎么办？

只能重建整块缓冲，或者从一开始就别合并它。合并是"烘焙"：位置、旋转、颜色全部写进顶点，运行时改动没有意义。工程上的折中是按可动性分组——把需要独立移动的物体留在独立 Mesh 或 InstancedMesh 里，只合并真正永久静止的装饰件（围墙、地砖、远景楼群）。如果只有零星几个物体要动，也可以合并其余部分，把这几件单独列出来，代价只是多几次 draw call。

动手小练习 ​

  1. 把盒子数量拉到 2000，记录三种实现的 calls、几何显存、FPS，画一张对照表。再用 performance.now() 粗略测 renderer.render() 的耗时，验证"独立 Mesh 慢在提交、合并慢在缓冲"。
  2. 给 InstancedMesh 模式加一个"每帧随机抖动实例矩阵"的开关，对比开启前后 FPS 与帧时间。解释为什么动态实例的带宽成本比静态实例高。
  3. 参照本篇的 CI 断言片段，为工作台写一条最小门禁：calls < 10、triangles === 12000、textures === 0。想想为什么"几何显存"不适合做硬门禁（提示：它随盒子数量线性增长，阈值要跟着配置走）。
