35.3 实战案例：可保存的迷你场景编辑器 ​

核心概念讲解 ​

接桥：㉝ 的多端交付需要"内容生产端"，编辑器就是那个入口 ​

㉝ 跨端与框架广度 讲的是"一套内容，多端呈现"：大屏、平板、H5、甚至小程序壳，都在消费同一份场景数据。那篇里已经有一个隐含前提——内容从哪来？

如果每个端都像 21 篇那样在代码里写死楼栋坐标，那么"多端"只是把同一份硬编码复制了四遍。真正可交付的跨端方案必须有两条流水线：

  • 运行时（runtime）：负责渲染、交互、适配不同屏幕与输入方式；
  • 生产端（authoring）：负责摆放、调色、增删内容，输出可复用的场景数据。

这个"生产端"就是本篇要写的迷你场景编辑器。它不追求 Maya、Blender 那样的完整度，但必须闭环：能加、能选、能拖、能改、能删、能撤销、能存、能读、能导出、能容错。把这个闭环跑通，你就拥有了一个可以交给美术和运营的最小工具，也拥有了 35.1 与 35.2 所有知识点的落地容器。

产品结构：三栏布局 ​

迷你编辑器采用最经典的三栏结构：

区域职责本案例实现
左栏 · 资源库提供"可以添加什么"方块 / 球体 / 圆柱 / 圆锥 / 圆环，缩略图程序化绘制
中栏 · 视口选择、拖拽、观察Three.js canvas + OrbitControls + TransformControls + BoxHelper
右栏 · 属性面板编辑当前选中对象名称、颜色、尺寸、XYZ 位置、删除按钮

三栏之外还有一条顶栏，放全局动作：撤销、重做、保存、读取、导入、导出、重置。顶栏和右栏的按钮不是"装饰"，它们共享同一套命令栈与同一份场景数据，任何入口改完都必须走同一个 refreshUI()。

布局用 CSS Grid 一行就能定骨架：

css
.editor {
  display: grid;
  grid-template-columns: 160px minmax(0, 1fr) 230px;
  height: calc(100vh - 46px);
}

minmax(0, 1fr) 里的 0 很重要。默认的 1fr 最小尺寸是 auto，当视口里的 canvas 或长文本撑开时，中间栏会把左右栏挤扁。写成 minmax(0, 1fr)，中间栏才允许真正收缩。

窄屏时把三栏改成三行：资源库横向滚动、视口占中间、属性面板置底。编辑器是生产工具，桌面优先是合理的，但至少要让平板上能完成"选—拖—改"。

数据流：一次点击经过哪些层 ​

以"从资源库添加一个方块"为例，完整链路是：

  1. 点击资源库按钮，调用 addFromLibrary('box')；
  2. 工厂根据类型创建 Mesh，分配 id、名称、默认颜色与出生位置；
  3. 包装成 AddCommand，交给 execute()；
  4. execute() 执行 do()、压入撤销栈、清空重做栈；
  5. select(mesh) 把新对象设为当前选中；
  6. refreshUI() 更新包围盒、gizmo、属性面板、顶栏按钮状态与统计；
  7. 用户点"保存"时，serialize() 遍历节点，输出最小 JSON 并写入 localStorage。

这条链路里有两个纪律：

  • 所有修改都走命令。包括颜色、尺寸、位置输入，也包括删除。这样撤销栈才是完整的。
  • 所有 UI 都从状态派生。属性面板不缓存"上一次的颜色"，按钮的禁用态不自己维护计数器，全部读 selected、undoStack.length、redoStack.length。

输入框的提交时机：input、change 与 blur ​

这是编辑器手感的关键细节，也是最容易做出 bug 的地方。

事件触发时机适合做什么
input每次值变化（拖动滑杆、输入数字）实时预览：改材质颜色、改缩放、改位置
change值"确定"（失焦、回车、滑杆松开）提交一条命令，写入撤销栈
focus / pointerdown开始编辑拍一张"前"快照，作为命令的 before

正确姿势是"input 预览，change 提交"：

js
let editBefore = null
let editColor = null

pColor.addEventListener('focus', () => {
  editBefore = capture(selected)
  editColor = '#' + selected.material.color.getHexString()
})

pColor.addEventListener('input', () => {
  selected.material.color.set(pColor.value)   // 只改视图，不写历史
})

pColor.addEventListener('change', () => {
  const after = '#' + selected.material.color.getHexString()
  if (editColor !== after) execColor(selected, editColor, after)
})

如果反过来，在 input 里提交命令，用户选一次颜色会生成几十条 MaterialCommand，撤销一次只退一个色相，体验灾难。数字输入框同理：每敲一个字符都进栈，按一次撤销只删掉一个数字。

还有几个配套细节：

  • 数字步进：step="0.1" 让上下箭头和滚轮有明确粒度；不要用 step="any"，否则用户很难精确调到 1.20。
  • 非法输入：parseFloat 得到 NaN 时直接忽略，不要把 NaN 写进 position，否则整个矩阵会变成 NaN，物体瞬间消失。
  • 范围钳制：位置限制在 ±40，尺寸限制在 0.2~4，既防止误操作把物体丢到天边，也避免极端缩放导致阴影/包围盒异常。
  • 连续编辑的基线：提交命令后，把"前"快照重置为当前值，再继续步进时才能正确合并。

资源库：程序化几何缩略图 ​

本案例的资源库不加载任何外部模型，缩略图用 Canvas 2D 程序化绘制：方块画等轴测三个面，球体画径向渐变，圆柱画上下椭圆，圆锥画三角形加底椭圆，圆环用椭圆描边。

这样做有三个好处：

  1. 零网络请求：演示页可以单文件运行，断网也能展示；
  2. 体积可控：没有 GLB、没有贴图，整个 HTML 只有几十 KB；
  3. 可控的视觉一致性：所有缩略图用同一套调色板，暗色背景下不会出现"某张图特别亮"的违和感。

真实项目里，资源库通常会换成 glTF 缩略图：后台渲染一次，缓存成图片；或者用 WebGLRenderTarget 实时渲染小图。那时要考虑资源加载失败、缩略图缓存、模型 LOD 等问题。迷你编辑器的目标是先把"添加—选中—变换"的闭环跑通，而不是先做资产管线。

删除、撤销与"对象不能立刻销毁" ​

删除一个物体时，为了支持撤销，不能立刻 dispose() 它的几何与材质：

js
const cmd = {
  do() { scene.remove(obj); nodes.splice(index, 1) },
  undo() { scene.add(obj); nodes.splice(index, 0, obj) }
}

对象被移出场景，但引用仍被命令持有；撤销时把它原样插回原索引，父子关系、材质、几何都还在。只有当命令被历史淘汰、场景被重置或重新加载时，才真正释放：

js
mesh.geometry.dispose()
mesh.material.dispose()

反过来说，如果每次删除都 dispose，撤销时就得重新创建几何与材质，不仅慢，还会丢失用户改过的颜色与缩放。"删除"在编辑器里是逻辑删除，不是资源销毁。

保存到 localStorage：简单，但有边界 ​

localStorage 的 API 只有四行，但它有四个现实约束：

约束表现应对
容量约 5MB（各浏览器不同）大场景或内嵌图片会写失败只存最小 JSON；捕获 QuotaExceededError
同步阻塞写入大字符串会卡主线程场景小没问题；大场景改用 IndexedDB
同源隔离换域名/端口/协议读不到存档 key 里带版本号，并提示用户导出文件
隐私模式/被禁用读写抛异常try/catch，失败时降级为"仅内存"并提示

本案例的 key 是 mini-scene-editor:v1，结构是 { version: 1, nodes: [...] }。刷新页面时优先读它；读失败或 JSON 损坏时，清除坏存档并回退到默认场景，绝不让页面白屏。

保存成功要给出反馈（toast："已保存 N 个物体"），保存失败也要给明确原因（"存储已满或不可用"）。静默失败是编辑器最糟糕的体验——用户以为存了，刷新后全没了。

导入与导出：JSON 是跨端交接合同 ​

导出用 Blob + URL.createObjectURL + 临时 <a download>：

js
const text = JSON.stringify(serialize(), null, 2)
const blob = new Blob([text], { type: 'application/json' })
const url = URL.createObjectURL(blob)
const link = document.createElement('a')
link.href = url
link.download = 'mini-scene.json'
link.click()
URL.revokeObjectURL(url)

导入用 <input type="file" accept=".json,application/json"> + file.text()，不要用 fetch('file://...')——浏览器会因同源策略拒绝本地文件。

导入必须假设"文件是坏的"。校验顺序建议是：

  1. 文件大小上限（比如 2MB），防止解析超大文件卡死；
  2. JSON.parse 包在 try/catch 里，失败提示"不是合法 JSON"；
  3. 根必须是对象，nodes 必须是数组；
  4. version 不能高于当前支持版本；
  5. 节点数量上限（比如 200），防止一次导入把页面拖垮；
  6. 类型白名单，未知类型跳过；
  7. 坐标必须是有限数字，颜色必须是合法十六进制，缩放钳制到合理范围；
  8. id 冲突时重新分配，并推进 id 序号。

坏 JSON 不能崩：所有错误都收敛成一条 toast，当前场景保持不变。用户导入失败最多是"没成功"，不能是"当前作品也没了"。

js
try {
  const specs = parseScene(await file.text())   // 先完整解析、校验
  applyData(specs)                              // 校验通过才清空旧场景
  toast(`已导入 ${nodes.length} 个物体`)
} catch (err) {
  toast(`导入失败：${err.message}`, true)
}

注意第 2 行与第 3 行的顺序：先解析，后清场。如果先 clearSceneNodes() 再解析，一旦解析失败，用户原来的场景已经被你删了。

容错与可用性清单 ​

一个"能演示"的编辑器和"能交付"的编辑器，差距往往在这些不起眼的地方：

  • 没有选中时，属性面板显示空状态，而不是一堆禁用但看不懂的输入框；
  • 删除按钮在没有选中时禁用，而不是点了没反应；
  • 撤销/重做按钮的禁用态与栈长度严格同步；
  • 输入框失焦时提交，回车也提交，且不会重复提交；
  • 颜色选择器支持实时预览，取消选择时能回到原色；
  • 导入失败保留原场景，保存失败明确提示；
  • 重置操作在正式产品里应二次确认，演示页为了流畅省略了确认；
  • 节点数量、文件大小、坐标范围都有上限；
  • 移动端把三栏堆叠，按钮可横向滚动，不依赖悬停。

快捷键 ​

快捷键行为备注
Ctrl/Cmd + Z撤销输入框聚焦时交给浏览器原生撤销
Ctrl/Cmd + Shift + Z重做部分平台也支持 Ctrl + Y
Ctrl/Cmd + S保存到 localStorage阻止浏览器"保存网页"
Delete / Backspace删除选中输入框聚焦时跳过
Esc取消选中同时 detach gizmo

快捷键的第一原则仍然是不要和输入框抢事件。第二原则是不要在 keydown 里直接改场景，而是调用与按钮相同的函数（doUndo()、deleteSelected()），保证所有入口共享同一套命令与 UI 刷新。

三个常见坑 ​

  1. 保存成功但刷新没恢复。常见原因是保存到了 sessionStorage、key 不一致、或者读取时被旧版本 JSON 的校验挡住。先确认 key 与版本号，再确认读取逻辑真的在初始化时执行。
  2. 拖动尺寸滑杆产生几十条历史。根因是在 input 里提交命令。改成 input 只预览、change 才提交，并用"按下时拍快照"的基线合并连续操作。
  3. 导入坏文件把页面搞白。根因是先清空再解析，或者直接信任 data.nodes 的类型。坚持"先校验、后清场、再重建"，并把所有异常收敛到 toast。

② 添加物体与命令：创建、入栈、选中、刷新，四步不能少：

js
function addFromLibrary(type) {
  const spec = {
    type,
    id: nextId(),
    name: `${TYPE_DEFS[type].name} ${nameSeq++}`,
    color: TYPE_DEFS[type].color,
    position: nextSpot(TYPE_DEFS[type].height),
    quaternion: [0, 0, 0, 1],
    scale: 1
  }
  const mesh = buildNode(spec)
  execute({
    type: 'add',
    name: 'AddCommand',
    obj: mesh,
    do() { scene.add(mesh); nodes.push(mesh) },
    undo() { scene.remove(mesh); nodes.splice(nodes.indexOf(mesh), 1) }
  })
  select(mesh)
}

③ 校验后再清场：parseScene 只返回"可重建的最小描述"，不碰场景：

js
function importText(text) {
  try {
    const specs = parseScene(text)
    applyData(specs)                 // 此时才清空旧场景
    toast(`已导入 ${nodes.length} 个物体`)
  } catch (err) {
    toast(`导入失败：${err.message}`, true)  // 旧场景保持不变
  }
}

④ 保存与自动恢复：写入时捕获异常，读取时也捕获异常：

js
function saveLocal() {
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(serialize()))
    toast(`已保存 ${nodes.length} 个物体`)
  } catch (err) {
    toast(`保存失败：${err.message}`, true)
  }
}

// 启动时
let restored = false
try {
  const raw = localStorage.getItem(STORAGE_KEY)
  if (raw) {
    applyData(parseScene(raw))
    restored = true
  }
} catch (err) {
  localStorage.removeItem(STORAGE_KEY)   // 坏存档直接丢弃
}
if (!restored) buildDefaults()

常见问题解答 ​

Q1：导出的 JSON 换台机器打不开，是格式不兼容吗？

JSON 本身是纯文本，换机器不影响读取。真正导致"打不开"的通常是四类原因：

  1. 资产路径失效。本案例只有程序化几何，JSON 自带颜色与变换，理论上换机器就能用；但如果你的项目把贴图 / 模型存成相对路径（如 "src": "/assets/wood.jpg"），换一台机器或换一个部署目录，路径就找不到。
  2. 版本不匹配。新编辑器导出的 version: 2 被旧编辑器读取，旧代码只认识 v1，直接报错。应该在校验阶段明确提示"版本过新，请升级编辑器"，而不是静默失败。
  3. 编辑器类型白名单不同。文件里有 cone，但目标编辑器只注册了 box 和 sphere，节点会被跳过，看起来像"打开是空的"。
  4. 打开方式不对。双击 JSON 文件默认用文本编辑器打开，不会启动你的编辑器。需要先启动编辑器，再通过"导入"选择文件。

排查顺序：先用文本编辑器确认 JSON 能被解析，再看 version、nodes 里的 type 与资源路径，最后确认导入流程是不是 try/catch 把所有错误吞掉了。

Q2：点了保存，刷新后却没有恢复，localStorage 哪里出了问题？

按这个清单排查：

  • key 是否一致。保存用 mini-scene-editor:v1，读取却用了 mini-editor，这是最常见的低级错误。
  • 是否写进了 sessionStorage。sessionStorage 关标签页就没了，刷新有时还在、重开就消失，容易误判。
  • 是否被隐私模式/浏览器策略禁用。某些环境下 localStorage.setItem 会抛 QuotaExceededError 或 SecurityError，而代码里没有 try/catch，保存其实失败了。
  • 读取是否在初始化时执行。有些实现把恢复逻辑写在按钮回调里，刷新自然不会自动加载。
  • 存档是否被校验逻辑丢弃。旧版本 JSON 缺少 nodes 或 version 过高，解析失败后代码可能直接 removeItem，表现为"每次都从默认场景开始"。

演示页的启动顺序是：先读 localStorage → 解析校验 → 成功则恢复，失败则清坏档 → 回退默认场景，并在成功时弹一条"已恢复"的 toast。照着这个顺序对照你的实现即可。

Q3：在数字输入框里改位置，为什么每敲一个字符就多一条撤销记录？

因为你在 input 事件里提交了命令。数字输入框每敲一个字符都会触发 input，-1 会先经过 -、-1，每一步都进栈。

正确做法：

  • focus 时拍一张"前"快照；
  • input 只更新对象，不写历史；
  • change（失焦或回车）时比较前后值，有变化才提交一条 TransformCommand；
  • 提交后把"前"快照重置为当前值，支持用户继续用上下箭头步进；
  • 如果连续步进仍然产生多条，用"同一对象 + 800ms 窗口"的合并规则兜底。

还要注意：Ctrl/Cmd + Z 在输入框聚焦时应该交还给浏览器原生撤销，不要抢过来去撤销场景。否则用户想撤销刚输入的数字，结果把上一步拖拽撤销了。

Q4：导入一个坏 JSON 会不会把当前场景搞没？怎样做到不崩？

关键是先校验、后清场。任何"先清空场景再解析"的顺序都是危险的：

js
const specs = parseScene(text)   // 失败会 throw，此时场景还没动
applyData(specs)                 // 只有成功才清空重建

parseScene 内部要覆盖这些情况：

  • JSON.parse 失败 → "不是合法 JSON"；
  • 根不是对象 / nodes 不是数组 → "结构不合法"；
  • 版本过新 → "请升级编辑器"；
  • 节点不是对象、type 未知 → 跳过该节点，不整体失败；
  • 坐标是 NaN / Infinity → 回退默认值；
  • 颜色非法 → 回退默认色；
  • id 重复 → 重新分配；
  • 节点超过上限 → 截断并提示。

最后用 try/catch 把所有异常收敛成一条 toast。用户最多看到"导入失败：原因"，当前场景原封不动。容错不是让坏数据变得正确，而是让坏数据不产生破坏。

Q5：为什么资源库不用 glTF 模型，而要用程序化几何？

本案例的目标是演示编辑器的数据流与交互闭环，不是资产管线。程序化几何有三个直接优势：

  • 零外部请求，单文件可运行，断网也能展示；
  • 体积小，加载快，不会因为模型路径 404 让整个演示卡住；
  • 几何参数明确，序列化只需要 type + scale，不用处理模型内部的骨骼、动画、材质槽。

真实项目里换成 glTF 之后，需要额外处理：模型加载器与缓存、缩略图渲染、材质替换、动画状态、LOD、 Draco 压缩、跨域与路径。这些都属于"资产系统"的范畴，可以在闭环跑通之后逐步替换，而不是一开始就把复杂度堆上来。

如果要做迁移，建议保留"节点类型 → 工厂函数"的抽象，把 type: 'box' 换成 type: 'lamp' 并让工厂去加载 /models/lamp.glb，上层的选择、变换、撤销、序列化逻辑都不用改。

动手小练习 ​

  1. 给编辑器加一个"复制选中物体"按钮：复制时生成新 id、位置偏移 0.6，并作为一条 DuplicateCommand 入栈；要求撤销后副本完全消失，重做后原样出现。
  2. 给属性面板加一个"旋转 Y"输入框（角度制），提交时转成四元数写回对象。要求与 gizmo 的旋转操作共享同一个 TransformCommand，并能正确合并。
  3. 把 localStorage 换成 IndexedDB，保存多个命名存档（默认 / 草稿 / 版本 A），并在顶栏加一个下拉框切换。要求切换存档时清空撤销栈，坏存档不影响其他存档。
