35.1 基础入门：选择、变换操控与 gizmo ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ②⑤ 再阅读。

核心概念讲解 ​

接桥：㉑ 的园区是"写死的"，编辑器要让人现场摆 ​

在 ㉑ 大屏与数字孪生 的实战里，63 栋楼是这样长出来的：

js
for (let r = 0; r < ROWS; r++)
  for (let c = 0; c < COLS; c++)
    buildings.push({ x: (c - (COLS - 1) / 2) * GAP, z: (r - (ROWS - 1) / 2) * GAP, h: 4 + Math.random() * 14 })

这段代码很漂亮，但它把布局决策写死在了源码里。想把 A 栋楼往东挪两个车位、想让广场中央的水景换成雕塑、想给某栋楼单独换一种材质——都得回到编辑器里改常量、重新构建、重新部署。对于演示够用，对于一个真正要交付给运营和美术的系统就不够了。

数字孪生的运营方通常不是程序员。他们需要的是现场摆：在视口里点一下楼、拖到新位置、改个颜色、存盘，第二天大屏刷新就生效。这就是"内容生产端"的需求，也是本模块的主题：场景编辑器。

编辑器不是另一个渲染器。它仍然用同一套 Three.js 场景图，只是在场景图之上又加了三层"编辑能力"：知道当前在操作谁（选中态）、把手势翻译成变换（操控器）、把内存里的状态变成可保存的数据（序列化）。这一篇先把前三层讲透，序列化留给 35.2，组装成完整产品留给 35.3。

编辑器的四块拼图 ​

把任何三维编辑器拆开，核心都不外乎四件事：

拼图回答的问题本篇落点
场景图场景里有哪些对象、谁是谁的子节点Object3D 树 + userData 标记可编辑根节点
选中态当前操作的是哪一个（或哪几个）对象selected 引用 + 包围盒高亮
操控器鼠标拖拽如何变成 position / rotation / scaleTransformControls 的平移 / 旋转 / 缩放 gizmo
序列化如何把场景存下来、下次原样恢复35.2 的最小 JSON 描述

术语解释：

  • gizmo：视口里的那组彩色箭头、圆环、方块，用来拖动对象。它本身不是被编辑对象，只是一组"手柄"。
  • 可编辑根节点：真正参与变换与保存的节点。一个路灯由灯杆、灯头、底座组成，编辑时应该整体选中"路灯 Group"，而不是单独选中灯头。
  • 选中态：编辑器内部"当前操作目标"的状态，通常是一个 id 或对象引用，而不是依赖"某个材质变黄了"这种副作用。

这四块拼图有一个隐含顺序：先有场景图，才有可编辑对象；先有选中态，操控器才知道该挂到谁身上；先有稳定的数据描述，序列化才不会把 GPU 资源一起写进 JSON。很多编辑器写着写着就乱了，往往是因为顺序反了——先做了漂亮的工具栏，却没有统一的选中态。

选中态不是高亮，而是编辑器的"当前指针" ​

初学者容易把"选中"实现成"把材质颜色改成黄色"，然后所有操作再去读材质颜色。这样做的后果是：取消选中时不知道该恢复成什么颜色；同一材质被多个物体共享时，选一个全变黄；撤销一步之后，高亮和真实状态对不上。

正确的做法是把选中态当成一个独立的状态变量：

js
let selected = null          // 单选的简化模型
// 多选时：const selected = new Set()

function select(root) {
  selected = root || null
  transform.detach()
  boxHelper.visible = false
  if (!selected) return
  transform.attach(selected)
  boxHelper.setFromObject(selected)
  boxHelper.visible = true
}

所有"改物体"的命令都先读 selected，再决定操作对象；所有高亮都从 selected 派生出来。这样做的收益是：撤销、重做、删除、保存，全都只需要关心一个状态源，而不是满场景找"哪个物体被染黄了"。

工程上还可以再进一步，把选中态收进一个数据模型：selection = { ids: ['n3'], hovered: 'n7' }，Three.js 对象只是这个模型的视图。这样即使对象被重建（比如反序列化之后），选中态也能靠 id 恢复。35.2 会把这条"单一数据源"的线讲完。

TransformControls：把拖拽翻译成 TRS ​

TransformControls 是 Three.js 官方提供的操控器。它的职责非常单一：把鼠标在 gizmo 上的拖拽，翻译成被附着对象的 position / quaternion / scale 变化。

js
import { TransformControls } from 'three/addons/controls/TransformControls.js'

const transform = new TransformControls(camera, renderer.domElement)
scene.add(transform.getHelper())   // r169+：gizmo 是独立的 helper 对象
transform.setMode('translate')     // translate / rotate / scale
transform.setSpace('world')        // world / local
transform.setTranslationSnap(0.5)  // 平移吸附步长
transform.setRotationSnap(Math.PI / 12) // 旋转吸附：15°
transform.setSize(0.9)             // gizmo 的视觉尺寸

三个模式对应三套手柄：

模式手柄长什么样实际改的量典型用途
translate三根箭头 + 三个平面方块position摆位置、对齐、堆叠
rotate三个彩色圆环 + 视线环quaternion调整朝向
scale三根带方块的轴 + 中心方块scale改大小、拉伸

两个空间决定了拖拽的参考坐标系：

  • world：箭头永远和世界轴对齐，拖 X 轴就是世界 X 方向。适合"把物体摆到世界坐标的网格上"。
  • local：箭头跟随对象自身的旋转，拖 X 轴是对象自己的"右方向"。适合调整一个已经旋转过的零件的局部尺寸或朝向。

术语解释：local 和 world 只影响拖拽如何解释，不会改变对象当前的变换值。切换空间不会让物体跳一下，但下一次拖拽的数学路径不同。

TransformControls 的另一个要点是生命周期。它通过事件告诉你"什么时候开始拖、什么时候结束、拖的过程中对象变了"：

js
transform.addEventListener('dragging-changed', (event) => {
  orbit.enabled = !event.value
})

transform.addEventListener('objectChange', () => {
  if (selected) boxHelper.setFromObject(selected)
})

dragging-changed 是编辑器里最重要的一个事件：它把"正在拖物体"这个瞬时状态暴露出来，让相机控制器、撤销系统、属性面板都能在正确的时机介入。

和 OrbitControls 的互斥：一次只让一只手操作 ​

OrbitControls 和 TransformControls 都监听同一个 canvas 的指针事件。如果不做互斥，会出现两种典型故障：

  1. 拖 gizmo 时相机也在转，物体没动多少，视角先飞了；
  2. 松开鼠标后物体位置和相机朝向都被改了一点点，用户说不清是谁干的。

最直接的解法就是上面那行 orbit.enabled = !event.value：拖拽开始关相机，拖拽结束开相机。它成立的前提是 TransformControls 的 dragging-changed 在指针按下时同步触发，而 Three.js 的实现正是如此。

还有两个细节值得补上：

  • 不要在 pointerdown 时立刻取消选中。用户按下 gizmo 的箭头时，pointerdown 也会冒泡到你的拾取逻辑；如果拾取逻辑无脑执行"点空白就取消选中"，gizmo 刚按下就被拆掉了。正确做法是在 pointerdown 时记录 transform.axis !== null，把它当成"这次点击属于 gizmo"的标记，pointerup 时直接跳过拾取。
  • 拖拽阈值。相机旋转和"点一下选中"共用左键，必须用位移阈值区分。按下与抬起之间的距离超过 4~5 像素，就视为拖拽而不是点击。
js
let downX = 0, downY = 0, gizmoHit = false

canvas.addEventListener('pointerdown', (event) => {
  gizmoHit = transform.axis !== null   // 指针按下时，TransformControls 已算好命中的轴
  downX = event.clientX
  downY = event.clientY
})

canvas.addEventListener('pointerup', (event) => {
  if (event.button !== 0 || gizmoHit) return
  if (Math.hypot(event.clientX - downX, event.clientY - downY) > 4) return
  pick(event)
})

这里有一个容易踩的顺序问题：TransformControls 在构造时就把自己的 pointer 监听器挂到了 canvas 上，你的监听器是后挂的，所以 pointerdown 回调里读到的 transform.axis 已经是本次按下计算出的结果。如果你把监听器挂在更早的位置（比如用捕获阶段），就会读到上一次悬停留下的旧值。

Raycaster 拾取：从像素到可编辑节点 ​

TransformControls 解决"拖"，Raycaster 解决"选"。流程分三步：

  1. 把鼠标的屏幕坐标转换成归一化设备坐标（NDC），x、y 都在 −1 到 1；
  2. 用相机生成射线，intersectObjects(可编辑根节点数组, true) 递归检测所有子网格；
  3. 命中的可能是子网格，沿着 parent 向上回溯，直到找到带"可编辑根节点"标记的那个对象。
js
const raycaster = new THREE.Raycaster()
const pointer = new THREE.Vector2()

function pick(event) {
  const rect = canvas.getBoundingClientRect()
  pointer.x = ((event.clientX - rect.left) / rect.width) * 2 - 1
  pointer.y = -((event.clientY - rect.top) / rect.height) * 2 + 1
  raycaster.setFromCamera(pointer, camera)

  const hits = raycaster.intersectObjects(roots, true)
  if (!hits.length) return select(null)

  let node = hits[0].object
  while (node && !node.userData.isRoot) node = node.parent
  select(node)
}

为什么一定要回溯到根节点？ 因为变换是有继承性的。一个路灯 Group 的位置是 (3, 0, −2)，灯头子网格的局部位置是 (0, 2.4, 0)。如果直接把 gizmo 挂到灯头上，拖动时改的是灯头的局部坐标，灯杆不会跟着走；而且保存时到底存 Group 还是存灯头，会变得含糊。选中根节点，子节点自然跟随，序列化也只需要记录一个节点。

术语解释：intersectObjects(objects, recursive) 的第二个参数为 true 时，会同时检测对象的所有后代。Line、Points、Sprite 也参与射线检测，所以如果场景里有辅助线，记得把它们排除在 roots 之外，或者设置 raycast = () => {}。

InstancedMesh 是另一个特例：命中的 instanceId 指向某个实例，但 gizmo 只能附着到整个 InstancedMesh。想让单个实例可编辑，需要把"实例的变换"另存为数据，再把 gizmo 挂到一个隐藏的代理对象上——这是大规模场景编辑器的常见做法，本篇不展开。

包围盒与选中描边：BoxHelper 与自定义 outline ​

选中之后必须给反馈，否则用户不知道 gizmo 挂到了谁身上。最便宜的做法是 BoxHelper：

js
const boxHelper = new THREE.BoxHelper(new THREE.Object3D(), 0xffd166)
boxHelper.visible = false
scene.add(boxHelper)
// 选中时：
boxHelper.setFromObject(root)
boxHelper.visible = true
// 拖拽中（objectChange 里）：
boxHelper.setFromObject(root)

BoxHelper 内部用 Box3.setFromObject() 计算世界空间包围盒，再画 12 条边。它会递归统计所有子网格，因此对 Group 也有效。

它的优点是零成本、随对象动、颜色可换；缺点是线宽固定（WebGL 的 lineWidth 大多只支持 1）、不能做发光描边。如果想要"选中物体边缘发光"，有两条更高级的路：

方案做法成本适合场景
BoxHelper包围盒线框极低编辑器内部、快速原型
反向外壳 outline复制模型、BackSide + 沿法线外扩，再叠加中单个角色、道具展示
后处理描边法线 / 深度边缘检测高影视风格、全屏统一描边

反向外壳的思路在 ㉘ NPR 与风格化 里出现过：把材质换成 side: THREE.BackSide，顶点沿法线方向外扩一点，先画外壳再画本体，就得到一圈轮廓。编辑器里如果只对"当前选中"做，成本可以接受；但要注意 Group 里每个子网格都要复制一份，且外扩量要随物体尺寸缩放，否则大物体描边粗、小物体描边细。

对绝大多数编辑器来说，BoxHelper 已经够用。先把选中这件事做对，再谈描边美学。

网格吸附：让摆放从"手抖"到"对齐" ​

自由拖拽的坐标永远是 -1.2374 这种小数，摆一排路灯时根本对不齐。TransformControls 内置了三种吸附：

js
transform.setTranslationSnap(0.5)              // 每 0.5 个单位停一下
transform.setRotationSnap(THREE.MathUtils.degToRad(15)) // 每 15° 停一下
transform.setScaleSnap(0.1)                    // 缩放按 0.1 步进

三个细节：

  • 吸附值传 null 表示关闭。不要传 0——0 在部分版本里会被当成"步长为 0"，行为不确定。
  • 旋转吸附的单位是弧度，不是角度。面板上写 15°，代码里必须 degToRad(15)。
  • 吸附发生在拖拽过程中，不是松手时才修正。所以 objectChange 里读到的值已经是吸附后的值，属性面板可以直接显示。

如果项目需要"对齐到场景里已有的物体"，比如把一个箱子贴到另一个箱子的边缘，那就不是固定步长能解决的了，需要自己写"吸附候选点"：遍历附近物体的包围盒顶点，找最近点，再把位置钳过去。这类功能通常放在 objectChange 里做二次修正，注意别和 setTranslationSnap 同时开，否则两次修正会打架。

多选与组变换 ​

单选是编辑器的最小模型。多选之后，变换的语义会变复杂：拖一个 gizmo，要让多个物体一起动。

最稳的实现是"代理组"：

  1. 创建一个临时 Group，位置为多选物体包围盒的中心；
  2. 把 gizmo 附着到这个临时 Group；
  3. 记录拖拽开始时每个物体的世界矩阵；
  4. gizmo 变化时，计算临时 Group 的增量变换，再逐个应用到每个物体；
  5. 拖拽结束后，把增量写进撤销栈，销毁临时 Group。

不要偷懒把多个物体 add 到临时 Group 里——那会改变它们的父子关系和世界变换，撤销时还要把父子关系还原，坑比收益多。

多选还有两个配套问题：高亮要覆盖并集（用 Box3.union 把多个包围盒合并），属性面板要显示"混合值"（多个物体的颜色不同时，颜色输入框显示为空或显示 —，不能随便取第一个）。

三个常见坑 ​

  1. 忘了把 gizmo 加进场景。r169 之后 TransformControls 本身不再是 Object3D，必须 scene.add(transform.getHelper())。只 new 不 add，物体会被选中、position 也会变，但视口里什么都看不见。
  2. 点 gizmo 时选中被取消。根因是拾取逻辑没有避开操控器。用 transform.axis !== null 记录"这次按下属于 gizmo"，并且在 pointerup 时检查位移阈值。
  3. 吸附开了，坐标还是带小数。常见原因有三个：父节点本身有非整数变换（子物体的世界坐标仍会带小数）；旋转用欧拉角显示，四元数转欧拉角会有微小误差；以及你在 mouseUp 之后又做了一次"回弹修正"，把吸附值改掉了。

  obj.userData.name = name

  return obj

    boxHelper.visible = false

  transform.attach(selected)
  boxHelper.setFromObject(selected)
  boxHelper.visible = true
}

常见问题解答 ​

Q1：为什么点中灯头，选中的却是整盏路灯？我想单独编辑灯头怎么办？

编辑器默认把"可编辑根节点"定义在 Group 上，拾取到子网格后沿 parent 向上回溯，直到 userData.isRoot。这样做是为了保证变换与保存的粒度一致：拖路灯时灯杆、灯头、底座一起动，序列化也只记录路灯一个节点。

如果要支持"进入组内编辑"，需要引入编辑层级的概念：双击进入 Group，把 roots 临时替换成该 Group 的子节点，并给 Group 本身加一个"锁定"标记；退出时再恢复。还要处理"组内节点的局部坐标"与"世界坐标"的换算，否则 gizmo 的 world 空间会把你绕晕。建议先把扁平编辑做稳，再考虑组内编辑。

Q2：拖拽 gizmo 时相机还是会动，或者松手后选中被取消，怎么排查？

先查两件事：

  1. dragging-changed 有没有真的接上。在回调里打印 event.value，拖拽开始应打印 true、结束打印 false。如果一次都没有，多半是 TransformControls 没有绑定到同一个 domElement，或者 enabled 被别处改成了 false。
  2. 拾取逻辑有没有避开 gizmo。TransformControls 在 pointerup 里会把 axis 重置为 null，所以不能只在 pointerup 里判断 axis。必须在 pointerdown 时就把 axis !== null 存成一个布尔值，pointerup 直接读这个布尔值。

如果相机在拖拽过程中仍然转动，还有一种可能：你同时用了 DragControls 或自定义的 pointermove 旋转逻辑，它们没有读 orbit.enabled。互斥要覆盖所有"会改相机"的入口，而不是只关 OrbitControls。

Q3：`BoxHelper` 的线太细、看不见，能加粗或发光吗？

WebGL 原生 lineWidth 在大多数平台被限制为 1，改材质里的 linewidth 通常无效。想要更醒目的选中反馈，可以：

  • 把 BoxHelper 的材质设成 depthTest: false，让线框穿过物体显示；
  • 用 BoxHelper 之外再加一层半透明 Box3Helper 或自定义 LineSegments，画双线；
  • 用反向外壳做描边（见正文的对比表），视觉最好但成本最高。

另外，BoxHelper 会跟着对象一起被缩放，物体被拉得很扁时线框也会变形。如果只是要"选中提示"，不必追求线框和物体完全贴合，稍微外扩一点反而更清楚。

Q4：吸附设成 0.5，为什么旋转还是会出现 37.3° 这种角度？

setTranslationSnap 只管平移，旋转要用 setRotationSnap，缩放要用 setScaleSnap，三个是独立的。很多人只设了平移吸附，然后奇怪旋转为什么没有对齐。

另外，旋转吸附的单位是弧度。写 setRotationSnap(15) 不是 15°，而是 15 弧度（约 859°），几乎等于关闭吸附。正确写法是 setRotationSnap(THREE.MathUtils.degToRad(15))。

最后，面板显示的角度如果是从四元数反解欧拉角得到的，可能出现 -0.0、359.9 这类边界值，这是浮点误差，不是吸附失效。

动手小练习 ​

  1. 给 gizmo-lab.html 加一个"聚焦选中"按钮：点击后让 OrbitControls 的 target 平滑移动到选中对象的包围盒中心，并保持当前观察方向。提示：用 Box3.setFromObject 取中心，再在渲染循环里 lerp。
  2. 把包围盒换成自定义描边：只对当前选中的对象复制一份 BackSide 外壳，沿法线外扩 0.02，观察它与 BoxHelper 的视觉差异与开销差异。
  3. 实现"按住 Shift 多选"：维护一个 Set，用 Box3.union 合并所有选中物体的包围盒，并尝试把 gizmo 挂到一个临时 Group 上做组平移。先不做撤销，只验证"多个物体一起动"。
