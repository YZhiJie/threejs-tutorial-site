35.2 进阶应用：场景图、撤销重做与序列化 ​

核心概念讲解 ​

接桥：2.3 的层级操作是"直接改"，编辑器要能"撤回" ​

在 ② 场景 · 层级与分组 里，我们学会了用 add() 挂子节点、用 parent 遍历、用 Group 组织一群物体。那套写法解决的是"场景怎么长出来"，默认所有操作都是一次性、不可逆的：

js
scene.add(cube)        // 加了就加了
cube.position.x += 2   // 改了旧值就没了
parent.remove(child)   // 删了就得重新建

对渲染来说这没问题，对编辑器来说却致命。用户拖歪了一次、手滑删错了一个物体，如果没有"撤销"，这个工具就不敢被真正使用。撤销不是一个锦上添花的功能，而是编辑器可信度的底线。

这一篇要解决三个问题：怎样把"修改"变成可回滚的命令；怎样让连续的拖拽只留下一条历史；怎样把一个场景压缩成足够小、又能原样重建的 JSON。

命令模式：把"改"变成可执行、可回滚的对象 ​

命令模式（Command Pattern）的核心只有一句话：不要直接改对象，而是把"怎么改"封装成一个对象，这个对象同时知道怎么做、怎么撤。

一个最小命令长这样：

js
const moveCommand = {
  name: 'MoveCommand',
  do() { box.position.set(2, 1, 0) },
  undo() { box.position.set(0, 1, 0) }
}

但真实编辑器里的命令需要携带数据，而不是把值写死在闭包里：

js
const cmd = {
  type: 'transform',
  obj: box,
  before: { position: [0, 1, 0], quaternion: [0, 0, 0, 1], scale: [1, 1, 1] },
  after:  { position: [2, 1, 0], quaternion: [0, 0, 0, 1], scale: [1, 1, 1] },
  do() { applySnapshot(cmd.obj, cmd.after) },
  undo() { applySnapshot(cmd.obj, cmd.before) }
}

注意 do / undo 内部引用的是 cmd.after / cmd.before，而不是两个被解构出去的局部变量。这样后续做"合并"时，只要改写 cmd.after，do 的行为会自动跟着更新。

编辑器里常见的命令类型：

命令需要存的数据do()undo()备注
TransformCommand对象引用 + 前后 TRS 快照应用 after应用 before拖拽、数值输入都走它
AddCommand新对象引用 + 插入位置加回场景 / 数组移除撤销添加是删除
DeleteCommand对象引用 + 原索引移除按原索引插回不要销毁对象，否则无法撤销
MaterialCommand对象 + 前后颜色 / 材质参数应用新值恢复旧值颜色选择器常用
ReparentCommand子对象 + 旧父 + 新父换父换回注意世界变换保持
RenameCommand对象 + 前后名称改 userData改回轻量，适合演示

有两个容易忽略的设计点：

  • 对象引用 vs 对象 id。命令里直接存 Three.js 对象引用最省事，但对象被反序列化重建后引用会失效。产品级编辑器通常存 id，执行时再从 Map<id, object> 里查。演示阶段可以先存引用，但要在文档里明确这是简化。
  • 命令必须可序列化吗？ 如果你想做"操作历史回放"或协同编辑，命令本身也要能变成 JSON；如果只做本地撤销，存对象引用就够了。先明确需求，不要一上来就追求"命令可传输"。

撤销栈与重做栈：两个数组就够了 ​

历史系统的最小实现就是两个数组：

js
const undoStack = []
const redoStack = []

function execute(cmd) {
  cmd.do()
  undoStack.push(cmd)
  redoStack.length = 0     // 新操作让"未来"失效
}

function undo() {
  const cmd = undoStack.pop()
  if (!cmd) return
  cmd.undo()
  redoStack.push(cmd)
}

function redo() {
  const cmd = redoStack.pop()
  if (!cmd) return
  cmd.do()
  undoStack.push(cmd)
}

规则只有一条：任何新操作都必须清空重做栈。否则用户撤销两步、又做了一步新操作，再按重做会重放一条"本不该存在"的命令，场景直接错乱。

工程上还要补三件事：

  1. 上限。undoStack 不能无限增长，通常限制 50~200 步，超出时从头部丢弃最旧命令。
  2. 异常保护。undo() 里如果抛错，要保证栈状态不被破坏；可以在 try/finally 里维护指针。
  3. UI 同步。按钮的 disabled、栈面板的列表、序列化 JSON，都从同一份栈状态派生，不要各自维护一份计数。

术语解释：撤销栈（undo stack）存"已经发生、可以回滚"的命令；重做栈（redo stack）存"被撤销、可以再执行"的命令。两者是同一段历史的两侧，任意一侧被 push 时，另一侧通常要被清空。

合并：连续拖拽应该只留一条 ​

如果每次 objectChange 都 push 一条命令，拖一次物体能产生上百条历史，用户按一次撤销只退回一帧，体验极差。所以"连续拖拽合并为一条"是编辑器的标配。

推荐的做法是按拖拽生命周期提交，而不是按事件次数提交：

js
let dragObj = null
let dragBefore = null

transform.addEventListener('dragging-changed', (event) => {
  if (event.value) {
    dragObj = selected
    dragBefore = capture(selected)          // 按下时拍一张"前"快照
  } else if (dragObj && dragBefore) {
    const after = capture(dragObj)          // 松开时拍一张"后"快照
    if (!same(dragBefore, after)) pushTransform(dragObj, dragBefore, after)
    dragObj = null
    dragBefore = null
  }
})

这样一次"按下—拖动—松开"永远只产生一条 TransformCommand。但用户可能会连续拖好几次，每次都产生一条，历史仍然很碎。可以在 push 时再做一层时间窗口合并：

js
const top = undoStack[undoStack.length - 1]
if (top && top.type === 'transform' && top.obj === obj &&
    performance.now() - top.time < 700) {
  top.after = after
  top.time = performance.now()
} else {
  undoStack.push(newCommand)
}

合并的边界条件必须写清楚，否则会出现"拖 A 物体却把 B 物体的历史吞掉"这种灵异现象：

  • 同一对象：top.obj === obj；
  • 同一类命令：只有 transform 合并 transform，color 不要和 transform 混；
  • 时间窗口：700ms~1000ms，超过就视为新操作；
  • 选择未切换：切换选中时显式 mergeKey = null；
  • 撤销/重做后不合并：撤销或重做会改变历史指针，之后的命令必须重新开始。

更严谨的做法是给每次操作生成一个 mergeKey（对象 id + 属性名 + 拖拽批次），只有 key 相同才合并。这比时间窗口更可控，也不依赖用户手速。

快照式 vs 命令式：两种历史哲学 ​

维度快照式（Snapshot）命令式（Command）
每步存什么整个场景的完整副本一条命令 + 前后差异
内存增长步数 × 场景大小步数 × 单次改动大小
实现复杂度低：深拷贝即可中：每种操作都要写 do/undo
撤销正确性天然正确：直接恢复副本依赖每条命令的逆操作写对
粒度粗，通常整场景细，可精确到单个属性
合并连续操作困难，副本之间没有语义容易，按对象/属性合并
调试可以逐步 diff 两个 JSON需要读命令日志
协同编辑基本不可行命令可作为操作传输
适用场景小场景、崩溃自动保存、原型大场景、产品级编辑器、多人协作

快照式的诱惑很大：undoStack.push(JSON.stringify(scene)) 一行就能撤销。它在小场景里确实好用，但有两个硬伤：

  • 内存：一个 500 节点的场景，单份 JSON 可能 100KB，100 步就是 10MB，还没算贴图与几何。
  • 粒度：用户拖一下物体，快照式只能整场景回滚，无法和"只改了这个物体的位置"建立语义联系，合并、协同、操作日志都无从谈起。

命令式也不是银弹：每条命令都要正确实现逆操作，AddCommand 的 undo 是删除，DeleteCommand 的 undo 是插回原位置，ReparentCommand 的 undo 还要恢复世界变换。写错一条，用户就会遇到"撤销之后场景炸了"。

实务上的折中是命令式为主 + 周期性快照：日常撤销走命令栈，每隔 N 步或每隔一段时间存一份完整快照，用于崩溃恢复和"跳到某个时间点"。演示页里把两种栈的体积同时显示出来，就是为了让这个取舍变得可见。

场景序列化：只存"可重建的最小信息" ​

序列化的目标不是"把 Three.js 对象变成 JSON"，而是"存下足够重建场景的信息，且不存任何可以重新计算或由 GPU 管理的东西"。

应该存的：

  • 节点 id：稳定标识，供选中态、父子引用、撤销命令使用；
  • 类型：box / sphere / lamp，决定用什么几何与材质；
  • 变换：位置、旋转（建议四元数）、缩放；
  • 材质引用：颜色、粗糙度、金属度，或者外部材质的 URL / 资源 id；
  • 父子关系：parent: "n2" 或嵌套 children；
  • 业务字段：名称、可见性、userData 里的设备编号等。

不该存的：

  • BufferGeometry 的顶点数组、索引、法线——可以由"类型 + 参数"重建；
  • Texture 的像素数据——存 URL 或资源 id，让运行时去加载；
  • WebGLRenderer、Program、uniform、帧缓冲——GPU 资源不可序列化；
  • 相机、控制器、gizmo、辅助线——它们是编辑器状态，不是场景内容（相机位姿可以作为可选的 camera 字段单独存）。

      "material": {
        "color": "#60a5fa",
        "roughness": 0.44
      }
    }
  ]
}

几个约定值得提前定下来：

  • 旋转用四元数。欧拉角有旋转顺序问题（XYZ / YXZ / ZYX），不同库的默认顺序不同，存成四元数最稳；显示时再转成欧拉角给用户看。
  • 位置用数组，不要存 {x, y, z} 对象，JSON 更短，解析也更快。
  • 数字要收敛。导出前对浮点做 toFixed(3) 再转回数字，既减小体积，也避免 0.30000000000000004 这种噪声。
  • 颜色用 sRGB 十六进制字符串。Three.js 的颜色管理会把十六进制按 sRGB 解释，存 #3b82f6 比存线性浮点数组更可读，也更容易跨工具交换。

术语解释：序列化（serialization） 是把内存中的对象图转成可存储/传输的格式；反序列化（deserialization） 是反向过程。最小可重建信息指"去掉它就无法恢复，保留它又必须存"的那部分字段——判断标准是：运行时能不能用代码重新算出来。

反序列化与 id 重映射 ​

反序列化不是 JSON.parse 之后无脑 scene.add。至少要过四道关：

  1. 版本检查：version 高于当前编辑器支持的最大版本，直接拒绝并提示，不要"猜着解析"。
  2. 结构校验：根是对象、nodes 是数组、节点数量有上限、坐标是有限数字、颜色格式合法。
  3. 类型白名单：只接受已知类型；未知类型跳过并计数，而不是让整个文件失败。
  4. id 重映射：如果当前场景已有同名 id，或者粘贴进来的节点 id 冲突，需要重新分配 id，并把 parent 引用里的旧 id 一起改写。

父子关系的重建有一个顺序问题：父节点必须先存在。两种做法：

  • 两遍法：第一遍创建所有节点并放进 Map<旧id, 新节点>，第二遍按 parent 字段挂接；
  • 递归法：如果 JSON 是嵌套的 children 结构，从根递归创建。

两遍法更适合扁平数组，也更容易做 id 映射：

js
const map = new Map()
const nodes = []

for (const spec of data.nodes) {
  const obj = buildObject(spec.type)      // 只建对象，不挂父级
  obj.userData.id = spec.id
  map.set(spec.id, obj)
  nodes.push(obj)
}

for (const spec of data.nodes) {
  const obj = map.get(spec.id)
  if (spec.parent && map.has(spec.parent)) {
    map.get(spec.parent).add(obj)         // 父级已存在
  } else {
    scene.add(obj)                        // 无父级或父级缺失，挂到根
  }
}

id 重映射的典型场景：

  • 加载一个场景到非空的编辑器里，新旧 id 撞车；
  • 复制粘贴一组节点，副本必须换新 id；
  • 合并两个存档，双方都用 n1、n2 这种自增 id。

重映射时一定要同时改写引用（parent、命令里的目标 id、选中态里的 id），否则会出现"节点换了 id，父子关系还指着旧 id"的悬空引用。演示页为了简化只做单场景加载，但把 /^n(\d+)$/ 的序号推进逻辑写进了 idSeq，避免新建节点再次撞号。

数据模型与 Three.js 对象：谁是唯一事实 ​

这是编辑器架构里最容易被含糊过去的问题：场景状态到底以谁为准？

方案 A：Three.js 对象是唯一事实。 命令直接改 position、material.color；序列化时遍历场景读值。优点是实现快，所见即所得；缺点是选中态、名称、业务字段只能塞进 userData，对象一重建就丢，撤销命令也只能存对象引用。

方案 B：纯数据模型是唯一事实。 用一个普通对象数组描述场景，Three.js 只是它的"视图"。命令改模型，同步层把模型变化推到对象上。优点是序列化、撤销、协同全都围绕数据，id 稳定；缺点是要写同步层，且"拖拽中的实时预览"需要额外处理。

对产品级编辑器，推荐 B 的变体：模型为主，Three.js 对象为视图，拖拽期间允许视图先行（为了 60fps 的手感），松手时再把最终值写回模型并提交命令。

无论选哪个方案，都要有脏标记：

js
let dirty = true

function markDirty() {
  dirty = true
}

function tick() {
  if (dirty) {
    syncViewFromModel()
    dirty = false
  }
  renderer.render(scene, camera)
}

没有脏标记，就会出现"属性面板已经更新、视口还没变"或者"每帧都在重建整个场景"两种极端。脏标记不是性能优化的小技巧，而是"单一数据源"能否落地的前提。

版本号与迁移 ​

任何会被保存到磁盘或 localStorage 的 JSON，都应该在最外层带 version。版本号的作用不是好看，而是让未来的你能安全地改结构。

js
function migrate(data) {
  if (!data || typeof data !== 'object') throw new Error('根节点必须是对象')
  if (data.version === undefined) data.version = 1
  if (data.version > 3) throw new Error('版本过新，请升级编辑器')

  if (data.version === 1) {
    data.nodes = data.nodes.map((node) => ({
      ...node,
      material: node.material || { color: node.color || '#cccccc' }
    }))
    data.version = 2
  }
  if (data.version === 2) {
    data.nodes = data.nodes.map((node) => ({
      ...node,
      rotation: node.rotation || [0, 0, 0, 1]
    }))
    data.version = 3
  }
  return data
}

三条纪律：

  • 只升不降。旧编辑器读新文件应该明确报错，而不是丢掉不认识的字段继续跑。
  • 迁移函数要幂等且可组合。每一步只做一件事，从 v1 到 v3 串起来跑。
  • 不要静默丢字段。不认识的字段可以保留在 userData 里，或者明确记录"已忽略"，否则用户的数据会在一次保存后永久消失。

三个常见坑 ​

  1. 把对象引用塞进 JSON。JSON.stringify 遇到 Three.js 对象会得到一堆 {} 或者直接循环引用报错。序列化函数必须显式挑选字段，不能 JSON.stringify(scene)。
  2. 命令里的 before/after 是同一个可变对象。如果你写 before = obj.position 而不是 obj.position.clone()，那么拖拽过程中 before 会跟着变，"撤销"就变成了"撤销到当前位置"，看起来像没生效。
  3. 新操作忘了清空重做栈。表现为：撤销两步 → 新加一个物体 → 按重做 → 场景里出现了一个本不该存在的旧物体。所有写历史的入口（execute、合并、拖拽提交）都必须清空 redoStack。

代码示例 ​

演示页 undo-serialization-lab.html 的核心可以归纳成四段。

① 命令与执行：所有修改都从 execute() 进入，保证"执行 + 入栈 + 清空重做"三步不被漏掉：

js
function execute(cmd) {
  cmd.do()
  undoStack.push(cmd)
  redoStack.length = 0
  refreshAll()
}

② 拖拽生命周期与合并：按下拍"前"快照，松手拍"后"快照，窗口内合并：

js
transform.addEventListener('dragging-changed', (event) => {
  if (event.value) {
    dragBefore = capture(selected)
  } else {
    const after = capture(selected)
    if (!sameSnapshot(dragBefore, after)) {
      pushTransform(selected, dragBefore, after)
    }
  }
})

③ 序列化与体积对比：同一份场景既算 JSON 体积，也估算"如果每步存整份快照"的体积：

js
const text = JSON.stringify(serialize(), null, 2)
const jsonBytes = new Blob([text]).size
const snapshotCost = undoStack.length * new Blob([JSON.stringify(serialize())]).size

④ 栈面板：命令名 + 参数文本从命令对象直接读取，面板只负责渲染，不持有历史状态：

js
undoStack.forEach((cmd, i) => {
  rows.push(`${i + 1}. ${cmd.name}  ${cmd.argText}`)
})

常见问题解答 ​

Q1：撤销栈越用越卡，是内存泄漏吗？

先看两个方向：

  • 栈没有上限。每条命令都持有对象引用、前后快照和参数文本，几百步之后内存会持续上涨。给 undoStack 设一个上限（比如 100 步），超出时 shift() 掉最旧的命令。
  • 命令持有了大对象。如果命令里存了整份 BufferGeometry、整张贴图或整棵子树，单条命令就可能几 MB。命令应该只存"改动所需的最小数据"，几何与材质由对象本身持有。

另外，如果撤销后对象被移除却没有释放材质/几何，反复"添加—删除—撤销—重做"会积累 GPU 资源。注意：为了支持撤销，删除时不能立刻 dispose；要等命令被历史淘汰、对象确定不再回来时再释放。

Q2：连续拖拽合并成一条，但用户拖了 A 又拖 B，为什么 A 的历史被吞了？

合并条件里少了"同一对象"。只按时间窗口合并，会变成"700ms 内的所有 transform 都算一次"。必须同时检查 top.obj === obj，或者用更严格的 mergeKey = obj.userData.id + ':' + mode。

还有两个隐蔽的边界：

  • 用户切换了选中对象，但你的 dragObj 还在指向上一个对象，松手时把旧对象的快照提交到了新对象上；
  • 撤销/重做之后没有清空合并窗口，新的拖拽和"被撤销的那条命令"被合并，undo 时把历史改得面目全非。

最稳的做法是：每次 dragging-changed 开始时重置 mergeKey，结束时才允许合并；撤销/重做后强制 mergeKey = null。

Q3：序列化只存最小信息，那贴图和模型文件怎么办？

存引用，不存内容。常见做法有三种：

  • 存 URL："texture": "/assets/wood.jpg"，运行时按 URL 加载；
  • 存资源 id："material": "mat-wood-01"，由资源库把 id 映射到实际材质；
  • 存内嵌 data URL：适合小图标，不适合大贴图，会让 JSON 体积爆炸。

模型也是同理：存 "type": "gltf" + "src": "/models/lamp.glb"，而不是把顶点数组写进 JSON。真正的资产由文件服务器或 CDN 管理，JSON 只负责"谁引用了哪个资产"。

这样做的代价是场景 JSON 不能单独带走：换一台机器、换一个部署环境，资产路径可能失效。解决办法是导出时打包资产清单，或者使用绝对 URL / 资源服务。

Q4：反序列化后 id 冲突，父子关系错乱，怎么避免？

核心原则：反序列化时先分配新 id，再按映射表改写所有引用。不要指望"旧 id 在新场景里仍然唯一"。

具体步骤：

  1. 为文件里的每个节点生成一个运行时唯一 id，建立 旧 id → 新 id 的映射；
  2. 创建对象时用新 id；
  3. 挂父子关系时，用映射表把 parent 的旧 id 翻译成新 id；
  4. 把选中态、撤销命令里的目标 id 一并改写，或者直接清空历史；
  5. 如果父节点缺失，挂到根节点并记录一条警告，不要让节点消失。

演示页里省掉了父子关系，但保留了"id 冲突则重新分配"和"序号推进"的逻辑。真实项目里，建议把 id 生成器做成独立服务（nextId()），所有创建路径都走它。

Q5：数据模型和 Three.js 对象，到底该以谁为准？

看项目阶段：

  • 原型 / 单机小工具：以 Three.js 对象为准，序列化时遍历读取，命令直接改对象。上手最快。
  • 产品级编辑器 / 需要协同：以数据模型为准，Three.js 作为视图，命令改模型，脏标记驱动同步。前期慢，后期改结构、做回放、做多人协作都顺。

最怕的是"两头都想当权威"：属性面板改模型，gizmo 改对象，保存时读对象，撤销时读模型。两套状态一旦不同步，就会出现"面板显示 1.0，视口里是 1.5，存下来是 0.8"的经典事故。

如果暂时只能选一个，选 Three.js 对象为准，但把 id、名称、业务字段统一放进 userData，并且所有修改都走命令，别让任何代码绕过命令直接改对象。

动手小练习 ​

  1. 给演示页加一个 ScaleCommand：在属性面板拖动"尺寸"滑杆时，按下记录前值、松手提交一条命令。要求连续拖动只留一条历史，并且能和拖拽 gizmo 的 TransformCommand 正确区分。
  2. 把"快照式"真正实现一遍：每次操作后 push(JSON.stringify(serialize()))，与命令式并排显示体积和撤销耗时。故意加 300 个节点，观察两者的内存差距。
  3. 实现一个 ReparentCommand：支持把物体拖到另一个 Group 下，要求撤销后世界变换保持不变。提示：换父之前先记录世界矩阵，换父之后用 attach() 或手动换算局部矩阵。
