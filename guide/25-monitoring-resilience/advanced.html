25.2 进阶应用：容错分级与监控上报体系 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ④ 与 ⑲ 再学习本篇。

核心概念讲解 ​

接桥：④ 的帧率自适应只降了像素比，降级其实有阶梯 ​

在 ④ 渲染器 · 帧率自适应 里，我们写过一个很实用的自适应回路：连续两个采样窗口 FPS 低于 45 就降一档 pixelRatio，连续六个窗口高于 57 再升回来。它解决了"同一份代码在高端机和低端机上都要能跑"这个最基本的问题。

但真实项目的画质不是一个标量，而是一摞可以逐层拆掉的东西：

  • 像素比只影响填充率，对顶点密集、draw call 爆炸的场景几乎没用；
  • 泛光（Bloom）是全屏后处理，关掉它能省下一整条 render target 链；
  • 实时阴影要额外渲染一张（或多张）深度图，关掉它往往比降 DPR 更划算；
  • 环境反射、粒子、透明叠加、抗锯齿，每一项都有自己的成本曲线；
  • 当这些都拆完还是卡，最后还有一条路：停止渲染，给用户一张静态图。

所以"降级"应该是一架阶梯，而不是一个 setPixelRatio 的开关。本篇要解决三件事：第一，怎么根据设备能力决定从哪一档起步；第二，怎么设计一架既能降、又能升、还不会来回抖的阶梯；第三，降级和恢复的每一次决策，怎么变成可上报、可聚合、可诊断的遥测事件。

一句话：降级不是"把画面变丑"，而是在预算内做有顺序的取舍；上报不是"多发几个请求"，而是把取舍过程留下证据。

能力探测：先知道自己在谁的机器上跑 ​

在决定初始档位之前，先回答四个问题：是不是 WebGL2？关键扩展在不在？纹理上限多大？GPU 是谁家的？

js
const gl = renderer.getContext()
const isWebGL2 = typeof WebGL2RenderingContext !== 'undefined'
  && gl instanceof WebGL2RenderingContext

const caps = {
  maxTexture: gl.getParameter(gl.MAX_TEXTURE_SIZE),
  maxCube: gl.getParameter(gl.MAX_CUBE_MAP_TEXTURE_SIZE),
  maxRenderbuffer: gl.getParameter(gl.MAX_RENDERBUFFER_SIZE),
  floatLinear: !!gl.getExtension('OES_texture_float_linear'),
  colorBufferFloat: !!gl.getExtension('EXT_color_buffer_float'),
  anisotropy: renderer.capabilities.getMaxAnisotropy(),
  compressed: !!gl.getExtension('WEBGL_compressed_texture_s3tc')
    || !!gl.getExtension('WEBGL_compressed_texture_etc')
}

GPU 型号需要 WEBGL_debug_renderer_info 扩展：

js
const dbg = gl.getExtension('WEBGL_debug_renderer_info')
const gpu = dbg
  ? gl.getParameter(dbg.UNMASKED_RENDERER_WEBGL)
  : 'unknown'   // Firefox 等浏览器可能出于隐私考虑不返回
探测项用途典型决策
WebGL2判断能否用浮点纹理、VAO、实例化高级特性不支持则禁用 GPGPU 粒子
MAX_TEXTURE_SIZE决定贴图上限与是否降采样2048 以下禁用 4K 贴图
EXT_color_buffer_float浮点 render target 是否可渲染不支持则 GPGPU 退回半精度或 CPU
压缩纹理扩展决定 KTX2 / DDS 资产能否直接用不支持则走未压缩兜底
WEBGL_debug_renderer_info识别某批显卡驱动用于分维度上报与黑名单
getMaxAnisotropy()各向异性过滤成本低端机限制到 2

能力探测的原则是只探测会影响决策的项，不要把所有扩展都查一遍再打印到控制台。探测结果应该在会话开始时算一次，缓存起来，作为遥测的固定维度上报。不要在每一帧里调用 getParameter，那是同步的 GPU 查询，频繁调用会打断管线。

还有一条经验：能力探测告诉你"能不能"，不告诉你"快不快"。同样是 WebGL2，十年前的集显和今年的独显完全不是一个量级。所以初始档位通常是"能力上限 + 设备类型启发式 + 历史数据"三者结合，而不是单纯看扩展。

降级阶梯：从 DPR 到静态图 ​

一架好的阶梯要满足三个条件：顺序合理（先关性价比最高的）、粒度够细（不要一次从全画质跳到最低）、可逆（每一档都能升回去）。下面是一份可以直接落地的七档设计：

档位关掉什么省下的开销视觉损失适用信号
L0 全画质什么都不关基线无帧时间稳定在预算内
L1 降分辨率pixelRatio 2.0 → 1.5像素填充约 44%轻微变软填充率瓶颈、高分屏
L2 关泛光Bloom / 后处理链全屏 Pass + 多张 FBO高光不再外溢后处理占帧时间 > 20%
L3 关阴影实时阴影贴图一次额外场景渲染物体失去落地感阴影 Pass 占比高
L4 关反射环境反射 / 屏幕空间反射环境采样与额外 Pass地面变哑光反射 Pass 或带宽瓶颈
L5 关粒子透明粒子、体积雾大量 overdraw氛围变弱透明填充导致 GPU 饱和
L6 静态兜底停止实时渲染几乎全部 GPU 开销变成一张图以上全部无效或上下文失败

顺序不是绝对的。一个以 UI 为主的数字孪生大屏，可能先关阴影再降 DPR；一个粒子特效为主的展厅，可能先降粒子密度。判断依据只有一个：用 profiler 看时间花在哪，就先砍哪。如果拿不到 profiler，就按"全屏后处理 > 阴影 > 反射 > 透明 > 分辨率"这个通用顺序试。

每一档还要定义三个元数据，方便上报和回滚：

  • level：档位编号，单调递增表示越来越低；
  • reason：触发原因，例如 low-fps、manual、context-lost、rollback；
  • rollbackable：是否允许自动升回。静态兜底通常不可自动升回，必须人工确认。

熔断与恢复：为什么必须带迟滞 ​

如果只用"这一帧低于 16.6ms 就降级"，你会得到一个疯狂跳档的系统：降一档 → 帧率回升 → 立刻升档 → 又掉下去。用户看到的不是"卡"，而是"画质在抽搐"，体验比稳定低画质更差。

所以降级控制器必须有三件套：

① 窗口聚合，而不是单帧判断。 单帧抖动可能来自一次 GC、一次布局、一次后台任务。用 20~30 帧的滑动窗口算平均帧时间，或者用 1 秒的时间窗口，噪声会小一个数量级。

② 连续计数，而不是瞬时越线。 只有连续 N 个窗口都低于阈值，才允许降一档。N 取 3 左右比较合适：既能在一两秒内响应真实劣化，又不会被一次尖峰骗到。

③ 迟滞（hysteresis），让升档比降档更难。 降档阈值设 50fps，升档阈值设 56fps，中间留一段"死区"；降档只需要连续 3 个窗口，升档需要连续 5~6 个窗口。这样在临界点附近，系统会稳定停在低一档，而不是来回横跳。

js
// 伪代码：状态只有两个计数器和一个冷却时间
if (fps < 50) { lowStreak++; highStreak = 0 }
else if (fps > 56) { highStreak++; lowStreak = 0 }
else { lowStreak = 0; highStreak = 0 }   // 死区，什么都不做

if (lowStreak >= 3 && level < MAX) degrade()
if (highStreak >= 6 && level > 0) upgrade()

还要加一个冷却时间：每次档位变化后 1.5~3 秒内不再变化。原因是降档本身会引发一次资源重建（DPR 改变会重建 render target，关阴影会触发材质重编译），这几百毫秒的抖动不应该被算进下一次决策。

恢复还有一条更严格的纪律：恢复要一步一步来，并且每次只升一档。不要因为帧率回到了 120fps 就从 L5 直接跳回 L0，那样很可能再次掉下去。升一档、观察两个窗口、稳定再升，才是可逆的。

当阶梯走到 L6（静态兜底）时，自动恢复应该停止。此时系统已经承认"这台设备跑不动实时场景"，继续自动升档只会制造抖动。要不要给用户一个"仍然尝试实时渲染"的按钮，是产品决策，不是技术决策。

上报设计：采样、去重、聚合、投递 ​

有了降级决策，还要让它变成可分析的数据。一个合格的 3D 遥测体系包含五层：

① 会话采样。 全量采集会自己拖慢页面。按会话采样比按事件采样更合理：一个会话要么全程采，要么全程不采。采样率通常 5%~20%，流量越大取值越低。采样决策要在会话开始时用一次随机数定下来，不要每个事件都掷骰子，否则同一个会话的数据会断断续续。

② 窗口聚合。 不要每帧上报，也不要每次事件都单独发一条。把 3~10 秒内的数据聚合成一个窗口：帧时间只发 P50/P95/P99，事件按"类型 + 档位 + 原因"去重后发计数。原始帧时间永远不出浏览器。

③ 去重与聚合键。 同一类事件在一个窗口里可能发生几百次，比如同一档位的 level 事件、同一区间的 frame 事件。用聚合键把它们的次数累加，而不是发几百条一模一样的记录：

js
const key = type + '|' + (meta.from ?? '') + '>' + (meta.to ?? '')

④ 投递。 页面存活时用 fetch 或 sendBeacon 批量发送；页面退出时用 navigator.sendBeacon，它在卸载阶段也能可靠发出，且不阻塞页面。单批 payload 控制在几 KB 到几十 KB，别逼近 sendBeacon 约 64KB 的安全上限。

⑤ 维度。 没有维度的性能数据只能告诉你"变慢了"，有维度才能告诉你"谁的哪个版本哪个场景变慢了"。最小维度集：

维度示例诊断价值
appVersion2.6.0判断是否为新版本引入
sceneIdplant-twin定位到具体场景
deviceTierhigh / mid / low区分设备分层
qualityLevelL0 ~ L6判断降级是否生效
gpuApple M2 / Adreno 640识别驱动/显卡批次
stageboot / steady / recover区分初始化与稳态
phaseidle / orbit / flyTo区分空闲与交互负载

一份典型的上报 payload 长这样：

字段类型说明
schemastring协议版本，如 tlm/1
vstring应用版本
scenestring场景 ID
sidstring会话随机 ID，不含用户身份
dimsobject设备、GPU、屏幕、档位等维度
winobject窗口内的 fps、帧时间分位数、预算
eventsarray去重聚合后的事件列表

隐私与合规：不要采集用户 ID、URL 参数、精确地理位置、输入内容；GPU 型号和屏幕分辨率属于设备特征，通常可接受，但在部分司法辖区需要告知；会话 ID 应该是随机的、不可反查的，并在采集声明里写清楚用途和保留期限。上报失败必须静默降级，不能让监控拖垮业务。

埋点不能拖慢主线程 ​

性能采集最讽刺的错误，是采集器自己变成了性能问题。四条纪律：

  1. 不在每帧做 JSON 序列化。JSON.stringify 在热路径上是纯浪费，把原始数据留在内存里，窗口结束时算一次。
  2. 不在 rAF 里发网络请求。请求会占主线程、抢带宽，还会让帧时间出现周期性尖峰。用 setInterval + 批量投递。
  3. 长任务用 PerformanceObserver 观测，而不是自己计时。longtask 条目能告诉你主线程被谁阻塞了多久，比在业务代码里埋 performance.now() 更全面。
  4. 重活延后到 requestIdleCallback。聚合、压缩、拼接字符串都可以放到空闲时段；页面退出时再用 sendBeacon 兜底。
js
try {
  new PerformanceObserver((list) => {
    const n = list.getEntries().length
    if (n) record('longtask', { count: n })
  }).observe({ entryTypes: ['longtask'] })
} catch (e) {
  // Safari 等不支持 longtask 的环境直接跳过，不要影响主流程
}

长任务和帧时间要分开看：帧时间长但长任务少，通常是 GPU 瓶颈；帧时间长且长任务多，通常是主线程被业务逻辑占住。前者降画质有效，后者降画质没用，得去优化 JS。

① 能力探测与初始档位：

js
const gl = renderer.getContext()
const dbg = gl.getExtension('WEBGL_debug_renderer_info')

② 阶梯定义与统一的应用函数：每一档显式写出开关，避免"降了 DPR 却忘了关阴影"这种半吊子状态：

js
const LEVELS = [
  { name: 'L0', dpr: 2.0, bloom: true,  shadows: true,  reflect: true,  particles: true },
  { name: 'L1', dpr: 1.5, bloom: true,  shadows: true,  reflect: true,  particles: true },
  { name: 'L2', dpr: 1.5, bloom: false, shadows: true,  reflect: true,  particles: true },
  { name: 'L3', dpr: 1.5, bloom: false, shadows: false, reflect: true,  particles: true },
  { name: 'L4', dpr: 1.25, bloom: false, shadows: false, reflect: false, particles: true },
  { name: 'L5', dpr: 1.0, bloom: false, shadows: false, reflect: false, particles: false },
  { name: 'L6', dpr: 1.0, bloom: false, shadows: false, reflect: false, particles: false }
]

function applyLevel(n, reason) {
  const L = LEVELS[n]
  renderer.setPixelRatio(Math.min(devicePixelRatio, L.dpr))
  composer.setPixelRatio(Math.min(devicePixelRatio, L.dpr))
  bloomPass.enabled = L.bloom
  sun.castShadow = L.shadows
  floorMat.metalness = L.reflect ? 0.9 : 0.05
  floorMat.roughness = L.reflect ? 0.14 : 0.95
  particles.visible = L.particles

  if (n >= 6) { stopRender(); showStaticPoster() }
  record('level', { from: level, to: n, reason })
  level = n
}

这里有一个小细节：record 要在 level = n 之前调用，否则 from 会等于 to，上报数据里全是"原地踏步"。

③ 迟滞控制器：

js
let lowStreak = 0, highStreak = 0, lastChange = 0

function onWindow(avgMs) {
  const fps = 1000 / avgMs
  if (performance.now() - lastChange < 1500) return

  if (fps < 50) { lowStreak++; highStreak = 0 }
  else if (fps > 56) { highStreak++; lowStreak = 0 }
  else { lowStreak = 0; highStreak = 0 }

  if (lowStreak >= 3 && level < 6) {
    lastChange = performance.now()
    lowStreak = 0
    applyLevel(level + 1, '连续 3 窗口 < 50fps')
  } else if (highStreak >= 4 && level > 0 && level < 6) {
    lastChange = performance.now()
    highStreak = 0
    applyLevel(level - 1, '连续 4 窗口 > 56fps')
  }
}

演示里把恢复窗口设成 4 而不是 6，是为了让读者在几十秒内看到完整闭环；生产环境建议更保守，恢复到 6 甚至 8。

④ 遥测队列：聚合、去重、按会话采样：

js
const pending = new Map()
let sentBatches = 0

function record(type, meta = {}) {
  const key = type + '|' + (meta.from ?? '') + '>' + (meta.to ?? '')
  const now = Math.round(performance.now())
  const item = pending.get(key)
  if (item) {
    item.n++
    item.t1 = now
  } else {
    pending.set(key, { type, n: 1, t0: now, t1: now, ...meta })
  }
}

function flush() {
  if (!pending.size) return
  if (!SESSION.sampled) { pending.clear(); return }

  const payload = {
    schema: 'tlm/1',
    sid: SESSION.id,
    dims: { gpu: GPU.slice(0, 36), dpr: devicePixelRatio, level },
    win: { fps: Math.round(lastFps), frameMs: +lastMs.toFixed(1), budgetMs: 16.6 },
    events: [...pending.values()].map((e) => ({
      type: e.type, n: e.n, from: e.from, to: e.to, t0: e.t0, t1: e.t1
    }))
  }

  // 生产环境用下面这行；演示页只写控制台，不发网络请求
  // navigator.sendBeacon('/tlm', new Blob([JSON.stringify(payload)]))
  console.log('[telemetry:dry-run]', payload)
  sentBatches++
  pending.clear()
}

setInterval(flush, 3000)
addEventListener('pagehide', flush)

常见问题解答 ​

Q1：降级阈值为多少合适？为什么不能写死 16.6ms？

16.6ms 是 60Hz 屏的预算，不是所有屏幕的预算。120Hz 设备的预算只有 8.3ms，高刷手机上"稳定 60fps"其实已经掉了一半帧。更合理的做法是把预算定义为"目标帧率对应的帧时间"，并且允许一定容差：60Hz 用 16.6ms、90Hz 用 11.1ms、120Hz 用 8.3ms，降级阈值取预算的 1.5~2 倍。另外，降级判据最好用相对劣化而不是绝对值：同一台设备、同一场景，P95 比基线差 20% 才动，这样不会因为设备本身慢就永远停在最低档。绝对阈值只适合做兜底红线。

Q2：为什么降了 DPR，帧率几乎没变？

说明瓶颈不在像素填充。降 DPR 只减少片元数量和带宽，如果场景卡在顶点处理、draw call 提交、骨骼动画、或者主线程 JS 上，降分辨率当然没感觉。判断方法：打开渲染器的 renderer.info 看 calls 和 triangles；如果 calls 上千，先做合批/实例化；如果 JS 每帧耗时远大于 GPU，先查长任务。演示页里"合成负载"占 12ms 主线程，这段时间降 DPR 也救不回来，正是为了提醒这一点：降级阶梯只对 GPU 侧的开销有效，CPU 侧要靠代码优化。

Q3：上报数据里全是同一档位的重复事件，怎么压缩？

先做聚合键去重，再做窗口合并。聚合键可以设计成"事件类型 + 关键维度"，例如 level|3>4 表示从 L3 降到 L4，frame|bad> 表示差帧区间。同一个窗口内相同键只保留一条，附带 count、firstAt、lastAt。如果同一个会话里同一档位反复升降，那本身就是重要信号——说明迟滞设计有问题，应该单独聚合成 oscillation 事件上报。更进一步，可以把"连续 N 个窗口"的中间过程完全丢弃，只上报最终的档位变化和触发原因。

Q4：`sendBeacon` 和 `fetch` 该怎么选？失败要不要重试？

页面还活着、数据量不大时用 fetch + keepalive: true，方便看状态码；页面即将卸载时用 sendBeacon，它由浏览器接管投递，不阻塞卸载，也不怕请求被取消。失败不要无限重试：监控数据的重要性和业务请求不在一个量级，重试会挤占带宽、放大故障。合理策略是：本地保留最近 1~2 个窗口的缓冲，下次 flush 时合并发送；连续失败 3 次就丢弃并记录一个 transport-fail 计数，避免监控系统自己变成雪崩源。另外，发送前要做体积裁剪，别把整段原始帧时间塞进 payload。

动手小练习 ​

  1. 把演示页的降级阈值改成"P95 帧时间超过预算 2 倍"，恢复阈值改成"P95 低于预算 1.2 倍"，观察降级和恢复的行为差异，思考为什么分位数比平均值更适合做决策。
  2. 给 record() 增加一个"同一会话内同一事件最多保留 50 条"的上限，超出时只累加计数、不新增键。然后用重负载跑一分钟，对比加上限前后的 payload 体积。
  3. 设计一份"降级阶梯验收清单"：每一档至少写出触发条件、视觉验收点、恢复条件、监控指标四项，并说明如果某一档关掉后帧率反而下降（例如重编译导致卡顿），你会怎么排查。
