25.3 实战案例：给 3D 应用装上"黑匣子" ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ④ 与 ⑲ 再学习本篇。

核心概念讲解 ​

接桥：㉑ 数字孪生大屏为什么必须能"自证健康" ​

㉑ 大屏与数字孪生 里的园区孪生，有一个和普通官网完全不同的运行假设：它要 7×24 小时挂在墙上，旁边通常没有懂技术的人。用户不会打开控制台，不会看 RUM 看板，也不会因为"帧率掉了 5ms"给你提工单。他们对系统的全部判断，就是抬头看一眼屏幕——亮着、能动、数据在跳，就是健康；黑了、卡住、花屏，就是坏了。

这带来两个工程要求，普通页面可以糊弄，大屏不能：

  1. 自愈：出了问题先自己救，不能等运维千里迢迢来按 F5。上下文丢了要能重建，帧率掉了要能降级，实在救不回来至少要留一张兜底图。
  2. 自证：救完之后要留下证据。是哪一次操作触发的？当时什么画质档？GPU 什么型号？最后 30 秒帧时间怎么走的？没有这些，你拿到的工单永远只有一句"昨天下午黑了一下"。

25.1 给了我们上下文事件的接线方式，25.2 给了我们降级阶梯和遥测管道。这一篇把它们装进同一个对象——ResilienceManager，让"自愈"和"自证"变成一个有状态、有日志、可回放的闭环。你可以把它理解成 3D 应用的黑匣子：平时安静地记录，出事时保存现场，事后能还原时间线。

一句话：黑匣子不是给用户看的，是给未来的你留的。事故现场只存在一次，记录必须提前写好。

ResilienceManager：把散落的容错收敛成一个状态机 ​

没有管理器的项目，容错逻辑通常散在四个地方：窗口 resize 里改 DPR、webglcontextlost 回调里停循环、定时器里检查帧率、用户点击"重试"时又重建一次场景。它们各自能用，但组合起来就会互相踩脚：降级逻辑不知道上下文已经丢了，还在往下调档；恢复逻辑不知道当前画质档，直接跳回 L0；兜底图显示了，渲染循环却还在后台偷偷跑。

解决办法是把所有状态收敛成一个有限状态机：

状态含义允许的渲染允许的自动动作
healthy全画质稳定运行是帧率劣化时降级
degraded已降级运行是继续降级或逐步恢复
suspended渲染挂起（上下文丢失 / 页面不可见）否等待恢复窗口或超时
recovering正在重建资源否（或仅兜底图）重建、校验、恢复原档位
failed恢复失败，进入兜底否只接受人工重试

状态迁移必须显式、单向、可审计：

从到触发条件
healthydegraded连续 N 窗口低于阈值，档位 > 0
degradedhealthy连续 N 窗口高于阈值，档位回到 0
healthy / degradedsuspendedwebglcontextlost、页面隐藏、主动挂起
suspendedrecovering收到 restored 事件，或超时后主动尝试
recoveringhealthy / degraded重建成功，回到崩溃前档位
recoveringfailed重建抛错、超时、连续失败超过上限
failedrecovering用户点击"重试"
任意suspended页面切后台（可选策略）

这张表的好处是：任何时刻你都能回答"系统现在在干什么、下一步允许干什么"。监控上报也可以直接带上 state 维度，排查时一眼就能看出"事故发生在 recovering 阶段"还是"卡在 failed 没出来"。

环形缓冲：最近 30 秒的可回溯现场 ​

事故排查最痛的不是"没有日志"，而是"日志太多，关键的那 30 秒被淹没了"。一个 7×24 运行的应用，一天可能产生几十万条帧记录，你不可能全存。

环形缓冲（ring buffer）是标准解法：固定长度数组，写满之后覆盖最旧的数据。它有三个好处：

  • 内存恒定：1800 个 Float32 只占约 7KB，跑一年也不会涨；
  • 永远保留最近一段：不需要清理策略，新数据自动挤掉旧数据；
  • 适合快照：出事的瞬间把整个数组复制一份，就得到"最后 30 秒"的完整现场。
js
const RING_SIZE = 1800                 // 30 秒 × 60fps
const ring = new Float32Array(RING_SIZE)
let head = 0
let len = 0

function push(ms) {
  ring[head] = Math.min(ms, 200)       // 截断异常大值，避免污染分位数
  head = (head + 1) % RING_SIZE
  len = Math.min(len + 1, RING_SIZE)
}

缓冲里除了帧时间，还建议保留最近一段事件日志（降级、恢复、上下文事件、用户关键操作）。帧时间回答"卡不卡"，事件日志回答"为什么卡"。两者时间轴对齐，才能还原出"用户点了 flyTo → 相机穿模 → 帧率骤降 → 触发降级 → 用户以为卡死"这样的完整因果链。

崩溃快照：renderer.info 是被低估的现场证据 ​

renderer.info 里有一组几乎不要钱、但信息量极大的计数器：

字段含义能回答什么
render.calls本帧 draw call 数是否合批失败、是否漏了实例化
render.triangles本帧三角形数是否 LOD 失效、是否误加载了高模
render.points本帧点精灵数粒子系统是否失控
memory.geometries当前几何体数量是否泄漏（重建后应稳定）
memory.textures当前纹理数量是否重复上传贴图
programs.length编译过的着色器程序数是否材质变体爆炸

崩溃快照应该包含：最近 30 秒帧时间的 P50/P95/最大值、最后一次 renderer.info 快照、当前档位与状态、最近 12 条事件、以及设备维度（GPU、屏幕、DPR）。这份 JSON 控制在几 KB，可以直接进日志系统。

关键纪律是快照要在挂起/失败的那一刻生成，而不是事后补。上下文丢了之后 renderer.info 里的数据会迅速失真，场景对象也可能已经被释放。把快照函数放在状态迁移到 suspended 或 failed 的同一帧里，才拿得到真实现场。

恢复策略：回到原画质，而不是回到 L0 ​

一个很容易犯的错误：恢复时直接 applyQuality(0)。看起来"恢复全画质"很美好，实际是在最脆弱的时刻给 GPU 加最重的负载——刚经历过上下文丢失或崩溃的设备，很可能立刻二次崩溃。

正确做法是记住崩溃前的档位 lastQuality，恢复后先回到那一档，观察若干个窗口稳定，再交给自动控制器慢慢往上升。这和 25.2 的迟滞逻辑是同一套思路：恢复要保守，降级要果断。

如果恢复过程中再次失败，不要无限重试。设一个失败上限（例如 2 次），超过就进入 failed，展示静态兜底图，把决定权交给用户或运维。黑匣子的价值在于"记录失败"，而不是"假装永远成功"。

静态兜底与错误边界 ​

failed 状态的用户体验，取决于你有没有准备兜底图。三种常见做法：

方案优点缺点
纯黑 + 一行提示实现最简单看起来像坏了，用户会以为断网
预先截好的静态图视觉连续，有品牌感场景/数据变化后图片会过期
轻量 2D 兜底（Canvas 2D 绘制）可动态更新关键数字需要额外维护一套绘制逻辑

大屏项目通常选第二种或第三种。静态图不是"放弃治疗"，而是"体面地降级"：告诉用户系统还在，只是暂时用低功耗模式显示。配合一个"重试"按钮，把恢复的主动权交出去。

错误边界则是兜底图的触发器。除了 webglcontextlost，下面这些也应该把状态送进 failed：

  • 场景初始化抛错（模型加载失败、着色器编译失败）；
  • 渲染循环里出现未捕获异常；
  • 连续多次恢复失败；
  • 关键资源（字体、贴图、配置）加载超时。
js
addEventListener('error', (e) => manager.fail('uncaught: ' + e.message))
addEventListener('unhandledrejection', (e) => manager.fail('rejection: ' + e.reason))

注意错误边界要防抖：同一个错误在渲染循环里可能每帧都抛，不能让 fail() 被调用几千次。进入 failed 之后要立刻停循环，并给重复错误加一个静默窗口。

与业务侧 <canvas> 容器的边界 ​

最后一条经常被忽略：3D 场景只是页面的一部分，外面还有导航、图表、告警列表。黑匣子应该只负责画布容器内部的生死，不要把整个页面拖下水。

推荐的结构是：

  • 一个固定的容器 <div id="viewport">，里面放 canvas 和兜底图；
  • ResilienceManager 只接管这个容器，失败时在容器内显示兜底，不弹全局遮罩；
  • 容器外由 React/Vue 的错误边界负责，两套边界各自兜各自的；
  • 管理器通过事件（statechange）通知外部，外部决定是否显示"3D 模块不可用"的提示。

这样即使 3D 挂了，告警列表、数据面板仍然可用——这才是大屏该有的降级姿态：丢一个模块，不丢整个系统。

值守视角：黑匣子应该回答的三个问题 ​

写完代码并不算结束，还要站在值班人员的角度验收。一个好的黑匣子，至少要能在三十秒内回答三个问题：

  1. "刚才发生了什么？" —— 看状态机日志和最近事件，能说出是上下文丢失、帧率劣化还是初始化失败；
  2. "现在是什么状态？" —— 看当前档位、是否在 recovering、兜底图是否已经显示；
  3. "下次怎么避免？" —— 看快照里的 GPU、DPR、draw call 与帧时间分位数，判断是设备问题、资源问题还是代码问题。

这三个问题对应三份数据：事件日志、实时状态、崩溃快照。三者缺一不可——只有日志没有状态，值班人员不知道现在该不该介入；只有状态没有快照，事后又无法复盘。把这三份数据放在同一个面板里，比接十个监控大盘都管用。

代码示例 ​

对应演示 resilience-ladder.html。下面是一份可以直接复制进项目的管理器骨架，按职责分成六段，每段都有中文注释。

① 构造函数与状态定义：

js
const STATES = ['healthy', 'degraded', 'suspended', 'recovering', 'failed']

class ResilienceManager {
  constructor(options) {
    this.opts = options
    this.state = 'healthy'
    this.level = 0
    this.lastQuality = 0
    this.rebuilds = 0
    this.failCount = 0

    // 环形缓冲：最近 30 秒帧时间（60fps × 30s）
    this.ringSize = 1800
    this.ring = new Float32Array(this.ringSize)
    this.head = 0
    this.len = 0

    // 事件日志：只保留最近 120 条，够还原一条时间线
    this.events = []

    // 帧窗口与迟滞计数
    this.window = 30
    this.frameAcc = 0
    this.frameN = 0
    this.lowStreak = 0
    this.highStreak = 0
    this.lastChange = 0
    this.suspendedAt = 0
    this.listeners = new Set()
  }

② 状态迁移与事件记录：所有状态变化只走 setState，保证上报、UI、日志三处永远一致：

js
  setState(next, reason) {
    if (!STATES.includes(next) || next === this.state) return
    const prev = this.state
    this.state = next
    this.record('state', { from: prev, to: next, reason })
    this.emit('statechange', { prev, next, reason })
    if (next === 'suspended' || next === 'failed') this.captureSnapshot(reason)
  }

  record(type, meta = {}) {
    const now = Math.round(performance.now())
    this.events.unshift({ t: now, type, ...meta })
    if (this.events.length > 120) this.events.pop()
  }

  emit(name, detail) {
    for (const fn of this.listeners) fn(name, detail)
  }

③ 帧记录与自动降级：窗口聚合、连续计数、冷却时间三件套：

js
  frame(dtMs) {
    this.push(dtMs)
    this.frameAcc += dtMs
    this.frameN++
    if (this.frameN < this.window) return

    const fps = 1000 / (this.frameAcc / this.frameN)
    this.frameAcc = 0
    this.frameN = 0
    this.onWindow(fps)
  }

  push(ms) {
    this.ring[this.head] = Math.min(ms, 200)
    this.head = (this.head + 1) % this.ringSize
    this.len = Math.min(this.len + 1, this.ringSize)
  }

  onWindow(fps) {
    if (this.state !== 'healthy' && this.state !== 'degraded') return
    if (performance.now() - this.lastChange < 1500) return

    if (fps < 50) { this.lowStreak++; this.highStreak = 0 }
    else if (fps > 56) { this.highStreak++; this.lowStreak = 0 }
    else { this.lowStreak = 0; this.highStreak = 0 }

    if (this.lowStreak >= 3 && this.level < 5) {
      this.lowStreak = 0
      this.lastChange = performance.now()
      this.degrade(this.level + 1, 'auto-low-fps')
    } else if (this.highStreak >= 5 && this.level > 0) {
      this.highStreak = 0
      this.lastChange = performance.now()
      this.degrade(this.level - 1, 'auto-recover')
    }
  }

④ 降级与恢复画质：档位应用交给业务注入的 applyQuality，管理器不直接碰渲染器：

js
  degrade(target, reason) {
    const from = this.level
    this.level = target
    this.opts.applyQuality(target)          // 业务侧的统一档位函数
    this.record('level', { from, to: target, reason })
    this.setState(target === 0 ? 'healthy' : 'degraded', reason)
    this.opts.telemetry && this.opts.telemetry.record('level', { from, to: target, reason })
  }

⑤ 挂起、恢复与失败兜底：

js
  suspend(reason) {
    if (this.state === 'suspended' || this.state === 'recovering') return
    this.lastQuality = this.level          // 记住崩溃前档位
    this.suspendedAt = performance.now()
    this.setState('suspended', reason)
    this.opts.stopLoop()
  }

  sinceSuspended() {
    return this.suspendedAt ? Math.round(performance.now() - this.suspendedAt) : 0
  }

  async recover() {
    this.setState('recovering', 'restore-begin')
    try {
      await this.opts.rebuildScene()       // 重建场景，返回 Promise 更稳
      this.rebuilds++
      this.failCount = 0
      this.degrade(this.lastQuality, 'restore-quality')  // 回到原档位，而不是 L0
      this.opts.startLoop()
      this.setState(this.lastQuality === 0 ? 'healthy' : 'degraded', 'restore-ok')
      this.record('recover', { ms: this.sinceSuspended(), rebuilds: this.rebuilds })
    } catch (err) {
      this.failCount++
      this.record('recover-fail', { message: String(err) })
      if (this.failCount >= 2) this.fail('rebuild-failed')
      else this.setState('suspended', 'retry-wait')
    }
  }

  fail(reason) {
    this.opts.stopLoop()
    this.setState('failed', reason)
    this.opts.showFallback(true)
  }

  retry() {
    if (this.state !== 'failed') return
    this.opts.showFallback(false)
    this.recover()
  }

⑥ 快照与接线：

js
  captureSnapshot(reason) {
    const vals = this.ringValues()
    const sorted = [...vals].sort((a, b) => a - b)
    const pct = (p) => sorted[Math.floor(sorted.length * p)] || 0

    this.snapshot = {
      t: new Date().toISOString(),
      reason,
      state: this.state,
      quality: this.level,
      rebuilds: this.rebuilds,
      frame: {
        p50: +pct(0.5).toFixed(1),
        p95: +pct(0.95).toFixed(1),
        max: +(vals.length ? Math.max(...vals) : 0).toFixed(1)
      },
      render: {
        calls: this.opts.renderer.info.render.calls,
        triangles: this.opts.renderer.info.render.triangles,
        geometries: this.opts.renderer.info.memory.geometries,
        textures: this.opts.renderer.info.memory.textures
      },
      events: this.events.slice(0, 12)
    }

    // 挂到全局，便于现场取证；同时交给遥测系统落盘
    window.__BLACK_BOX__ = this.snapshot
    this.opts.telemetry && this.opts.telemetry.record('snapshot', { reason })
  }

  ringValues() {
    const out = []
    const start = (this.head - this.len + this.ringSize) % this.ringSize
    for (let i = 0; i < this.len; i++) out.push(this.ring[(start + i) % this.ringSize])
    return out
  }

接线的顺序很重要：先创建渲染器与场景，再创建管理器，最后把事件绑上去。

const waitFirstFrame = () => new Promise((resolve) => requestAnimationFrame(resolve))

const manager = new ResilienceManager({
  renderer, stopLoop, startLoop,
  applyQuality: (n) => applyQuality(n),

canvas.addEventListener('webglcontextlost', (e) => {
  e.preventDefault()
  manager.suspend('context-lost')
  setTimeout(() => manager.recover(), 1200)   // 超时也要有兜底
})

canvas.addEventListener('webglcontextrestored', () => manager.recover())
document.addEventListener('visibilitychange', () => {
  if (document.hidden) manager.suspend('hidden')
})

常见问题解答 ​

Q1：用户反馈黑屏，但我在本地复现不了，怎么办？

先别急着复现，先让现场自己说话。三步走：① 查遥测里的 state 维度，确认系统最终停在 suspended、recovering 还是 failed；如果根本没有状态事件，说明监控没接上，先补埋点。② 查黑匣子快照：frame.p95 / max 能看出崩溃前是否已经严重劣化，render.calls / triangles 能看出是否加载了不该加载的模型，memory.geometries / textures 能看出是否泄漏。③ 复刻设备条件：用户机型的 GPU、屏幕 DPR、是否切过后台、是否开着省电模式。很多"复现不了"其实是"设备条件没对上"。最后，主动触发一次 WEBGL_lose_context，确认恢复路径本身是通的——如果连强制丢失都恢复不了，就不是偶发问题，而是恢复代码有 bug。

Q2：为什么恢复后要回到崩溃前的档位，而不是直接回 L0？

因为恢复瞬间是系统最脆弱的时候。刚经历过上下文丢失的设备，往往正处在显存紧张、驱动不稳定、温度偏高的状态；这时候给它全画质，等于让刚出院的人去跑马拉松。回到 lastQuality 是"先站稳"，之后再靠 25.2 的迟滞控制器慢慢升级，每一步都观察几个窗口。代价是用户会短暂看到略低的画质，收益是避免二次崩溃。如果产品对画质极度敏感，可以折中：恢复后先回 lastQuality + 1，但把升级窗口拉长，并且失败一次就永久停在 lastQuality。

Q3：环形缓冲只有 30 秒，会不会太短？事故可能发生在更早。

30 秒是"帧级现场"的合理长度，不是"全部历史"的长度。帧时间数据的价值在于定位崩溃前的那一刻，30 秒足够覆盖"劣化 → 触发 → 崩溃"的完整过程；更早的数据用聚合指标（每分钟 P95、降级次数、上下文丢失计数）就够了。正确的分层是：秒级环形缓冲 + 分钟级聚合 + 小时级事件。如果确实需要更长的帧级回溯，可以把环形缓冲扩到 60 秒（3600 个样本，约 14KB），但不要再长——收益递减，而且快照 JSON 会变大。真正需要长期保留的是事件和快照，不是每一帧。

Q4：错误边界把整个页面都兜住了，3D 挂了连图表也不显示，怎么改？

把边界收窄到画布容器。具体做法：① 3D 模块自己包一层容器，管理器的 showFallback 只操作这个容器内部的兜底层；② 容器外不要用全局 window.onerror 直接切整页，而是把错误转成事件，由页面级错误边界决定是否影响其它模块；③ 页面级错误边界只处理"框架/数据层"的错误，3D 的内部错误在模块内消化；④ 兜底图上加一行"3D 视图暂时不可用，数据面板正常"，让用户知道系统还在。记住原则：一个模块的失败，不应该升级成整个系统的失败。演示页里兜底图只覆盖 3D 区域，正是这个边界意识的体现。

动手小练习 ​

  1. 给 ResilienceManager 加一个 oscillation 检测：如果 10 秒内档位变化超过 4 次，记录一条 oscillation 事件并临时冻结自动调节 15 秒。想一想为什么"抖"比"低画质"更值得报警。
  2. 把演示页的「恢复时注入故障」连续触发两次，观察 failCount 达到上限后进入 failed 的行为；再手动点重试，确认快照里的 rebuilds 与 state 是否符合预期。
  3. 设计一份"大屏值守交接单"：至少包含当前档位、最近 24 小时上下文丢失次数、最近一次恢复耗时、兜底图是否可用、重试按钮是否可点五项，并说明每一项异常时值班人员应该做什么。
