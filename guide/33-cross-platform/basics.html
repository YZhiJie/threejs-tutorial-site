33.1 基础入门：Vue 3 + TresJS 声明式 3D ​

前置提示：本篇属于跨端与框架广度内容，建议先完成 ⑱ 再阅读；不涉及后端与构建细节。

核心概念讲解 ​

接桥：⑱ 的 R3F 让 React 用户如鱼得水，Vue 团队的答案叫 TresJS ​

在 ⑱ React Three Fiber 里，我们把"亲手 new 对象、亲手 add、亲手写循环"的命令式写法，换成了用 JSX 描述场景的声明式写法。那一篇的结论很清楚：声明式不是不写 three，而是把"什么时候改哪个 three 对象"交给框架。React 生态的答案是 R3F，Vue 生态的答案是 TresJS。

这篇不再重复"声明式为什么好"——那是 ⑱ 已经讲透的内容。本篇只回答一个问题：一个 Vue 3 团队要把同一套 three 能力接进项目，代码长什么样、和 R3F 差在哪、哪些坑是 Vue 特有的。学完你应该能把一个 R3F 示例"翻译"成 TresJS，也能判断什么时候根本不该用声明式。

先看一段最小的 TresJS 场景，感受一下它的形状：

vue
<script setup>
import { TresCanvas } from '@tresjs/core'
import { OrbitControls } from '@tresjs/cientos'
</script>

<template>
  <TresCanvas clear-color="#0b0e14">
    <TresPerspectiveCamera :position="[0, 2, 5]" />
    <TresAmbientLight :intensity="0.4" />
    <TresDirectionalLight :position="[3, 4, 2]" :intensity="2" />
    <TresMesh>
      <TresBoxGeometry :args="[1.4, 1.4, 1.4]" />
      <TresMeshStandardMaterial color="#22d3ee" />
    </TresMesh>
    <OrbitControls />
  </TresCanvas>
</template>

如果读过 ⑱，你会发现除了标签前缀和写法从 JSX 变成模板，结构几乎一一对应。这正是本篇要建立的直觉：两套框架共享同一套 three 对象模型，差异集中在"数据怎么进场景"。

TresJS 的定位：Vue 3 的自定义渲染器 ​

TresJS 不是对 three 的二次封装，而是用 Vue 3 的 custom renderer 能力写了一个"渲染到 three 场景图"的渲染器。Vue 的运行时本来就把"虚拟节点树"和"真实宿主环境"解耦：浏览器里宿主是 DOM，TresJS 里宿主就是 THREE.Object3D 组成的场景图。

这意味着几件事：

  • 你在模板里写的每一个 TresXxx 标签，最终都会对应一个 three 实例；
  • Vue 的响应式系统负责"数据变了通知谁"，TresJS 的节点操作负责"把变化落到 three 对象上"；
  • v-if、v-for、ref、watch、组件插槽这些 Vue 能力可以直接用来组织场景。

核心组件只有几个，记住它们就能读懂大部分 TresJS 项目：

组件作用近似原生写法
TresCanvas创建 renderer、scene、默认相机，接管尺寸与像素比new WebGLRenderer() + new Scene() + resize 监听
TresPerspectiveCamera透视相机new THREE.PerspectiveCamera()
TresMesh网格节点new THREE.Mesh()
TresBoxGeometry / TresTorusKnotGeometry几何体对应的 Geometry 构造函数
TresMeshStandardMaterial材质new THREE.MeshStandardMaterial()
TresGroup分组new THREE.Group()

术语解释：

  • 自定义渲染器（custom renderer）：Vue 3 允许你提供一套"创建元素、插入、删除、更新属性"的宿主实现，从而把组件树渲染到非 DOM 目标。TresJS 就是把目标换成了 three 场景图。
  • 节点操作（node ops）：渲染器与宿主之间的最小接口，例如 createElement、insert、remove、patchProp。TresJS 在这些接口里调用 three 的构造与赋值。
  • Composable：Vue 3 的组合式函数，相当于 React 的自定义 Hook，用 useXxx() 形式复用有状态逻辑。

与 R3F 的 API 对照：换的是语法，不是模型 ​

两套框架最容易被误解的地方是"API 名字不同，所以模型也不同"。实际上模型高度同构，差异主要在语言习惯。下面这张表可以直接当翻译表用：

能力R3F（React）TresJS（Vue 3）备注
画布/基础设施<Canvas><TresCanvas>都负责 renderer、scene、相机、resize
每帧回调useFrame((state, delta) => {})useRenderLoop 的 onLoop(({ delta, elapsed }) => {})v5 部分版本提供 useLoop 别名，以官方文档为准
拿底层对象useThree()useTresContext() / useTres()都能拿到 scene、camera、renderer
自定义类注册extend({ MyClass })用 Tres 前缀标签 + 自定义组件TresJS 更依赖组件封装
状态管理zustand / useStateref、reactive、PiniaVue 自带细粒度响应式
控制器drei 的 <OrbitControls>cientos 的 <OrbitControls>用法几乎一样
模型加载useGLTF()cientos 的 useGLTF()返回结构与加载器封装略有差异
事件onClick / onPointerOver@click / @pointer-over内部都走 raycast
属性命名position、rotation-x、args:position、:rotation-y、:args模板里统一用 : 绑定表达式

最容易踩的差异有三个：

  1. JSX 的 {} 变成了 Vue 的 : 绑定。R3F 写 position={[0, 1, 0]}，TresJS 写 :position="[0, 1, 0]"；纯字符串属性可以不加冒号，例如 color="#22d3ee"。
  2. args 仍然是构造函数参数数组。:args="[1.4, 1.4, 1.4]" 等价于 new THREE.BoxGeometry(1.4, 1.4, 1.4)，这条规则与 ⑱ 完全一致。
  3. 事件监听用 Vue 的 @ 语法。@click="onPick" 对应 R3F 的 onClick，回调参数里同样能拿到 object、point、eventObject 等信息。

@tresjs/cientos：Vue 版的 drei ​

R3F 有 drei，TresJS 有 cientos（西班牙语"百"，寓意"上百个现成件"）。它把高频需求封装成组件或 composable：

cientos 提供替代的原生写法用途
<OrbitControls>控制器 + 每帧 update轨道相机
<Environment>PMREMGenerator + HDR 加载环境光照与反射
<ContactShadows>自建阴影相机廉价接触阴影
<Text3D> / <Html>SDF 文字 / 手工投影场景内文字与 DOM 标注
useGLTF() / useTexture()加载器 + 缓存 + 色彩空间设置资产加载
<Levioso> / <Float>手写正弦浮动展示类动效

选型建议很务实：先看 cientos 有没有，没有再自己包组件。cientos 的版本节奏比 core 慢，遇到 API 不匹配时，优先锁定版本而不是在业务代码里打补丁。

响应式数据驱动 3D：改值即改场景 ​

这是 Vue 团队最舒服的一点，也是最容易用错的一点。先看正确用法：

vue
<script setup>
import { reactive } from 'vue'

const scene = reactive({
  color: '#22d3ee',
  spin: 0.8
})
</script>

<template>
  <TresMesh>
    <TresTorusKnotGeometry :args="[0.75, 0.24, 160, 32]" />
    <TresMeshStandardMaterial :color="scene.color" />
  </TresMesh>
</template>

当你执行 scene.color = '#f472b6'，Vue 会追踪到模板里绑定了 scene.color 的那个 prop，触发一次 patch，TresJS 再把新值写到 material.color。你不需要自己调 material.color.set()，也不需要手动标记 needsUpdate——框架帮你做了"赋值"这一步。

但响应式不是万能的。Vue 的 reactive() 默认会做深层代理，如果直接把 three 对象塞进去，代理会递归包裹它的所有属性，既慢又可能破坏 three 内部的引用判断。正确做法是：

js
import { shallowRef, markRaw } from 'vue'
import * as THREE from 'three'

// ✅ 只追踪引用替换，不代理内部属性
const meshRef = shallowRef(null)

// ✅ 明确告诉 Vue：这个对象不需要响应式
const rawMaterial = markRaw(new THREE.MeshStandardMaterial())

判断标准可以记成一句话：要驱动模板的数据用 reactive，three 实例本身用 shallowRef 或 markRaw。

生命周期与清理：Vue 的卸载不等于 GPU 释放 ​

TresJS 会在组件卸载时把对应的节点从场景图移除，但"移除"和"释放显存"是两件事：

  • 几何体、材质、纹理、RenderTarget 占用的 GPU 资源，需要在 onUnmounted 里显式 dispose()；
  • 自己用 watch 注册的副作用，要在 onUnmounted 里取消；
  • 自己创建的 requestAnimationFrame、ResizeObserver、事件监听，同样要清；
  • useRenderLoop 的回调会随组件卸载自动停止，不需要手动 remove（但回调里引用的外部对象仍要置空）。
js
import { onUnmounted } from 'vue'

onUnmounted(() => {
  geometry.dispose()
  material.dispose()
  texture.dispose()
})

这条纪律在任何框架里都成立，只是在 Vue 项目里更容易被"组件卸载了应该就没事了"的直觉骗过去。

性能注意：渲染循环里不要触发响应式更新 ​

⑱ 的铁律在这里原样适用：每帧都在变的值，不要写进响应式状态。

js
// ❌ 每帧改 reactive，触发模板 patch + 组件更新
onLoop(({ delta }) => { scene.angle += delta })

// ✅ 直接改 three 对象，完全绕过响应式
onLoop(({ delta }) => {
  if (knot.value) knot.value.rotation.y += delta * 0.8
})

区别在于：Vue 的响应式更新会走"调度器 → 组件更新 → 虚拟节点比对 → patch"整条链路，60fps 下等于每秒触发 60 次组件级更新。旋转角、动画进度、悬浮偏移这类值，只应该存在于 three 对象上。

另外三条与性能有关的经验：

  • v-if 是挂载/卸载，visible 是开关。频繁切换用 visible，彻底不用了才 v-if；
  • 几百个同类对象不要写几百个组件。用 InstancedMesh，组件只负责把矩阵写进去（复习 ⑯）；
  • shallowRef 比 ref 更适合持有 three 实例。ref 会深层代理对象，shallowRef 只关心引用变化。

与 Vite 工程集成：让编译器认识 Tres 标签 ​

Vue 的单文件组件编译器默认只认识已注册的组件，遇到 TresCanvas 这类标签会报"Failed to resolve component"。TresJS 提供了编译选项，在 vite.config.ts 里展开即可：

ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import { templateCompilerOptions } from '@tresjs/core'

export default defineConfig({
  plugins: [
    vue({
      ...templateCompilerOptions
    })
  ]
})

依赖侧通常只需要三个包：three、@tresjs/core、@tresjs/cientos。版本上要留意 three 与 TresJS 的兼容区间：TresJS 的 peer dependency 对 three 版本有要求，升级 three 前先看 release note，不要一次升两个。

从 R3F 示例翻译到 TresJS：一次逐行演练 ​

拿 ⑱ 里那个"旋转立方体"做一次逐行翻译，比看十张对照表更有效。原版 R3F 的核心是四句话：useRef 拿 mesh、useFrame 改旋转、<Canvas> 包基础设施、drei 的 <OrbitControls> 收尾。翻成 TresJS 之后：

R3F 写法TresJS 写法翻译要点
const ref = useRef()const meshRef = shallowRef(null)Vue 用 shallowRef 持有 three 实例，避免深层代理
useFrame((state, dt) => { ref.current.rotation.y += dt })onLoop(({ delta }) => { meshRef.value.rotation.y += delta })回调参数从 (state, dt) 变成解构对象
<Canvas shadows camera={...}><TresCanvas shadows> + <TresPerspectiveCamera :position="..." />相机从 props 变成显式组件
<boxGeometry args={[1, 1, 1]} /><TresBoxGeometry :args="[1, 1, 1]" />args 语义不变，只换绑定语法
<mesh castShadow><TresMesh cast-shadow>JSX 驼峰变成模板 kebab-case
<OrbitControls enableDamping /><OrbitControls :enable-damping="true" />布尔 prop 要显式绑定，不能只写属性名

翻译过程中最容易卡住的是布尔属性。JSX 里写 castShadow 就等于 true，Vue 模板里写 cast-shadow 只是传了一个字符串，必须写成 :cast-shadow="true" 或 cast-shadow 配合组件声明。另一个差异是容器尺寸：R3F 在 style 里直接给 height: 100vh，TresJS 通常让 TresCanvas 填满父容器，尺寸交给外层 CSS 决定。把这两点记住，剩下的基本都是机械替换。

什么时候不该上声明式 ​

声明式很适合"由状态驱动的场景组合"，但不是所有 3D 代码都适合。下面这些情况，命令式反而更直接：

  • 一次性小场景：只有几个对象、没有状态切换，包一层框架只会增加阅读成本；
  • 每帧重写大量顶点数据：粒子、流体、程序化地形这类算法，直接在 BufferAttribute 上写更可控，声明式包装帮不上忙；
  • 深度定制的渲染管线：自定义 RenderTarget、手工 pass 编排、特殊的多视图渲染，框架的逃生舱口未必覆盖；
  • 团队不熟 Vue / React：调试要同时理解框架调度与 three 生命周期，学习曲线会翻倍；
  • 目标端是小程序 / 小游戏：33.2 会讲，TresJS 的宿主假设在那边不成立，硬套只会增加适配层负担。

判断标准不是"声明式更先进"，而是这个场景的变化是否主要来自数据。是，就用声明式；变化主要来自算法与每帧计算，就让 three 保持命令式。两者可以在同一个项目里共存：外层用 Vue 管 UI 与状态，内层用一个命令式渲染器管高频计算，中间只传少量参数。

一个务实的混合模式 ​

真实项目里更常见的不是"全声明式"或"全命令式"，而是混合：Vue 负责页面、面板、路由与低频状态，一个独立的 SceneController 负责 three 的创建、循环与资源生命周期，两者之间只留三条通道：

  • 数据向下：Vue 把参数（颜色、档位、选中对象）通过 watch 或方法调用传给控制器，控制器自己决定怎么改 three 对象；
  • 事件向上：控制器把"点击了哪个对象""加载进度""帧率"通过回调抛给 Vue，由 Vue 更新界面；
  • 资源自管：纹理、几何体、RenderTarget 的创建与释放都在控制器内部完成，Vue 不持有 GPU 资源。

这种分工的好处很直接：高频动画不经过响应式，低频 UI 又能享受 Vue 的开发体验；未来要加小程序端时，只需要替换控制器里的运行时，页面层几乎不动。反过来，如果一开始把所有 three 操作都塞进模板绑定，后期想抽离就要重写场景。

三个高频坑 ​

  • 用 ref 直接包 new THREE.Mesh()：深层代理会让 three 内部引用比较失效，改用 shallowRef 或 markRaw；
  • 在 onLoop 里写 scene.angle += delta：每帧触发组件更新，改 three 对象而不是改响应式状态；
  • 切换质量档位时重建整个 renderer：多数情况下只需要改 DPR、阴影开关与纹理规格，重建代价极高。

代码示例 ​

下面是一个可直接放进 Vite + Vue 3 项目的完整单文件组件：响应式颜色与转速、useRenderLoop 驱动旋转、cientos 的控制器与接触阴影、卸载时释放资源。

vue
<script setup>
import { reactive, shallowRef, onUnmounted } from 'vue'
import { TresCanvas, useRenderLoop } from '@tresjs/core'
import { OrbitControls, ContactShadows } from '@tresjs/cientos'

const scene = reactive({
  color: '#22d3ee',
  spin: 0.8
})

const knot = shallowRef(null)
const geometry = shallowRef(null)

const { onLoop } = useRenderLoop()
onLoop(({ delta }) => {
  // 高频值直接改 three 对象，不经过响应式
  if (knot.value) {
    knot.value.rotation.y += scene.spin * delta
    knot.value.rotation.x += scene.spin * 0.3 * delta
  }
})

function onReady(ctx) {
  // 拿到几何体引用，便于卸载时释放
  geometry.value = ctx.geometry
}

onUnmounted(() => {
  geometry.value?.dispose()
})
</script>

<template>
  <div class="stage">
    <div class="panel">
      <label>
        外壳颜色
        <input v-model="scene.color" type="color" />
      </label>
      <label>
        转速倍率
        <input v-model.number="scene.spin" type="range" min="0" max="2.5" step="0.05" />
      </label>
    </div>

    <TresCanvas clear-color="#0b0e14" :dpr="[1, 2]" shadows>
      <TresPerspectiveCamera :position="[3.2, 2.6, 4.4]" :fov="42" />
      <TresAmbientLight :intensity="0.35" />
      <TresDirectionalLight
        :position="[4, 6, 3]"
        :intensity="2.2"
        cast-shadow
      />

      <TresMesh ref="knot" :position="[0, 1.1, 0]" cast-shadow>
        <TresTorusKnotGeometry :args="[0.75, 0.24, 160, 32]" />
        <TresMeshStandardMaterial
          :color="scene.color"
          :roughness="0.3"
          :metalness="0.25"
        />
      </TresMesh>

      <TresMesh :rotation-x="-Math.PI / 2" receive-shadow>
        <TresPlaneGeometry :args="[20, 20]" />
        <TresMeshStandardMaterial color="#131a26" :roughness="1" />
      </TresMesh>

      <ContactShadows :position="[0, 0.02, 0]" :opacity="0.45" :blur="2.4" :scale="8" />
      <OrbitControls :enable-damping="true" :max-polar-angle="Math.PI / 2 - 0.05" />
    </TresCanvas>
  </div>
</template>

<style scoped>
.stage { position: relative; height: 100vh; }
.panel {
  position: absolute; top: 16px; left: 16px; z-index: 10;
  display: grid; gap: 10px; padding: 14px 16px;
  background: #0b1220cc; border: 1px solid #1e2a44; border-radius: 10px;
  color: #e2e8f0; font-size: 13px;
}
</style>

这段代码值得逐段读三遍：

  • scene 是普通 reactive 对象，模板里的 :color、:spin 直接绑到它，改值就改场景；
  • knot 用 shallowRef，只持有 three 实例引用，避免 Vue 深层代理；
  • onLoop 里的旋转不碰响应式，只有 scene.spin 是读取（不是写入），不会触发更新；
  • ContactShadows、OrbitControls 来自 cientos，省掉自建阴影相机和每帧 update() 的样板；
  • onUnmounted 里释放几何体，是对"组件卸载 ≠ GPU 释放"的补丁。

常见问题解答 ​

Q1：TresJS 和 R3F 能不能共用一套组件？

不能直接共用，但可以共用"模型层"。把场景描述抽成与框架无关的数据（位置、材质参数、资产 URL、状态机），再写两个很薄的适配层：R3F 版把数据映射成 JSX，TresJS 版映射成模板标签。真正值得复用是业务数据与 three 算法，不是组件语法本身。反过来说，如果你只有一个 Vue 项目，不必为了"未来可能换框架"而过度抽象。

Q2：为什么我把 `reactive` 包住 `THREE.Mesh` 之后，场景行为变得很奇怪？

因为 reactive() 默认做深层代理，three 对象内部的矩阵、向量、材质引用都会被包一层 Proxy，某些引用比较（===）和内部缓存会失效，性能和正确性都会受损。three 实例一律用 shallowRef() 或 markRaw()；只有真正要驱动模板的数据才用 reactive()。判断口诀：给模板看的用 reactive，给 three 用的用 raw。

Q3：`useRenderLoop` 的回调需要手动取消吗？

不需要。它绑定在组件实例的生命周期上，组件卸载时 TresJS 会注销回调。但要注意回调里闭包引用的外部资源：如果回调里访问了某个纹理或几何体，卸载时仍要自己 dispose()；如果你在回调里启动了自己的定时器或监听器，也要在 onUnmounted 里清掉。"回调自动注销"不等于"资源自动释放"。

Q4：Vite 报 "Failed to resolve component: TresCanvas" 怎么办？

这是 Vue 编译器不认识 Tres 前缀标签，不是运行时错误。把 TresJS 提供的 templateCompilerOptions 展开进 @vitejs/plugin-vue 的配置里（见上文），重启 dev server 即可。另一个常见原因是组件没有正确注册或依赖版本不匹配，先确认 @tresjs/core 已安装、版本与 three 兼容。

动手小练习 ​

  1. 把示例里的环结换成 TresIcosahedronGeometry，给 scene 增加一个 detail 字段并把 :args 绑到它，观察改数字时几何体如何重建；想一想为什么几何体段数不适合每帧改。
  2. 给 TresMesh 加 @click 与 @pointer-over，点击时改 scene.color、悬停时改 scene.spin，比较"事件改数据 → 场景更新"和 ⑱ 里"事件直接改对象"的差别。
  3. 用 v-for 生成 12 个小立方体围成一圈，每帧只让父级 TresGroup 旋转；再尝试给每个立方体单独写 onLoop，对比两种写法的心智负担与性能。
