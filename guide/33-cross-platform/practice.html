33.3 实战案例：一套场景多端交付 ​

前置提示：本篇属于跨端与框架广度内容，建议先完成 33.1、33.2 与 ㉕ 再阅读；代码是架构示意，不依赖特定小程序 SDK 版本。

核心概念讲解 ​

接桥：㉕ 的降级阶梯是"同一端内"的降级，跨端是"换了一整个运行环境" ​

在 ㉕ 线上监控与容错 里，我们设计过一架降级阶梯：降 DPR、关泛光、关阴影、减粒子、最后退到静态图。那套阶梯的前提是运行环境不变——还是同一个浏览器、同一个 WebGL、同一套 DOM 事件，只是把成本高的特性一层层关掉。

跨端不是这样。小程序没有 DOM，纹理加载走平台 API，事件模型换成 touchstart，生命周期换成 onHide / onShow，包体有硬预算。你不是在"关掉几个特性"，而是在换一整个宿主环境。所以架构目标也要换：

  • 同端降级：一个场景 + 一条质量阶梯；
  • 跨端交付：一份场景描述 + 多个运行时适配器。

这篇把 33.1 的 Vue/TresJS 路线与 33.2 的小程序适配路线组装起来，给出一套可以落地的目录结构、适配器接口、资源策略、交互抽象、生命周期与验收清单。

先分清三层：描述、运行时、适配器 ​

跨端项目最容易犯的错，是把平台判断写进业务代码：if (isWeapp) { ... } else if (isGame) { ... } 散落在几十个文件里。正确的分层是三层：

层职责不应该出现的东西
场景描述（scene spec）相机、灯光、材质、资产引用、交互意图、质量档位wx.、DOM API、平台判断
运行时（runtime）创建 renderer / scene / camera，驱动循环，管理尺寸与生命周期具体业务字段、UI 文案
适配器（adapter）把平台能力翻译成统一接口：canvas、加载器、输入、存储、埋点场景结构、渲染算法

术语解释：

  • 场景描述（scene spec）：用数据描述"场景长什么样、要加载什么、允许哪些交互"，与运行环境无关。
  • 能力清单（capability manifest）：描述当前目标端"能跑多大、支持什么"，是资源选型与降级的依据。
  • 运行时适配器（runtime adapter）：实现统一接口的一层薄壳，把平台差异关在内部，业务层只依赖接口。

一句话：场景描述说"要什么"，运行时说"怎么跑"，适配器说"在哪跑"。

场景描述：把"场景"从代码里抽出来 ​

场景描述不必是完整引擎，先从最容易跨端复用的部分开始：相机、灯光、资产、质量档位、交互意图。下面是一份示意配置：

json
{
  "id": "product-showcase",
  "camera": {
    "position": [4.2, 3.4, 6.2],
    "target": [0, 1.6, 0],
    "fov": 42
  },
  "lights": [
    { "type": "hemisphere", "sky": "#7dd3fc", "ground": "#0b0e14", "intensity": 0.55 },
    { "type": "directional", "position": [4.5, 7.5, 3.5], "intensity": 2.2, "shadow": true }
  ],
  "assets": {
    "texture": {
      "web": 2048,
      "weapp": 1024,
      "game": 512
    },
    "model": {
      "web": "crystal.glb",
      "weapp": "crystal.mid.glb",
      "game": "crystal.low.glb"
    }
  },
  "interaction": {
    "orbit": true,
    "tapSelect": true,
    "pinchZoom": true
  },
  "qualityTiers": ["high", "balanced", "low"]
}

这份 JSON 有几个刻意的设计：

  • 资产按目标端给出不同规格，而不是运行时临时判断；
  • 质量档位是数组，运行时根据能力清单选一档，而不是硬编码；
  • 交互只描述"意图"（可轨道旋转、可点选、可缩放），不描述"用哪个事件"；
  • 没有任何 if (isMiniGame)，平台差异被推到适配器。

配置最好带 version 与 schemaVersion，场景结构升级时能识别旧数据。真实项目里还要加 budgetMB、maxTexture 这类约束，但那些更适合放进能力清单，而不是场景描述——场景描述关心"长什么样"，能力清单关心"能跑多大"。

能力清单：运行前先问"你是谁" ​

能力清单（capability manifest）是跨端架构的中枢。它由适配器在启动时探测或按目标端注入，统一长这样：

js
export const CAPABILITIES = {
  web: {
    target: 'web',
    dom: true,
    maxTexture: 4096,
    dprCap: 2,
    shadows: true,
    antialias: true,
    postprocessing: true,
    input: 'pointer',
    lifecycle: 'visibilitychange',
    packageBudgetMB: null
  },
  weapp: {
    target: 'weapp',
    dom: false,
    maxTexture: 1024,
    dprCap: 2,
    shadows: false,
    antialias: true,
    postprocessing: false,
    input: 'touch',
    lifecycle: 'onHide / onShow',
    packageBudgetMB: 20
  },
  game: {
    target: 'game',
    dom: false,
    maxTexture: 512,
    dprCap: 1.5,
    shadows: false,
    antialias: false,
    postprocessing: false,
    input: 'wx',
    lifecycle: 'onHide / onShow',
    packageBudgetMB: 4
  }
}

真正探测时，maxTexture 要取 Math.min(平台上限, renderer.capabilities.maxTextureSize)；dprCap 取 Math.min(设备 DPR, 策略上限)。能力清单不是"写死的平台表"，而是"平台表 + 运行时探测"的组合。

运行时工厂：一个入口，三种实现 ​

运行时工厂只做一件事：根据目标端返回同构的适配器对象。

js
// runtime/index.js
import { createWebRuntime } from './web.js'
import { createWeappRuntime } from './weapp.js'
import { createGameRuntime } from './game.js'

export function createRuntime(target, options) {
  if (target === 'web') return createWebRuntime(options)
  if (target === 'weapp') return createWeappRuntime(options)
  if (target === 'game') return createGameRuntime(options)
  throw new Error('unknown target: ' + target)
}

适配器接口要定死，别让调用方猜：

js
/**
 * @typedef {Object} RuntimeAdapter
 * @property {(container: unknown) => Promise<void>} mount
 * @property {(dt: number, elapsed: number) => void} frame
 * @property {(w: number, h: number, dpr: number) => void} resize
 * @property {() => void} pause
 * @property {() => void} resume
 * @property {() => void} dispose
 * @property {(handler: (p: { x: number, y: number }) => void) => () => void} onPointer
 * @property {(tier: string) => void} setQuality
 */

这七个方法覆盖了绝大多数场景：挂载、逐帧、尺寸、暂停、恢复、销毁、输入、切档。mount 返回 Promise，因为小程序要先拿 canvas 节点、Web 端要等容器布局；onPointer 返回取消函数，避免宿主生命周期切换时泄漏监听。

资源加载：能力清单驱动，而不是临时判断 ​

加载层要回答两个问题：用哪个规格、怎么加载。

js
export function resolveAsset(assetSpec, caps) {
  const target = caps.target
  const size = assetSpec.texture?.[target] ?? 512
  const clamped = Math.min(size, caps.maxTexture)
  return {
    size: clamped,
    url: assetSpec.model?.[target] ?? assetSpec.model?.web
  }
}

做法上建议三条：

  1. 规格在配置里写清楚，运行时只做 clamp 与 fallback；
  2. 加载器按能力清单注入：Web 用 TextureLoader / GLTFLoader，小程序替换 ImageLoader / FileLoader，小游戏再换文件系统 API；
  3. 失败要能降级：高清贴图失败 → 中清 → 纯色材质；模型失败 → 占位几何体 + 错误埋点。

不要把"加载失败"处理成 console.error 就结束。跨端环境里网络、域名白名单、文件系统权限都可能出问题，必须有可见的降级结果，否则用户看到的就是黑屏或空场景。

交互抽象：三套事件，一个内部接口 ​

业务层只应该看到"指针移动到 (x, y)""点击了某个对象""双指缩放了 1.2 倍"，而不是 touches[0].clientX 或 wx.onTouchMove。适配器负责把三套事件归一化：

平台原始事件归一化后
Webpointermove / pointerdown{ x, y, id }（归一化坐标）
小程序touchstart / touchmove + touches[0]同上，附带 touchCount
小游戏wx.onTouchStart / wx.onTouchMove同上

手势层再基于归一化事件实现：单指拖动 = 轨道旋转，点击（位移小于阈值）= 选中，双指距离变化 = 缩放，长按 = 上下文菜单。阈值要按端调整：移动端点击容差通常比鼠标大，小游戏还要考虑摇杆区域与场景拖拽的冲突。

生命周期与暂停策略 ​

运行时统一暴露 pause() / resume()，宿主只负责在正确的时机调用：

  • Web：document.addEventListener('visibilitychange')；
  • 小程序：Page.onHide / Page.onShow；
  • 小游戏：wx.onHide / wx.onShow。

暂停时要做四件事：停循环、释放可重建资源、记录逻辑时间、把状态切到"已暂停"。恢复时做四件事：重建资源、重置计时器、恢复循环、补一次渲染。不要只做"停循环"——后台占着显存，iOS 上很容易被系统回收，回来时上下文丢失。

统一埋点：同一份 schema 跑三端 ​

埋点最怕"每端一套字段"，最后没法聚合。建议定义一份最小 schema：

js
track('scene_ready', {
  target: 'weapp',
  quality: 'balanced',
  firstFrameMs: 860,
  textureSize: 1024,
  fps: 30,
  memoryMB: 42
})

字段尽量用数字与枚举，避免自由文本；target、quality、textureSize 这三个维度必须统一，否则无法回答"小程序低档位的首帧是多少"。上报通道由适配器提供：Web 用 fetch / sendBeacon，小程序用 wx.request，小游戏用平台网络 API。

    loader/
      web.js
      weapp.js
      game.js
  telemetry/
    track.js                   # 统一埋点

这个结构的好处是：场景改动只动 scene/，平台适配只动 platform/，运行时只负责组装。评审时也很容易看出"这个 PR 改的是描述还是实现"。

交付清单与验收标准 ​

跨端交付不能只看"能跑"。建议用一张验收表把主观判断变成可勾选项：

验收项Web小程序小游戏
首帧时间< 1.2s< 2s< 2.5s
稳定帧率60 / 30fps30fps 以上30fps 以上
纹理加载成功率99%+99%+98%+
包体不设限≤ 20MB≤ 4MB 主包
切后台恢复正常正常且不瞬移正常且不瞬移
上下文丢失可恢复可恢复可恢复
埋点字段完整是是是

验收时还要加两项"跨端专项"：同一份场景描述在三端的视觉一致性（构图、色彩、交互反馈），以及降级路径的可达性（断网、纹理失败、低端机）。前者靠截图对比，后者靠故障注入。

四个常见架构坑 ​

  1. 把平台判断写进场景组件：短期快，长期会让每个新端都变成一次大改。解法是把差异收敛到能力清单与适配器。
  2. 资产路径与规格硬编码：Web 能跑的 2048 贴图直接搬到小游戏，包体和显存同时爆。解法是配置化规格 + 构建期检查。
  3. 埋点各自为政：三端字段不同，最后只能看"大概"。解法是先定 schema，再让适配器实现上报。
  4. 只测功能不测环境：在开发者工具里一切正常，真机弱网、切后台、内存紧张时全崩。解法是把"环境矩阵"写进验收表，按机型、网络、生命周期逐项过一遍。

质量档位如何映射到三端 ​

"高质量 / 均衡 / 低"不是三个形容词，而是一组可被适配器执行的参数。建议把档位定义成配置，让运行时按目标端再做一次 clamp：

档位DPR阴影纹理后处理装饰对象
highmin(设备, 2)实时阴影2048可选全部
balancedmin(设备, 1.5)接触阴影 / 关闭1024关闭主要对象
low1关闭512关闭只保留主体

映射规则是"档位给意图，能力清单给上限"：high 档在 Web 上可以真的开到 2048，到了小游戏会被 maxTexture 压到 512；balanced 在小程序上可能仍是 1024，在小游戏上则是 512。这样同一份档位配置在三端都能执行，而不是每端维护一份不同的质量表。档位切换时只重建受影响的资源，不要整棵场景重建。

版本与回滚 ​

跨端交付的版本不止一个：场景描述有 version，适配器有版本，能力清单的 schema 也可能演进。三者要能独立回滚，否则一次"只改了 Web 端"的发布可能把小程序拖下水。

实践上有三条纪律：

  • 场景描述带版本号与默认值：解析时补默认值，旧版本数据不会因为新增字段而崩；
  • 适配器按端独立发布：Web、小程序、小游戏的适配器版本号分开记录，埋点里带上 adapterVersion；
  • 回滚要能只回一端：远程配置里按 target 下发开关与版本，出问题时先切回上一版配置，而不是全量发版。

发布节奏上建议"先灰度高线，再放量"：选一小批设备跑新配置，盯首帧、帧率、纹理成功率、上下文丢失四个指标，稳定后再扩大。跨端问题往往只在特定机型 + 特定网络组合下出现，没有灰度就只能等用户反馈。

代码示例 ​

下面给出一个最小的 Web 运行时，重点看它如何只依赖 RuntimeAdapter 接口，不关心上层是 Vue 还是原生：

js
// runtime/web.js
import * as THREE from 'three'
import { OrbitControls } from 'three/addons/controls/OrbitControls.js'

export function createWebRuntime(options) {
  const { container, spec, caps } = options

  const scene = new THREE.Scene()
  scene.background = new THREE.Color(0x0b0e14)

  const camera = new THREE.PerspectiveCamera(spec.camera.fov, 1, 0.1, 200)
  camera.position.fromArray(spec.camera.position)

  const renderer = new THREE.WebGLRenderer({ antialias: caps.antialias })
  renderer.setPixelRatio(Math.min(devicePixelRatio, caps.dprCap))
  renderer.outputColorSpace = THREE.SRGBColorSpace
  renderer.shadowMap.enabled = caps.shadows
  container.appendChild(renderer.domElement)

  const controls = new OrbitControls(camera, renderer.domElement)
  controls.target.fromArray(spec.camera.target)
  controls.enableDamping = true

  const timer = new THREE.Timer()
  timer.connect(document)

  function frame(dt, elapsed) {
    controls.update()
    renderer.render(scene, camera)
  }

  return {
    async mount() {
      await Promise.resolve()
      resize(container.clientWidth, container.clientHeight, devicePixelRatio)
    },
    frame,
    resize(w, h, dpr) {
      camera.aspect = w / h
      camera.updateProjectionMatrix()
      renderer.setPixelRatio(Math.min(dpr, caps.dprCap))
      renderer.setSize(w, h)
    },
    pause() {
      paused = true
      renderer.setAnimationLoop(null)
    },
    resume() {
      paused = false
      timer.update()
      renderer.setAnimationLoop(loop)
    },
    dispose() {
      renderer.setAnimationLoop(null)
      controls.dispose()
      renderer.dispose()
    },
    onPointer(handler) {
      const el = renderer.domElement
      const onMove = (e) => {
        const r = el.getBoundingClientRect()
        handler({ x: (e.clientX - r.left) / r.width, y: (e.clientY - r.top) / r.height })
      }
      el.addEventListener('pointermove', onMove)
      return () => el.removeEventListener('pointermove', onMove)
    },
    setQuality(tier) {
      // high / balanced / low 的具体策略由运行时决定
      renderer.shadowMap.enabled = caps.shadows && tier !== 'low'
    }
  }
}

注意几个刻意的取舍：

  • 运行时只接收 container、spec、caps，不 import 任何业务组件；
  • mount 是 async 的，Web 端虽然用不上，但接口保持与小程序一致；
  • pause / resume 负责计时器重置，宿主不需要知道 THREE.Timer 的存在；
  • setQuality 里的策略可以更细，但入口必须统一，否则调用方又要写平台分支。

小程序运行时的核心差异只有三处：拿 canvas 节点是异步的、加载器换成平台实现、生命周期回调由宿主触发。把它写成同构的 RuntimeAdapter，上层场景代码就可以完全复用。

常见问题解答 ​

Q1：小程序里纹理加载失败，适配层应该怎么兜底？

先把失败分层：网络失败（域名白名单、证书、弱网）、文件失败（路径、包内资源未打包）、解码失败（格式、尺寸超限）、上传失败（显存或上下文丢失）。适配层对每层给出不同结果：网络失败走 CDN 重试 + 中清兜底；文件失败直接降级到纯色材质并上报；解码失败记录尺寸与格式，改用 2 的幂尺寸重试；上传失败触发上下文恢复流程。关键是任何失败都要有可见的降级结果，而不是让场景停在黑屏。

Q2：包体超限怎么裁，先动哪一刀？

先算清楚"谁占了大头"：把构建产物按类型分组（代码、纹理、模型、音频、字体），打印每类体积。通常纹理和模型占 70% 以上，所以第一刀是纹理降规格与格式转换（PNG→JPG、去掉未使用通道），第二刀是模型减面/合并/去掉动画，第三刀是把非首屏资产移到分包或 CDN，最后才动代码分割。每刀都要配套一次验收：包体、首帧、视觉一致性三项一起看，避免"体积降了但画面糊了"。

Q3：一套场景描述，怎么保证三端视觉一致？

先统一"可量化的基线"：同一相机参数、同一色彩配置、同一光照方向、同一构图比例。跨端差异主要来自三处：DPR 与画布比例（用 CSS 尺寸做相机 aspect，而不是缓冲尺寸）、阴影有无（用接触阴影或烘焙替代实时阴影）、纹理精度（低清贴图要重新调材质参数，而不是直接换图）。验收时用固定相机截图对比，允许的差异写进规范，而不是靠肉眼说"差不多"。

Q4：埋点统一 schema 之后，怎么定位"只有小程序卡"的问题？

在 schema 里固定三个维度：target、quality、textureSize，再加 firstFrameMs、fps、memoryMB、contextLost 四个指标。排查顺序是：先按 target 分组看分布，再看同一 quality 下不同 textureSize 的差异，最后看 contextLost 与内存曲线。只有维度统一，才能回答"是小程序整体慢，还是低档位 + 1024 纹理这一组慢"。如果三端字段不一致，再多的数据也只能得出"大概有点卡"。
