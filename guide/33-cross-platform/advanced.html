33.2 进阶应用：小程序 / 小游戏端的三.js 适配 ​

前置提示：本篇属于跨端与框架广度内容，建议先完成 ④ 与 ⑱ 再阅读；示例只讲适配思路，不绑定某一个小程序平台的具体版本。

核心概念讲解 ​

接桥：④ 的 canvas 在浏览器里唾手可得，在小程序里得先"造假" ​

在 ④ 渲染器 · 渲染循环 里，拿到一个可渲染的画布是理所当然的：document.createElement('canvas')、canvas.getContext('webgl2')、requestAnimationFrame、addEventListener('pointermove')，四件事都是浏览器白送的。WebGLRenderer 的所有便利，都建立在这套 DOM/BOM 之上。

到了小程序和小游戏，这套前提全部消失：

  • 没有 document，没有 window，也没有 new Image()；
  • canvas 不是 DOM 节点，而是平台提供的一个组件（小程序）或全局对象（小游戏）；
  • 没有标准的 requestAnimationFrame（小程序需要宿主提供补丁）；
  • 触摸事件不是 pointerdown，而是 touchstart / touchmove，坐标字段也不一样；
  • 页面会被系统切后台，必须自己处理 onHide / onShow；
  • 包体、显存、纹理上限都比浏览器紧得多。

所以"把 three 搬到小程序"这件事，本质上是先造一个以假乱真的运行环境，再让 three 以为自己还在浏览器里。这一层就是适配层（adapter / platform shim）。

术语解释：

  • shim（垫片）：在缺失的宿主能力上补一个同名接口，让上层代码无感知。例如给小程序补 window、document.createElement、requestAnimationFrame。
  • adapter（适配器）：把平台特有的 API 翻译成通用接口。shim 解决"没有"，adapter 解决"不一样"。
  • 能力清单（capability manifest）：一份描述当前运行环境支持什么的配置，例如最大纹理、DPR 上限、是否支持阴影、包体预算。跨端方案通常先探测能力，再决定加载什么。

适配层到底补了什么 ​

把 three 的依赖倒着数一遍，适配层的工作清单就出来了：

three 依赖浏览器里的来源小程序 / 小游戏里的补法
window / self / globalThis浏览器全局挂一个空对象，补 devicePixelRatio、innerWidth 等字段
document.createElement('canvas')DOM返回平台离屏 canvas（用于程序化贴图、文字纹理）
canvas.getContext('webgl')浏览器 canvas通过 SelectorQuery 拿 canvas 节点后调用
new Image()浏览器平台图片对象：canvas.createImage() / wx.createImage()
fetch / XMLHttpRequest浏览器wx.request / wx.downloadFile / 文件系统 API
requestAnimationFrame浏览器小程序补定时器；小游戏用宿主 rAF
devicePixelRatio / 屏幕尺寸windowwx.getSystemInfoSync() / getWindowInfo()
指针事件DOM 事件bindtouchstart / wx.onTouchStart
页面生命周期visibilitychangeApp.onHide / Page.onHide

一个常见的误区是"只要把 three 的 WebGLRenderer 塞进 canvas 就能跑"。实际上最先崩的往往不是渲染器，而是加载器：TextureLoader 内部会 new Image()，GLTFLoader 会 fetch 二进制，FontLoader 会请求字体文件。所以适配层通常要同时替换 ImageLoader、FileLoader、TextureLoader 这一整条资产链路。

主流方案横向对比 ​

没必要从零手写适配层。市面上已经有三条成熟路径：

方案做法优点代价 / 风险
three-platformize提供 platform 抽象 + 一组 patch，把小程序、小游戏、H5 统一到同一套 three 调用覆盖面广，资产加载、事件、生命周期都有现成实现版本耦合较强，升级 three 时要同步升级适配层
微信官方 threejs-miniprogram / adapter官方维护的最小 shim + 示例工程与小游戏运行时贴合，问题排查路径清晰能力偏基础，复杂加载器、后处理要自己补
Taro / uni-app 的 canvas 组件用跨端框架的 canvas 组件承载 WebGL，再用选择器查询拿节点复用现有跨端工程与路由、状态管理组件差异大，不同端要写条件分支；调试链路更长
手写最小适配层只补项目实际用到的那几个接口体积最小、可控性最高每加一个资产类型就要补一次，长期维护成本高

选型建议：先确定"只做小程序，还是要同时覆盖小游戏/H5"。只做一端，手写最小适配层往往比引入大而全的方案更稳；要覆盖多端，优先 three-platformize 或官方 adapter，别自己造轮子。

尺寸、DPR 与安全区 ​

小程序里最容易出问题的是"画布看起来对，画面却是糊的或被裁掉"。原因通常是三个尺寸概念混在一起：

  1. CSS 布局尺寸：组件在页面里占多大（windowWidth / windowHeight，或 canvas 组件的 width / height）；
  2. 绘制缓冲尺寸：canvas.width / canvas.height，通常等于布局尺寸 × DPR；
  3. 渲染器尺寸：renderer.setSize() 写入的视口尺寸，以及 renderer.setPixelRatio() 影响的内部缩放。

推荐的做法是：自己算 DPR，自己放大缓冲，渲染器只按 CSS 尺寸走。

js
const info = wx.getSystemInfoSync()
const dpr = Math.min(info.pixelRatio, 2) // 上限 2，避免低端机填充率爆炸
canvas.width = cssWidth * dpr
canvas.height = cssHeight * dpr

const renderer = new THREE.WebGLRenderer({ canvas, antialias: true })
renderer.setPixelRatio(1) // 缓冲已经放大，这里不要再乘一次
renderer.setSize(cssWidth, cssHeight, false)
camera.aspect = cssWidth / cssHeight
camera.updateProjectionMatrix()

安全区（safeArea）决定 UI 覆盖层该躲开哪里，而不是决定 3D 画布的大小。全屏 canvas 可以铺满，HUD 按钮要放在 safeArea 之内，否则刘海屏或底部手势区会挡住。这个分工要提前定好，不然后期每次适配新机型都要改场景代码。

生命周期：onHide 必须真的停下来 ​

浏览器切后台时，requestAnimationFrame 通常会被节流甚至暂停；小程序 / 小游戏不一定这么客气。如果不主动停，可能出现：

  • 后台继续渲染，耗电、发热，被系统降权；
  • 纹理、RenderTarget 占着显存，iOS 上更容易被内存回收；
  • 回到前台时 delta 巨大，动画瞬移。

标准做法是：onHide 时停掉渲染循环并释放可重建的资源，onShow 时重建并重置计时器。

js
let texture = null

function pause() {
  renderer.setAnimationLoop(null)
  texture?.dispose()
  texture = null
  material.map = null
  material.needsUpdate = true
}

function resume() {
  texture = buildTexture(512)
  material.map = texture
  material.needsUpdate = true
  timer.update() // 丢掉后台期间累积的 delta
  renderer.setAnimationLoop(loop)
}

App({
  onHide() { pause() },
  onShow() { resume() }
})

小游戏里还有一层：wx.onHide / wx.onShow 是全局回调，页面级并不存在。写代码时把"暂停/恢复"抽成两个函数，别直接写进生命周期回调里，方便在 Web 端用 visibilitychange 复用。

触摸事件映射：坐标要换算，手势要自己写 ​

小程序 canvas 的触摸事件不是 PointerEvent。典型字段是 e.touches[0].x / e.touches[0].y（相对 canvas），也有 clientX / clientY 的版本，具体字段随基础库版本和组件类型变化。稳妥做法是先打印事件对象确认字段，再做归一化：

js
function toNdc(touch, width, height) {
  return {
    x: (touch.x / width) * 2 - 1,
    y: -(touch.y / height) * 2 + 1
  }
}

function onTouchStart(e) {
  const t = e.touches[0]
  const p = toNdc(t, cssWidth, cssHeight)
  raycaster.setFromCamera(p, camera)
  const hit = raycaster.intersectObjects(pickables, false)[0]
  if (hit) select(hit.object)
}

多指缩放没有现成的 wheel 事件，要自己用两指距离变化算缩放比例；长按、双击也要自己计时。另一个坑是事件绑定位置：小程序里事件绑在 <canvas> 组件的 bindtouchstart 上，而不是像 Web 那样 canvas.addEventListener；小游戏里则是 wx.onTouchStart 全局回调。适配层可以把三套都收敛成同一个 onPointer 内部接口，业务代码只写一份。

纹理、显存与包体：三端最现实的差距 ​

浏览器可以随手加载 2048×2048 的贴图，小程序和小游戏不行。差距来自三处：

  • 包体：小游戏主包通常只有 4MB 量级，小程序 20MB 左右（含分包），纹理和模型都要计入；
  • 显存：移动端 GPU 纹理上限常见 4096，但可用显存远小于桌面，2048 贴图开几张就可能触发回收；
  • 首屏：下载、解码、上传纹理都在主线程附近，大图会直接拖慢首帧。

所以跨端项目要把"资产规格"当成配置的一部分，而不是美术给什么就用什么：

资产Web小程序小游戏
颜色贴图20481024512
法线贴图1024~2048512~1024256~512
模型原模 / Draco简化 + Draco简化 + 低面数
纹理格式PNG / JPG / KTX2JPG 优先JPG / 平台压缩格式
阴影实时阴影接触阴影 / 烘焙烘焙或关闭

纹理尺寸尽量取 2 的幂，方便 mipmap 与压缩；能用 JPG 就别用 PNG（法线、遮罩除外）；能用顶点色就别用贴图。把"最大纹理边长"写进能力清单，运行时按清单裁，比在代码里散落 if (isMiniGame) 可靠得多。

字体与音频：别假设 DOM 存在 ​

  • 字体：小程序没有 CSS @font-face 那套加载链路，TextGeometry 依赖的字体文件也未必能加载。稳妥做法是用 Canvas 2D 画文字再当纹理（系统字体直接可用），或者用 SDF 文字方案把字形烘成图集。
  • 音频：没有 new Audio()，要用 wx.createInnerAudioContext()；音效要预加载、及时 destroy()，否则实例会累积。
  • 视频/视频纹理：小游戏有平台视频对象，小程序视频组件不能直接当纹理源，通常要转成帧序列或放弃视频纹理。

这些差异不会让 3D 场景崩掉，但会让"功能看起来做了却没反应"。跨端验收时，把字体、音频、视频单独列成检查项。

小游戏与小程序的关键差异 ​

这两个端经常被当成"同一件事的两种叫法"，但它们的宿主模型差别很大：

维度小程序小游戏
页面结构WXML + WXSS + canvas 组件没有 WXML，只有一个全局 canvas
UI 覆盖层可以用普通组件叠在 canvas 上没有 DOM 式 UI，HUD 要画进 canvas 或用平台 UI
生命周期页面级 onHide / onShow全局 wx.onHide / wx.onShow
canvas组件节点，需选择器查询全局对象，启动即可用
包体约 20MB，可分分包约 4MB 主包，分包空间也紧
事件组件 bindtouch*wx.onTouchStart 等全局回调

这决定了三件事：小程序可以把"暂停按钮、提示文案"用普通组件实现，小游戏则要把这些画进 canvas 或交给平台原生 UI；小游戏的适配层更像"补一个最小的浏览器"，而小程序更像"把 canvas 组件接到 three 上"；小游戏的包体压力更大，首屏资产必须极致精简。写跨端代码时，先把 UI 层抽象出来，再谈渲染，否则小游戏端会返工。

上下文丢失与恢复 ​

移动端在后台、内存紧张或 GPU 重置时，WebGL 上下文可能丢失。浏览器里对应 webglcontextlost / webglcontextrestored 事件；小程序 / 小游戏的适配层若没有暴露，就要在 onShow 时主动检测 renderer.getContext().isContextLost()。

处理策略分两步：

  1. 丢失时：阻止默认行为（Web 端 event.preventDefault()），停掉渲染循环，把状态标记为"已丢失"，暂停输入，埋点记录时间与目标端；
  2. 恢复时：不要试图复用旧的 GPU 资源。保留 CPU 侧的场景图与场景描述，重建纹理、材质、RenderTarget，必要时重建 renderer；如果重建失败，退回静态占位图并给出重试入口。

关键认知是：上下文丢失不是异常，而是移动端的常态事件。把它当成一次"资源重建"来设计，比在代码里到处补 try/catch 更可靠。

三个高频坑 ​

  • 只补了 canvas，没补 ImageLoader：渲染器能创建，但所有贴图都是黑的；
  • 把浏览器的域名白名单思路带进小程序：远程图片还要过平台后台的 downloadFile 白名单；
  • onHide 只停渲染循环、不释放资源：后台继续占显存，回前台更容易上下文丢失。

代码示例 ​

下面是一段"小程序 + WebGL canvas"的最小启动骨架，重点看尺寸、上下文、循环、生命周期四件事如何接起来：

js
// miniprogram/pages/scene/scene.js —— 最小启动骨架（示意）
import * as THREE from 'three'
import { patchThree } from './platform/patch' // 适配层入口

patchThree() // 补 window / document / Image / rAF 等

Page({
  data: { ready: false },

  onReady() {
    const query = wx.createSelectorQuery()
    query.select('#gl').fields({ node: true, size: true }).exec((res) => {
      const info = wx.getSystemInfoSync()
      const canvas = res[0].node
      const cssW = res[0].width
      const cssH = res[0].height
      const dpr = Math.min(info.pixelRatio, 2)

      canvas.width = cssW * dpr
      canvas.height = cssH * dpr

      const renderer = new THREE.WebGLRenderer({ canvas, antialias: true })
      renderer.setPixelRatio(1)
      renderer.setSize(cssW, cssH, false)
      renderer.outputColorSpace = THREE.SRGBColorSpace
      renderer.shadowMap.enabled = false

      const scene = new THREE.Scene()
      scene.background = new THREE.Color(0x0b0e14)

      const camera = new THREE.PerspectiveCamera(45, cssW / cssH, 0.1, 100)
      camera.position.set(0, 1.6, 4.2)

      const mesh = new THREE.Mesh(
        new THREE.TorusKnotGeometry(0.7, 0.22, 96, 20),
        new THREE.MeshStandardMaterial({ color: 0x22d3ee, roughness: 0.35 })
      )
      mesh.position.y = 1
      scene.add(mesh)
      scene.add(new THREE.HemisphereLight(0x7dd3fc, 0x0b0e14, 1.2))

      const timer = new THREE.Timer()
      const loop = () => {
        timer.update()
        mesh.rotation.y += timer.getDelta() * 0.6
        renderer.render(scene, camera)
      }

      this._renderer = renderer
      this._loop = loop
      this._renderer.setAnimationLoop(loop)
      this.setData({ ready: true })
    })
  },

  onHide() {
    this._renderer?.setAnimationLoop(null)
  },

  onShow() {
    if (this._renderer) this._renderer.setAnimationLoop(this._loop)
  },

  onUnload() {
    this._renderer?.dispose()
  }
})

配套的 WXML 只需要一个 canvas 组件：

html
<canvas id="gl" type="webgl" class="stage"
        bindtouchstart="onTouchStart"
        bindtouchmove="onTouchMove"></canvas>

几个容易忽略的点：

  • renderer.setSize(cssW, cssH, false) 的第三个参数 false 表示"不要改 canvas 的 CSS 尺寸"，因为尺寸已经被组件布局决定了；
  • setPixelRatio(1) 是刻意的：缓冲已按 DPR 放大，再乘一次会重复放大；
  • onHide / onShow 里只做暂停/恢复，真正的资源释放抽成函数，方便 Web 端复用；
  • 触摸事件先用 console.log(e.touches[0]) 确认字段，再写坐标换算。

常见问题解答 ​

Q1：小程序里纹理加载失败，`TextureLoader` 一直不回调怎么办？

先确认三件事。第一，TextureLoader 走的是 ImageLoader，内部 new Image() 在小程序里不存在，必须由适配层替换成 canvas.createImage()；第二，图片域名要加到小程序后台的下载白名单，否则 wx.getImageInfo / downloadFile 会直接失败；第三，加载本地包内图片时路径要用相对包内路径，不能用 /assets/... 这种浏览器习惯的绝对路径。排查顺序建议：先换成本地 1×1 图确认链路通，再换远程图确认域名，最后再查色彩空间与 needsUpdate。

Q2：包体超限怎么裁？

按"收益/成本"排序裁：① 纹理降规格（2048→1024→512，JPG 替代 PNG）通常收益最大；② 模型减面、去掉不必要的骨骼与动画轨道，必要时用 Draco / Meshopt；③ 删除未使用的贴图通道（很多 glTF 带了三张用不上的贴图）；④ 把非首屏资产放分包或 CDN，主包只留启动必需；⑤ 最后才考虑砍功能。做法上，把资产清单和体积预算写进构建脚本，每次构建打印"当前体积 / 预算"，比上线前才发现超限更可控。

Q3：为什么切后台回来，动画会"瞬移"一大段？

因为 delta 累计了后台停留的时间。修复方式有两个层面：暂停时停掉渲染循环，恢复时先 timer.update() 丢弃累积时间；更稳妥的是在 onShow 里把计时器重置，并从"暂停时的逻辑时间"继续，而不是从真实时间继续。THREE.Timer 的 connect(document) 在 Web 端能利用页面可见性避免超大 delta，但在小程序里要自己接管生命周期。

Q4：小程序里能不能直接用 TresJS？

不能直接照搬。TresJS 的宿主是浏览器 DOM，TresCanvas 依赖 document、ResizeObserver、标准事件模型。小程序端要么用"Vue 3 + 手写 canvas 组件 + three 适配层"，要么用跨端框架把模板编译成各端组件，再在 WebGL 容器里跑原生 three。TresJS 的价值在 Web 端的开发体验，不在小程序运行时。

动手小练习 ​

  1. 打开 platform-adapter-lab.html，依次切换三个目标端，记录每端的纹理上限、DPR、事件模型与包体预算，并解释哪一项最先导致画面变化。
  2. 把示例骨架里的阴影打开（renderer.shadowMap.enabled = true + 灯光 castShadow），在小程序真机上观察帧率与发热，再改回关闭，记录两组数据。
  3. 写一个最小适配层，只补 requestAnimationFrame 与 Image 两个接口，让一个"加载贴图的旋转立方体"跑起来；再列出还缺哪些接口才能支持 glTF。
