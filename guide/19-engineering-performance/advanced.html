19.2 进阶应用：内存管理、Worker 与按需加载 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑯ 再学习本篇。

核心概念讲解 ​

上一篇定了预算、学会了采集。这一篇解决预算表上最隐蔽的一项——内存：它不直接拖慢某一帧，而是慢慢累积，直到低端机闪退、白屏、标签页崩溃。顺带把两件工程化标配也收了：用 Web Worker 把重计算挪出主线程，用动态 import() 把首屏包瘦下来。

资源 dispose 全景 ​

Three.js 对象的 JS 引用交给 GC 回收，但它们背后占的 GPU 资源（顶点缓冲、着色器程序、纹理显存）必须手动释放——这就是 dispose() 家族：

方法释放什么忘了会怎样
geometry.dispose()显存中的顶点/索引缓冲几何体越积越多
material.dispose()该材质的着色器程序程序对象泄漏
texture.dispose()纹理显存（大头！）显存涨满直接崩
renderer.dispose()渲染器内部缓存（FBO、程序缓存）整个渲染器拆不干净
renderTarget.dispose()后处理/离屏渲染目标多 pass 场景的隐形泄漏

整棵场景树的通用释放函数：

js
function disposeObject3D(root) {
  root.traverse(obj => {
    if (obj.geometry) obj.geometry.dispose()
    const mats = Array.isArray(obj.material) ? obj.material : [obj.material]
    for (const m of mats) {
      if (!m) continue
      for (const key in m) {          // 材质上挂的纹理一并释放
        const v = m[key]
        if (v && v.isTexture) v.dispose()
      }
      m.dispose()
    }
  })
  root.clear()                        // 摘掉所有子节点引用
}

注意：共享资源不能一竿子打完。多个 Mesh 共用一份 geometry/材质/纹理时，重复 dispose() 不会报错，但会提前释放仍在使用的资源。谁创建谁负责，或像下面那样用缓存计数管理。

SPA 路由切换：泄漏重灾区 ​

Vue / React 单页应用里，3D 页面通常挂在某个路由组件上。用户来回切换路由时：

  • 组件卸载只移除了 <canvas> 元素——GPU 资源、渲染循环、事件监听全活着；
  • renderer.setAnimationLoop 还在跑，每帧继续渲染一个看不见的场景；
  • 切进切出十几次后，十几个渲染器同时活着，低端机直接白屏。

卸载时必须按顺序收尸：

js
function destroyScene() {
  renderer.setAnimationLoop(null)  // ① 停渲染循环
  removeEventListener('resize', onResize) // ② 摘事件监听
  disposeObject3D(scene)           // ③ 释放场景树全部 GPU 资源
  composer?.dispose?.()            // ④ 后处理链（含内部 RenderTarget）
  renderer.dispose()               // ⑤ 渲染器内部缓存
  renderer.forceContextLoss()      // ⑥ 主动丢弃 WebGL 上下文
  renderer.domElement.remove()     // ⑦ 移除 canvas
}

纹理/几何体复用缓存 ​

同一张贴图被 50 个模型引用，就别加载 50 次。用一个 Map 做缓存，加载前查、释放时引用计数：

js
const texCache = new Map()         // url → { texture, refs }
function acquireTexture(url) {
  let e = texCache.get(url)
  if (!e) {
    e = { texture: new THREE.TextureLoader().load(url), refs: 0 }
    texCache.set(url, e)
  }
  e.refs++
  return e.texture
}
function releaseTexture(url) {
  const e = texCache.get(url)
  if (e && --e.refs <= 0) { e.texture.dispose(); texCache.delete(url) }
}

Web Worker：把重计算挪出主线程 ​

几何体程序化生成、大模型解析、寻路/物理这类 CPU 重活，放主线程会直接吃掉帧预算。Web Worker 在独立线程跑，通过 postMessage 通信；传大块二进制数据时用 Transferable（第二个参数列出要转移的 buffer），零拷贝、不拖速度：

js
// main.js —— 主线程
const worker = new Worker('./geo-worker.js', { type: 'module' })
worker.postMessage({ count: 100000 })
worker.onmessage = (e) => {
  const { positions } = e.data          // ArrayBuffer 已转移过来
  geometry.setAttribute('position', new THREE.BufferAttribute(new Float32Array(positions), 3))
}

// geo-worker.js —— Worker 线程
self.onmessage = (e) => {
  const buf = new Float32Array(e.data.count * 3)
  // ……重型计算，填满 buf……
  self.postMessage({ positions: buf.buffer }, [buf.buffer]) // 转移所有权，零拷贝
}

注意：Transferable 转移后，发送方手里的 buffer 立即失效（长度变 0），别再用它。

动态 import()：three 按需加载 ​

three.module.js 体积不小，首屏不一定用得上 3D 的页面，可以等用户进入 3D 区块再加载：

js
button.onclick = async () => {
  const THREE = await import('three')                       // 点击时才下载/解析
  const { OrbitControls } = await import('three/addons/controls/OrbitControls.js')
  initScene(THREE, OrbitControls)                           // 加载完再初始化
}

构建工具（Vite/webpack）会把动态 import 自动切成独立 chunk，按需下发，首屏 JS 体积立刻瘦下来。

代码示例 ​

一个"内存泄漏实验室"：一键创建 500 个各带独立纹理的盒子，一键销毁整个场景。开着 dispose 销毁——内存回落；关掉 dispose 销毁——JS 堆只涨不落。页内实时绘制 performance.memory 曲线，泄漏肉眼可见：

js
// —— 核心：创建与销毁 ——
let scene = null

function createScene() {
  scene = new THREE.Scene()
  scene.background = new THREE.Color(0x0b0e14)
  scene.add(new THREE.HemisphereLight(0xbfd9ff, 0x202020, 1))
  const geo = new THREE.BoxGeometry(0.5, 0.5, 0.5)
  for (let i = 0; i < 500; i++) {
    // 每个盒子一张独立 CanvasTexture —— 显存压力的主要来源
    const cv = document.createElement('canvas')
    cv.width = cv.height = 256
    const ctx = cv.getContext('2d')
    ctx.fillStyle = `hsl(${Math.random() * 360},70%,55%)`
    ctx.fillRect(0, 0, 256, 256)
    const tex = new THREE.CanvasTexture(cv)
    const m = new THREE.Mesh(geo, new THREE.MeshStandardMaterial({ map: tex }))
    m.position.set((Math.random() - 0.5) * 20, Math.random() * 8, (Math.random() - 0.5) * 20)
    scene.add(m)
  }
}

function destroyScene(withDispose) {
  if (!scene) return
  if (withDispose) {
    scene.traverse(obj => {                    // 正确姿势：全树释放
      obj.geometry?.dispose()
      const mats = Array.isArray(obj.material) ? obj.material : [obj.material]
      mats.forEach(m => { m?.map?.dispose(); m?.dispose() })
    })
  }                                            // 错误姿势：直接丢引用，GPU 资源全泄漏
  scene = null
}

// —— 内存曲线：每 250ms 采样一次 usedJSHeapSize，画在页内 canvas 上 ——
const samples = []                             // { mb, leaking }
setInterval(() => {
  if (!performance.memory) return
  samples.push({
    mb: performance.memory.usedJSHeapSize / 1048576,
    leaking: !params.dispose                   // 当前是否处于"泄漏模式"，决定曲线颜色
  })
  if (samples.length > 240) samples.shift()    // 只留最近 60 秒
  drawCurve()                                  // 折线图：横轴时间，纵轴 MB
}, 250)

销毁按钮连按几次"创建 → 销毁"循环：dispose 开启时曲线呈锯齿形（涨上去又回落）；dispose 关闭时曲线阶梯式上涨——这就是教科书级的内存泄漏图像。

常见问题解答 ​

Q1：明明 dispose 了，内存为什么还在涨？

按嫌疑大小排查：① 共享资源被漏算——材质/纹理被多个 Mesh 共享，只 dispose 了其中一处引用的那批对象，或者反过来重复 dispose 后缓存逻辑混乱，用引用计数管理；② 渲染目标没释放——EffectComposer、WebGLRenderTarget、阴影贴图、PMREM 环境贴图都有自己的显存，要各自 dispose()；③ JS 侧引用没断——对象还挂在某个数组、闭包、事件回调里，GC 根本收不走，DevTools Memory 面板拍堆快照对比两次采样，看哪类对象在涨；④ GC 本来就懒——堆不到阈值不回收，曲线晚几秒回落是正常的，看长期趋势别看瞬时。

Q2：Worker 里能用 three.js 吗？

能算不能渲染。Worker 里可以 import * as THREE from 'three'，用它的数学库（Vector3、Matrix4、几何算法）、程序化生成 BufferGeometry 数据——这是最常见用法，算完把 TypedArray 用 Transferable 甩回主线程。但 Worker 里没有 DOM、没有 document，常规 WebGLRenderer 无法创建。例外是 OffscreenCanvas：主线程把 canvas 的离屏控制权转给 Worker（canvas.transferControlToOffscreen()），Worker 里就能完整跑 WebGL 渲染——适合"渲染线程与 UI 线程彻底分离"的架构，代价是兼容性要写降级路径。

Q3：three.js 打包后到底多大？gzip 呢？

以 r186 量级估算：three.module.js 原始约 1.2~1.3 MB，gzip 后约 300 KB 出头，brotli 再小一圈。Tree-shaking 后业务实际用到的部分通常更小（纯场景+常用材质可压到 gzip 200 KB 上下）。结论：three 本体对现代网络不算致命，真正该砍的是高清贴图与未压缩的 glTF 模型——一张 4K PNG 就比整个 three 还大。首屏仍想更快，用本篇的动态 import() 把 three 挪出关键路径。

Q4：dispose 会不会把正在用的东西释放掉，导致画面崩了？

会，典型事故：两个 Mesh 共享同一材质，其中一个销毁时把材质 dispose 了，另一个下一帧渲染时 GPU 侧资源已失效——three 会静默重新上传（dispose 后资源标记为待重建），表现为偶发卡顿而非报错。真正危险的是 dispose 后立刻 forceContextLoss 或在异步加载途中 dispose。对策就是那句：谁创建谁释放，共享资源引用计数。

动手小练习 ​

  1. 在演示里关掉 dispose，连续"创建/销毁"5 次，打开 DevTools Memory 面板拍两次堆快照做对比，找出增长最快的对象类型（应是 CanvasTexture 关联的显存对象）。
  2. 给演示的纹理加上引用计数缓存：让 500 个盒子只共享 10 张纹理，对比改造前后"创建"按钮按下时内存曲线的涨幅差异。
  3. 写一个 geo-worker.js：在 Worker 里生成 10 万个随机点坐标并用 Transferable 传回主线程渲染成 THREE.Points，体会主线程在计算期间完全不卡。
