19.4 企业实践：生产监控与灰度发布 ​

前置提示：本篇属于精通方向扩展内容，建议先完成 19.1 性能预算与采集、19.2 内存管理 与 19.3 画质分级 再学习本篇。

核心概念讲解 ​

接桥：开发机上的预算，管不住线上的真实设备 ​

前三篇把预算、采集、内存和画质分级都备齐了，但它们都有一个共同前提——你就坐在那台开发机前。上线之后情况完全变了：

  • 用户里有省电模式的旧安卓、有开着 20 个标签页的办公本、有发热降频的 iPhone；
  • 你不在现场，卡顿不会报错，只会变成"页面有点卡"的客诉；
  • 新版本发布后，某类机型帧时间突然翻倍，而你两周后才知道。

19.3 的画质分级是单机自救，本篇补的是全局视角：把真实用户的帧时间采集回来（RUM），用看板和告警盯住预算，再用灰度发布把风险控制在 1% 的用户身上。

一句话：开发环境的性能是"实验室数据"，生产环境才是"临床数据"。没有 RUM 的性能优化，等于闭着眼睛开车。

RUM：在真实用户身上量帧时间 ​

RUM（Real User Monitoring）的核心不是"多加一个监控 SDK"，而是用最小成本拿到可分维度的真实数据。设计顺序是：先定指标 → 再定维度 → 最后才写采集代码。

① 采集哪些指标 ​

指标口径为什么需要
帧时间 P50 / P95 / P99相邻 rAF 回调间隔，10 秒窗口聚合平均值掩盖尖峰，P95/P99 才代表"难受的用户"
长帧占比单帧 > 50ms 的帧数 / 总帧数直接对应"卡了一下"的体感
长任务次数PerformanceObserver longtask（>50ms）区分 CPU 卡顿与 GPU 卡顿
WebGL 上下文丢失webglcontextlost 事件计数低端机显存耗尽的直接信号
JS 堆峰值performance.memory.usedJSHeapSize（Chrome 系）发现慢性泄漏，配合 19.2 的 dispose
首帧耗时navigationStart → 第一次 render首屏体验，和包体积/资产加载直接相关

别采平均值：平均值是"平均用户"的体验，而你的客诉永远来自最差的那 5%。产品验收看 P95，事故排查看 P99 和长帧占比。

② 按哪些维度切分 ​

同一份 P95，按维度切开才有诊断价值。最小维度集：

appVersion（版本） × deviceTier（高/中/低） × qualityTier（画质档） × sceneId（页面/场景）

再加两个辅助维度：GPU 厂商（WEBGL_debug_renderer_info，用于识别某批显卡驱动）和 prefers-reduced-motion / 省电模式。没有维度的性能数据只能告诉你"变慢了"，有维度才能告诉你"谁的哪个版本哪个场景变慢了"。

③ 采样与上报成本 ​

全量采集会自己拖慢页面，企业级做法是三层削减：

  1. 会话采样：按 5%~20% 的会话采样，低流量产品取高值，大流量产品取低值；
  2. 窗口聚合：不是每帧上报，而是每 10 秒把窗口内的数据算成 P50/P95/P99 + 计数，原始帧时间不出浏览器；
  3. 页面退出时上报：visibilitychange / pagehide 里用 navigator.sendBeacon 发一批，不阻塞卸载，也不怕请求被取消。

上报体控制在 几 KB（sendBeacon 的安全上限约 64KB）：只发聚合值、枚举和版本号，不发原始数组、不发用户标识、不发 URL 里的敏感参数。

告警：让指标自己喊人 ​

看板是"人找问题"，告警是"问题找人"。企业里能活下来的告警规则通常同时满足三条：

规则要素推荐做法反例
阈值相对基线劣化 > 10%，而非绝对毫秒写死 "P95 > 16.6" 在 CI 虚机上全员误报
持续性连续 3 个窗口超标才触发单窗口抖动就打电话，一周后没人看告警
静默期触发后 30 分钟不重复；发布窗口内自动静默同一次事故刷 200 条通知
分级P0（大面积卡死/崩溃）电话；P1（局部劣化）IM；P2（趋势上涨）日报所有告警都走电话，等于没有告警

告警要带可执行的上下文：版本号、机型分布、出问题的场景、对比基线、最近一次发布记录。收到"P95 从 18ms 涨到 41ms，集中在某机型 + 版本 2.4.0 + 画质档中"的人，才知道下一步是回滚还是降档。

灰度发布：把新版本先给 1% 的人 ​

性能事故最贵的不是修复，而是全量用户一起中招。灰度发布把"发布"拆成"放量"，每一档都是一个小型实验：

阶段放量观察窗口晋级条件回滚条件
冒烟内部 1%2 小时无 P0 错误、P95 不劣化任意 P0
小流量5%1 个业务高峰P95 劣化 ≤ 10%、崩溃率 ≤ 基线P95 劣化 > 20%
中流量20% ~ 50%24 小时同上，且低端机不劣化低端机 P95 劣化 > 15%
全量100%持续—保留一键回滚 7 天

放量要按设备分层，而不是随机均匀：先放高端机，确认逻辑没问题；再放中端机，验证预算；最后放低端机，这是最容易翻车的一档。若产品支持，优先按"用户 ID 哈希"分桶，保证同一用户始终落在同一版本，避免体验跳变。

回滚与降级：两条逃生通道 ​

发现劣化后有两种动作，优先级不同：

  1. 降级开关（kill switch）：远程关闭最贵的渲染特性（Bloom、实时阴影、高 pixelRatio），30 秒内生效，不用发版。这是第一反应；
  2. 版本回滚：把流量切回上一版本。代码回滚要重新构建、可能受 CDN 缓存影响，通常慢于开关。

企业级项目会为这两条通道分别准备预案：开关配置放在配置中心而不是代码里，并且每次发布前先验证开关可用——很多团队的"一键降级"只在 PPT 里存在。

代码示例 ​

① RUM 采集器：采样 + 窗口聚合 + beacon 上报 ​

一个无依赖的采集器，控制在百来行内。核心是三件事：用 rAF 记帧间隔、用 PerformanceObserver 记长任务、页面退出时上报聚合值：

js
// rum.js —— 挂到生产页面即可，失败不影响主流程
const RUM = {
  sampleRate: 0.1,          // 10% 会话采样；流量越大调越低
  flushMs: 10_000,          // 10 秒一个聚合窗口
  version: '2.4.0',
  tier: 'mid',              // 由 19.3 的自动选档写入
  sceneId: 'campus'
}

// 没被采样到，直接不启动，零成本
if (Math.random() < RUM.sampleRate) startRum()

function startRum() {
  const frames = []          // 当前窗口的帧间隔
  const longTasks = { n: 0 }
  let last = performance.now()
  let ctxLost = 0
  let heapPeak = 0

  // 长任务：CPU 卡顿的独立信号
  try {
    new PerformanceObserver(list => { longTasks.n += list.getEntries().length })
      .observe({ entryTypes: ['longtask'] })
  } catch { /* Safari 不支持则跳过 */ }

  // WebGL 上下文丢失：显存耗尽的直接证据
  addEventListener('webglcontextlost', () => { ctxLost++ }, true)

  const tick = now => {
    frames.push(now - last)
    last = now
    if (performance.memory) heapPeak = Math.max(heapPeak, performance.memory.usedJSHeapSize)
    requestAnimationFrame(tick)
  }
  requestAnimationFrame(tick)

  // 窗口结束：算分位数 + 发一批，原始数组不上报
  const flush = () => {
    if (!frames.length) return
    const sorted = [...frames].sort((a, b) => a - b)
    const pct = p => sorted[Math.min(sorted.length - 1, Math.floor(sorted.length * p))]
    const payload = {
      v: RUM.version, tier: RUM.tier, scene: RUM.sceneId, // 维度
      p50: pct(0.5), p95: pct(0.95), p99: pct(0.99),
      longFrame: frames.filter(f => f > 50).length / frames.length,
      longTask: longTasks.n, ctxLost, heapMB: Math.round(heapPeak / 1048576)
    }
    // beacon：退出时也能可靠发出，不阻塞页面
    navigator.sendBeacon?.('/rum', new Blob([JSON.stringify(payload)], { type: 'application/json' }))
    frames.length = 0; longTasks.n = 0; ctxLost = 0; heapPeak = 0
  }
  setInterval(flush, RUM.flushMs)
  addEventListener('pagehide', flush)  // 关页/切后台时兜底上报
}

落库后就是普通数仓问题：按 v × tier × scene 分组算 P95，再和上一版本同维度做对比。

② 灰度门禁：用同一份 RUM 数据自动放量/回滚 ​

放量决策不要靠人盯着看板，写成可执行的判定函数，接在发布系统里：

js
// canary-gate.js —— 每 5 分钟跑一次，输入是过去 30 分钟的 RUM 聚合
function canaryGate({ baseline, canary }) {
  const regress = {
    p95: canary.p95 / baseline.p95 - 1,          // 帧时间劣化比例
    edge: canary.edgeP95 / baseline.edgeP95 - 1, // 低端机单独看
    crash: canary.crashRate / Math.max(baseline.crashRate, 1e-6) - 1,
    ctxLost: canary.ctxLostRate                // 上下文丢失率直接看绝对
  }

  // 一票否决：上下文丢失、崩溃率翻倍 —— 直接回滚
  if (regress.ctxLost > 0.01 || regress.crash > 1) {
    return { action: 'rollback', reason: '稳定性红线' }
  }
  // 低端机劣化超过 15% —— 暂停放量，先排查
  if (regress.edge > 0.15) {
    return { action: 'hold', reason: '低端机 P95 劣化 ' + (regress.edge * 100).toFixed(0) + '%' }
  }
  // 整体劣化 ≤ 10% 且样本充足 —— 继续放量
  if (regress.p95 <= 0.1 && canary.sessions >= 500) {
    return { action: 'promote', reason: '预算内，样本充足' }
  }
  return { action: 'hold', reason: '样本不足或劣化待观察' }
}

配套的告警规则可以写成声明式配置，便于统一管理：

- name: frame-time-regression
  expr: rum_p95{version="canary"} / rum_p95{version="baseline"} > 1.1
  for: 15m          # 连续 15 分钟才触发，过滤抖动
  severity: P1
  runbook: 先切 kill-switch 关 Bloom/阴影，再判断是否回滚

③ 降级开关：30 秒生效，不打版 ​

开关的最小实现是"配置中心下发 + 页面轮询/长连接"，渲染侧只需要读布尔值：

js
// 远端配置：{ bloom: true, shadows: true, maxDpr: 2 }
const flags = { bloom: true, shadows: true, maxDpr: 2 }

function applyFlags() {
  bloomPass.enabled = flags.bloom
  sun.castShadow = flags.shadows
  renderer.setPixelRatio(Math.min(devicePixelRatio, flags.maxDpr))
}

// 拉取失败就保持上次配置：监控平台挂了不能拖垮业务
async function pullFlags() {
  try {
    const res = await fetch('/config/feature-flags.json', { cache: 'no-store' })
    if (res.ok) Object.assign(flags, await res.json())
  } catch { /* 静默降级 */ }
  applyFlags()
}
setInterval(pullFlags, 30_000)

常见问题解答 ​

Q1：RUM 采集本身会不会拖慢页面？采样率怎么定？

会，但可以忽略不计——前提是别踩三个坑：① 不要每帧做字符串拼接或 JSON 序列化，只在窗口结束时算一次；② 不要在 rAF 里做网络请求，用 setInterval + sendBeacon 批量发；③ 采样率随流量反比：日活 1 万以下可以采 20%，百万级日活 5% 就足够拟合 P95。判断标准很实用：打开采样后，对比 19.1 的 HUD，帧时间均值上升超过 0.3ms 就说明采集代码太重。另外，本地开发和生产预览环境默认关闭 RUM，避免测试流量污染数据。

Q2：线上 P95 和本地测试差一倍，该信哪个？

都信，但要分清用途。本地（尤其 CI 虚机）测的是相对变化：同一台机器、同一场景，改前改后的比值有意义；线上 RUM 测的是绝对体验：真实机型、真实网络、真实后台负载。常见差异来源：省电模式把 GPU 频率砍半、高 dpr 屏幕填充压力大、其它标签页抢 CPU、热量降频。做法是把两端对齐：本地用 19.3 的三档预算验收，线上用同版本同维度的 P95 做趋势和告警；跨设备比绝对值没有意义，纵向比同一设备才有。

Q3：灰度放多少比例合适？样本要多少才够判断？

先算样本再定比例：要比较 P95，至少需要几百个会话才能让分位数稳定。假设日活 10 万、目标观察 2 小时，5% 放量约 400 个会话，刚够看 P95；如果日活只有 5000，5% 两小时只有 20 个会话，分位数毫无意义——此时应该延长观察窗口，或直接按设备分层小范围试跑。经验值：P0 故障 1% 就能暴露；性能劣化通常要 5% 放量 + 一个业务高峰。低于 500 会话的数字只能看崩溃率这类计数指标，别看分位数。

Q4：用户说卡，但看板 P95 正常，怎么办？

P95 正常说明"95% 的用户没事"，不代表没人难受。三步排查：① 看 P99 和长帧占比，个别用户可能每 10 秒卡一次，被 P95 平均掉了；② 按维度下钻——特定机型、特定画质档、特定场景（比如用户走到密集城区）才出现；③ 在交互触发点埋点：点击/拖拽后的 2 秒窗口单独统计帧时间，因为空闲时页面可能很流畅。最后，给用户侧加一个"反馈卡顿"按钮，附带版本和机型，比事后猜高效得多。

动手小练习 ​

  1. 把示例采集器的 sampleRate 改成 1（全量采集），在演示页里对比开启前后的帧时间 HUD，估算采集开销，再定一个你项目能接受的采样率。
  2. 给 canaryGate 增加一条规则：首帧耗时（firstFrameMs）劣化超过 20% 也暂停放量——思考首帧和稳态帧时间为什么需要分开验收。
  3. 设计一份"发布前检查清单"：至少包含灰度比例、观察窗口、回滚开关验证、告警静默设置、值班人五项，并说明每一项缺失会导致什么后果。
