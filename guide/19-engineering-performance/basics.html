19.1 基础入门：性能预算与采集 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑯ 再学习本篇。

核心概念讲解 ​

接桥：把"读数习惯"固化成"预算表" ​

在 16.1 性能瓶颈认知与读数 里，我们养成了一个好习惯：遇到卡顿先看 renderer.info，用 draw calls、triangles、geometries/textures 三组读数定位瓶颈，再对症下药。

但"出问题了才去看一眼"仍然是被动的。本篇把这习惯再往前推一步——在项目开工时就把读数写进预算表：帧时间上限多少、draw calls 封顶多少、纹理显存不能超过几 MB，白纸黑字定死，开发过程中持续采集、对照验收。

一句话：优化不是感觉，是指标。没有预算表的优化，就像没有工资单的家庭开销——月底永远不知道钱花哪儿了。

性能预算：16.6ms 的工资单 ​

60fps 意味着每帧只有 16.6ms（1000/60）。这一帧里，JS 脚本、CPU 提交、GPU 渲染、浏览器合成都要从同一份预算里领钱，任何一项超支，整帧迟到、用户看到掉帧。目标 30fps 的低端机，预算放宽到 33.3ms。

除了帧时间，还有几项关键资源要定上限。下面是三档设备的参考预算（按目标用户群中最弱的一档定你的红线）：

指标高端桌面中端手机低端机（30fps 可接受）
帧时间≤ 16.6ms≤ 16.6ms≤ 33.3ms
draw calls≤ 3000≤ 500≤ 150
三角形总数≤ 500 万≤ 100 万≤ 30 万
纹理显存≤ 2 GB≤ 512 MB≤ 256 MB
JS 堆内存≤ 1 GB≤ 300 MB≤ 150 MB

预算使用纪律：① 按目标设备中最弱的一档定红线，别按自己的开发机；② 各项预留约 30% 余量，留给系统开销、GC 与浏览器合成；③ 预算一旦写下，每个迭代对照验收，超支就是 bug。

性能采集三板斧 ​

① Stats.js 面板（16.1 已用过）：FPS / MS / MB 三页点击切换，嵌在页面左上角，开发期常驻。MS 页（每帧毫秒数）比 FPS 更直观。

② Performance API：浏览器原生，不用装任何库，适合写进自己的 HUD 与上报逻辑：

js
const t0 = performance.now()          // 高精度时间戳（毫秒，带小数）
renderer.render(scene, camera)
const cost = performance.now() - t0   // 这一段 CPU 耗时

// JS 堆内存（仅 Chrome/Edge 系提供）
if (performance.memory) {
  performance.memory.usedJSHeapSize / 1048576  // 已用堆，换算 MB
  performance.memory.jsHeapSizeLimit / 1048576 // 堆上限
}

③ Chrome DevTools Performance 面板：深度排查用。按 F12 → Performance → 点录制跑 5 秒 → 停止，重点看三处：

  • Frames 条：红色长帧就是掉帧现场，高度即帧时间；
  • Main 火焰图：主线程每帧在干什么，黄色长条（Scripting）是 JS 慢，紫色（Rendering）是布局/样式，绿色是绘制；
  • 底部 Summary：各阶段耗时占比，一眼看出钱被谁领走了。

代码示例 ​

给场景做一个常驻页内 HUD：每 0.5 秒刷新一次，同时显示帧时间（均值与峰值）、draw calls / 三角形、JS 堆内存——这就是预算表的"仪表盘"：

js
import * as THREE from 'three'
import { OrbitControls } from 'three/addons/controls/OrbitControls.js'

// —— 常规场景搭建（略，与前几章一致）——
const scene = new THREE.Scene()
scene.background = new THREE.Color(0x0b0e14)
const camera = new THREE.PerspectiveCamera(50, innerWidth / innerHeight, 0.1, 200)
camera.position.set(6, 6, 10)
const renderer = new THREE.WebGLRenderer({ antialias: true })
renderer.setSize(innerWidth, innerHeight)
renderer.setPixelRatio(Math.min(devicePixelRatio, 2))
document.getElementById('app').appendChild(renderer.domElement)
const controls = new OrbitControls(camera, renderer.domElement)
scene.add(new THREE.HemisphereLight(0xbfd9ff, 0x202020, 1))
scene.add(new THREE.Mesh(
  new THREE.TorusKnotGeometry(1, 0.3, 160, 24),
  new THREE.MeshStandardMaterial({ color: 0x4f9cf9, roughness: 0.4 })
))

// —— 预算：目标 60fps，帧时间红线 16.6ms ——
const BUDGET_MS = 16.6

// —— 采集状态：0.5s 一个采样窗口 ——
const hud = document.getElementById('hud')
let frames = 0          // 窗口内帧数
let winStart = performance.now()
let lastFrame = winStart
let costSum = 0         // 窗口内帧时间总和（算均值）
let costPeak = 0        // 窗口内最长一帧（抓尖峰）

const timer = new THREE.Timer()
timer.connect(document)
renderer.setAnimationLoop(() => {
  timer.update()
  const frameStart = performance.now()
  controls.update()
  renderer.render(scene, camera)

  // 采集：帧时间 = 相邻两帧 rAF 回调的间隔
  const now = performance.now()
  costSum += now - lastFrame
  costPeak = Math.max(costPeak, now - lastFrame)
  lastFrame = now
  frames++

  if (now - winStart >= 500) { // 0.5s 窗口结束，刷新 HUD
    const avg = costSum / frames
    const mem = performance.memory
      ? (performance.memory.usedJSHeapSize / 1048576).toFixed(0) + ' MB'
      : 'N/A（非 Chrome）'
    const info = renderer.info
    // 超红线的指标标红提示（HUD 里用 CSS 类控制颜色）
    hud.innerHTML =
      `帧时间：均值 <b class="${avg > BUDGET_MS ? 'over' : ''}">${avg.toFixed(1)}ms</b>` +
      `　峰值 <b class="${costPeak > BUDGET_MS * 2 ? 'over' : ''}">${costPeak.toFixed(1)}ms</b><br>` +
      `draw calls：<b>${info.render.calls}</b>　triangles：<b>${info.render.triangles.toLocaleString()}</b><br>` +
      `JS 堆内存：<b>${mem}</b>　geometries：${info.memory.geometries}　textures：${info.memory.textures}`
    frames = 0; costSum = 0; costPeak = 0; winStart = now // 开新窗口
  }
})

要点：峰值帧时间比平均帧率更能反映卡顿——平均 60fps 但偶尔一帧 80ms，用户看到的就是"卡了一下"。所以 HUD 同时盯均值与峰值，双双对照预算红线。

常见问题解答 ​

Q1：Stats 显示 60fps，但画面看起来还是一顿一顿的？

FPS 是平均值，会掩盖尖峰。比如 1 秒里 59 帧都是 16ms、1 帧是 80ms，平均下来仍接近 60fps，但那一个长帧人眼一定能察觉。排查思路：① 切到 Stats 的 MS 页看帧时间曲线是否抖动；② 用本篇 HUD 的峰值帧时间抓尖峰；③ 打开 DevTools Performance 录制，找红色长帧——常见元凶是 GC、纹理首次上传、着色器即时编译、主线程长任务。优化目标应是"帧时间方差小"，而不只是"平均帧率高"。

Q2：performance.memory 只有 Chrome 有，其它浏览器怎么办？

分层兜底：① 先判断 if (performance.memory) 再读，不支持的浏览器显示 N/A，别让 HUD 报错；② 显存占用本来就没有跨浏览器 API，可以自己估算——遍历场景累加纹理的 宽×高×4 字节×1.33（mipmap）；③ Firefox 可在地址栏输入 about:memory 手动查看；④ 真机内存压力测试直接观察是否闪退/白屏，低端机上这比读数更诚实。跨浏览器场景把预算验收的主力放在帧时间上，它是到处都能测的硬指标。

Q3：预算到底定多少合适？

三步定预算：① 看用户群：统计目标用户的设备分布，取最弱的一档作为红线基准——大众 C 端产品通常按"中端安卓机 60fps、低端机 30fps"定；② 留余量：在理论极限上打 7 折，例如中端机 calls 理论能扛 700，预算就写 500，余量留给系统调度、GC 与后台任务；③ 实测校准：拿 2~3 台真机跑你的场景，把"刚好开始掉帧"的读数记下来，预算定在那个读数的 70%~80%。预算不是一次定终身，每个大版本复测一次。

Q4：帧时间都花在哪儿了，怎么快速拆分？

粗略拆分用 performance.now() 掐三段：渲染前脚本耗时（场景更新/动画）、renderer.render() 调用耗时（CPU 提交）、以及两者之外的时间（GPU 等待与浏览器合成）。若 render() 耗时高——CPU 瓶颈，查 draw calls；若总帧时间高但 render() 很低——多半 GPU 瓶颈，查三角形、像素比与后处理。精确拆分交给 DevTools Performance 面板的火焰图。

动手小练习 ​

  1. 把 HUD 的采样窗口从 0.5s 改成 3s，观察均值与峰值的变化——体会"窗口越长越能掩盖尖峰"，理解为什么采集窗口不宜过长。
  2. 在 HUD 里加一行"预算达成率"（窗口内帧时间 ≤ 16.6ms 的帧数占比），把场景旋转着跑 10 秒，看达成率是 99% 还是只有 80%。
  3. 打开 Chrome DevTools Performance 录制 5 秒你的页面，在火焰图里找到最长的一帧，说出它的耗时被哪一类任务（Scripting/Rendering/Painting）领走了。
