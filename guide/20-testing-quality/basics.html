20.1 基础入门：3D 页面的可测性设计 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑲ 再学习本篇。

核心概念讲解 ​

接桥：预算是纸面目标，测试是硬约束 ​

上一模块 19.1 性能预算与采集 里，我们给项目开了一张"工资单"：帧时间 ≤ 16.6ms、draw calls ≤ 500、纹理显存 ≤ 512MB。但预算写在文档里，只是纸面目标——没人盯着，下个版本有人给园区加两栋楼，draw calls 就悄悄超支了，直到用户投诉才发现。

这一模块把预算从纸面搬进流水线：把每一条预算写成一条会自动运行的断言。改一行代码，CI 立刻告诉你"draw calls 从 320 涨到 510，超红线了"——约束不再靠自觉，靠门禁。

一句话：没有测试的预算表，就像没有门禁的小区规定——全靠自觉，等于没有。

3D 页面为什么难测 ​

写过普通 Web 页面测试的人，第一次测 3D 页面都会懵，因为三座大山：

难点普通页面3D 页面
输出DOM 树，可断言文本/类名/属性一张像素画布，没有语义可断言
时间交互是离散的点击，断言时机明确动画逐帧连续，"第几秒的画面"每次不同
环境渲染结果跨平台基本一致不同 GPU/驱动的抗锯齿、精度，像素会有差异

断言 canvas 元素 toBeTruthy() 毫无意义——那只能证明画布存在，证明不了画对了。所以 3D 测试的核心思路是：别指望用像素断言一切，分层测。

可测性设计三原则 ​

① 场景与渲染解耦。把"搭场景"写成一个纯函数：传入参数，返回 scene 对象；不碰 renderer、不启动渲染循环、不读 window。这样单测里不需要 WebGL 环境，直接对返回的场景图做断言——树上有几个节点、巡逻车是不是贴在 y=0.2 的高度，全是普通对象检查，Node 里毫秒级跑完。

② 确定性随机。楼群高度、粒子初速度常用 Math.random()，每次运行都不同，断言没法写、截图基线也永远对不上。改用带种子的随机数：

js
import seedrandom from 'seedrandom'
const rng = seedrandom('campus')  // 同一份种子 → 同一串"随机"数，跨机器逐位一致
const h = 1 + rng() * 10          // 凡是 Math.random() 的地方都换成 rng()

③ 暴露测试钩子。页面入口挂两行，e2e 测试就能摸到场景内部：

js
window.__scene = scene        // 测试钩子：暴露场景图
window.__renderer = renderer  // 顺手暴露 renderer.info 性能读数

测试里 page.evaluate(() => window.__scene.children.length) 即可读到真实场景。纪律：名字统一双下划线前缀、只在测试参数（如 ?test=1）或开发构建下注入，别污染生产环境。

3D 项目的测试金字塔 ​

层测什么工具速度与稳定性
纯逻辑单测数据台账、配置计算、状态机Vitest最快最稳，多写
场景图断言节点数量/位置/层级/材质齐全Vitest + three（不渲染）快而稳，主力
视觉回归像素级截图对比Playwright + 软件渲染慢而脆，只保关键视角

越往下越便宜，越往上越接近用户所见。下层多写，上层少而精——视觉回归守住 3~5 个关键视角就够，别给动画每一帧都截图。

代码示例 ​

假设把 21.3 园区 Demo 的场景搭建抽成了纯函数 buildCampus(seed)（只返回 scene，不渲染），给它写场景图单测：

ts
// campus.spec.ts —— Vitest，跑在 Node 里，全程不需要 GPU
import { describe, it, expect } from 'vitest'
import { buildCampus } from '../src/campus'   // 纯函数：seed → scene

describe('园区场景图', () => {
  // 固定种子搭一份场景，全部用例共享——确定性随机保证每次构建一致
  const scene = buildCampus('campus')

  it('楼群必须是 1 个 InstancedMesh，共 63 栋', () => {
    const city = scene.getObjectByName('city')     // 按名字找节点
    expect(city).toBeDefined()
    expect(city!.isInstancedMesh).toBe(true)       // 16.2 的纪律：一次 draw call
    expect((city as any).count).toBe(63)           // 台账里 63 栋楼
  })

  it('0 号楼位置与台账一致（确定性随机）', () => {
    const city = scene.getObjectByName('city') as any
    const m = new Float32Array(16)
    city.getMatrixAt(0, { elements: m })           // 取 0 号实例的矩阵
    // 种子固定 → 0 号楼的 y 高度是定值，断言到小数点后 3 位
    expect(m[13]).toBeCloseTo(3.412, 3)            // 矩阵第 13 项 = y 平移
  })

  it('初始无告警：instanceColor 尚未染色', () => {
    const city = scene.getObjectByName('city') as any
    expect(city.instanceColor).toBeNull()          // 有告警推送才该出现
  })

  it('扫描环贴地放置，不与地面 z-fighting', () => {
    const ring = scene.getObjectByName('scanRing') as any
    expect(ring.position.y).toBeCloseTo(0.05, 3)   // 贴地但略抬高
    expect(ring.rotation.x).toBeCloseTo(-Math.PI / 2, 5) // 躺平在地面
  })

  it('全场景可渲染：每个 Mesh 都有材质', () => {
    scene.traverse((o: any) => {
      if (o.isMesh) expect(o.material).toBeDefined()
    })
  })
})

要点：全程没有 WebGLRenderer。three 的场景树、矩阵、数学库都是纯 JS，Vitest 在 Node 环境直接跑。"画没画对"交给 20.2 的视觉回归，这一层只保证"场景搭得对"。

  }

常见问题解答 ​

Q1：CI 服务器没有 GPU，WebGL 测试跑得起来吗？

跑得起来，分两层看：① 场景图单测根本不碰 WebGL——three 的场景树、矩阵、加载器解析都是纯 JS，Node 里直接跑，这也是本篇建议把单测主力放在这一层的原因；② 需要真渲染的测试（下一篇的视觉回归），用软件渲染兜底——Playwright 自带的 Chromium 内置 SwiftShader（CPU 实现的 GL），无 GPU 的 Linux 容器里默认就能回退到它，新版本浏览器可加启动参数 --use-angle=swiftshader、--enable-unsafe-swiftshader 显式开启；Node 侧也有 headless-gl，但只支持 WebGL1 且维护停滞，新项目优先走 Playwright 路线。注意软件渲染比真 GPU 慢 10~50 倍，帧时间类断言要相应放宽（20.2 详述）。

Q2：单测里要 mock 掉 three 吗？

不要，这是 3D 单测最常见的误区。 我们测的是"场景图结构"——你的代码往树上挂了什么、参数算得对不对，这些用真 three 跑反而最诚实：真的 Vector3、真的矩阵乘法，断言才有意义。mock 掉 three 之后，断言的就只剩"我的代码调用了某个函数"，等于测了个寂寞。真正该 mock 的是外部副作用：网络请求（TextureLoader.load 的 fetch）、定时器、performance.now——这些用 Vitest 的 vi.fn() / vi.useFakeTimers() 处理。一句话：测场景图，不测渲染；mock 环境，不 mock three。

Q3：动画依赖时间，断言结果每次都漂，怎么控？

两招：① 注入时钟。动画函数别在内部 Date.now()，改成接收参数：tick(dt) 或 tick(t)，单测里手动喂时间——tick(0); tick(0.5); tick(1.0)，每一步的状态都是确定的，mixer.update(dt) 同理，喂固定步长就行；② 固定步长快进。要验证"3 秒后巡逻车到大门口"，就循环 180 次 tick(1/60)，代替真等 3 秒。e2e 层面同理：测试钩子里加 freeze()（停渲染循环、固定相机）和 step(n)（手动推 n 帧），截图只在 freeze 之后拍——画面静止，像素才可对比。

Q4：老项目场景搭建和渲染混在一起，怎么改造成可测？

三步小手术，不用重写：① 抽函数——把"new 一堆对象、add 进 scene"的代码原样搬进 buildCampus(seed)，返回 scene，渲染循环留在原地调用它；② 换随机源——全局搜 Math.random()，逐个换成注入的 rng()；③ 挂钩子——入口加两行 window.__scene / __renderer。改完行为零变化，但单测和 e2e 的门都打开了。可以先只抽一个子系统（比如楼群）练手，别一次动整个场景。

动手小练习 ​

  3. 给场景加一条"结构预算"断言：scene.traverse 统计 Mesh 总数与估算三角形总数，超过你们团队的预算红线就 fail，把它接进 npm run test:unit。
