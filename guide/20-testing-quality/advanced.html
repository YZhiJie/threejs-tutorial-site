20.2 进阶应用：视觉回归与性能断言 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑲ 与 20.1 可测性设计 再学习本篇。

核心概念讲解 ​

上一篇用场景图断言回答了"场景搭得对不对"。这一篇回答剩下两个问题："画得对不对"（视觉回归）和"跑得快不快"（性能断言）——前者盯像素，后者盯帧时间，都是 19.1 预算表在 CI 里的执行者。

视觉回归：让机器玩找茬 ​

原理一句话：第一次运行存一张"基线截图"，之后每次运行拍新图，逐像素对比，差异超阈值就失败。人眼回归 20 个页面要看到凌晨，机器对比 20 张图只要几十秒，而且连"阴影偏移了 2 像素"都逃不掉。

但像素对比天生怕噪，3D 页面尤甚。四条抗噪纪律，缺一条都会被"假阳性"淹没：

噪声源对策
视口/像素比不同配置里锁死 viewport 与 deviceScaleFactor: 1
动画时机漂移测试钩子 freeze() 停循环后再截图；随机动画用固定种子
首帧资源未就绪等"已渲染 N 帧"再动手，着色器编译、纹理上传都算完
动态内容（时钟、告警列表）截图时 mask 掉这些区域，只比稳定的画面

Playwright 截图对比配置 ​

Playwright 内置 toHaveScreenshot() 断言，核心参数：

ts
await expect(page).toHaveScreenshot('campus.png', {
  maxDiffPixelRatio: 0.01,   // 容忍 1% 像素有差异（抗锯齿噪声）
  threshold: 0.2,            // 单个像素的色差容忍（0~1，越小越严格）
})

首次运行本地没有基线会自动生成（或显式跑 npx playwright test --update-snapshots），基线按"浏览器 + 操作系统"分目录存放——所以基线必须在与 CI 一致的环境里生成（见 FAQ Q2）。

无 GPU 环境：SwiftShader 与 WebGL 兜底 ​

CI 容器没有显卡，Chromium 用 SwiftShader（CPU 软件实现的 GL）渲染 WebGL。启动参数建议显式给全：

ts
launchOptions: {
  args: [
    '--use-angle=swiftshader',        // WebGL 走软件渲染
    '--enable-unsafe-swiftshader',    // 新版 Chrome 要求显式允许
    '--disable-font-subpixel-positioning' // 字体亚像素对齐，减少文字噪声
  ]
}

反向场景——单测里不小心触到 WebGL，与其 mock 整个上下文，不如把架构调对：渲染相关代码收进"仅在浏览器执行"的薄壳层（20.1 的场景/渲染解耦），Node 里压根不 import 它。真绕不开时，可以给 HTMLCanvasElement.prototype.getContext 打一个返回 null 的桩，让 three 走"无 WebGL"分支——但记住这是兜底，不是设计。

性能断言：把帧时间变成数字 ​

采集方式：测试页里用 requestAnimationFrame 连续采样 100 帧，把相邻帧间隔存成数组，传回 Node 侧算均值与 P95（95 分位——比均值敏感，又不像最大值那样被单次 GC 带偏），然后对预算做断言：

ts
expect(stats.p95).toBeLessThan(33)   // 30fps 红线：19.1 的低端档预算
expect(info.calls).toBeLessThan(500) // draw calls 是结构量，CI 上最可靠

注意分工：draw calls、三角形数这类"结构量"在软件渲染下依然准确，适合做 CI 硬门禁；帧时间受 CI 虚机性能影响大，适合放宽阈值 + 趋势告警（FAQ Q3 详述）。

代码示例 ​

一份完整的 Playwright 测试：打开园区演示页 → 等 60 帧就绪 → 截图对比基线 → 采样 100 帧算 P95。逐段拆解：

① 准备工作：带测试参数打开页面，等"真正画过 60 帧"

ts
// campus.e2e.spec.ts
import { test, expect } from '@playwright/test'

test.beforeEach(async ({ page }) => {
  // ?test=1：页面据此注入 __scene / __renderer / __probe 测试钩子（见 20.1）
  await page.goto('/demos/digital-twin/campus-twin.html?test=1')
  // 等渲染循环真正跑过 60 帧：着色器编译、纹理上传全部完成，画面才稳定
  await page.waitForFunction(() => (window as any).__probe?.frames >= 60)
})

② 视觉回归：冻结画面，对比基线

ts
test('视觉：默认视角与基线一致', async ({ page }) => {
  // 冻结动画与相机（测试钩子实现：停渲染循环 + 渲染一帧静帧）
  await page.evaluate(() => (window as any).__probe.freeze())
  await expect(page).toHaveScreenshot('campus-default.png', {
    maxDiffPixelRatio: 0.01,          // 容忍 1% 差异像素，吃掉抗锯齿噪声
    mask: [page.locator('#alarm-list')] // 告警列表内容随时间变，盖掉不比
  })
})

③ 性能断言：采样 100 帧，算均值与 P95

ts
test('性能：P95 帧时间低于 33ms', async ({ page }) => {
  const stats = await page.evaluate(() => {
    return new Promise<{ avg: number; p95: number }>(resolve => {
      const times: number[] = []
      let last = performance.now()
      const tick = (now: number) => {
        times.push(now - last); last = now
        if (times.length < 100) requestAnimationFrame(tick) // 采满 100 帧
        else {
          times.sort((a, b) => a - b)
          const p95 = times[Math.floor(times.length * 0.95)]
          const avg = times.reduce((s, t) => s + t, 0) / times.length
          resolve({ avg, p95 })
        }
      }
      requestAnimationFrame(tick)
    })
  })
  console.log(`帧时间 avg=${stats.avg.toFixed(1)}ms p95=${stats.p95.toFixed(1)}ms`)
  expect(stats.p95).toBeLessThan(33)  // 19.1 预算：中端档 30fps 红线
})

④ 顺手做一条结构量断言（软件渲染下依然准确）

ts
test('预算：draw calls 低于 500', async ({ page }) => {
  const calls = await page.evaluate(
    () => (window as any).__renderer.info.render.calls
  )
  expect(calls).toBeLessThan(500)
})

常见问题解答 ​

Q1：截图总有零点几的像素差异，阈值放宽了又漏真回归，怎么办？

组合拳而非单靠阈值：① 固定种子 + freeze，把"内容本身的变化"降到零，剩下的只有渲染噪声；② mask 动态区域——时钟、告警列表、FPS 计数器这些每次必变的 UI，盖掉不参与对比；③ 两层参数搭配：threshold（单像素色差容忍，抗锯齿用 0.2 左右）+ maxDiffPixelRatio（差异像素占比，0.01 起步）；④ 仍有顽固噪声的区域，可以缩小截图范围到 locator.screenshot() 只比关键画面。目标不是"零差异"，是"差异全部可解释"——真回归的差异通常是成片的（几百像素起），噪声是零散的。

Q2：本地 macOS 生成的基线，到 Linux CI 上全挂，字体和抗锯齿都不一样？

渲染栈跨平台不可能逐像素一致，基线必须在与 CI 相同的环境里生成。标准做法：用官方容器镜像（如 mcr.microsoft.com/playwright:v1.xx.x-jammy）统一两边——本地更新基线也跑在容器里：docker run --rm -v $PWD:/work -w /work 镜像 npx playwright test --update-snapshots，再把生成的 PNG 提交进仓库。团队纪律：基线更新单独提交、PR 里附 diff 图说明"这次是故意改的视觉"。千万不要在 macOS 上更新基线再指望 Linux CI 通过。

Q3：CI 虚机里 SwiftShader 慢 10 倍，P95 < 33ms 永远过不了，性能断言还有意义吗？

分层处理：① 硬门禁换成结构量——draw calls、三角形数、纹理显存这些与 GPU 快慢无关，CI 上严格卡死（本篇第④条用例）；② 帧时间放宽 + 看趋势——CI 上用环境变量把阈值放宽（如 P95_BUDGET_MS=80），同时把每次运行的 avg/p95 收集起来画趋势曲线，"连续三次构建上涨 20%"告警，而不是单次超线就红；③ 真机/有 GPU 的自托管 runner 上保持 33ms 硬门禁，定时跑（如每晚）而非每个 PR。帧时间在不同机器间没有绝对可比性，同一台机器上的相对变化才是信号。

Q4：CI 里页面打开后 canvas 全黑 / 报 WebGL context 创建失败？

按序排查：① 确认启动参数带上了 --enable-unsafe-swiftshader（新版 Chrome 默认禁止软件 WebGL 回退）；② 在测试里加一行健康检查 page.evaluate(() => !!document.createElement('canvas').getContext('webgl2'))，失败就把 Chromium 的 stderr 打出来看具体原因；③ 容器内存给足（SwiftShader 渲大场景吃内存，Docker 默认 shm 太小会崩，加 --shm-size=1g）；④ 偶发的 context lost 可以让 playwright.config 里 retries: 1 吸收掉，但只允许重试一次——靠无限重试变绿的门禁等于没有门禁。

动手小练习 ​

  1. 给园区演示页加上 __probe 钩子（frames 计数 + freeze 方法），跑通本篇的截图对比，然后故意把某栋楼颜色改亮一度，观察 diff 图长什么样。
  2. 把视觉用例的 maxDiffPixelRatio 从 0.01 调成 0，跑一次看误报；再调回 0.01 并把告警列表 mask 掉，体会两层抗噪参数的分工。
  3. 把性能采样从 100 帧改成 1000 帧，对比 P95 的稳定性；再算一个 P99，说说为什么门禁用 P95 而不是 P99 或最大值。
