38.3 实战案例：关卡系统、计分与存档 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ②④ 与 ㉓ 再阅读。

核心概念讲解 ​

接桥：㉟ 的编辑器产出场景，㊱ 的配置描述场景，现在要让场景"有目标" ​

到了这里，你已经能让场景漂亮地渲染出来，也能用编辑器或配置文件把平台、道具、灯光摆到位。相关背景可以回看 ㊱ 配置化平台。但一个"场景"离"关卡"还差最后一步：玩家进来之后要做什么、做多久、做得好不好、下次还能不能接着挑战。

这一步就是关卡系统。它不负责渲染，也不负责角色控制，而是把 38.1 的状态机与 38.2 的交互事件组织成一条可结算的流程：准备 → 游玩 → 暂停 → 完成 / 失败 → 结算 → 重玩。再加上计分、连击、评级与存档，场景才真正变成"可以反复玩的内容"。

本篇的演示是一个完整可玩的限时收集关卡：45 秒内收集 5 个光球，HUD 显示倒计时、得分、连击与目标进度，结束后按 S/A/B 评级，并把最佳成绩写进带版本号的 localStorage 存档。它不包含跳跃与碰撞，所有玩法都建立在"移动 + 距离判定 + 状态"之上。

关卡配置 DSL：把"关卡"变成数据 ​

关卡配置应该描述"目标与规则"，而不是描述"每一帧做什么"。一个够用的骨架包含：

json
{
  "id": "level-01",
  "title": "限时收集 · 关卡一",
  "timeLimit": 45,
  "targets": [
    { "type": "orb", "position": [-5.2, -4.2], "weight": 1 }
  ],
  "goal": { "type": "collect", "need": 5 },
  "score": {
    "base": 80,
    "comboWindow": 2.6,
    "comboCap": 5,
    "timeBonusPerSecond": 8
  },
  "rating": { "S": 1200, "A": 850 },
  "saveSlot": "1"
}
字段含义调整后的体感
timeLimit关卡总时长越短越强调路线规划
goal.need需要完成的目标数越少越像教学关，越多越像耐力关
score.base单次收集基础分决定"随手收集"的收益下限
comboWindow连击有效期（秒）越长越鼓励连续路线，越短越强调精确
comboCap连击倍率上限防止后期分数指数爆炸
timeBonusPerSecond剩余时间折算系数让"快"与"稳"形成取舍
rating评级阈值直接决定玩家追求的目标

配置化的关键不是"把所有东西都塞进 JSON"，而是把策划会改的参数抽出来。目标坐标、时限、分数、阈值属于高频调整项；网格材质、雾效、相机参数属于美术方向，放在场景配置里更合适。两者混在一起，改一个分数线都要重新导出整个场景。

关卡状态机：ready / playing / paused / finished / failed ​

关卡状态机与角色状态机同构，但关注的是"整局流程"：

当前状态可接收事件去向说明
readystartplaying展示规则，等待玩家确认
playingpause / finish / fail / restartpaused / finished / failed / ready计时与判定只在此时推进
pausedresume / restartplaying / ready冻结逻辑，仍可渲染与旋转视角
finishedrestartready成功结算后的终态
failedrestartready超时或目标失败后的终态

把 finished 与 failed 分开很重要：结算面板的文案、评级、是否写入最佳成绩都不同。如果只用 finished 加一个 success 布尔值，很容易出现"失败局也刷新了最佳分数"的 bug。

状态迁移同样要表驱动：

js
const PHASE_ALLOWED = {
  ready: { start: 'playing' },
  playing: { pause: 'paused', finish: 'finished', fail: 'failed', restart: 'ready' },
  paused: { resume: 'playing', restart: 'ready' },
  finished: { restart: 'ready' },
  failed: { restart: 'ready' }
}

function setPhase(next, event) {
  const allowed = PHASE_ALLOWED[phase] ? PHASE_ALLOWED[phase][event] : undefined
  if (allowed !== next) return false
  phase = next
  return true
}

注意 playing 状态下允许 restart 直接回 ready，这是"玩家想重开"的正常路径；但 paused 状态下不允许 finish，因为暂停时不应该结算。把这些规则写进表里，比在按钮回调里各写一遍 if 可靠得多。

计分与连击：让操作质量有上限 ​

一个简单但有决策空间的计分公式：

text
单次得分 = base × 当前连击倍率
连击倍率 = min(连击次数, comboCap)
最终得分 = 单次得分总和 + 剩余时间 × timeBonusPerSecond

连击的判定通常是"两次收集的间隔小于 comboWindow"：

js
if (comboTimer > 0) combo = Math.min(combo + 1, 5)
else combo = 1
comboTimer = 2.6
score += 80 * combo

这样设计有三个效果：连续收集的收益显著高于逐个慢慢收集；comboCap 防止高分无限膨胀；时间奖励让"快"与"连"形成双重压力，但不会压过收集本身。若不做上限，5 个目标就能滚出 1、2、3、4、5 的倍率；目标增加到 20 个，分数会变成天文数字，评级阈值也会失效。

计分还要防三类"刷分"：重复触发同一个目标、暂停期间继续计时、结算后仍能收集。对应的守卫分别是目标 active 标记、只在 playing 推进逻辑、finishLevel 里检查当前状态。

存档：版本化、损坏兜底、多存档槽 ​

localStorage 只存字符串，所以存档必须自己定义"信封"：

json
{
  "version": 1,
  "slots": {
    "1": { "bestScore": 1430, "bestRating": "S", "bestTime": 18.4, "plays": 12 },
    "2": { "bestScore": 0, "bestRating": "-", "bestTime": 0, "plays": 0 }
  },
  "updatedAt": 1793800000000
}

三个工程要点：

  1. 版本号：读取时先比对 version。未来字段变更时可以走迁移函数，而不是让旧存档把新代码喂崩。
  2. 字段校验：不要相信 JSON.parse 的结果。分数必须是有限数字，评级必须是字符串，槽位必须存在。任何一项不合法，都按"损坏存档"处理。
  3. 兜底：解析失败时 removeItem 并返回默认存档，同时在界面上提示"存档已损坏，已回退"。最糟的做法是让异常冒到顶层，整个页面白屏。

多存档槽的价值不只是"两个存档"，而是让玩家可以分别挑战不同难度或不同账号。实现上把 slots 设为对象，用 currentSlot 指向当前槽；切换槽位时只换读取目标，不销毁场景。

写入也要 try/catch：隐私模式、存储配额满、企业策略禁用 localStorage 都会让 setItem 抛错。写入失败时保留内存里的成绩，只提示"本次成绩未保存"，不要阻断结算。

暂停与恢复：时间缩放的坑 ​

暂停最常见的错误是"只把 isPaused 设为 true，但计时器还在跑"。恢复后倒计时瞬间少了几秒，或者角色在暂停期间继续受重力影响。

正确结构是主循环永远消费 dt，但只在 playing 推进游戏逻辑：

js
renderer.setAnimationLoop(() => {
  timer.update()
  const dt = Math.min(timer.getDelta(), 0.05)
  if (phase === 'playing') {
    updateGame(dt)
    updatePlayer(dt)
    animateWorld(dt)
  }
  controls.update()
  renderer.render(scene, camera)
})

这样即使暂停 10 秒，timer 的 delta 也在每帧被消费掉，恢复时不会出现一个巨大的 dt。如果使用物理引擎，还要注意引擎内部的 step 是否被暂停；只停渲染不停物理，角色会在暂停期间继续下落。更稳妥的做法是暂停时停止调用 world.step，并在恢复时重置累积时间。

另一个坑是动画与逻辑用了不同的时间源。目标悬浮用 performance.now()，倒计时用 dt，暂停后就会出现"光球还在转、倒计时不动"的割裂。统一用游戏内累积时间，暂停时一起冻结。

结算与重玩：结果对象与幂等奖励 ​

结算不应该写成一堆散落的赋值，而是先生成一个结果对象：

js
const result = {
  success: true,
  score: finalScore,
  timeBonus,
  remaining,
  grade,
  elapsed
}

这个对象同时喂给结算面板、存档系统与埋点，避免三处各算一遍分数。评级函数应该是纯函数：输入分数与是否成功，输出 S/A/B，方便单测与调参。

"重玩"要做的是重置一局的状态，而不是重建整个场景：分数、连击、计时、目标显隐、玩家位置、暂停遮罩全部回到初始值，相机与场景保留。重建场景会让加载时间变长，也容易泄漏旧的监听器。

奖励发放必须幂等：同一局只写一次最佳成绩、只发一次成就。用 phase 守卫即可——结算函数开头判断 if (phase !== 'playing') return，重复调用天然被拒。

一局的生命周期：进入、退出与资源清理 ​

把"打开页面"与"开始一局"分开。页面加载时只做一次的场景初始化、材质编译、事件绑定，不应该在每次重玩时重复执行；而"一局"的范围是分数、计时、目标显隐、玩家位置、连击与暂停遮罩。

推荐给关卡写一对 enterLevel() / exitLevel()：enter 里重置本局数据、恢复目标、把阶段切成 ready；exit 里停止计时、清空输入意图、解绑本局临时订阅的事件总线回调。很多人只写 reset()，忘了清理定时器与监听器，重玩几次之后同一个事件被触发多次，分数翻倍、结算面板叠着弹。

如果关卡会切换场景，还要处理几何体与材质的释放；演示只有一个场景，所以只重置对象状态，不销毁 GPU 资源。记住一条判断标准：跨局保留的东西放在页面级，局内变化的东西放在 enterLevel。分不清这条线，重玩逻辑迟早变成一堆"上次的残留"。

难度曲线：把参数当旋钮 ​

难度不是"把时间调短"这一根旋钮，而是多个参数的组合：

关卡时限目标数连击窗口S 阈值设计意图
145s52.6s1200教学：熟悉移动与收集
240s62.2s1350路线开始有取舍
335s71.9s1500连击与时间双重压力
430s81.6s1650精通：几乎不允许回头

调参时一次只动一个旋钮，并记录每关的通关率与平均分。时间与目标数同时收紧，玩家只会感到"莫名其妙地难"；先拉长路线，再压缩窗口，难度曲线才有层次。

术语解释：

  • 关卡配置 DSL：用声明式数据描述目标、时限、计分与评级，把策划参数与运行时逻辑分离。
  • 终态 terminal state：没有后续主动事件、只能被重开或退出的状态，如 finished、failed。
  • 连击窗口 combo window：两次有效操作之间允许的最大间隔，超过则倍率归零。
  • 存档信封 save envelope：带 version 与外层结构的存储格式，用于校验、迁移与多槽管理。
  • 幂等 idempotent：重复执行不改变结果，结算与奖励发放必须满足。

五个常见坑 ​

  1. 暂停只停渲染不停逻辑：倒计时、物理、动画继续跑，恢复后时间对不上。所有推进都要挂在 playing 状态上。
  2. 失败局写入最佳成绩：只判断"分数更高"，没判断 success，会让 0 分失败局覆盖不了高分，却可能把"失败但分高"写进最佳。
  3. 存档没有版本号：字段一改，旧数据把新代码喂出 undefined，界面显示 NaN。版本号与字段校验是最小成本。
  4. 结算面板重复弹出：目标收集与倒计时同时触发结算，或者暂停按钮误触。结算入口要有状态守卫。
  5. 重玩不重置目标：只把分数清零，光球仍是隐藏状态，第二局一开始就"无目标可收集"。

  const finalScore = score + bonus

function collectTarget(target) {
  if (phase !== 'playing' || !target.active) return
  target.active = false
  target.group.visible = false
  collected += 1
  combo = comboTimer > 0 ? Math.min(combo + 1, LEVEL.comboCap) : 1
  comboTimer = LEVEL.comboWindow
  score += LEVEL.baseScore * combo
  if (collected === targets.length) finishLevel(true)
}

④ 存档读取：版本、字段、兜底三件套：

js
function loadSave() {
  try {
    const raw = localStorage.getItem(SAVE_KEY)
    if (!raw) return makeSave()
    const data = JSON.parse(raw)
    if (!data || data.version !== SAVE_VERSION) throw new Error('版本不匹配')
    if (!isValidSlot(data.slots?.['1']) || !isValidSlot(data.slots?.['2'])) {
      throw new Error('字段损坏')
    }
    return data
  } catch (error) {
    try { localStorage.removeItem(SAVE_KEY) } catch (removeError) { /* 忽略 */ }
    return makeSave()
  }
}

⑤ 主循环：暂停时仍消费 delta：

js
renderer.setAnimationLoop(() => {
  timer.update()
  const dt = Math.min(timer.getDelta(), 0.05)
  if (phase === 'playing') {
    updateGame(dt)
    updatePlayer(dt)
    visualTime += dt
    animateWorld(dt)
  } else if (phase !== 'paused') {
    visualTime += dt
    animateWorld(dt)
  }
  controls.update()

})

暂停分支里不推进 visualTime，所以目标悬浮、旋转与角色呼吸都会冻结；但 timer.update() 始终执行，恢复时不会出现时间跳变。

常见问题解答 ​

Q1：暂停后物理 / 动画继续跑，恢复时角色掉下去了怎么办？

说明暂停只停了输入或渲染，没停逻辑步进。处理顺序是：先把"是否推进世界"收敛成一个状态位，暂停时跳过 updateGame 与物理 step；主循环仍然每帧调用计时器并消费 dt，避免恢复瞬间累积出一个巨大的 delta；如果物理引擎内部有累加器，恢复前重置它或把 dt 置零。动画也要用同一套游戏时间，不能用 performance.now() 另起一套，否则会出现"倒计时停了、光球还在转"的割裂。

Q2：存档损坏为什么会导致白屏？怎么兜底？

常见原因是直接 JSON.parse(localStorage.getItem(...)) 并把结果当可信对象用：字段缺失、类型不对、版本升级后结构变化，都会在后续访问 .slots['1'].bestScore 时抛出异常，而异常发生在渲染前的初始化阶段，页面就白了。兜底三步：try/catch 包住解析与校验；校验 version、槽位存在性、分数字段是否为有限数字；失败时删除损坏键并返回默认存档，同时在界面上用一行提示告知玩家"存档已重置"，让失败可见而不是静默。

Q3：为什么结算后分数还会变？

多半是结算后仍有收集逻辑在跑。检查三处：collectTarget 是否判断当前阶段为 playing；倒计时归零与"收集最后一个目标"是否会在同一帧重复调用结算；结算面板的按钮是否会再次触发 finishLevel。最稳的方案是让 finishLevel 第一行做状态守卫 if (phase !== 'playing') return，并在收集入口也做同样判断。结算应当只发生一次，结果对象只生成一次。

Q4：localStorage 存不下或直接抛错怎么办？

localStorage 在隐私模式、配额已满、企业策略禁用时都可能抛 QuotaExceededError 或 SecurityError。写入必须 try/catch，失败时保留内存中的成绩并提示"本次成绩未保存"，不能阻断结算流程。更进一步可以降级到 sessionStorage（仅当前会话）或 IndexedDB（容量更大但异步）。不要把"存档成功"当成结算的前置条件，否则一次存储异常就会让整局游戏卡死。

动手小练习 ​

  1. 把演示的时限改成 30 秒、目标数改成 7、连击窗口改成 1.8 秒，分别单独调整并记录通关分数变化，找出哪一个参数对难度影响最大；据此重设 S/A/B 阈值。
