38.1 基础入门：输入映射与状态机 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ②④ 与 ㉓ 再阅读。

核心概念讲解 ​

接桥：㉓ 的角色能跑能跳，但"它在想什么"没人管 ​

在 ㉓ 物理仿真与游戏化 里，我们拼出了一台能通关的闯关小游戏：胶囊体角色、刚体平台、土狼时间、跳跃缓冲、金币感应区。那篇解决的是"角色如何被物理世界接住"，属于运动层。

但把镜头拉远，你会看到另一堆散落的布尔值：isGrounded、isJumping、isAttacking、isHurt、canMove。它们各自在不同函数里被打开、关闭，最后组合出一张没人能完整说清的真值表。角色明明在跳跃，却又被判定为可以攻击；受伤动画还没播完，移动输入又把角色推着走。物理是对的，行为却是乱的。

这一篇不重复跳跃与碰撞，只补上"系统层"的第一块：输入如何变成语义动作，动作又如何驱动一个可验证的状态机。可以把它理解成给角色装上"决策中枢"——物理继续负责"能不能站住"，状态机负责"现在该做什么"。

输入映射层：从 keyCode 到语义动作 ​

最原始的写法是在 keydown 里直接读 event.keyCode，然后到处写 if (keyCode === 32) jump()。这种写法有三个问题：keyCode 已被废弃且布局相关；同一动作在键盘、手柄、触摸屏上要复制三套判断；改键位要全项目搜索数字。

正确做法是加一层输入映射：设备事件 → 语义动作 → 游戏逻辑。设备层只负责"哪个物理输入被按下"，游戏层只认 jump、attack、moveForward 这样的词。

js
const KEY_TO_ACTION = {
  KeyW: 'moveForward',
  KeyA: 'moveLeft',
  KeyS: 'moveBack',
  KeyD: 'moveRight',
  Space: 'jump',
  KeyJ: 'attack',
  KeyH: 'hurt'
}

addEventListener('keydown', (event) => {
  const action = KEY_TO_ACTION[event.code]
  if (!action) return
  event.preventDefault()
  input.press(action)
})

注意这里用 event.code 而不是 event.key：code 表示物理键位，key 会受输入法、大小写、键盘布局影响。做"按 W 前进"的固定键位时，code 更稳定；做"按当前布局的某个字符"时，才轮到 key。

映射层还要处理三件事：长按与单击的区别（移动是持续意图，跳跃是边沿触发）、重复事件（浏览器长按会持续触发 keydown，用 event.repeat 过滤）、多设备合并（键盘、手柄、触摸按钮都向同一个 input 对象写状态，而不是各写各的）。

有限状态机：把"正在做什么"变成一个变量 ​

有限状态机（Finite State Machine，FSM）只有四个要素：

  1. 状态集合：角色可能处于哪些状态，例如 idle、move、jump、attack、hurt。
  2. 转移条件：在某个状态下，收到什么事件才会切换。
  3. 进入 / 退出动作：切进状态时初始化什么，离开时清理什么。
  4. 每帧更新：当前状态下持续推进的逻辑，例如计时、动画、位移。

最关键的一条纪律是：任何时刻只有一个当前状态。不要用 isJumping && isAttacking 这种组合表达，因为它允许出现"既跳又攻击"的非法组合。把状态收敛成一个字符串，非法组合就从"可能发生"变成"根本无法表示"。

角色状态机的合法出口可以写成一张表：

当前状态含义可接收事件去向
idle站立待机move / jump / attack / hurtmove / jump / attack / hurt
move地面移动stop / jump / attack / hurtidle / jump / attack / hurt
jump空中land / hurtidle 或 move / hurt
attack攻击动作done / hurtidle 或 move / hurt
hurt受击硬直recoveridle

这张表就是"合法转移表"。它的价值不在于好看，而在于所有非法输入都有统一的拒绝路径：查表失败就记一条日志、播放一个"无效"反馈，而不是让角色进入一个没人预料的状态。

三种写法：switch、状态对象与表驱动 ​

同一个状态机有三种常见实现，复杂度与可维护性递增：

写法核心形态优点代价适用规模
switch在 update 里按当前状态分支直观、代码少状态一多就变成巨型函数，转移散落各处3~4 个状态
状态对象每个状态一个对象，含 enter / update / exit逻辑内聚，易扩展需要约定生命周期，跨状态共享要设计5~10 个状态
表驱动一张转移表 + 通用执行器转移集中可审计、易做工具化前期抽象成本高，动态逻辑要额外钩子10 个以上或需要配置化

本篇演示采用"表驱动 + 状态对象"的混合：转移表负责合法性，状态对象负责表现。这样既能在面板上高亮当前状态、打印转移日志，也能让每个状态拥有自己的计时与动画。

js
const TRANSITIONS = {
  idle: { move: 'move', jump: 'jump', attack: 'attack', hurt: 'hurt' },
  move: { idle: 'idle', jump: 'jump', attack: 'attack', hurt: 'hurt' },
  jump: { land: 'idle', hurt: 'hurt' },
  attack: { done: 'idle', hurt: 'hurt' },
  hurt: { recover: 'idle' }
}

严格模式下，request('attack') 在 jump 状态查不到出口，就直接拒绝。宽容模式则允许"容错转移"，用来观察两套策略的差异——这不是鼓励放宽，而是让调试时能看清"如果没有守卫，角色会滑到哪里"。

角色状态示例：idle / move / jump / attack / hurt ​

五个状态足够覆盖大多数第三人称角色：

  • idle：待机呼吸，允许所有主动动作。
  • move：持续位移，松开方向键回到 idle；移动中仍可跳跃、攻击、受击。
  • jump：上升与下落由状态时间驱动，落地发 land；跳跃中只允许受击，攻击输入进入缓冲。
  • attack：固定时长的攻击动作，结束发 done；攻击中可被受击打断。
  • hurt：受击硬直，期间不接受主动动作，结束发 recover。

这里有一个容易忽略的细节：自动转移与玩家事件要走同一个入口。落地、攻击结束、硬直结束都是"系统事件"，也必须经过 request('land') 这样的函数，而不是直接改 state。否则日志会缺失一半，调试时根本还原不出完整时间线。

输入缓冲与土狼时间：宽恕玩家的两种时间窗 ​

土狼时间解决的是"离开平台边缘后仍允许起跳"，输入缓冲解决的是"动作收尾前按下的键不丢失"。两者都属于宽容时间窗，但作用对象不同：

  • 土狼时间（Coyote Time）宽恕"位置判断的迟滞"，窗口通常 0.1~0.15 秒，属于物理 / 地面检测层。
  • 输入缓冲（Input Buffer）宽恕"动作切换的空档"，窗口通常 0.15~0.3 秒，属于输入与状态机层。

缓冲的实现不是"立刻执行"，而是"先存一个待办动作，等当前状态回到可行动状态再补发"。一个单槽缓冲就够用：

js
function requestWithBuffer(action) {
  if (state === 'jump' || state === 'attack') {
    bufferedAction = action
    bufferTimer = 0.22
    return
  }
  request(action)
}

要记住两条纪律：缓冲只存一个动作，后按的覆盖先按的；补发前要重新查合法转移表，不能因为"是缓冲来的"就跳过守卫。否则缓冲会变成非法状态的另一个后门。

帧率无关：dt 积分与状态计时 ​

状态机的所有时间都必须用 dt 累加，而不是"经过了多少帧"。60Hz 与 144Hz 下，固定帧数计时会让动作时长差出一倍多。

js
const timer = new THREE.Timer()
timer.connect(document)

renderer.setAnimationLoop(() => {
  timer.update()
  const dt = Math.min(timer.getDelta(), 0.05)
  stateTime += dt
  update(dt)
  renderer.render(scene, camera)
})

Math.min(dt, 0.05) 是必要的保护：切后台、断点调试、长任务卡顿都会让 dt 突然变大，一次积分可能把角色瞬移穿墙。把单帧上限压到 50ms，相当于"卡顿后最多补 20 分之一秒的逻辑"，宁可慢放，也不要瞬移。

调试可视化：让状态机自己说话 ​

状态机最难排查的不是"逻辑写错"，而是"没人知道现在到底在哪个状态"。因此调试信息要和状态机一起设计，而不是出 bug 后再临时加 console.log。

最小可用的调试面板包含三块：

  1. 当前状态徽章：用颜色区分 idle、move、jump、attack、hurt，一眼看出角色"在想什么"。
  2. 状态机图高亮：把合法转移画成节点与连线，当前节点发光。它同时是文档、是调试器，也是新人的上手图。
  3. 转移日志：记录"从哪来、到哪去、因为什么事件、是否被拒绝"。日志只保留最近 10 条，避免刷屏，但足够还原一次误操作的上下文。

日志要区分四种结果：合法转移、非法拒绝、宽容强制、输入缓冲。颜色与符号必须稳定，否则玩家看久了只会看到一堆彩色文字。演示里用 ✓ 表示合法、✕ 表示拒绝、~ 表示宽容、! 表示缓冲，并且每条都带时间戳。排查"为什么按了没反应"时，先看日志里有没有一条红色拒绝，比在代码里撒 console.log 快得多。

更进一步，可以把"事件 → 转移"记录成可回放的序列：记录时间、动作、前后状态，就能在离线环境重放一局，复现偶发 bug。这一步不影响线上性能，却能把"我怎么也复现不了"变成"把日志粘给我"。

术语解释：

  • 语义动作 semantic action：与设备无关的游戏意图，如 jump、attack，不是某个具体按键。
  • 有限状态机 FSM：任意时刻只处于一个状态，且只能沿合法转移表切换的系统。
  • 合法转移表 transition table：用数据描述"从哪个状态、收到哪个事件、去哪个状态"，是状态机的单一事实来源。
  • 输入缓冲 input buffer：把动作收尾前按下的输入暂存一小段时间，回到可行动状态时补发。
  • 土狼时间 coyote time：离开地面后的短暂宽限期，期间仍允许起跳。

三个常见坑 ​

  1. 状态与布尔值混用：一边维护 state，一边又维护 isJumping、isAttacking。两者迟早不同步，表现为"状态显示 idle，角色却还在空中"。
  2. 只在 exit 里清动画，忘了清逻辑：离开 attack 时只停动画，却没把"攻击中不可移动"的标记复位，角色会永久失去移动能力。
  3. 在 keydown 里直接执行动作：长按会连发，输入法会吞键，切窗口会漏 keyup。正确做法是先写入意图集合，再在每个逻辑帧统一消费。

代码示例 ​

对应演示 fsm-lab.html：一个几何角色站在网格上，左侧是 HTML/CSS 画的状态机图，右侧是最近 10 条转移日志；可以按键盘、点按钮，也可以在右上角切换严格 / 宽容模式。

① 输入映射：设备层只写语义动作：

js
const KEY_TO_ACTION = {
  KeyW: 'forward', KeyA: 'left', KeyS: 'back', KeyD: 'right',
  Space: 'jump', KeyJ: 'attack', KeyH: 'hurt'
}
const MOVE_ACTIONS = new Set(['forward', 'left', 'back', 'right'])

addEventListener('keydown', (event) => {
  const action = KEY_TO_ACTION[event.code]
  if (!action) return
  event.preventDefault()
  if (MOVE_ACTIONS.has(action)) {
    moveHeld.add(action)
    if (state === 'idle') request('move')
    return
  }
  if (event.repeat) return
  requestWithBuffer(action)
})

② 合法转移表与统一入口：

js
function request(action) {
  const target = TRANSITIONS[state]?.[action]
  if (target) {
    go(target, action, 'ok')
    return true
  }
  if (!strict) {
    go(FALLBACK[action], action + '（宽容）', 'force')
    return true
  }
  logRejected(state, action)
  return false
}

③ 进入状态时统一重置计时与表现：

js
function go(next, action, result) {
  const from = state
  state = next === 'idle' && moveHeld.size > 0 ? 'move' : next
  stateTime = 0
  bodyMat.emissive.setHex(STATE_COLOR[state])
  highlightDiagram(state)
  pushTransitionLog(from, state, action, result)
}

④ 用状态时间驱动程序化动画，而不是另开一套计时器：

js
if (state === 'jump') {
  const p = Math.min(stateTime / STATE_DURATION.jump, 1)
  lift = Math.sin(p * Math.PI) * 1.05
} else if (state === 'attack') {
  const p = Math.min(stateTime / STATE_DURATION.attack, 1)
  tilt = Math.sin(p * Math.PI) * 0.42
}

画面里的跳跃高度、攻击倾斜、受伤抖动全部来自 stateTime，因此暂停、慢放、回放都能天然同步；如果每个动作各用 performance.now() 起一套计时，三套时间线迟早对不上。

常见问题解答 ​

Q1：为什么不能用 `keyCode`，`event.key` 和 `event.code` 又该怎么选？

keyCode 是旧标准，数值与键盘布局、输入法、浏览器实现相关，已经废弃。event.key 表示"按下的字符"，受大小写、Shift、输入法影响；event.code 表示"物理键位"，例如 KeyW 就是左下角那一颗 W 键。游戏里做固定键位映射时优先用 code；做"玩家自定义按键"时，把 code 存进配置，再映射到语义动作。真正要防的是越过映射层直接判断键值，那样改键位、加手柄、加触摸按钮都得改业务代码。

Q2：状态机是不是过度设计？用几个布尔值也能跑。

3 个状态以内，布尔值确实更省事；一旦出现"跳跃中不能攻击、攻击中不能移动、受伤中不能跳跃"这类交叉规则，布尔组合会以指数级增长。状态机的价值是把非法组合变成不可表示，同时让转移日志、可视化、自动测试都有统一入口。判断标准不是状态数量，而是"是否出现了需要互相排斥的规则"。如果规则只是"开/关"两个值，别上状态机；如果规则开始互相打断，就该上。

Q3：为什么在跳跃中按攻击没反应？是键盘坏了吗？

先看转移表和缓冲策略。多数角色设计不允许空中攻击，jump 状态没有 attack 出口，所以严格模式会拒绝并记日志；如果实现了输入缓冲，这次按键会被暂存，落地后再补发。演示里刻意让"跳跃中按 J"在严格模式下被拒绝、在宽容模式下强制切换，方便观察差异。真实项目里要明确产品意图：是"不允许"，还是"允许但延后"，不要用"没反应"当默认答案。

Q4：`dt` 已经取了真实时间，为什么还要 clamp？

因为真实时间会在切后台、断点、长任务后突然变得很大。一次 dt = 2.5s 的积分会让角色瞬移、计时器跳秒、连击窗口直接过期。clamp 到 50ms 的本质是"单帧最多推进一小段逻辑"，把卡顿转化为慢动作，而不是让世界瞬移。更严谨的做法是维护固定步长的逻辑循环，但对大多数网页 3D 场景，clamp 加 Timer 已经足够。

动手小练习 ​

  1. 打开 fsm-lab.html，在严格模式下连续按空格，让角色在跳跃中再次起跳，观察日志里是"拒绝"还是"缓冲"；再切到宽容模式，记录同一操作的结果差异，并解释为什么会不同。
  2. 给状态机增加一个 dash（冲刺）状态：它只能从 move 进入，持续 0.25 秒，结束后回到 move。要求同时更新转移表、状态时长、动画分支与状态机图，并保证 hurt 能打断冲刺。
  3. 把演示里的"攻击中按跳跃进入缓冲"改成"两槽缓冲"（先按跳跃、再按攻击都保留），思考：补发顺序应该先进先出还是后进先出？如果两个动作都合法，会不会产生新的非法组合？
