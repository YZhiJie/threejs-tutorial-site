38.2 进阶应用：交互系统与任务设计 ​

前置提示：本篇属于行业纵深内容，建议先完成基础模块 ②④ 与 ㉓ 再阅读。

核心概念讲解 ​

接桥：⑨ 的射线拾取只会"点一下有反应"，交互需要"可发现、可反馈、可追踪" ​

在 ⑨ 交互 · 射线拾取 里，我们学会了把鼠标位置转成 NDC 坐标，再让 Raycaster 从相机射出去，命中最前面的物体。那是最小闭环：点一下，有反应。

但真实项目里的"交互"远不止一次命中。玩家要先发现这里可以交互（准星变化、物体高亮、提示文案），触发时要得到反馈（描边、缩放、音效、动画），触发之后还要被系统追踪（任务进度、存档、成就）。这三件事分别属于感知层、表现层与系统层，射线拾取只解决了"输入怎么到达物体"。

这一篇把 38.1 的输入与状态机接到交互对象上：注册表负责"有哪些可交互物"，事件总线负责"交互发生了"，任务系统负责"这件事算不算进度"。三者解耦之后，新增一个可交互物不需要改任务代码，新增一个任务也不需要改交互代码。

可交互对象注册表：把散落的 if (object === xxx) 收进一张表 ​

最直觉的写法是给每个物体挂一个 onClick，然后在点击回调里写业务逻辑。物体一多，代码会变成"谁都能改谁"的泥潭：开关要知道灯的存在，箱子要知道任务面板的存在，终端要知道存档的存在。

注册表把可交互物统一描述成数据：

字段作用示例
id唯一标识，用于存档与日志terminal-a
type交互类型，任务系统按类型统计terminal / crate / switch
label提示文案激活终端
pick用于射线拾取的 Mesh屏幕面板
group显隐与整体缩放的根节点终端组
conditions触发前置条件通电、未收集、冷却结束
cooldown两次触发的最小间隔0.45s
onInteract具体表现：开灯、隐藏、变色由业务方提供

注册表通常用数组保存顺序，用 Map 保存 id → item 的快速查询。注册与注销必须成对：关卡切换时如果只 scene.remove 而不从注册表移除，射线仍可能命中一个看不见的物体，任务也可能被幽灵对象推进。

可发现：准星、距离、朝向与提示 ​

"可交互"不等于"玩家知道它能交互"。可发现性至少包含四层：

  1. 准星变化：屏幕中心的点从灰色变成青色，告诉玩家"现在瞄准的东西可以操作"。
  2. 距离判定：太远时不允许触发，提示"再靠近一点"，而不是让玩家对着空气按键。
  3. 朝向判定：物体要在角色 / 相机前方一定角度内，避免"背对着终端也能隔空激活"。
  4. 提示文案：用 <kbd>E</kbd> 激活终端 这种明确句式，把"按什么、会发生什么"一次说清。

距离与朝向的判定顺序建议是：先算距离（便宜），再算朝向（一次点积），最后才做射线遮挡（贵）。如果先做射线，玩家在墙后也会被判定"瞄准了"，因为他确实隔着墙命中了物体。

js
function canInteract(item, playerPos, cameraForward) {
  const target = item.group.getWorldPosition(new THREE.Vector3())
  const distance = playerPos.distanceTo(target)
  if (distance > 3.1) return false
  const toObject = target.clone().sub(playerPos)
  toObject.y = 0
  toObject.normalize()
  return toObject.dot(cameraForward) > 0.25
}

阈值不是越严格越好。第三人称相机下，角色与相机位置不同，用相机朝向比用角色朝向更符合"玩家看到什么就能点什么"的直觉；第一人称则相反。演示里用的是"相机朝向 + 角色距离"的混合判定。

可反馈：描边、缩放、图标与音效怎么选 ​

反馈手段没有绝对优劣，只有成本与场景匹配：

手段实现方式成本适用场景注意
描边后处理边缘检测，或复制网格放大后反面渲染中~高需要强强调、物体轮廓复杂后处理会作用于全屏；复制网格要同步变换
缩放对 pick 或整组做 1.05~1.15 的脉冲低小物件、图标、按钮缩放会影响射线命中范围，最好只缩表现层
发光 / 自发光提高 emissiveIntensity低终端、能量核心、霓虹物件共享材质会被所有实例一起点亮，需 clone()
图标CSS2DRenderer 或 HTML 覆盖层挂图标低~中需要文字说明、任务标记图标始终朝向屏幕，可能遮挡场景
音效WebAudio 短促振荡器，或音频文件低确认触发、收集、失败首次播放需要用户手势解锁 AudioContext
动画开合、旋转、位移中门、抽屉、杠杆动画期间要锁住重复触发，避免状态错乱

演示里同时用了缩放、自发光与音效占位：靠近时物体轻微放大并提亮，触发时播放一个短促的振荡器音。三者叠加不是为了炫技，而是覆盖"视觉 + 听觉"两条反馈通道，让玩家在嘈杂环境里也能确认操作成功。

提示 UI：为什么优先用 HTML 覆盖层 ​

3D 场景里的文字提示有两条路：CSS2DRenderer 把 DOM 挂到 3D 坐标上，或者直接用固定定位的 HTML 覆盖层。

  • 世界锚定提示（CSS2D）：适合"物体头顶的名字""任务标记""伤害数字"，会跟随物体移动，但要做遮挡与深度排序。
  • 屏幕固定提示（HTML 覆盖层）：适合"按 E 交互""距离太远""任务完成"，位置稳定、可访问性好、移动端也好点。

演示选用屏幕固定提示，因为交互提示的本质是"操作说明"，不是"世界的一部分"。它不应该随相机晃动，也不应该被墙挡住。真要做世界锚定，记得给 CSS2DRenderer 的容器设置 pointer-events: none，否则透明的 DOM 层会拦截画布的鼠标事件。

任务系统：事件驱动，而不是每帧轮询 ​

任务系统最容易写错的版本是"每帧检查"：每帧遍历所有箱子，看有没有被收集，再更新进度。物体少时没问题，物体一多就是 O(任务 × 物体) 的无效扫描，而且"收集"这种一次性事件用轮询表达，天然容易重复计数。

正确做法是事件驱动：交互发生时发一条事件，任务系统订阅并按类型累计。任务本身只描述目标与完成条件：

js
const goals = [
  { type: 'terminal', label: '打开终端', need: 1, got: 0 },
  { type: 'crate', label: '收集箱子', need: 2, got: 0 }
]

bus.on('interact', (payload) => {
  const goal = goals.find((item) => item.type === payload.type)
  if (!goal || goal.got >= goal.need) return
  goal.got += 1
  if (goals.every((item) => item.got >= item.need)) {
    bus.emit('tasks:complete', {})
  }
})

这段代码有两个关键守卫：goal.got >= goal.need 防止超额计数，every 判断完成而不是"最后一个目标单独判断"。后者能让任务目标增删时不用改完成逻辑；前者能防止"终端被反复激活却把进度刷到 99"。

事件总线：让交互与任务互不认识 ​

事件总线的最小实现只需要 on、emit 与 off。它的价值不是"高级架构"，而是把依赖方向从"网状"改成"星形"：交互对象只负责发事件，任务、音效、成就、存档各自订阅。

js
const bus = {
  handlers: new Map(),
  on(event, handler) {
    if (!this.handlers.has(event)) this.handlers.set(event, [])
    this.handlers.get(event).push(handler)
  },
  emit(event, payload) {
    const list = this.handlers.get(event)
    if (list) list.forEach((handler) => handler(payload))
  }
}

工程上要补三条纪律：

  • 事件命名带领域：interact:crate、task:complete 比 click、done 更不容易撞名。
  • 错误隔离：一个订阅者抛错不应该阻断其他订阅者，必要时对每个回调做 try/catch 并上报。
  • 订阅生命周期：场景销毁、关卡切换时要 off，否则旧关卡的任务系统会继续响应新关卡的事件。

引导与新手流程：把"可发现"做成渐进式 ​

新手引导不是"弹一个巨大的教程弹窗"，而是逐步暴露系统：

  1. 第一次靠近：只提示"按 E 交互"，不解释任务。
  2. 第一次完成目标：提示"任务进度已更新"，让玩家把动作与结果连起来。
  3. 卡住超过一段时间：提示升级为"试试右前方的终端"，给出方向而不是答案。
  4. 完成全部目标：结算面板总结"你做了什么"，而不是只显示分数。

引导的触发条件应该是"玩家状态"，不是"时间到了"。例如"30 秒内没有发生任何交互"才提示，而不是"进入关卡 5 秒必弹窗"。前者尊重玩家节奏，后者只会让人烦。

无障碍与移动端：没有键盘时怎么办 ​

网页 3D 交互必须假设"玩家可能没有键盘"：

  • 点击 / 触摸也能完成同一动作：演示里点击物体与按 E 走同一个 interact()，而不是两套逻辑。
  • 屏幕按钮：移动端提供半透明摇杆或方向按钮，交互键固定在右下角，命中区域至少 44×44 CSS 像素。
  • 焦点与键盘可达：如果做了 HTML 任务面板，按钮要能被 Tab 聚焦，Enter / Space 能触发。
  • 状态播报：任务进度变化通过 aria-live="polite" 播报，别只靠颜色。
  • 减少动态：尊重 prefers-reduced-motion，把缩放脉冲改成静态描边。

术语解释：

  • 可交互对象注册表 registry：用统一数据结构描述所有可交互物，避免业务逻辑散落在各个 Mesh 上。
  • 射线拾取 raycast：从相机发一条射线，返回与场景物体最近的交点，用于"屏幕坐标 → 3D 物体"。
  • 事件总线 event bus：发布 / 订阅的中介，让交互、任务、音效互不直接依赖。
  • 幂等 idempotent：同一操作执行多次与执行一次结果相同；任务计数必须有这个性质。
  • CSS2DRenderer：把 DOM 元素按 3D 坐标投影到屏幕上，适合世界锚定的标签。

四个常见坑 ​

  1. 长按 E 连续触发：keydown 会重复，必须在交互入口过滤 event.repeat，或在注册表里设冷却。
  2. 共享材质被一起高亮：两个箱子用同一个 MeshStandardMaterial 时，点亮一个等于点亮全部；交互物应各自 clone() 材质。
  3. 任务重复计数：交互事件被两个系统转发，或射线一次点击命中多个 Mesh，都会让进度多加。事件里带唯一 id，任务侧做幂等。
  4. 覆盖层挡住画布：任务面板、提示条如果没设 pointer-events，会把拖拽视角与点击物体全部吃掉。

代码示例 ​

对应演示 interaction-lab.html：一个带墙的小房间，开关、两个箱子、一台终端。走近时出现提示，按 E 或点击触发；右侧任务面板按"终端 0/1、箱子 0/2"实时更新。

① 注册表：把物体描述成数据：

js
function register(config) {
  const item = {
    id: config.id,
    type: config.type,
    label: config.label,
    cooldown: config.cooldown ?? 0.45,
    lastTrigger: -Infinity,
    collected: false,
    pick: config.pick,
    group: config.group,
    onInteract: config.onInteract
  }
  config.pick.userData.item = item
  interactables.push(item)
  pickMeshes.push(config.pick)
  return item
}

② 距离 + 朝向判定，先便宜后昂贵：

js
function itemInRange(item) {
  if (!item.group.visible || item.collected) return false
  const target = item.group.getWorldPosition(objWorld)
  const playerPos = player.getWorldPosition(playerWorld)
  playerPos.y += 0.85
  if (playerPos.distanceTo(target) > 3.1) return false
  const toObject = target.clone().sub(playerPos)
  toObject.y = 0
  toObject.normalize()
  return toObject.dot(flatCameraForward(camForward)) > 0.25
}

③ 交互入口统一：键盘、点击、按钮都走同一个函数：

js
function interact(item) {
  if (!canTrigger(item)) return
  item.lastTrigger = elapsed
  item.onInteract()
  bus.emit('interact', { id: item.id, type: item.type })
}

④ 任务只订阅事件，不扫描场景：

js
bus.on('interact', (payload) => {
  const goal = goals.find((item) => item.type === payload.type)
  if (!goal || goal.got >= goal.need) return
  goal.got += 1
  renderGoals()
  if (goals.every((item) => item.got >= item.need)) {
    bus.emit('tasks:complete', {})
  }
})

常见问题解答 ​

Q1：为什么交互距离判定要分"水平距离"和"三维距离"？

看场景语义。终端、开关这类贴墙物体，如果严格用三维距离，玩家站在正下方时头部与屏幕的垂直差会缩短可用范围；反过来，如果只算水平距离，玩家在二楼也能激活一楼的门。通用做法是：先算三维距离做粗筛，再按物体高度决定是否把 y 压平。演示里开关位置较高，仍用三维距离，是因为它本来就需要玩家靠近墙面；平台类游戏则更适合水平距离加高度差阈值。

Q2：任务系统为什么不能每帧遍历物体检查状态？

每帧遍历的复杂度是"任务数 × 物体数"，而交互是低频事件。用轮询表达一次性事件还有两个副作用：一帧内状态变化可能被漏掉或重复计入；暂停、回放时轮询时机不同，进度会漂移。事件驱动的写法把"发生"与"统计"分离，复杂度只与事件次数相关，并且任务系统可以在没有场景的情况下单独测试。

Q3：点击触发和按 E 触发，应该写两套逻辑吗？

不应该。正确结构是让输入层只负责"产生交互意图"，所有意图都落到同一个 interact(item)。按 E 时用"当前提示对象"作为参数，点击时用射线命中的对象作为参数；后面的冷却、前置条件、事件派发、反馈完全复用。两套逻辑最典型的后果是：键盘路径有冷却，鼠标路径没有，玩家可以双击刷任务进度。

Q4：移动端没有键盘，交互提示应该怎么改？

把提示从"按 E"改成"点一下物体"或"点右下角交互键"，并同时保留两种输入方式。触摸设备上，准星没有意义，应该用"点击命中"或"靠近后自动显示大按钮"；按钮命中区至少 44×44 CSS 像素，且不要放在系统手势区。任务进度变化用 aria-live 播报，颜色之外再加文字或图标，避免只靠青色高亮传达状态。

动手小练习 ​

  1. 给 interaction-lab.html 增加第四个可交互物：一扇需要"终端激活后才能打开"的门。要求用注册表的 conditions 字段表达前置条件，并让提示文案在未满足条件时显示"先去激活终端"。
  2. 把任务系统改成"完成 1 个箱子得铜徽章、完成 2 个得银徽章"，观察事件总线需要新增哪些订阅者、任务数据应该如何表达"阶段奖励"，并避免同一奖励重复发放。
  3. 关闭演示里的音效与缩放，只保留自发光，请一个没看过代码的朋友试玩，记录他多久能发现终端可以交互；再恢复全部反馈重复测试，比较"可发现性"的变化。
