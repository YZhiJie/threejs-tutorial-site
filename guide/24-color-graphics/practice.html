24.3 实战案例：跨设备一致的色彩校准工作台 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ④⑥⑦ 再学习本篇。

核心概念讲解 ​

接桥：把 ⑭ 的 IBL 产品渲染搬进"色彩校准间" ​

在 ⑭ 光照与 IBL · 实战 里，我们用环境贴图把一个产品渲染得"像真的"：金属有反射，塑料有高光，背景有层次。但那套画面有一个隐含前提——你是在自己这台显示器上、用当前浏览器、以当前参数看到的。

一旦同一份模型和材质被搬到投放页、设计评审 PPT、客户手机上、工厂的工业相机里，颜色就可能整体偏黄、偏灰、偏暗。设计师说"这不是我要的橙色"，开发说"我按设计稿写的 #D67E2C"，两个人截图发到群里，谁也说服不了谁。

这一篇把 ⑭ 的产品渲染搬进"色彩校准间"：用一张 24 色卡和九级灰阶，把色调映射、曝光、输出色彩空间这三个最常出问题的旋钮逐个固定下来，最后沉淀成一份可以写进项目规范的色彩配置。

为什么要用色卡，而不是"看感觉" ​

人眼对绝对颜色极不可靠：同一块灰，在暖光环境里看偏黄，在冷光环境里看偏蓝；同一个橙色，放在深色背景上显亮，放在白色背景上显闷。色卡提供的是一组已知参考值：

  • 24 个色块覆盖肤色、天空、植物、红绿蓝黄等高饱和色，以及白、灰、黑等中性色。
  • 九级灰阶用来判断对比度与黑位：从 #000000 到 #ffffff 均匀分布，任何一级"发色"都说明白平衡或色调映射有问题。
  • 每个色块的设计值都是固定的 sRGB 十六进制，可以逐格比对，不依赖主观描述。

在世面上，Macbeth（现 X-Rite）ColorChecker 是最常见的 24 色卡标准。本篇不追求实验室级色度计，而是用它的排列与配色思路做一个浏览器内的校准台：3 行 × 8 列，共 24 格。

三类偏移：颜色错、亮度错、对比错 ​

把色卡放进不同参数下，会看到三种典型偏移：

现象常见原因色卡上的表现
整体发灰、发淡颜色贴图被当成线性数据所有色块对比度下降，暗部被抬亮
整体偏暗、饱和色发闷输出漏了 sRGB 编码中间调下压，红色变砖红、绿色变墨绿
高光发白、肤色发灰色调映射过强或曝光过高白色与浅肤色几乎并成一片
暗部死黑、层次丢失色调映射压得太狠 / 黑位设置错误深色块与黑色块无法区分
中性灰偏色白平衡或环境光染色九级灰阶整体偏黄 / 偏蓝 / 偏品红

注意一个关键区别："颜色错"通常是链路错，"亮度错"通常是 toneMapping / exposure 错。排查时先修链路，再调风格。链路错了，调曝光只是把错误整体放大或缩小。

一次真实的排查记录 ​

某次产品页上线后，设计反馈"金属橙变成了土黄"。我们按流程走了一遍：

  • 固定浏览器与缩放比例截图，线上取色 #B96E2E，设计稿是 #D67E2C；
  • 查颜色贴图：albedo 已设 SRGBColorSpace，没有问题；
  • 查数据贴图：法线贴图被误设成了 sRGB，先记入问题清单；
  • 查输出：outputColorSpace 是默认的 sRGB，没有问题；
  • 查色调映射：项目开了 ACES，toneMappingExposure 被某个业务组件改成了 1.15；
  • 临时关掉 ACES 后取色 #D17C2D，已经接近设计值，但金属高光变硬、层次变少。

最终结论：主因是 toneMapping + exposure 偏离基线，次因是法线贴图设置错误导致金属反射发脏。修复方式是：法线贴图改回 NoColorSpace；保留 ACES 但把 exposure 统一回 1.0；在规范里写明"设计稿颜色以 ACES + exposure 1.0 的渲染结果为验收基线"，而不是继续用直出值对照。整个过程没有改一行材质颜色，问题全在管线上。

企业里的排查流程：截图 → 取色 → 逐环节核对 → 定版 ​

设计师和开发争论"颜色不一致"时，最有效的方式不是继续发截图，而是走一条可复现的排查链：

  1. 同一份截图：规定浏览器、系统、缩放比例、是否开启夜间模式 / 护眼模式。不同设备上的截图不能直接比。
  2. 取色：用取色工具读取设计稿和线上页面的实际像素值，记录 sRGB 十六进制，而不是"看起来差不多"。
  3. 逐环节核对：按渲染链路的顺序检查——
    • 设计稿导出的色值是不是 sRGB？
    • 贴图加载后有没有设 colorSpace = SRGBColorSpace？
    • 数据贴图有没有被误设成 sRGB？
    • renderer.outputColorSpace 是不是 sRGB？
    • toneMapping 与 exposure 是否和设计评审时一致？
    • 后处理链里有没有重复色调映射或额外的色彩滤镜？
  4. 定版参数：把确认过的参数写成一个常量对象，提交到仓库，作为"色彩基线"。所有页面、所有构建产物都引用同一份配置。
  5. 回归验证：每次改灯光、改后处理、升级 Three.js 版本，都重新跑一遍色卡对比，防止"某次升级悄悄改了默认值"。

这条流程的价值在于：它把"我觉得颜色不对"变成"第 3 步的第 5 项与基线不一致"，可以直接指派、可以直接修复、可以回归测试；也让颜色问题第一次拥有了"可关闭"的判定标准。如果双方仍然无法达成一致，就把两台机器的系统版本、浏览器版本、显示器配置文件、取色值与参数快照一起归档，让争议回到可验证的数据上，而不是继续在聊天窗口里互发截图。

把参数沉淀成一份 color config ​

色彩配置不应该散落在十几个文件里。建议收敛成一个模块：

js
// color-config.js —— 项目唯一的色彩基线
export const COLOR_CONFIG = {
  outputColorSpace: 'srgb',          // 屏幕输出编码
  toneMapping: 'ACESFilmic',         // 色调映射曲线
  toneMappingExposure: 1.0,          // 曝光基线
  colorTextureSpace: 'srgb',         // 颜色贴图：必须解码
  dataTextureSpace: 'no-color-space',// 法线 / 粗糙度：绝不解码
  hdrRenderTarget: 'half-float',     // 后处理是否使用浮点缓冲
  premultipliedAlpha: true           // 透明合成约定
}

然后在渲染器初始化处集中应用：

js
renderer.outputColorSpace = THREE.SRGBColorSpace
renderer.toneMapping = THREE.ACESFilmicToneMapping
renderer.toneMappingExposure = COLOR_CONFIG.toneMappingExposure

function applyTextureColorSpace(texture, kind) {
  texture.colorSpace = kind === 'color'
    ? THREE.SRGBColorSpace
    : THREE.NoColorSpace
  texture.needsUpdate = true
}

配置对象最好带版本号，并在项目规范里写明：任何对 toneMapping、exposure、outputColorSpace 的修改，都必须附一张色卡对比截图。这样代码评审时，颜色变化不再是"顺手调了一下"，而是有据可查的变更。版本号还有一层现实意义：当 Three.js 升级、后处理插件替换、设计系统换色时，你至少能回答"上一版颜色基线是什么、为什么改、改了多少"。没有基线，所有关于颜色的讨论最后都会退化成"我觉得这个橙更好看"。

写进项目规范的六条硬规则 ​

  1. 颜色 token 一律使用 sRGB 十六进制，禁止在代码里手写"线性色值"却不标注。
  2. 颜色贴图必须显式 SRGBColorSpace；法线、粗糙度、AO、ORM 必须 NoColorSpace。
  3. renderer.outputColorSpace 固定 sRGB，除调试外不允许改成 Linear。
  4. 色调映射与曝光统一从 COLOR_CONFIG 读取，禁止在业务组件里各自设置。
  5. 后处理链最多做一次色调映射，OutputPass 负责最后的编码与压缩。
  6. 每个发布版本保留一张色卡基线截图，作为视觉回归的对照物。

这六条看起来像"形式主义"，但每一条都对应过真实事故：有人把法线贴图设成 sRGB 导致金属发脏；有人在组件里把 exposure 调到 1.4 导致同一页面两个模块亮度不一致；有人升级 Three.js 后没检查默认输出色彩空间，整站颜色偏了一档。

上线前的色彩验收清单 ​

把规范落成可执行的检查项，每次发布前逐条勾选：

  • 在 NoToneMapping、exposure = 1 下，24 色卡与设计值逐格一致（容差建议 ±2/255）；
  • 打开项目实际的 toneMapping 后，色卡偏移有记录、有批准，不是"悄悄变了"；
  • 颜色贴图全部是 SRGBColorSpace，法线 / 粗糙度 / AO / ORM 全部是 NoColorSpace；
  • 半透明物体边缘没有黑边，加法光效没有大面积死白；
  • 暗部渐变没有明显色带；如果出现，已启用 dither 或改用 HalfFloat RT；
  • 基线截图与取色记录归档到发布记录，下一版可以对照。

这套清单可以进一步自动化：在开发环境启动时遍历场景纹理，发现色彩空间与用途不匹配就在控制台告警；在持续集成里用固定参数渲染色卡，与基线截图做像素级差异比较，超过阈值就阻断发布。自动化的价值不是"替代人眼"，而是把"颜色回归"从一次性的人工对色，变成每次提交都会执行的守门员。

第一行是肤色、天空、植物、高饱和色；第二行是红紫黄绿蓝；第三行是品红、青、白与五级中性灰。new THREE.Color('#D67E2C') 默认按 sRGB 解释，并自动转成线性工作空间，这正是我们想要的。

② 排列：用正交相机保证每格都能被"按像素取色"：

js
PATCHES.forEach((hex, i) => {
  const col = i % 8
  const row = Math.floor(i / 8)
  const mesh = new THREE.Mesh(
    geo,
    new THREE.MeshBasicMaterial({ color: new THREE.Color(hex), toneMapped: true })
  )
  mesh.position.set((col - 3.5) * 1.0, 1.75 - row * 1.0, 0)
  scene.add(mesh)
})

用 MeshBasicMaterial 是为了排除灯光变量：色卡校准只关心"颜色经过渲染管线后变成什么"，不希望被环境光、阴影、反射干扰。

③ 读取屏幕真实像素：比"目测"可靠：

js
function readScreenColors() {
  const gl = renderer.getContext()
  renderer.getDrawingBufferSize(bufferSize)
  for (const cell of cells) {
    cell.patch.getWorldPosition(worldPos)
    worldPos.project(camera) // 世界坐标 -> NDC
    const px = Math.floor((worldPos.x * 0.5 + 0.5) * bufferSize.x)
    const py = Math.floor((worldPos.y * 0.5 + 0.5) * bufferSize.y)
    gl.readPixels(px, py, 1, 1, gl.RGBA, gl.UNSIGNED_BYTE, pixel)
    const hex = toHex(pixel[0], pixel[1], pixel[2])
    cell.label.textContent = hex
    cell.chip.style.background = hex
  }
}

这段代码的价值是：它显示的不是"设计值"，而是当前参数下屏幕实际收到的值。设计师给的 #D67E2C 在经过 ACES 与曝光后会变成另一个十六进制，这个差异就是需要沟通和定版的部分。

gui.add(params, 'outputColorSpace', Object.keys(COLOR)).onChange((v) => {

每次改完参数，只读一遍屏幕像素，避免每帧同步读取造成 GPU 停顿。

常见问题解答 ​

Q1：设计稿写的是 #D67E2C，线上取色却是 #C9772F，差在哪里？

先确认取色环境一致（同一浏览器、同一缩放、关闭夜间模式）。然后按链路核对：① 贴图是否被当成线性数据，导致整体发灰；② 是否开了 ACES / AgX，色调映射会压缩高光并改变饱和色；③ 曝光是否偏离基线；④ 后处理里是否有额外的 LUT、滤镜或色彩分级。最常见的组合是"链路正确 + ACES + 略有不同的曝光"，此时颜色偏移是风格选择，不是 bug。解决方式不是反复改代码，而是把最终参数定版，并让设计稿以定版后的渲染值为准。

Q2：为什么色卡上的白块看起来不是纯白，灰阶也偏色？

白块不是纯白通常是色调映射或曝光的结果：ACES 会把 1.0 附近的高光压下去，白看起来略灰；曝光低于 1 也会让白变灰。灰阶整体偏色则要怀疑三件事：① 场景里有染色光（例如暖色环境光）影响了材质；② 输出色彩空间不是 sRGB；③ 显示器或系统开了护眼模式 / 色彩滤镜。校准台用 MeshBasicMaterial 就是为了排除灯光，所以如果仍然偏色，优先查后两项。

Q3：团队里有人用 Mac、有人用 Windows，色卡基线应该以谁为准？

以"标准 sRGB 浏览器环境"为准，而不是以某台机器为准。具体做法：① 规定基线截图在关闭系统色彩滤镜、缩放 100%、使用同一浏览器版本的环境下生成；② 用取色值而不是肉眼判断；③ 允许不同屏幕存在轻微显示差异，但代码层面的输出值必须一致。跨设备一致性靠的是管线参数一致 + 可测量的输出值，不是靠"大家看起来差不多"。

Q4：项目里要不要默认开 ACES？开了以后设计稿颜色对不上怎么办？

ACES 适合写实渲染、产品展示、有 HDR 高光的场景；扁平插画、UI 风格、需要严格还原设计色的项目可以先用 NoToneMapping 或 Reinhard。关键是不要一半页面开、一半页面不开。如果开了 ACES，就把"设计稿 sRGB 值 → ACES 后的渲染值"当作新的验收基线，并在规范里写明；也可以给 UI 层单独关闭材质色调映射（material.toneMapped = false），让界面颜色严格等于设计值，而 3D 场景仍使用 ACES。这是一条常见的折中方案。

动手小练习 ​

  1. 打开校准台，把 toneMapping 依次设为 No、ACES、AgX、Reinhard，记录白色块、肤色块与红色块的十六进制变化，画出"哪种曲线最接近设计稿"的结论。
  2. 固定 toneMapping = No、exposure = 1，把 outputColorSpace 切成 Linear，再切回 sRGB，记录色卡整体偏移量。想想为什么这个偏移是"系统性"的，而不是某几个色块单独出错。
  3. 把 COLOR_CONFIG 复制到你自己的项目里，写一个启动时自检函数：遍历场景中的纹理，发现颜色贴图未设 sRGB 或数据贴图被设成 sRGB 时，在控制台输出警告。把这条自检加进项目的开发环境构建流程。
