24.2 进阶应用：精度、HDR 与图形学基础原理 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ④⑥⑦ 再学习本篇。

核心概念讲解 ​

接桥：13.1 的 RenderTarget 里到底存了什么 ​

在 13.1 后处理基础 里，我们把场景画进 WebGLRenderTarget，再把它当成一张贴图交给下一个 Pass。当时关注的是"怎么画进去、怎么取出来"，却没有追问一个更底层的问题：这块离屏画布每个像素到底用多少位、存的是线性值还是编码值？

这个问题的答案，直接决定你会在渐变背景上看到一条条硬边色带，还是看到丝滑过渡；也决定高光是一团死白，还是保留了层次。本篇把 RenderTarget 拆开，讲清位深、色带、抖动、HDR、混合与深度精度这些"看不见但处处在"的图形学基础。

位深：每个通道有几种"台阶" ​

像素的颜色最终要存成有限精度的数字。位深就是每个通道能表示的台阶数量：

格式每通道位数可表示级数内存（RGBA）典型用途
UnsignedByteType8 bit256 级4 字节普通 LDR 后处理、UI、最终输出
10 bit（RGB10_A2 等）10 bit1024 级4 字节HDR 显示、游戏机输出
HalfFloatType16 bit 浮点约 3 位十进制有效数字8 字节HDR 后处理、Bloom、色彩分级
FloatType32 bit 浮点约 7 位十进制有效数字16 字节科学可视化、GPGPU

8 位不是"颜色只有 256 种"，而是"每个通道只有 256 个台阶，三个通道组合出约 1677 万种颜色"。对于照片够用，对于平滑的大面积渐变就不够了：相邻两级之间的差值会成为肉眼可见的边界。

HalfFloat 的 16 位里，1 位符号、5 位指数、10 位尾数。它的绝对精度不如 16 位整数，但动态范围极大，能存下远超 1.0 的亮度，适合"先保留 HDR，最后再压缩"的管线。

色带 banding：平滑渐变的敌人 ​

把一条从黑到亮的线性渐变写进 8 位 RenderTarget，数学上连续的亮度会被四舍五入到 256 个台阶：

js
// 概念演示：8 位量化的本质
const step = 1 / 255
const quantized = Math.round(linearValue / step) * step

在亮部，一级台阶的跨度很小，看不出问题；在暗部，sRGB 编码会把线性值"拉开"，一级线性台阶可能对应屏幕上好几级显示值，于是暗部出现一条条明显的色带。这就是为什么深色渐变背景最容易暴露 8 位精度问题。

解决思路有三条：

  1. 提高位深：用 10 位或 HalfFloat RenderTarget，台阶变细，色带自然消失。
  2. 抖动 dithering：在量化之前加入微小噪声，让相邻像素"轮流"落在上下两级台阶上，人眼会把它们平均成平滑过渡。
  3. 改变内容：给渐变叠加细微噪点或纹理，用高频细节掩盖低频色带。这是设计上的"障眼法"，不是真正的精度修复。

抖动必须在量化之前 ​

抖动的关键顺序是：先加噪声，再写入低位深目标。如果先把画面存成 8 位、再在显示阶段加噪声，色带已经固化成台阶，噪声只能让台阶变脏，不能把它变平。

glsl
float hash(vec2 p) {
  return fract(sin(dot(p, vec2(127.1, 311.7))) * 43758.5453);
}

vec3 applyDither(vec3 color, float amount) {
  float n = hash(gl_FragCoord.xy) - 0.5;
  return color + n * amount;
}

噪声幅度通常取"一个量化步长"左右，例如 1.0 / 255.0。太小看不出效果，太大画面会像蒙了一层电视雪花。专业图像处理里还会用 Floyd–Steinberg 误差扩散或蓝噪声，把噪声能量集中到人眼不敏感的高频区域。

HDR 与 HalfFloatType ​

HDR 的意思是：亮度值可以超过 1.0。太阳、灯泡、金属高光在物理上远比"屏幕白"亮，如果一开始就裁到 1.0，高光细节会永久丢失。正确做法是把这些值先存进浮点 RenderTarget，最后用色调映射压回屏幕范围。

js
const rt = new THREE.WebGLRenderTarget(width, height, {
  type: THREE.HalfFloatType,   // 保留超过 1.0 的亮度
  format: THREE.RGBAFormat,
  minFilter: THREE.LinearFilter,
  magFilter: THREE.LinearFilter
})

使用 EffectComposer 时，合成器的读写缓冲默认是 8 位；做 Bloom、体积光、HDR 色彩分级时要在创建时传入 HalfFloat 的 RenderTarget，否则高光在进入第一个 Pass 时就已经被裁掉了。最后一个 OutputPass 负责色调映射与 sRGB 编码，把浮点 HDR 变成屏幕能显示的 LDR。

浮点的代价是带宽：RGBA HalfFloat 每个像素 8 字节，是 8 位的两倍；4K 分辨率下显存占用和读写带宽都会明显上升。移动端要在"高光层次"和"帧率预算"之间做取舍。

顺带区分两个相邻概念：浮点缓冲解决的是"计算过程中别丢高光"，10 位输出解决的是"最终显示时台阶更细"。网页默认输出仍以 8 位为主，10 位/HDR 显示需要操作系统、浏览器、显示器整条链路支持，不是改一个 renderer 参数就能开启。工程上更常见的做法是：内部用 HalfFloat 做 HDR 后处理，最终输出 8 位 sRGB，必要时加 dither；把"内部精度"和"输出精度"分开预算。

预乘 alpha 与混合模式 ​

透明物体的合成公式，比"把颜色叠上去"复杂得多。常见的有两种约定：

约定RGB 的含义优点常见场景
预乘 alphaRGB 已经乘过 alpha过滤 / 缩放时边缘不出现黑边游戏引擎、Canvas 合成
非预乘 alphaRGB 是原始颜色美术编辑直观图片编辑软件

WebGLRenderer 的 premultipliedAlpha 默认是 true，意思是画布输出按预乘约定与页面合成。透明 PNG 贴图若带半透明边缘，在非预乘流程里缩放后容易出现"黑边"，本质是 RGB 与 alpha 没有一起插值。处理办法：在导出资产时预乘，或在着色器里手动 rgb *= alpha。

混合模式则决定"新像素如何覆盖旧像素"：

  • NormalBlending：src * alpha + dst * (1 - alpha)，最常用。
  • AdditiveBlending：src + dst，光效、火花、辉光常用；叠加顺序影响较小，但很容易把亮度推到 1.0 以上——这正是需要浮点 RT 的原因。
  • MultiplyBlending：src * dst，阴影、染色、暗角常用。

把公式写全，更容易看清问题。设背景为 dst、前景为 src、前景透明度为 a：

js
// Normal：新像素按透明度覆盖旧像素
out = src * a + dst * (1 - a)
// Additive：光能相加，不考虑遮挡
out = src * a + dst
// Multiply：逐通道相乘，常用于阴影与染色
out = src * dst

半透明渲染还有一个排序问题：不透明物体先画，透明物体从远到近画。加法混合虽然对顺序不敏感，但多个高亮叠加会把亮度推到 1.0 以上，如果 RenderTarget 只有 8 位，超出的部分会直接被裁掉，看起来是一块死白。用 HalfFloat RT 保留这些超范围亮度，最后交给色调映射压缩，光晕才有层次。透明物体内部的顶点排序、depthWrite 开关、预乘 alpha 约定，也都会影响最终边缘是否干净。

所有混合都应该在线性空间里做。若在 sRGB 数值上做加法混合，亮部会过早饱和，颜色偏向黄白。

深度缓冲精度与 z-fighting ​

深度缓冲为每个像素记录"离相机多远"，用来决定谁遮挡谁。常见精度是 16 位、24 位、32 位。深度值不是线性的，越靠近远裁剪面精度越差。当两个面几乎共面时，深度值可能落到同一个台阶上，GPU 无法稳定判断前后，画面出现闪烁的条纹——这就是 z-fighting。

修法做法代价
拉开距离让共面物体在空间上错开一点最简单的工程手段
调整 near / far缩小远裁剪面范围，把精度留给近处远处可能被裁掉
polygonOffset给某个面加深度偏移适合贴花、路面标线
logarithmicDepthBuffer用对数分布重新分配深度精度增加片元成本，影响 early-z
分层渲染用 renderOrder + 清深度分两遍画增加 draw call

大多数 z-fighting 不是"精度不够"，而是"两个面本来就不该完全共面"。先问场景为什么要把两个面放在同一深度，再谈技术手段。还有一个容易被忽略的因素：相机的 near 与 far 比例。把 near 从 0.1 调到 0.01、far 保持 1000，深度精度会被大量浪费在极近处，远处立刻开始闪烁；反之把 far 从 1000 收到 100，深度精度会明显改善。先收紧裁剪面，再考虑对数深度缓冲。

颜色插值与 UI 层的落地 ​

Three.js 的顶点颜色、贴图采样、材质插值，默认都在线性空间里进行。这是正确的，但也带来一个跨端问题：CSS 渐变默认在 sRGB 空间插值。同样是从红到绿，WebGL 里的线性插值会经过偏暗的中间色，CSS 的 sRGB 插值则会经过偏亮的黄褐。两者放在同一页面并排，能明显看出不一致。

解决方法有二：① 用 CSS Color 4 的 linear-gradient(in srgb-linear, ...) 让浏览器也走线性插值；② 反过来在 3D 侧把渐变停靠点预先转成 sRGB 再插值，明确以设计稿为准。关键不是"哪种更科学"，而是两端使用同一套约定，并在项目规范里写死。如果团队有设计系统，最好把这条约定写进 token 文档：渐变属于哪一端、在哪个空间插值、验收以哪张截图为准，否则每次联调都会重新吵一遍。

UI 层的色彩管理还包括：设计 token 用 sRGB 十六进制；取色工具读的是屏幕像素，必须说明是否经过显示器 ICC；截图对比要在同一浏览器、同一缩放比例、同一色彩配置下进行。

代码示例 ​

对应演示 banding-precision-lab.html：全屏渐变先写进 RenderTarget，再复制到屏幕。三种模式分别是"8bit 无抖动 / 8bit 抖动 / HalfFloat HDR"。逐段拆解：

① 全屏渐变：着色器里保留线性值：

js
const gradientMat = new THREE.ShaderMaterial({
  uniforms: {
    uDither: { value: 0 },  // 抖动强度，单位是 1/255
    uGain: { value: 1 }     // HDR 模式下拉高亮度峰值
  },
  vertexShader: /* glsl */`
    varying vec2 vUv;
    void main() {
      vUv = uv;
      gl_Position = vec4(position.xy, 0.0, 1.0);
    }
  `,
  fragmentShader: /* glsl */`
    uniform float uDither;
    uniform float uGain;
    varying vec2 vUv;

    float hash(vec2 p) {
      return fract(sin(dot(p, vec2(127.1, 311.7))) * 43758.5453);
    }

    void main() {
      vec3 dark = vec3(0.006, 0.008, 0.014);
      vec3 warm = vec3(0.95, 0.36, 0.52);
      vec3 col = mix(dark, warm, vUv.y) * uGain;

      float n = hash(gl_FragCoord.xy) - 0.5;
      col += n * uDither * (1.0 / 255.0);

      gl_FragColor = vec4(col, 1.0);
    }
  `,
  depthTest: false,
  depthWrite: false
})

② RenderTarget：按模式换类型：

js
function buildRenderTarget() {
  if (rt) rt.dispose()
  const size = renderer.getDrawingBufferSize(new THREE.Vector2())
  rt = new THREE.WebGLRenderTarget(size.x, size.y, {
    type: params.mode === 'HalfFloat HDR'
      ? THREE.HalfFloatType
      : THREE.UnsignedByteType,
    minFilter: THREE.NearestFilter,
    magFilter: THREE.NearestFilter,
    depthBuffer: false,
    generateMipmaps: false
  })
  rt.texture.colorSpace = THREE.NoColorSpace // RT 里是线性数值
  copyMat.map = rt.texture
  copyMat.needsUpdate = true
}

这里故意用 NearestFilter，避免线性过滤把台阶"抹平"，让色带更直观。真实项目里当然用 LinearFilter，但观察原理时清晰比好看重要。

③ 复制到屏幕：色调映射与编码交给内置材质：

js
renderer.setRenderTarget(rt)
renderer.render(gradientScene, camera)   // 先画进离屏缓冲

renderer.setRenderTarget(null)
renderer.render(copyScene, camera)        // 再把 RT 当贴图铺满屏幕

复制材质用 MeshBasicMaterial，它能自动带上色调映射与输出编码。切换到 HalfFloat 模式时把 renderer.toneMapping 设为 ACES，HDR 峰值经过压缩后仍保留高光层次。

④ 模式切换：一个函数管住精度、抖动与色调映射：

js
function applyMode() {
  const isHDR = params.mode === 'HalfFloat HDR'
  const useDither = params.mode === '8bit · 抖动'
  gradientMat.uniforms.uDither.value = useDither ? params.dither : 0
  gradientMat.uniforms.uGain.value = isHDR ? params.hdrGain : 1
  renderer.toneMapping = isHDR ? THREE.ACESFilmicToneMapping : THREE.NoToneMapping
  renderer.toneMappingExposure = isHDR ? 0.8 : 1
  copyMat.needsUpdate = true
  buildRenderTarget()
}

常见问题解答 ​

Q1：8 位真的不够用吗？为什么专业显示器都在推 10 位？

对"照片和普通 UI"来说 8 位通常够用，因为内容本身有噪声和纹理，色带被细节掩盖。不够用的是大面积平滑渐变：天空、雾、暗部背景、色彩分级后的电影感画面。10 位把台阶从 256 级提升到 1024 级，色带阈值大约提高四倍；再配合抖动，肉眼几乎看不到断层。专业显示器推 10 位，是为了在 HDR 和高对比内容里保留更多层次，而不是"颜色更多"。

Q2：开了抖动以后画面有噪点，能既去色带又完全无噪吗？

不能，这是信息论层面的取舍。8 位只有 256 级，要让相邻像素看起来更平滑，只能让它们在两级之间"分配比例"，这个比例就表现为噪声。专业做法是把噪声做成高频、低幅度、接近蓝噪声的分布，让它在正常观看距离下不可见；或者在最终输出前才抖动，避免噪声被后续滤镜放大。如果完全不能接受噪声，正确答案是提高位深，而不是加强抖动。

Q3：用了 HalfFloat RenderTarget 后变卡，甚至部分设备黑屏，怎么办？

先确认运行环境是 WebGL2（Three.js r186 已以 WebGL2 为主），再确认 HalfFloat 纹理过滤是否被支持。工程上的折中方案：① 只在 Bloom / HDR 阶段用 HalfFloat，最终合成仍回 8 位；② 降低 RenderTarget 分辨率（后处理对分辨率不敏感的场景可以半分辨率）；③ 提供降级开关，检测不到浮点渲染能力时回退到 8 位 + 抖动。黑屏通常不是"浮点不能用"，而是浮点 RT 被当成了需要线性过滤的纹理却没有对应扩展。

Q4：两个面贴在一起就闪烁，除了调相机 near/far 还有什么办法？

优先改几何关系：把两个面在法线方向错开极小距离，或者干脆合并成一个材质用贴图区分。其次用 polygonOffset 给"应该显示在上层"的面加偏移，适合路面标线、贴花、UI 面板。最后才考虑 logarithmicDepthBuffer 或分层渲染，因为它们会增加片元成本或 draw call。z-fighting 的第一原则是"不要让两个面共面"，技术手段只是补丁。

术语解释：

  • 位深 bit depth：每个颜色通道用多少位存储，决定台阶数量。
  • 色带 banding：平滑渐变被量化成离散台阶后出现的可见边界。
  • 抖动 dithering：量化前加入微小噪声，用空间混合换取感知上的平滑。
  • HDR：亮度值可超过 1.0 的动态范围，需要浮点缓冲与色调映射配合。
  • 预乘 alpha：RGB 在存储前已经乘以 alpha，避免透明边缘出现黑边。
  • z-fighting：共面或近共面的几何在深度测试中反复"争胜"，表现为闪烁条纹。

动手小练习 ​

  1. 把 banding-precision-lab.html 的抖动强度从 1.0 调到 0.1 与 2.5，分别截图，比较"色带残留"与"噪点可见度"，找到你认为的平衡点并记录数值。
  2. 把渐变方向从纵向改成径向，观察色带分布是否变化。想一想：为什么径向渐变的色带更像同心圆，而纵向渐变是横条？
  3. 给场景加一个半透明的发光平面，分别在 NormalBlending 与 AdditiveBlending 下观察高光叠加。把 RenderTarget 从 8 位换成 HalfFloat，看看加法混合的高光是否更少"死白"。
