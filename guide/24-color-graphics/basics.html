24.1 基础入门：色彩空间与线性工作流 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ④⑥⑦ 再学习本篇。

核心概念讲解 ​

接桥：从 4.2 的色调映射说起 ​

在 ④ 渲染器 · 色调映射 里，我们已经用过 renderer.toneMapping：把灯光算出来的高动态范围亮度"压"回屏幕能显示的范围。当时留了一个尾巴——只说了"开 ACES 会变灰变淡，用 exposure 找回来"，却没有解释为什么同一张红色贴图，换个开关就会从鲜红变成砖红。

答案藏在另一条链路上：在 ⑦ 纹理 里，我们给贴图设置过 texture.colorSpace = THREE.SRGBColorSpace，但很多人把它当成一句"保险咒语"抄进代码，并不知道它在解码什么。

这一篇把两根线接起来：纹理怎么把颜色交进渲染器、渲染器怎么把颜色交回屏幕。中间那条"线性空间"的传送带如果走错，色调映射再准也救不回来。

sRGB 与 Linear-sRGB：同一束光，两种记账方式 ​

先给结论：sRGB 和 Linear-sRGB 描述的是同一批颜色（同样的红绿蓝原色、同样的白点），区别只在"数值怎么记账"。

sRGB（显示编码）Linear-sRGB（线性工作空间）
数值含义经过"感知均匀"压缩的编码值与真实光强成正比
典型用途图片文件、CSS 颜色、屏幕输出光照计算、混合、插值、mipmap
0.5 代表什么大约是 18% 的反射率（中灰）正好一半的光强
类比把音量旋钮刻度做成对数记录真实的声压

人眼对暗部变化更敏感，所以 sRGB 把暗部"拉开"、亮部"压扁"，用 8 位就能存出看起来平滑的渐变。代价是：sRGB 数值不能直接做数学运算。两个 sRGB 值相加、相乘、取平均，结果都不符合物理直觉。例如把纯黑 #000000 与纯白 #ffffff 在 sRGB 数值上取平均得到 #808080，但它在屏幕上看起来远比"一半亮度"暗；在线性空间里取平均，才是真正的半亮度。

这就是"线性工作流"的全部理由：把解码后的线性值交给光照与混合，做完所有运算，最后再编码回 sRGB。

为什么插值、混合与 mipmap 都偏爱线性 ​

除了"两个颜色取平均"这个最直观的例子，线性工作流还影响三个经常被忽略的环节：

  • 纹理缩小与 mipmap：生成 mipmap 的过程本质上是把相邻像素做平均。如果在 sRGB 编码值上平均，暗部会被系统性地压暗，缩小后的贴图看起来比原图更黑、更"脏"；在线性空间平均，才是真实的光能平均。
  • 半透明混合：src * alpha + dst * (1 - alpha) 这个公式只有在光强线性时才成立。在 sRGB 数值上混合，半透明边缘会偏暗，透明物体叠在亮背景上容易出现一圈灰边。
  • 顶点颜色与渐变：几何体顶点色、着色器里的 mix、后处理里的颜色分级，都是插值。插值空间选错，渐变中段就会偏色。Three.js 的顶点色属性若来自 sRGB 数据，需要先解码再上传。

所以"线性工作流"不是某个开关的别名，而是一条贯穿资产、材质、光照、后处理、输出的完整约定。资产在 sRGB 里创作，进入渲染前解码；渲染内部全部线性；输出前再编码。任何一段破坏这个约定，问题都会以"颜色不对"的形式冒出来。

完整链路：四步，一步都不能少 ​

正确的渲染管线可以画成四步：

  1. 解码：颜色贴图从 sRGB 解码成线性值（texture.colorSpace = SRGBColorSpace）。
  2. 计算：材质、灯光、阴影、混合、后处理全部在线性空间里做。
  3. 色调映射：线性 HDR 亮度经 ACES / AgX 等曲线压缩到 0~1 的线性 LDR。
  4. 编码：输出前线性值编码成 sRGB（renderer.outputColorSpace = SRGBColorSpace）。

把这张表记成"进门前脱鞋，出门前穿鞋"：贴图进门时脱掉 sRGB 这双鞋，屏幕出门前再穿上。中间所有房间（光照、混合、后处理）都只认线性。

renderer.outputColorSpace：最后那道编码 ​

renderer.outputColorSpace 决定渲染结果写进屏幕时用哪种编码，r152 之后默认就是 THREE.SRGBColorSpace。它只影响"最后一笔"，不参与光照计算。

js
renderer.outputColorSpace = THREE.SRGBColorSpace      // 默认，正确
// renderer.outputColorSpace = THREE.LinearSRGBColorSpace  // 实验用：故意漏掉编码

如果把它改成线性，屏幕收到的仍是线性数值，显示器却按 sRGB 理解，于是整体明显变暗、饱和色发闷。这不是"更物理"，而是"忘了穿鞋"。

texture.colorSpace：颜色贴图与数据贴图的区别 ​

texture.colorSpace 是每张贴图自己的属性。它回答的问题是：这张图里的数值，是 sRGB 编码的颜色，还是线性数据？

贴图类型应设的 colorSpace原因
颜色贴图 albedo / baseColor / diffuseTHREE.SRGBColorSpace美术在 sRGB 软件里画的颜色
自发光 emissiveMapTHREE.SRGBColorSpace同样是颜色
环境贴图 / 光照贴图（LDR 版本）THREE.SRGBColorSpace存的是可见颜色
法线贴图 normalMapTHREE.NoColorSpace 或 LinearSRGBColorSpace存的是方向分量，不是颜色
粗糙度 / 金属度 / AO / ORM同上存的是物理参数
位移 / 高度 / 遮罩同上存的是标量数据

法线贴图是重灾区：它的 RGB 三个通道分别表示法线在 X/Y/Z 上的分量，把 0.5 当成"中灰颜色"去解码会直接扭弯法线，光照看起来"脏""油""糊"。颜色贴图要解码，数据贴图绝不能解码，这条规则比记 API 更重要。

SRGBColorSpace 与 LinearSRGBColorSpace ​

Three.js 里这两个常量容易混：

  • THREE.SRGBColorSpace（字符串 "srgb"）：表示"这是 sRGB 编码值"，采样时会做 sRGB → 线性解码，输出时会做线性 → sRGB 编码。
  • THREE.LinearSRGBColorSpace（字符串 "srgb-linear"）：表示"这是线性值"，采样时不解码，输出时也不编码。
  • THREE.NoColorSpace（字符串 ""）：不声明色彩空间，通常用于纯数据纹理。

对颜色贴图来说，写 NoColorSpace 和写 LinearSRGBColorSpace 在采样结果上几乎一样——都相当于"不做解码"。所以判断标准不是背常量名，而是问自己：这张图是给人看的颜色，还是给着色器算的数据？

gamma 2.2 与 sRGB 传输曲线不是一回事 ​

很多教程用 pow(color, 1/2.2) 近似 sRGB 编码。它够用，但不精确。sRGB 的传输函数是分段的：

glsl
// sRGB to linear (simplified, no clamp)
vec3 srgbToLinear(vec3 c) {
  vec3 low = c / 12.92;
  vec3 high = pow((c + 0.055) / 1.055, vec3(2.4));
  return mix(high, low, step(c, vec3(0.04045)));
}

线性 → sRGB 则是它的逆函数：暗部走 12.92 倍线性段，亮部走 1.055 次幂段。分段设计是为了让暗部在 8 位精度下更平滑。Three.js 内部用的是标准 sRGB 曲线，不是粗暴的 pow(2.2)。自己写 Shader 时如果要做精确匹配，别用 2.2 近似；做视觉近似则无所谓。

色调映射属于哪一步 ​

renderer.toneMapping（ACESFilmicToneMapping / AgXToneMapping / ReinhardToneMapping）位于第 3 步：在线性空间里压缩 HDR 亮度，输出仍是线性值。它不是色彩空间转换，也不是"滤镜"。

顺序必须是：先线性运算 → 再色调映射 → 最后 sRGB 编码。反过来先编码再色调映射，等于在错误的数值空间里做压缩，暗部会更脏、亮部会更早死白。

renderer.toneMappingExposure 是进入色调映射前的曝光倍增器，相当于相机的曝光补偿。它应该在色调映射之前生效——Three.js 的内置材质就是这么做的。

THREE.Color 的 setHex 默认是 sRGB ​

js
const c1 = new THREE.Color().setHex(0xff0000)                        // 默认按 sRGB 解释
const c2 = new THREE.Color().setHex(0xff0000, THREE.LinearSRGBColorSpace) // 按线性解释

在 ColorManagement.enabled = true（默认）时，setHex、setStyle、setHSL 默认把输入当作 sRGB，并转换到内部的 Linear-sRGB 工作空间。也就是说，new THREE.Color('#ff0000') 存进内存的并不是 1.0/0.0/0.0，而是解码后的线性值。如果你从设计工具里拿到线性色值，必须显式传第二个参数，否则会被再解码一次。

这里还有一个容易踩的细节：Color.setRGB(r, g, b) 的默认色彩空间是工作空间（Linear-sRGB），而不是 sRGB。也就是说，setHex 默认按 sRGB 解释、setRGB 默认按线性解释，两个方法的默认约定并不相同。从着色器或色彩计算库拿到线性三元组时用 setRGB 是对的；从设计稿抄十六进制时用 setHex 是对的。混淆两者，颜色会悄悄偏掉一档。

ColorManagement.enabled 是全局总开关，关掉它会让所有 Color 不再做任何转换，通常只用于从旧版本迁移时的临时兼容。新项目不要关，否则你会在"某些颜色正常、某些颜色偏"的泥潭里浪费大量时间。

对比表格：错误链路 vs 正确链路 ​

环节常见错误链路症状正确链路
颜色贴图colorSpace 留空 / 设 Linear整体发灰、对比度被拉平SRGBColorSpace
数据贴图法线 / 粗糙度设成 sRGB光照发脏、法线方向错NoColorSpace
混合与插值在 sRGB 数值上做平均渐变发脏、边缘黑边在线性空间混合
色调映射先编码再 tone mapping暗部死黑、亮部死白线性空间里 tone mapping
输出outputColorSpace 设 Linear整体偏暗、过饱和SRGBColorSpace

术语解释：

  • 工作色彩空间 working color space：Three.js 内部做运算的空间，r152+ 固定为 Linear-sRGB。
  • 输出色彩空间 output color space：最终写给屏幕的编码，通常 sRGB。
  • 传输函数 transfer function：数值与真实光强的映射曲线，sRGB 用分段函数，不是纯 gamma 2.2。
  • 色域 gamut：能表示的颜色范围。sRGB / Linear-sRGB 色域相同，只是编码不同；Display-P3 才是另一块更大的色域。

三个常见坑 ​

  1. 贴图加载完才改 colorSpace，却忘了 needsUpdate：纹理已经上传到 GPU，改属性不会自动重传，必须 texture.needsUpdate = true。
  2. 用 EffectComposer 时重复做色调映射：RenderPass 会按 renderer.toneMapping 做一次，最后的 OutputPass 又做一次。正确做法是用 OutputPass 统一处理，渲染阶段保持 NoToneMapping，或者明确只保留一处。
  3. 把 DOM / CSS 颜色当成渲染结果：renderer.outputColorSpace 只管 WebGL 画布；HTML 覆盖层的颜色由浏览器按 CSS 规则显示。做"截图取色"对比时，两者可能因为浏览器色彩管理而不同，必须说明测量环境。

这三个坑有一个共同点：它们都不会报错，只会让颜色安静地偏掉。所以色彩问题必须靠链路检查与取色验证，而不能靠"看起来还行"。

代码示例 ​

对应演示 color-space-lab.html：一个红→黄→绿的渐变球，加一条六色参考条（红 / 绿 / 蓝 / 中灰 / 暗灰 / 白），用三个开关实时破坏或修复链路。

① 输出编码：先声明屏幕这一端：

js
const renderer = new THREE.WebGLRenderer({ antialias: true })
renderer.outputColorSpace = THREE.SRGBColorSpace // 出门前穿鞋：线性 -> sRGB
renderer.toneMapping = THREE.NoToneMapping       // 本篇先不压缩 HDR，专心看色彩空间
renderer.toneMappingExposure = 1

② 程序化贴图：明确声明它是 sRGB 颜色：

js
const canvas = document.createElement('canvas')
canvas.width = 512
canvas.height = 256
const ctx = canvas.getContext('2d')
const g = ctx.createLinearGradient(0, 0, 512, 0)
g.addColorStop(0.0, '#ff2020')   // Canvas 2D 画出来的是 sRGB 颜色
g.addColorStop(1.0, '#16d96b')
ctx.fillStyle = g
ctx.fillRect(0, 0, 512, 256)

const tex = new THREE.CanvasTexture(canvas)
tex.colorSpace = THREE.SRGBColorSpace // 进门时脱鞋：采样时解码成线性

这里有一个容易忽略的事实：Canvas 2D 画出的像素本身就是 sRGB 编码。若不声明，Three.js 会把它当线性数据直接乘进光照，红色会变得偏亮偏粉。

③ 开关：改属性只是第一步，还要通知 GPU 重编译 / 重传：

js
const COLOR = {
  'sRGB': THREE.SRGBColorSpace,
  'Linear-sRGB': THREE.LinearSRGBColorSpace
}

gui.add(params, 'textureColorSpace', Object.keys(COLOR)).onChange((v) => {
  gradientTex.colorSpace = COLOR[v]
  swatchTex.colorSpace = COLOR[v]
  gradientTex.needsUpdate = true   // 纹理参数变了，重新上传
  swatchTex.needsUpdate = true
})

gui.add(params, 'outputColorSpace', Object.keys(COLOR)).onChange((v) => {
  renderer.outputColorSpace = COLOR[v]
  scene.traverse((obj) => {
    if (!obj.material) return
    const mats = Array.isArray(obj.material) ? obj.material : [obj.material]
    mats.forEach((m) => { m.needsUpdate = true }) // 输出编码写进着色器，要重编译
  })
})

④ 把当前链路写在 HUD 上，避免"看不出差别"：

js
const tex = params.textureColorSpace === 'sRGB' ? 'sRGB' : 'Linear'
const out = params.outputColorSpace === 'sRGB' ? 'sRGB' : 'Linear'
document.getElementById('chain').textContent =
  `贴图(${tex}) → 着色器(线性) → 输出(${out})`

演示里的判定文案是固定的四种组合：贴图错 → 发灰；输出错 → 偏暗；两头都错 → 既灰又暗；全对 → 正常。这样读者不需要"凭感觉"，直接读链路就能预测症状。

常见问题解答 ​

Q1：贴图明明很鲜艳，渲染出来却发灰、发淡，是灯光太弱吗？

先别加灯，先查 texture.colorSpace。发灰最典型的成因是颜色贴图没有声明 SRGBColorSpace：sRGB 数值被当成线性值直接参与运算，等价于把暗部整体抬亮，对比度被拉平。检查顺序：① 贴图加载后是否设置 colorSpace = THREE.SRGBColorSpace；② 设置之后是否 needsUpdate = true；③ 是否在 onLoad 回调里设置，而不是在纹理还没加载完就设置。三步都对，才轮到怀疑灯光。

Q2：我把 `renderer.outputColorSpace` 改成 Linear，为什么画面变暗了？

因为显示器默认按 sRGB 解释收到的数值。你把线性值直接写进屏幕，等于让显示器"用错误的曲线"显示，中间调会明显下压，饱和色看起来发闷。LinearSRGBColorSpace 作为输出只在两种场景有意义：调试管线、或者输出给明确知道要线性数据的下游（例如某些后期合成软件）。正常网页项目保持默认的 SRGBColorSpace。

Q3：色调映射和色彩空间转换，到底谁先谁后？

顺序是：解码贴图 → 线性空间计算 → 色调映射（仍是线性值）→ 编码成 sRGB 输出。可以记成"先算光，再压光，最后才编码"。如果先编码再色调映射，等于在 sRGB 数值上做非线性压缩，暗部会被压得更脏；如果色调映射后又做一次线性化再编码，则会重复转换，颜色发灰。使用 EffectComposer 时让 OutputPass 统管"色调映射 + 输出编码"，不要在 RenderPass 阶段再开一次。

Q4：法线贴图、粗糙度贴图要不要设成 sRGB？

不要。它们存的是方向向量或物理参数，不是"给人看的颜色"。法线贴图被 sRGB 解码后，三个分量会被非线性地拉开，法线方向整体偏移，光照会出现"油光""脏边"。正确设置是 THREE.NoColorSpace（或等价的 LinearSRGBColorSpace）。判断口诀：能当颜色画出来的图用 sRGB，只能当数字读的图用 NoColorSpace。

动手小练习 ​

  1. 打开 color-space-lab.html，把 texture.colorSpace 切成 Linear，再切回 sRGB，用截图工具取球体左侧红色区域与下方红色色块的像素值，记录两次的 RGB 差异，并解释哪一次更接近 #ff2020。
  2. 把 outputColorSpace 切成 Linear、toneMapping 保持 No，再把 toneMappingExposure 从 1 调到 1.8，观察"偏暗"是否能被曝光补回来。想一想：为什么曝光补偿无法真正修复编码错误？
  3. 自己写一个小页面，同时加载一张颜色贴图和一张法线贴图（可以用 Canvas 程序化生成），分别尝试两种 colorSpace 设置，记录光照结果的变化，并总结"数据贴图不能解码"的原因。
