27.3 实战案例：材质预设库与运行时切换 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑥⑫ 与 ⑭ 再学习本篇。

核心概念讲解 ​

接桥：⑥ 的材质实验室只是一个滑块面板，企业里要的是"可交付的材质资产" ​

在 ⑥ 材质 · 材质实验室 里，我们把 color、roughness、metalness、clearcoat、envMapIntensity 全部接到 lil-gui 的滑条上，一边拖一边看。那是探索：参数是临时的，结果在你脑子里，关掉页面就没了。

到了真实项目，需求会变成另一句话："把这套材质交给别人，并且在任何页面、任何时间打开都一模一样。" 于是需要的是资产，不是滑条：一个可序列化的描述、一个稳定的工厂函数、一套缓存与释放规则、一份可回归的基线。设计师改了一个色号，你得知道哪些预设受影响；上线后发现某个预设偏亮，你得能定位到是参数、贴图还是色调映射。

这一篇把材质从"面板上的数值"升级成"预设库"：预设 JSON、工厂、共享与独立、贴图缓存、按需释放、与后处理的约定、版本化回归。

预设的三层结构：参数、槽位、补丁 ​

一个可交付的材质预设，应该只包含纯数据，不含 THREE.Material 实例，也不含函数。推荐的结构：

字段类型含义示例
idstring稳定标识，不能改clearcoat-paint
typestring用哪个材质类standard / physical
paramsobject标量参数roughness、metalness、clearcoat
mapsobject贴图槽位 → 资源键{ roughnessMap: 'brushed' }
patchesstring[]需要挂载的补丁名['sheenBoost']
metaobject版本、作者、验收基线{ version: 2, toneMapping: 'ACES' }

这样存的好处是：JSON 可以直接进数据库、进 CMS、进版本库 diff；加载时由工厂把字符串颜色转成 THREE.Color、把资源键解析成纹理；补丁名解析成一组 onBeforeCompile 注入器。数据与实现分离，材质才可能被运营、被测试、被回滚。

工厂函数：把 JSON 变成实例，且只做一次 ​

工厂的核心不是"new 一个材质"，而是把创建集中到一处：

js
function buildMaterial(preset) {
  const Klass = preset.type === 'physical'
    ? THREE.MeshPhysicalMaterial
    : THREE.MeshStandardMaterial

  const opts = {}
  for (const [k, v] of Object.entries(preset.params)) {
    opts[k] = typeof v === 'string' ? new THREE.Color(v) : v
  }
  for (const [slot, key] of Object.entries(preset.maps)) {
    opts[slot] = textureCache.get(key)
  }

  const mat = new Klass(opts)
  mat.name = preset.id
  return mat
}

集中创建带来三个好处：① 颜色字符串统一经过色彩管理；② 贴图槽位统一走缓存；③ 所有材质都带 name，方便在 renderer.info 与调试器里定位。反例是在 renderer.setAnimationLoop 里 new MeshStandardMaterial()——每帧新建材质会不断产生 program 变体、不断触发编译，几秒内就能把帧率拖垮。

工厂还必须处理异常输入：未知 type 回退到 standard、缺失贴图键回退到 null、非法颜色回退到默认值。预设来自运营后台时，不能假设数据永远正确。

共享实例与每物体独立 ​

同一份预设，可以有两种落地策略：

策略实例数优点代价适用
共享实例1（每种预设）省显存、省编译、状态切换少改一个物体 = 改全部大批量标准件、场景家具
每物体独立物体数可单独调参、可单独动画实例多、program 可能变多需要高亮选中、逐物体变色

共享的关键是按预设 id 分组，而不是"每个物体一份"。演示里 assignments 记录每个物体用哪个预设，rebuild() 时先按 id 建缓存，再分发：

js
const cache = new Map()
assignments.forEach((key, i) => {
  let mat = cache.get(key)
  if (!mat) {
    mat = buildMaterial(PRESETS[key])
    cache.set(key, mat)
    activeMats.push(mat)
  }
  meshes[i].material = mat
})

注意 draw call 不会因为共享材质而减少。draw call 由"物体 + 材质"的批次决定，共享材质主要省的是显存、program 数量与状态切换。真正减少 draw call 要靠合批、实例化（InstancedMesh）或合并几何。

还有一个容易忽略的差异：共享材质改颜色会影响所有引用它的物体。做"点选高亮"时，正确做法是给被选中的物体临时克隆一份材质，取消选中时恢复共享实例，而不是直接改共享材质。

按需创建与 dispose：谁创建，谁释放 ​

材质是 GPU 资源的持有者：program、纹理绑定、uniform 缓冲。切换预设时如果只把引用换掉、不 dispose，旧材质会一直占着显存，直到页面关闭。

释放规则可以写成三条：

  1. 材质自己 dispose()：material.dispose() 会释放它持有的 program 引用，但不会释放贴图。
  2. 贴图由缓存负责：纹理在 textureCache 里跨预设复用，不能跟着材质一起释放，否则下一个预设会拿到已销毁的纹理。
  3. 几何与材质分离管理：几何通常跨预设不变，只换材质；几何的 dispose 应该在物体真正移除时做。

一个安全的切换函数：

js
function disposeActive() {
  activeMats.forEach((m) => m.dispose())
  activeMats = []
}

function rebuild() {
  disposeActive()          // 先释放旧的
  // ... 再按当前策略创建新的，并填入 activeMats
}

顺序不能反：先创建新的再释放旧的，会在切换瞬间同时持有两套 program，显存峰值翻倍；先释放再创建，如果创建过程中抛错，场景会短暂没有材质。工程上更稳的做法是"先建新、再切引用、最后释放旧"，用一次短暂的内存峰值换零空窗。

贴图缓存与引用计数 ​

贴图是材质资产里最重的一部分。一个拉丝金属预设可能引用 roughnessMap、normalMap、anisotropyMap 三张图，多个预设共用同一张拉丝图。缓存 + 引用计数的基本形态：

js
const textureCache = new Map() // key -> { texture, refs }

function acquireTexture(key, factory) {
  let entry = textureCache.get(key)
  if (!entry) {
    entry = { texture: factory(), refs: 0 }
    textureCache.set(key, entry)
  }
  entry.refs++
  return entry.texture
}

function releaseTexture(key) {
  const entry = textureCache.get(key)
  if (!entry) return
  entry.refs--
  if (entry.refs <= 0) {
    entry.texture.dispose()
    textureCache.delete(key)
  }
}

关键点是引用计数与材质生命周期对齐：材质创建时 acquire，材质 dispose 时 release。如果只在页面卸载时统一释放，长时间运行的编辑器会越用越占内存；如果每次切换都释放，共享贴图会被提前销毁，画面出现黑块。

还有两条与贴图相关的硬约束：颜色贴图 colorSpace = SRGBColorSpace，粗糙度/法线/AO 一律 NoColorSpace；数据贴图不要设 generateMipmaps = true 后再手动改尺寸，否则容易出现"贴图糊了但说不清原因"。

与后处理的配合：预设必须绑定色调映射 ​

一个预设的观感，是在特定色调映射与曝光下调出来的。同一个 emissiveIntensity = 1.6，在 NoToneMapping 下可能刺眼，在 ACES + exposure 0.8 下可能刚好。所以预设元数据里应该记录：

  • toneMapping：ACES / AgX / None
  • toneMappingExposure：调参时的曝光
  • envMapIntensity：环境光贡献
  • 是否进入 Bloom 阈值（发光类预设尤其重要）

如果团队后来把全站从 ACES 换成 AgX，所有预设都需要重新验一遍。把这条约定写进资产而不是记在某人脑子里，迁移时才有据可查。后处理链里如果有 Bloom，发光预设的 emissiveIntensity 还要与 Bloom 阈值联动：阈值 0.55、强度 0.9 的组合下，1.6 可能刚好起晕；换成阈值 0.8，同样的材质就不发光了。

渲染顺序：为什么"打散材质"会改变画面 ​

不透明物体的绘制顺序由 renderOrder、材质/程序的排序键、以及相机距离共同决定。材质一变，排序键就变，绘制顺序随之变化。多数时候这不可见，但在以下场景会显形：

  • 透明物体：顺序错了会出现遮挡错误；
  • 依赖深度写入的叠加效果：顺序影响混合结果；
  • 大量共面或贴花：polygonOffset 与顺序共同决定谁在上。

所以"随机打散材质"不只是玩具功能，它是渲染顺序的探测器：如果打散后出现闪烁、透明边缘异常，说明场景里存在顺序敏感的物体，需要显式设置 renderOrder 或拆分透明/不透明队列。

版本化与回归：让材质也能被测试 ​

预设库进入生产后，最重要的是可回归。呼应 ⑳ 测试与质量 · 视觉回归 的做法：

  1. 资产版本号：schemaVersion 管结构，preset.version 管观感。结构变更要迁移脚本，观感变更要新的基线截图。
  2. 黄金截图：每个预设在同一相机、同一环境、同一色调映射下渲染一张基准图，CI 里做像素差异对比。
  3. 参数快照：把 JSON 存进版本库，diff 就能看出"这次谁把 roughness 从 0.42 改成了 0.6"。
  4. 回归清单：新增预设必须同时提交 JSON、截图、以及一段"这个预设用来做什么"的说明。

没有基线的材质库，最终会变成"每个人都说自己的版本是对的"。

    patches: []
  },
  '布料': {
    id: 'fabric',
    type: 'physical',
    params: {
      color: '#b39df5', roughness: 0.96, metalness: 0.0,
      sheen: 1.0, sheenRoughness: 0.65, sheenColor: '#f2ecff'
    },
    maps: {},
    patches: []
  }
}

patches 现在为空，但结构留好了：未来加"自定义 sheen 补丁"或"品牌边缘光"时，只需在这里写名字，工厂负责解析。

② 贴图槽位解析：数据贴图必须声明为线性：

js
const tex = new THREE.CanvasTexture(canvas)
tex.colorSpace = THREE.NoColorSpace   // 粗糙度是数据，不是颜色
tex.wrapS = THREE.RepeatWrapping
tex.wrapT = THREE.RepeatWrapping
textureCache.set('brushed', tex)

拉丝贴图用 Canvas 程序化生成，不依赖外部图片。这里特别强调 NoColorSpace：它被 sRGB 解码后，粗糙度分布会整体偏移，金属看起来"一半亮一半脏"，而且很难联想到是色彩空间问题。

③ 工厂：字符串颜色统一走色彩管理：

js
for (const [k, v] of Object.entries(preset.params)) {
  opts[k] = typeof v === 'string' ? new THREE.Color(v) : v
}

new THREE.Color('#c8d4e8') 默认按 sRGB 解释并转到线性工作空间，这正是设计稿色号的正确入口。不要用 setRGB 直接塞十六进制分量，那会按线性解释，颜色会偏一档。

④ 共享与独立的切换：一段分支管住实例数：

js
if (params.share === '共享实例') {
  const cache = new Map()
  assignments.forEach((key, i) => {
    let mat = cache.get(key)
    if (!mat) {
      mat = buildMaterial(PRESETS[key])
      cache.set(key, mat)
      activeMats.push(mat)
    }
    meshes[i].material = mat
  })
} else {
  assignments.forEach((key, i) => {
    const mat = buildMaterial(PRESETS[key])
    activeMats.push(mat)
    meshes[i].material = mat
  })
}

共享模式下，六个物体若只用一种预设，实例数就是 1；随机打散后可能变成 3~5。HUD 里的"实例 N · 预设 M 种"就是这段逻辑的直接读数。

⑤ 随机打散：观察程序数与渲染顺序：

js
shuffle() {
  const keys = Object.keys(PRESETS)
  assignments = meshes.map(() => keys[Math.floor(Math.random() * keys.length)])
  rebuild()
}

打散后 程序 数会上升，说明场景里同时存在更多 shader 变体。这也是一个提醒：预设种类越多，首帧编译越贵。上线前可以把所有预设预编译一遍，避免用户第一次切换时卡顿。

⑥ HUD：把资产状态暴露出来：

js
statEl.textContent =
  `实例 ${activeMats.length} · 预设 ${uniquePresets} 种 · 程序 ${programs} · draw calls ${r.calls}`

实例 反映材质数量，预设 反映多样性，程序 反映 shader 变体，draw calls 反映绘制批次。四个数字一起看，才能判断一次切换到底是"省了内存"还是"加了编译"。

常见问题解答 ​

Q1：切换材质时卡了将近一秒，怎么排查？

先分清是"编译卡"还是"释放卡"。① 看是否在切换时新建了大量材质或贴图：每个新 program 都要编译，首次切换尤其贵；用 renderer.compile(scene, camera) 在空闲时预热，或把常用预设提前编译。② 看是否每次切换都 dispose 了共享贴图：贴图销毁后重新上传，几十张 2K 图足以卡住主线程。③ 看是否在切换回调里同步做了重活（生成 Canvas、解码大图、遍历全场景改材质）；把这些挪到 requestIdleCallback 或 Worker。④ 用 performance.now() 打点，把"销毁旧材质 / 创建新材质 / 首次渲染"三段分别计时，卡顿通常集中在其中一段。最后记得：material.dispose() 不会释放贴图，别把贴图释放算进材质切换成本里。

Q2：共享材质后，为什么"点选高亮"会点亮一整排物体？

因为它们引用的是同一个材质实例，改 emissive 等于改全部。正确做法是"临时克隆"：选中时 mesh.material = mesh.material.clone()，记录原引用；取消选中时释放克隆并恢复原共享实例。克隆后要给自定义 uniform 重新绑定（见 27.2 的 copy() 说明），否则高亮参数会串到别的物体。另一个更省的办法是用顶点色或一个 highlight uniform + 逐物体材质属性，但本质仍然是"被选中的物体不能继续共享"。

Q3：预设切来切去之后，显存一直涨，是哪里漏了？

按三层查。① 材质：每次 rebuild 是否把旧材质放进 activeMats 并在下次切换时 dispose()；如果只是把 mesh.material 指向新材质，旧实例还在内存里。② 贴图：缓存是否无上限增长，是否只 acquire 不 release；引用计数归零后要 texture.dispose() 并从 Map 删除。③ 程序：renderer.info.programs.length 是否持续上升；每多一个 customProgramCacheKey 变体就多一份 program，切预设时如果键不稳定（比如拼了随机数），程序会无限累积。用 renderer.info.memory 看纹理与几何计数，配合浏览器 Memory 面板确认是 JS 堆还是 GPU 资源。

Q4：同一份预设，在演示页好看，进项目就偏灰偏亮，为什么？

大概率是"宿主环境"不同：色调映射、曝光、环境贴图强度、灯光布局、后处理链。预设里的 envMapIntensity 是相对值，换了环境亮度就会变；emissiveIntensity 在 ACES 与 AgX 下的表现也不同。排查顺序：先对齐 renderer.toneMapping 与 toneMappingExposure，再对齐 scene.environment 与 envMapIntensity，最后检查后处理是否多做了色调映射或 Bloom。把这些参数写进预设的 meta，并在验收时使用同一套相机与环境，才是可复现的对比。

术语解释：

  • 材质预设 preset：一份可序列化的材质描述，含参数、贴图槽位与补丁列表。
  • 工厂 factory：把预设数据转换成材质实例的函数，集中处理颜色、贴图与异常。
  • 引用计数 refCount：记录资源被多少使用者持有，归零时才真正释放。
  • program 变体：由材质参数与宏组合出的独立着色器程序。
  • 黄金截图 golden image：作为验收基线的渲染结果，用于视觉回归对比。

动手小练习 ​

  1. 在 material-preset-lab.html 里把共享策略切成"每物体独立"，再随机打散，记录实例数、程序数与 draw call 的变化，并解释哪一项变了、哪一项没变。
  2. 给 PRESETS 新增一个"磨砂玻璃"预设（type: 'physical'，transmission: 1、thickness: 0.4、ior: 1.5），观察它与其他预设的渲染顺序差异，思考透明/透射物体为什么要单独排队。
