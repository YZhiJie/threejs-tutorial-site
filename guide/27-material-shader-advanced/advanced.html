27.2 进阶应用：自定义 PBR 与材质扩展架构 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑥⑫ 与 ⑭ 再学习本篇。

核心概念讲解 ​

接桥：⑭ 的 IBL 给了"环境"，但没给你自定义反射模型 ​

在 ⑭ 高级光照与 IBL 里，我们用 RoomEnvironment 加 PMREMGenerator 给金属球铺了一间"虚拟摄影棚"：灯箱的位置、亮度、模糊程度全都预先烘焙进一张环境贴图，MeshStandardMaterial 按粗糙度采样对应的 mip 级别，于是金属看起来有反射、塑料看起来有高光。那套流程解决的是**"环境从哪里来"**。

但它没有解决**"反射怎么算"**。内置 PBR 的反射模型是固定的：GGX 微表面分布 + 菲涅尔项 + 金属度/粗糙度工作流。你可以调参数，却没法让高光"沿某个方向拉长"（各向异性拉丝），也没法让边缘出现"逆光时发亮"的织物绒面（sheen），更没法做一个只存在于你项目里的"全息涂层"。

MeshPhysicalMaterial 已经内置了一部分扩展（清漆、虹彩、绒面、透射、各向异性），但它是封闭的参数集。真正想加一个引擎没提供的 BRDF 项，有两条路：在物理材质上打补丁（保留一切，只追加一项），或者用 ShaderMaterial 自己组装灯光。本篇把两条路的边界、写法和成本讲清楚。

MeshPhysicalMaterial 的扩展参数：官方给的那一柜子 ​

MeshPhysicalMaterial 继承 MeshStandardMaterial，在基础 PBR 之上追加了几组"物理层"：

参数组关键字段物理含义典型材质额外成本
清漆clearcoat、clearcoatRoughness、clearcoatNormalMap表面覆盖一层透明涂层，拥有独立的高光瓣车漆、钢琴漆、釉面陶瓷多一次高光计算，片元指令增加
虹彩iridescence、iridescenceIOR、iridescenceThicknessRange薄膜干涉，颜色随视角偏移肥皂泡、甲虫壳、CD 面薄膜厚度与光谱近似计算，较贵
绒面sheen、sheenColor、sheenRoughness、sheenColorMap掠射角下的柔软背向散射天鹅绒、麂皮、毛呢一个额外 BRDF 瓣，中等
透射transmission、thickness、ior、attenuationColor、attenuationDistance光线穿过介质并折射玻璃、水晶、水需要额外屏幕拷贝与折射采样，最贵
各向异性anisotropy、anisotropyRotation、anisotropyMap高光沿切线方向拉长拉丝金属、唱片、丝绸需要切线空间，片元成本中等
高光控制specularIntensity、specularColor非金属的电介质高光强度与颜色涂料、塑料很便宜

这些参数的好处是开箱即用、与管线完全兼容：环境贴图、阴影、色调映射、雾效全都照常工作。坏处是它们只覆盖"常见物理现象"，你想要的效果如果不在列表里，就只能自己写。

还有一条经常被忽略的规则：这些扩展不是免费的开关，而是会改变 shader 变体。clearcoat > 0 会定义 USE_CLEARCOAT，transmission > 0 会定义 USE_TRANSMISSION，每种组合都是一份独立的 program。一个项目里如果同时存在"有清漆/无清漆/有透射/无透射"的材质，程序数量会成倍增长，首帧编译时间随之上升。

用 onBeforeCompile 追加自定义 BRDF 项 ​

内置 PBR 的片元流程可以简化成：

text
基础色 → 法线 → 光照循环（直接光）
      → 间接光（IBL + 环境）
      → reflectedLight.directDiffuse / directSpecular
      → reflectedLight.indirectDiffuse / indirectSpecular
      → outgoingLight → 色调映射 → 输出

lights_fragment_end 正好是"光照已经结算完、还没组装最终颜色"的位置。在这里往 reflectedLight 里加一项，等于给这个材质追加一个新的能量来源，后面的色调映射、输出编码都会照常处理。

一个简化的布料 sheen 可以写成：

glsl
float ndv = saturate( dot( normal, normalize( vViewPosition ) ) );
float sheenTerm = pow( 1.0 - ndv, 2.0 + uSheenRoughness * 2.0 );
reflectedLight.indirectDiffuse += uSheenColor * sheenTerm * uSheenStrength;

它表达的是"视线越贴近表面，绒面反射越强"——这正是天鹅绒在逆光下边缘发亮的原因。真实 sheen 还要考虑光线方向与纤维朝向，但作为风格化近似，这一项已经足够让材质"看起来像布"。

同理，如果你想要一个引擎没提供的"清漆高光瓣"，可以用 Schlick 菲涅尔近似：

glsl
float fresnel = 0.04 + 0.96 * pow( 1.0 - ndv, 5.0 );
reflectedLight.indirectSpecular += uCoatColor * fresnel * uCoatStrength;

注意两个细节。第一，加在 indirectSpecular 还是 indirectDiffuse 决定了它是否受基础色影响：高光类应该进 specular，漫反射类的染色应该进 diffuse。第二，这是"额外加光"，不守恒能量：写得太猛会直接过曝，也没有阴影衰减。它适合做风格化增强，不适合做物理正确的材质模拟。

三条实现路径的对比 ​

路线能改什么是否保留 PBR维护成本适用场景
MeshPhysicalMaterial 内置参数清漆 / 虹彩 / 绒面 / 透射 / 各向异性完整保留最低，升级安全常规产品渲染，90% 的场景
内置材质 + onBeforeCompile在固定流程上追加项、改中间变量保留，但依赖 chunk 名称中，需要随版本核对 chunk自定义 BRDF、风格化材质、品牌专属效果
ShaderMaterial + lights: true整个光照流程需要自己组装，容易漏最高，等于自己维护一份 PBR引擎能力之外的渲染模型、特殊光学

选择顺序建议是：先问内置参数够不够，再问补丁能不能加，最后才考虑重写。 很多"看起来必须写着色器"的效果，其实一个 clearcoat 加一张法线贴图就解决了。

ShaderMaterial + lights: true：复用灯光 chunk ​

如果确实需要自己控制整个流程，不必从零实现灯光。ShaderMaterial 打开 lights: true 后，可以引入 Three.js 的灯光 chunk：

js
const mat = new THREE.ShaderMaterial({
  lights: true,
  uniforms: THREE.UniformsUtils.merge([
    THREE.UniformsLib.lights,
    { uBaseColor: { value: new THREE.Color(0x6f8dff) } }
  ]),
  vertexShader: /* glsl */`
    #include <common>
    #include <lights_pars_begin>
    void main() {
      #include <beginnormal_vertex>
      #include <begin_vertex>
      #include <project_vertex>
      #include <worldpos_vertex>
    }
  `,
  fragmentShader: /* glsl */`
    #include <common>
    #include <lights_pars_begin>
    uniform vec3 uBaseColor;
    void main() {
      vec3 normal = normalize( vNormal );
      vec3 diffuse = uBaseColor;
      #include <lights_fragment_begin>
      #include <lights_fragment_end>
      gl_FragColor = vec4( reflectedLight.directDiffuse + reflectedLight.indirectDiffuse, 1.0 );
    }
  `
})

这套写法有三个硬性前提：① UniformsLib.lights 必须并入 uniforms，否则灯光循环里的 uniform 全是空值；② #include <lights_pars_begin> 要在两个着色器里都出现；③ begin_vertex、beginnormal_vertex 等 chunk 的顺序不能乱。UniformsUtils.merge 会深拷贝 uniform 值，如果你在 merge 之后又持有原始对象去改，会发现改了不生效——贴图这类引用类型尤其容易踩。

它的代价是：环境贴图采样、色调映射、雾效、阴影全都要自己接。除非你在做引擎能力之外的东西（比如自发光体积、特殊次表面散射），否则性价比不高。

补丁注入的"能量账本" ​

写自定义 BRDF 时，最该养成的一个习惯是问自己：这笔能量从哪儿来、到哪儿去？

内置 PBR 的每一项都参与能量分配：漫反射、镜面反射、清漆反射各自分走一部分，剩下的通过环境与间接光循环补足。你在 lights_fragment_end 里 += 的一笔颜色，没有从任何一项里扣，属于"凭空增加"。少量使用是风格化，用多了就会破坏材质的可信度：

加法位置视觉效果是否参与能量守恒建议强度
directDiffuse像被某束光照亮否低，且要跟灯光方向一致
directSpecular额外高光斑否低，用于局部提亮
indirectDiffuse环境染色 / 绒面感否中低，适合 sheen
indirectSpecular边缘光 / 涂层反射否中，适合菲涅尔类效果

如果确实想让效果"看起来物理"，可以做一个近似扣减：把基础色乘以 1 - k，再把这部分能量作为自定义项加回去。这不是严格守恒，但至少不会让物体"越加越亮"。工程上更常见的是直接调低强度，用观感验收，而不是追求公式正确——前提是团队知道这是一个风格化补丁。

材质派生类封装：把补丁变成可复用资产 ​

补丁写到第三遍，就该封装了。最自然的做法是继承 MeshPhysicalMaterial：

js
class SheenFabricMaterial extends THREE.MeshPhysicalMaterial {
  constructor(params = {}) {
    super({ sheen: 1, sheenRoughness: 0.65, ...params })
    this.uniforms = {
      uSheenStrength: { value: params.sheenStrength ?? 0.55 }
    }
    this.onBeforeCompile = (shader) => {
      Object.assign(shader.uniforms, this.uniforms)
      shader.fragmentShader = 'uniform float uSheenStrength;\n' + shader.fragmentShader
      shader.fragmentShader = shader.fragmentShader.replace(
        '#include <lights_fragment_end>',
        `#include <lights_fragment_end>
        float ndv = saturate( dot( normal, normalize( vViewPosition ) ) );
        reflectedLight.indirectDiffuse += sheenColor * pow( 1.0 - ndv, 3.0 ) * uSheenStrength;`
      )
    }
  }
  get sheenStrength() { return this.uniforms.uSheenStrength.value }
  set sheenStrength(v) { this.uniforms.uSheenStrength.value = v }
}

封装时要额外做三件事：给 customProgramCacheKey 加类名与版本号（否则两个子类的补丁源码相同会撞键）、重写 copy()（克隆时把 uniforms 与钩子重新绑定，否则 clone 出来的材质还在改旧对象）、提供 dispose() 清理自己创建的资源。补丁从"一段代码"变成"一个类"，才可能进入预设库、被版本管理、被回归测试覆盖。

材质与几何、贴图的组合契约 ​

自定义 PBR 不是材质一个人的事，它和几何、贴图有一份隐式契约：

契约要求违约症状
UV 通道贴图用哪套 UV 要和 geometry.attributes.uv 对齐贴图错位、拉伸
切线空间各向异性、法线贴图依赖切线或屏幕导数高光方向乱、拉丝不沿纹理方向
顶点属性自定义 attribute 必须在几何上存在且命名一致编译报错或读到 0
贴图色彩空间颜色贴图 sRGB，数据贴图 NoColorSpace颜色发灰、光照发脏
顶点色用 vertexColors 时几何要有 color 属性材质全黑或全白

最后一列的问题都不是"材质写错了"，而是组合错了。工程上更稳妥的做法是把这些约束写进预设的结构里：贴图槽位、UV 通道、是否需要切线，都作为 JSON 字段显式声明，而不是散落在代码注释里。

性能成本：每个像素多算几行，乘以多少像素 ​

自定义 BRDF 的开销要看三个乘数：片元数量 × 每片元指令数 × 材质变体数。

成本项来源量级优化方向
额外 uniform每个自定义参数每个 1~4 个 float，几乎可忽略合并成 vec3/vec4
额外指令pow、噪声、多次采样每片元几到几十条用近似函数、降采样、移出屏幕外物体
程序变体宏与材质参数组合每个变体一次编译减少变体，用 uniform 代替宏
透射拷贝transmission 需要屏幕复制每帧一次全屏 pass控制透射物体数量与分辨率
纹理带宽额外的法线/粗糙度/AO 贴图每像素多次采样通道打包（ORM）、mipmap

移动端尤其敏感：pow 在部分 GPU 上成本高，可以用乘法近似；噪声函数不要在每个片元里跑满循环。优化顺序永远是：先减少像素（遮挡剔除、降低分辨率），再减少指令，最后才抠数学表达式。

代码示例 ​

对应演示 custom-pbr-lab.html：同一颗球在 Standard / Physical（clearcoat）/ 自定义 sheen 三种实现之间切换，环境来自程序化 RoomEnvironment，HUD 显示 draw call、程序数、帧耗时与切换编译耗时。

① 统一基础参数，只换实现：

js
const BASE = { color: 0x6f8dff, metalness: 0.35, roughness: 0.26, envMapIntensity: 1.3 }

const standardMat = new THREE.MeshStandardMaterial({ ...BASE })
const physicalMat = new THREE.MeshPhysicalMaterial({
  ...BASE,
  clearcoat: 1.0,
  clearcoatRoughness: 0.03,
  ior: 1.5
})

颜色、金属度、粗糙度全部一致，差异只来自"多了一层清漆"——这样对比才公平。如果两边的参数都不同，你看到的高光差异可能只是粗糙度造成的。

② 自定义 sheen：在光照结算之后追加一项：

js
const sheenUniforms = {
  uSheenColor: { value: new THREE.Color(0xffb4d2) },
  uSheenStrength: { value: 0.55 },
  uSheenRoughness: { value: 0.35 }
}

const sheenMat = new THREE.MeshStandardMaterial({
  ...BASE,
  color: 0x8a7bd8,
  metalness: 0.05,
  roughness: 0.62
})

sheenMat.onBeforeCompile = (shader) => {
  Object.assign(shader.uniforms, sheenUniforms)
  shader.fragmentShader = `
    uniform vec3 uSheenColor;
    uniform float uSheenStrength;
    uniform float uSheenRoughness;
  ` + shader.fragmentShader
  shader.fragmentShader = shader.fragmentShader.replace(
    '#include <lights_fragment_end>',
    `#include <lights_fragment_end>
    float ndv = saturate( dot( normal, normalize( vViewPosition ) ) );
    float sheenTerm = pow( 1.0 - ndv, 2.0 + uSheenRoughness * 2.0 );
    reflectedLight.indirectDiffuse += uSheenColor * sheenTerm * uSheenStrength;`
  )
}
sheenMat.customProgramCacheKey = () => 'standard-sheen-v1'

uSheenRoughness 在这里不是物理上的粗糙度，而是"绒面高光的扩散程度"：值越大，亮边越宽越软。把它做成 uniform，滑条就能实时预览，不需要重编译。

③ 运行时切换，并把编译成本量出来：

js
function setMode() {
  sphere.material = materials[params.mode]
  const t0 = performance.now()
  renderer.compile(scene, camera)   // 强制编译，让一次性成本显形
  compileMs = performance.now() - t0
}

第一次切到某个实现时，renderer.compile 会真的编译新的 program，耗时可观；再次切回同一实现，命中缓存，耗时接近 0。这个数值本身就是"材质变体要克制"的最好论据。

④ 帧耗时与程序数：把成本放到 HUD 上：

js
frameMs = frameMs * 0.9 + Math.min(delta * 1000, 100) * 0.1
statEl.textContent =
  `draw calls ${r.calls} · 程序 ${p} · 帧耗时 ${frameMs.toFixed(1)} ms · 切换编译 ${compileMs.toFixed(1)} ms`

用指数移动平均而不是单帧值，是为了把偶发的 GC 抖动过滤掉，留下稳定的趋势。切换实现后如果帧耗时明显上升，先怀疑变体数量与额外采样，而不是"球变重了"。

常见问题解答 ​

Q1：自定义 sheen 和 MeshPhysicalMaterial 自带的 sheen 有什么区别？该用哪个？

自带的 sheen 是完整实现的物理近似：它参与能量分配、支持 sheenColorMap / sheenRoughnessMap、与清漆和透射正确叠加，而且不需要你维护 chunk 名称。自定义 sheen 只是往 reflectedLight 里加了一笔颜色，便宜、可控、可以按项目风格调形，但不守恒能量、不参与阴影、也不会随材质参数自动变化。建议：能调到满意就用自带参数；需要"这个品牌特有的绒面光泽"或想在 sheen 上再叠图案时，再用补丁。

Q2：为什么加了自定义 BRDF 后，物体在暗处也发亮？

因为你加的是"无条件的光"。reflectedLight.indirectDiffuse += sheen 没有考虑光照强度、阴影、遮挡，哪怕场景全黑它也会输出颜色。修正方向有三：① 乘上环境光或某个灯光强度的近似值；② 只在掠射角生效（ndv 指数已经做了一部分）；③ 用 uSheenStrength 把它压到"只作为边缘提示"的量级。记住补丁加的是风格化项，不是物理光源，暗部亮起来是预期行为，调参而不是修 bug。

Q3：`ShaderMaterial` 开了 `lights: true`，灯光却完全不生效？

按顺序检查四件事。① uniforms 里有没有并入 THREE.UniformsLib.lights，没有的话灯光循环读到的全是零；② 两个着色器是否都引入了 #include <lights_pars_begin>，它定义了灯光结构体与数量宏；③ 顶点着色器是否产出了 vViewPosition / vNormal，片元的光照计算依赖它们；④ 片元里是否真的执行了 #include <lights_fragment_begin> 与 <lights_fragment_end>，只声明不执行当然没有结果。还有一点：UniformsUtils.merge 会克隆 uniform 值，合并之后你手里的原始对象已经和 shader 脱钩，改它不会生效。

Q4：材质派生类 clone 之后，补丁参数为什么不同步？

Material.clone() 走的是 copy()，默认只拷贝已知的材质属性，不会自动搬运你挂在 this.uniforms 上的自定义对象，也不会重新绑定 onBeforeCompile 里的闭包。需要在子类里重写 copy(source)：先 super.copy(source)，再把 uniforms 深拷贝一份新的，并把 onBeforeCompile 重新指向新实例的 uniforms。否则 clone 出来的材质仍在修改原材质的 uniform，表现为"改一个，另一个也跟着变"。

术语解释：

  • BRDF：双向反射分布函数，描述"从某个方向来的光，反射到某个方向有多少"。
  • clearcoat：表面透明涂层，拥有独立于底材的高光瓣。
  • sheen：掠射角下的柔软背向散射，织物绒面感的主要来源。
  • anisotropy：高光沿切线方向被拉长，拉丝金属与丝绸的关键。
  • transmission：光线穿过介质，需要额外的屏幕拷贝与折射采样。
  • program 变体：由宏与材质参数组合出的独立着色器程序，每个都要编译一次。

动手小练习 ​

  1. 打开 custom-pbr-lab.html，把 clearcoatRoughness 从 0.03 调到 0.4，观察清漆高光从"镜面点"变成"柔光面"的过程，记录两次的观感差异。
  2. 把 sheen 的指数从 2.0 + uSheenRoughness * 2.0 改成固定 5.0，再把 uSheenRoughness 滑条拖到两端，解释为什么此时滑条"失效"了。
  3. 给 sheen 材质再追加一项"沿 Y 方向的条纹染色"（在 color_fragment 里注入），让同一个材质同时拥有两种补丁，并确认 customProgramCacheKey 仍只有一个值。
