27.1 基础入门：onBeforeCompile 与材质补丁 ​

前置提示：本篇属于精通方向扩展内容，建议先完成基础模块 ⑥⑫ 与 ⑭ 再学习本篇。

核心概念讲解 ​

接桥：12.3 的全息材质"另起炉灶"，代价是丢了 PBR 的一切 ​

在 ⑫ 着色器 · 全息投影 里，我们用 ShaderMaterial 从零写了一个扫描线全息球：顶点阶段做轻微抖动，片元阶段用菲涅尔算出边缘辉光，再叠上一条向上滚动的亮带。那段代码很痛快——所有像素都由自己说了算。

但如果你把那个球放进一个已经调好的产品场景，会立刻发现它"格格不入"：它不接收环境贴图，金属部分不会反射摄影棚的灯箱；它不参与阴影，投不出也接不住影子；它不响应场景里的方向光；色调映射还得自己补。原因是 ShaderMaterial 只拿到了你写的那几行 GLSL，引擎内置的 IBL、灯光循环、阴影采样、色调映射、抖动、雾效全都不在。

换句话说，12.3 的写法是"另起炉灶"：厨房是自己的，但冰箱、烤箱、调料架都得重新买。

⑥ 材质 · 物理材质 里的 MeshStandardMaterial / MeshPhysicalMaterial 恰恰相反——它们是一整套已经装好的厨房：GGX 高光、金属度工作流、PMREM 环境采样、灯光 chunk、阴影、色调映射、输出编码，一样不少。本篇要学的 onBeforeCompile 就是在这间厨房里加一道自己的菜：不拆灶台，只往既定的流程里插几句话。

内置材质的 shader 是"拼装出来的" ​

很多人以为 MeshStandardMaterial 对应一段完整、固定的 GLSL。实际上它是由几十个 chunk 拼装出来的：

text
meshphysical_vert.glsl.js
  ├─ #include <common>
  ├─ #include <beginnormal_vertex>
  ├─ #include <begin_vertex>
  ├─ #include <project_vertex>
  └─ ...

meshphysical_frag.glsl.js
  ├─ #include <common>
  ├─ #include <color_fragment>
  ├─ #include <normal_fragment_begin>
  ├─ #include <lights_physical_fragment>
  ├─ #include <lights_fragment_begin>
  ├─ #include <lights_fragment_end>
  ├─ #include <output_fragment>
  └─ #include <dithering_fragment>

#include <xxx> 是 Three.js 自己的预处理指令：编译前，WebGLProgram 会把每个 include 展开成 ShaderChunk 里对应的真实代码，再按当前材质参数拼接 #define（比如 USE_ENVMAP、USE_MAP、USE_CLEARCOAT）。

这里有一个关键事实：onBeforeCompile 在 include 展开之前被调用。所以钩子里拿到的字符串仍然带着 #include <begin_vertex> 这样的占位符，你才能用字符串替换把代码插到指定位置。如果 include 已经展开，这个注入点就无从下手了。

拼装带来的直接好处是：你改一个参数，Three.js 只是换一组 #define，或者干脆复用同一份 program。这也是材质系统能同时跑几百个物体的原因。

onBeforeCompile(shader, renderer) 里能改什么 ​

onBeforeCompile 是材质上的一个可选回调，签名是 (shader, renderer) => void。shader 是一个普通对象，包含四样东西：

字段类型能做什么注意
shader.uniforms对象追加自己的 uniform，或替换内置 uniform值必须是 { value } 结构
shader.vertexShader字符串声明 uniform / varying，插入顶点逻辑只能做字符串替换，不能重排整段流程
shader.fragmentShader字符串插入片元逻辑、改写中间变量变量作用域取决于注入点
shader.defines（部分版本）对象追加宏改宏会改变 program 缓存键，慎用

它不能做的事也很明确：不能删除内置的光照循环，不能替换 main 函数整体，不能改变 attribute 布局。想做这些，才需要回到 ShaderMaterial。

一个最小可用的补丁长这样：

js
material.onBeforeCompile = (shader) => {
  shader.uniforms.uTint = { value: new THREE.Color(0xff5fa2) }
  shader.fragmentShader = 'uniform vec3 uTint;\n' + shader.fragmentShader
  shader.fragmentShader = shader.fragmentShader.replace(
    '#include <color_fragment>',
    '#include <color_fragment>\n  diffuseColor.rgb = uTint;'
  )
}

这里有两个动作值得记住：声明要加在文件最前面（GLSL 要求先声明后使用），注入要贴着 include 写（保证插入点前面已经定义了你要用的变量）。

注入点地图：在哪儿下手 ​

内置材质的片元着色器是一串有先后顺序的步骤。选错注入点，症状往往不是报错，而是"变量不存在"或"结果被后续步骤覆盖"。常用的几个位置：

注入点所在阶段可用的关键变量适合做什么
common最前无放工具函数（噪声、色相旋转）
begin_vertex顶点position、objectNormal、uv顶点波动、形变、风摆
color_fragment片元·基础色diffuseColor染色、程序化图案、贴图混合
normal_fragment_maps片元·法线normal法线扰动、凹凸细节
lights_fragment_end片元·光照结算后reflectedLight、normal、vViewPosition自定义高光项、边缘光、sheen
dithering_fragment片元·最终输出前gl_FragColor屏幕空间叠加、噪点、暗角
output_fragment 之前片元·组装输出outgoingLight改最终颜色但保留编码

选择原则很简单：越早注入，越容易被后续步骤"吃掉"；越晚注入，越接近"在成片上加滤镜"。 染色应该改 diffuseColor（早），因为后面的光照会正确地把它当基础色处理；而边缘光应该加在 lights_fragment_end（晚），因为它属于"额外光能"，不该再被基础色乘一遍。

customProgramCacheKey 为什么必须重写 ​

Three.js 的着色器程序是按缓存键复用的。默认实现大致等价于：

js
material.customProgramCacheKey = () => this.onBeforeCompile.toString()

问题在于 Function.prototype.toString() 只返回源码文本，不包含闭包捕获的变量。下面两个材质会得到同一个缓存键：

js
function makePatched(colorA) {
  const m = new THREE.MeshStandardMaterial()
  m.onBeforeCompile = (shader) => {
    shader.fragmentShader = shader.fragmentShader.replace(
      '#include <color_fragment>',
      '#include <color_fragment>\n diffuseColor.rgb = vec3(' + colorA + ');'
    )
  }
  return m
}

两段源码一模一样，只有拼接进去的数值不同。结果就是：第二个材质复用了第一个材质的已编译程序，颜色被"传染"。这类 bug 不会报错，只会让所有物体莫名其妙变成同一个颜色。

正确的做法是让缓存键把"注入内容的身份"表达出来：

js
m.customProgramCacheKey = () => 'standard-tint-v1:' + colorA

或者，更工程化的做法：把差异做成 uniform，让 GLSL 文本保持完全一致。这样所有材质可以共享同一份 program，缓存键只需一个版本号：

js
material.customProgramCacheKey = () => 'standard-patch-v1'

注意缓存键的颗粒度要克制：每多一个不同的键，就多一次编译。线上项目里成百上千种细微变体各拿一个键，会在首帧集中编译，表现为"进场景卡两秒"。

uniform 引用共享：把对象挂到 userData ​

onBeforeCompile 可能被调用不止一次——needsUpdate = true、切换 transparent、side、增加贴图都会触发重新编译。如果你在钩子内部 new 一份 uniform，第一次拿到的引用在第二次编译后就失效了，动画立刻停住。

正确姿势是把 uniform 对象放在材质外面，钩子里只做"挂载"：

js
const shared = {
  uTime: { value: 0 },
  uAmp: { value: 1 }
}

material.onBeforeCompile = (shader) => {
  Object.assign(shader.uniforms, shared)  // 同一批对象，重复编译也不会丢
  material.userData.shader = shader        // 可选：方便调试时查看
}

之后每帧只改 shared.uTime.value += delta。多个材质共用同一批 uniform 对象是实现"一次更新、全体生效"的标准手法，也是补丁系统能做成配置驱动的前提。

字符串替换的三种姿势 ​

补丁能不能写稳，八成取决于"怎么替换"。工程上常用的三种写法，各有适用边界：

写法形态优点风险
整行替换 include把 #include <x> 换成"include + 新代码"位置精确，不影响原有逻辑include 名写错时静默失败
追加到文件头'uniform ...;\n' + shader.fragmentShader声明永远在最前面只能放声明，不能放执行语句
锚点替换命名函数找到 vec3 xxx( 之类的特征串再替换可以改函数体特征串随版本变化，最脆弱

不推荐直接对整个 main 做正则替换：内置 shader 的 main 很长，正则很容易误伤其他块，而且升级版本后必然失效。补丁要尽量小而准，贴着官方 include 写，这样即使 chunk 内部实现变了，你的注入点依然存在。

还有一条实践建议：把每个补丁写成一个独立函数，接收 shader 并返回 shader，再按需组合：

js
const patches = {
  wave: (shader) => { /* 注入顶点波动 */ return shader },
  tint: (shader) => { /* 注入片元染色 */ return shader },
  rim:  (shader) => { /* 注入边缘光 */   return shader }
}

组合顺序会影响结果：先染色的补丁再叠加边缘光，和反过来，视觉上可能不同。把顺序写进预设（见 27.3 的 patches 字段），才谈得上"可复现"。

补丁与内置参数的边界 ​

最后一个容易搞混的问题：什么时候该用内置参数，什么时候该打补丁？

  • 内置参数能表达的（roughness、metalness、clearcoat、sheen、transmission、anisotropy），优先用内置参数。它们经过引擎验证，参与能量守恒，随版本升级自动正确。
  • 内置参数表达不了的（"沿某个轴拉长的品牌高光""随音乐跳动的边缘光""只在特定区域出现的图案"），再用补丁。
  • 需要替换整个光照模型的（非 GGX 的反射、卡通分级、次表面散射），考虑 ShaderMaterial 或后处理，而不是硬塞进标准材质。

补丁的定位是"扩展"，不是"重写"。一个健康的项目里，补丁数量应该远少于内置参数的使用量；如果每个材质都要靠补丁才能看，说明你需要的可能是一套自己的渲染管线。

三个常见坑 ​

  1. 缓存复用导致所有材质被改：就是上面说的 customProgramCacheKey 问题。症状是"只改了一个物体，其他物体跟着变"。
  2. 改 uniform 却调用了 needsUpdate：uniforms.xxx.value = 1 是每帧都该做的事，不需要重编译；反过来，needsUpdate = true 会丢弃 program、重新编译，放在滑条回调里会让画面卡顿。只有改 GLSL 文本、改宏、改影响 shader 结构的材质属性才需要它。
  3. 替换字符串匹配不到：replace 找不到目标就静默返回原串，补丁"看起来没生效"。常见原因是 include 名写错（比如把 color_fragment 写成 color_frag），或目标 chunk 在当前材质版本里不存在。调试时先打印 shader.fragmentShader.includes('#include <color_fragment>')，确认注入点存在再写替换。

还有一个容易被忽略的坑：补丁不会自动作用于阴影和深度。物体投射阴影用的是 customDepthMaterial / customDistanceMaterial，默认是 MeshDepthMaterial，你的顶点波动不会体现在影子上，会出现"球在动、影子不动"的穿帮。需要时得给同一份顶点逻辑再补一次深度材质。

代码示例 ​

对应演示 onbeforecompile-lab.html：左边是打了补丁的 MeshStandardMaterial 球，右边是同参数的原版球，三个开关分别控制顶点波动、片元染色和菲涅尔边缘光。

① 共享 uniform：所有补丁共用同一批对象：

js
const patchUniforms = {
  uTime: { value: 0 },
  uWaveAmp: { value: 0 },                              // 0 表示关闭波动
  uTintColor: { value: new THREE.Color(0xff5fa2) },
  uTintMix: { value: 0 },                              // 0 表示不染色
  uRimColor: { value: new THREE.Color(0x22d3ee) },
  uRimStrength: { value: 0 }
}

② 顶点补丁：在 begin_vertex 之后偏移 transformed：

js
patchMat.onBeforeCompile = (shader) => {
  Object.assign(shader.uniforms, patchUniforms)

  shader.vertexShader = `
    uniform float uTime;
    uniform float uWaveAmp;
  ` + shader.vertexShader

  shader.vertexShader = shader.vertexShader.replace(
    '#include <begin_vertex>',
    `#include <begin_vertex>
    float wave = sin( position.y * 5.0 + uTime * 2.2 ) * 0.045 * uWaveAmp;
    transformed += objectNormal * wave;`
  )
}

begin_vertex 的原内容是 vec3 transformed = vec3( position );，所以后面可以直接改 transformed。objectNormal 来自更早的 beginnormal_vertex，用它偏移可以保证"沿法线鼓起"，而不是沿某个固定轴斜切。

③ 片元补丁：在 color_fragment 之后染 diffuseColor：

js
shader.fragmentShader = `
  uniform vec3 uTintColor;
  uniform float uTintMix;
  uniform vec3 uRimColor;
  uniform float uRimStrength;
` + shader.fragmentShader

shader.fragmentShader = shader.fragmentShader.replace(
  '#include <color_fragment>',
  `#include <color_fragment>
  diffuseColor.rgb = mix( diffuseColor.rgb, uTintColor, uTintMix );`
)

染在 diffuseColor 上的好处是：后续的金属反射、粗糙度、环境光都会把这个新颜色当作"材质本身"，看起来是材质变了，而不是贴了一张半透明膜。

④ 菲涅尔边缘光：在光照结算之后加一笔间接高光：

js
shader.fragmentShader = shader.fragmentShader.replace(
  '#include <lights_fragment_end>',
  `#include <lights_fragment_end>
  float rimTerm = pow( 1.0 - saturate( dot( normal, normalize( vViewPosition ) ) ), 3.0 );
  reflectedLight.indirectSpecular += uRimColor * rimTerm * uRimStrength;`
)

lights_fragment_end 时 normal 与 vViewPosition 都已就绪，reflectedLight 也刚好汇总完成。加在 indirectSpecular 里，等于告诉引擎"这是我额外贡献的反射光"，后面的 output_fragment 与色调映射会照常处理，颜色不会脱离管线。

⑤ 缓存键：只写版本号，差异交给 uniform：

js
patchMat.customProgramCacheKey = () => 'standard-patch-v1'

因为三个补丁的开关只改 uniform 的数值，GLSL 文本从不变化，所以一个字符串就够。这样无论怎么拨开关，都只有一份 program。

⑥ HUD 验证"没有额外材质"：

js
const r = renderer.info.render
const p = renderer.info.programs.length
statEl.textContent =
  `draw calls ${r.calls} · 编译程序 ${p} · 补丁 ${on}/3 开`

拨动开关时，draw calls 始终是"两颗球 + 地面"的 3，程序数也不增加——这正是补丁的价值：没有新建材质、没有新建绘制批次，只是在原有 shader 里多说了一句话。

常见问题解答 ​

Q1：补丁写完了，但画面没有任何变化，怎么查？

按四步排查。① 确认 onBeforeCompile 确实被调用：在钩子里加一行 console.log('compiled')，如果没打印，说明材质根本没参与渲染或已命中缓存。② 确认替换字符串存在：打印 shader.fragmentShader.includes('#include <color_fragment>')，replace 找不到目标时不会报错，只会原样返回。③ 确认声明放在最前面：GLSL 编译器对"先使用后声明"会直接报错，但错误只出现在控制台，画面只是黑掉或不更新。④ 确认注入点之后的代码没有覆盖你的修改——比如在 color_fragment 里改了 diffuseColor，但后面某个 chunk 又根据贴图重算了一遍，那就得换到更靠后的位置。

Q2：为什么我只给一个材质打补丁，其他物体也跟着变了？

这是 customProgramCacheKey 撞车的典型症状。默认缓存键取的是 onBeforeCompile.toString()，两个源码相同、只有闭包数值不同的回调，会得到同一个键，于是第二个材质复用了第一个材质的 program。修法：让键包含真正区分补丁的字段（颜色、模式、版本号），或者把差异全部做成 uniform、让 GLSL 文本保持一致。排查时可以先给每个材质打印 customProgramCacheKey() 的返回值，看看是否有重复。

Q3：更新 uniform 到底要不要 `needsUpdate = true`？

不要。material.needsUpdate 的语义是"着色器或程序结构需要重建"，会让 Three.js 丢弃当前 program 并重新编译。每帧改 uniforms.uTime.value 只是往 GPU 传一个小常量，完全不需要重编译。真正需要 needsUpdate 的是：改了 GLSL 字符串、改了影响编译的宏或 defines、切换了 transparent / side / vertexColors / 增删贴图这类会改变 shader 变体的属性。把 needsUpdate 放进滑条回调里，是很多"拖滑条就卡一下"的来源。

Q4：顶点补丁做了形变，为什么影子还是原样？

阴影走的是另一套材质。投影时 Three.js 使用 customDepthMaterial（点光源用 customDistanceMaterial），默认是 MeshDepthMaterial，你写在标准材质顶点着色器里的波动不会自动复制过去。解决办法是再建一个 MeshDepthMaterial，用同样的 onBeforeCompile 注入同一段顶点逻辑，然后赋给 mesh.customDepthMaterial。这也是"补丁要成体系"的原因：视觉、阴影、深度、后期遮罩往往需要同一份顶点代码。

术语解释：

  • ShaderChunk：Three.js 内置的 GLSL 片段库，#include <xxx> 会展开成对应源码。
  • program cache key：着色器程序的缓存标识，相同键复用同一个 GPU 程序。
  • diffuseColor：片元阶段的基础色变量，光照计算会以它为起点。
  • reflectedLight：片元阶段累积的直接/间接光照结果的容器。
  • customDepthMaterial：物体投射阴影时使用的深度材质，与表面材质相互独立。

动手小练习 ​

  1. 打开 onbeforecompile-lab.html，把三个开关依次单独打开、再全部打开，记录每次 draw calls 与 编译程序 的数值。思考：为什么程序数从头到尾没有增加？
  2. 把 customProgramCacheKey 改成返回 Math.random().toString()，旋转视角并拖动几次 GUI，观察控制台与帧率。解释为什么"每次都不一样"的缓存键是灾难。
  3. 给顶点波动补丁再加一个"沿 Y 轴随时间扭动"的项（例如 transformed.xz += ...，注意 GLSL 的 swizzle 写法），并让波动幅度随鼠标位置变化。观察补丁与 OrbitControls 是否互不干扰。
