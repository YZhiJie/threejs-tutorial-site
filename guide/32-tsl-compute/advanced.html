32.2 进阶应用：Compute Shader 与 GPU 数据流 ​

前置提示：本篇属于战略前瞻内容，不纳入阶段考核；建议先完成基础模块 ⑫ 与 ⑰ 再阅读。

核心概念讲解 ​

接桥：17.2 的 GPGPU 靠"画一张纹理来算数"，compute 终于可以正经算数了 ​

在 ⑰ 粒子 · FBO 与 GPGPU 里，我们用 GPUComputationRenderer 把粒子位置和速度写进两张浮点纹理，再"渲染一个全屏四边形"来触发计算。片元着色器本来是给像素上色的，我们却让它输出 vec4 当作数据；像素坐标就是粒子索引，纹理采样就是读数组。这套方案非常巧妙，但它有三个天然限制：

  1. 写是"按像素"的：每个片元只能写自己那个像素，不能随便写别的粒子。
  2. 没有 shared memory：同一组粒子之间想共享临时结果，只能再开一张纹理。
  3. 调度是隐式的：你控制的是"画多大一张画"，而不是"开多少个线程"。

Compute Shader 把这些限制拿掉了。它本来就是为通用计算设计的：你可以按 instanceIndex 读任意一个元素、写任意一个元素，可以在 workgroup 内共享内存并做同步，也可以显式指定工作组大小。Three.js 的 TSL 在 WebGPU 后端上直接映射到 WGSL 的 compute；在 WebGL2 回退后端上，则用 transform feedback 做近似模拟，能力有折扣，但至少能跑。

一句话概括：FBO GPGPU 是"借渲染管线算数"，compute 是"正经开线程算数"。

Compute 与"渲染到纹理"的区别 ​

维度渲染到纹理（FBO GPGPU）Compute Shader
执行单元片元（像素）线程（invocation）
写入范围只能写当前像素可写任意 storage buffer 元素
调度单位绘制一张纹理dispatch 若干 workgroup
共享内存无，需要额外纹理有，workgroup 内可共享并同步
数据布局纹理坐标即索引，受尺寸限制一维/二维/三维 buffer，按索引访问
后端支持WebGL2 即可WebGPU 原生；WebGL2 仅近似
适合场景规则网格、图像处理、旧项目兼容粒子、物理、排序、剔除、后处理统计

本节的演示用 compute 更新 20 万粒子的位置与速度。每个线程只负责一个粒子：读自己的位置和速度，算受力，积分，再写回去。没有纹理坐标，没有"画一张 512×512 的图"的心理负担。

TSL 的 storage buffer：instancedArray ​

在 TSL 里，创建一块 GPU 存储缓冲用 instancedArray：

js
import { instancedArray, instanceIndex } from 'three/tsl'

const count = 200000
const positions = instancedArray(count, 'vec3')
const velocities = instancedArray(count, 'vec3')

它返回一个存储节点（storage node），底层对应一块 StorageInstancedBufferAttribute。节点有两个关键用法：

  • positions.element(instanceIndex)：按索引拿到一个元素，可以读，也可以 assign() 写。
  • positions.toAttribute()：把同一块数据暴露成"实例属性"，供渲染阶段使用。

instanceIndex 是 compute 里的内置索引，相当于 WGSL 的 global_invocation_id 展平后的一维编号。每次 dispatch 时，渲染器会保证它落在 0 到 count - 1 之间，并自动生成边界检查。

初始化数据有两种方式：一种是在 CPU 侧直接填 positions.value.array，然后标记 needsUpdate；另一种是再写一个 init compute，用随机函数在 GPU 上生成。演示采用前者，因为初始化只做一次，CPU 填充更直观，也方便重置。

compute() 与 dispatch 大小 ​

把一段 TSL 逻辑变成 compute，需要两步：先用 Fn 包住逻辑，再调用 .compute(count)：

js
const update = Fn(() => {
  const p = positions.element(instanceIndex).toVar()
  const v = velocities.element(instanceIndex).toVar()

  const force = vec3(
    sin(p.y.mul(0.55).add(uTime)),
    cos(p.z.mul(0.55).add(uTime.mul(0.8))),
    sin(p.x.mul(0.55).add(uTime.mul(0.6)))
  ).mul(uSwirl).toVar()

  force.subAssign(p.mul(uGravity))
  v.addAssign(force.mul(uDt))
  v.mulAssign(uDamping)
  p.addAssign(v.mul(uDt))

  positions.element(instanceIndex).assign(p)
  velocities.element(instanceIndex).assign(v)
})().compute(count)

这里的 count 是总调用次数（线程数），不是 workgroup 数量。底层会按 workgroup 大小（默认 64）自动换算 dispatch 尺寸：ceil(count / 64) 个工作组。.compute() 的第二个参数可以指定 workgroup 大小，例如 .compute(count, [64, 1, 1])；大多数一维粒子场景用默认值即可。

在渲染循环里，每帧调用：

js
renderer.compute(update)

这个调用是"提交"，不是"等待完成"。它把 compute pass 排进 GPU 队列，CPU 立即返回。GPU 上的真实耗时要用时间戳查询或性能面板观察，不能用 performance.now() 直接量。演示里的"compute 提交耗时"只是 CPU 侧提交开销，正文后面会专门解释这个误区。

读回数据：getArrayBufferAsync 与 await ​

大多数情况下，compute 的结果不需要回 CPU。位置留在显存里，渲染阶段通过 toAttribute() 直接拿去用，这是最快的数据流。但有时你需要读回：做拾取、做统计、把结果存盘、或者调试。

读回要用异步接口：

js
const buffer = await renderer.getArrayBufferAsync(positions.value)

positions.value 是那块存储缓冲对应的 attribute。返回的是 ArrayBuffer，你可以按 Float32Array 解析。要点有三条：

  1. 它返回 Promise，必须 await。同步版本 getArrayBuffer 在部分后端会阻塞管线，能不用就不用。
  2. 读回会打断 GPU 流水线。GPU 必须先把 compute 写完，把数据拷回可读内存，CPU 才能拿到。每帧读回 20 万个 vec3 会产生明显的带宽压力和同步等待。
  3. 不要在动画循环里每帧 await。正确做法是低频采样（例如每 30 帧一次），或者只在用户点击"导出/拾取"时读回。有些资料会提到节点侧的 toReadback()，不同版本的 API 名称与能力略有差异，实际项目以当前版本文档为准；核心原则不变：读回是昂贵的同步点。

双缓冲与乒乓：为什么改了值，渲染却没变 ​

compute 写入 storage buffer 后，渲染阶段读的是同一块数据，所以顺序必须是"先 compute，再 render"。如果顺序反了，你看到的就是上一帧的结果；如果渲染材质引用了另一块 buffer，你看到的就是完全没更新的旧数据。

在 WebGL2 回退后端上，instancedArray 会被模拟成 transform feedback 的输入/输出。为了避免"一边读一边写"的冲突，底层会自动做 ping-pong：这一帧写 B、下一帧写 A。对使用者是透明的，但意味着：

  • 同一帧内不要假设写入立即对另一个 pass 可见。
  • 读回时拿到的是"当前可读"的那一块，不一定是刚刚提交的那一块。
  • 需要多 pass 串联时，显式保证依赖顺序，别依赖浏览器的调度巧合。

在 WebGPU 上，storage buffer 的读写是显式的，没有自动双缓冲。TSL 的 compute 节点会把同一块 buffer 既当输入又当输出，这在本节的"每个线程只读写自己索引"模式下是安全的；如果你做的是"读邻居、写自己"的算法，就要自己准备两块 buffer 做乒乓，或者使用 workgroup 共享内存加屏障。

性能边界：什么时候 compute 反而更慢 ​

compute 不是"用了就快"的魔法。下面这些情况，它可能比 CPU 或 FBO 更慢：

  • 数据量很小：几十个粒子、几百个顶点，dispatch 的固定开销和管线切换比 CPU 循环还贵。
  • 每帧都要读回：GPU 算完再拷回 CPU，省下的计算时间被同步等待吃掉了。
  • 算法需要大量分支：GPU 擅长整齐的并行，线程发散会拖慢整个 workgroup。
  • WebGL2 回退：transform feedback 的模拟有额外拷贝，且不支持共享内存与任意写，性能与能力都不如原生 compute。
  • 频繁重建 buffer：每帧重新分配 storage buffer 会触发资源创建与销毁，应该复用。

判断标准很简单：数据已经在 GPU 上、每帧计算量足够大、结果不需要回 CPU，这三条同时满足时，compute 的收益最明显。本节的 20 万粒子正好落在这个区间。

与 InstancedMesh 结合：让顶点位置由 compute 驱动 ​

compute 算出来的位置，最终要进渲染。最直接的方式是 toAttribute()：

js
const material = new THREE.SpriteNodeMaterial()
material.positionNode = positions.toAttribute()
material.scaleNode = uniform(0.08)

const sprite = new THREE.Sprite(material)
sprite.count = count

Sprite 在这里被当作"实例化的公告板"使用：count 指定实例数，positionNode 为每个实例提供位置，scaleNode 提供尺寸。每个实例的 instanceIndex 会自动对应 storage buffer 的元素索引。

如果你用的是 InstancedMesh，思路相同：把 positions.toAttribute() 接到实例矩阵或位置节点上。区别在于 InstancedMesh 还需要处理旋转与缩放，而 Sprite 只需要位置和尺寸。对于几十万级的粒子，Sprite 的公告板路径通常更轻。

结构图可以这样理解：

text
CPU 初始化
   |
   v
[positions buffer] --compute--> [positions buffer 新值]
                                     |
                                     v
                              toAttribute()
                                     |
                                     v
                          Sprite / InstancedMesh 渲染

每一帧的循环是：

text
更新 uniform -> renderer.compute(update) -> renderer.render(scene, camera)

顺序不能反。compute 必须在 render 之前提交，渲染阶段才能读到本帧数据。

同步与依赖：什么时候需要两次 compute ​

单 pass 的粒子更新很直接：读自己、写自己、渲染。但真实项目经常有多步计算，例如"先算受力，再算积分，最后算排序"。这时要注意依赖关系：

  • 如果第二步要读第一步写出的结果，就必须保证第一步已经完成。WebGPU 的命令队列会按提交顺序执行，连续调用 renderer.compute 通常会保持顺序，但不要把"通常"当成规范，跨 pass 的关键依赖应该用两次明确的 compute 表达。
  • 如果两步读写的是同一块 buffer，并且存在"读邻居"的跨线程依赖，就需要双缓冲。TSL 默认不会替你处理 WebGPU 上的读写冲突，只有 WebGL2 的 transform feedback 模拟会做自动乒乓。
  • workgroup 内的共享内存适合"局部归约"（例如每个工作组统计一小段粒子的数量），跨工作组的结果仍要写回 buffer，再由下一个 pass 汇总。

把这些关系画成数据流，比在代码里猜顺序可靠得多。一个简单的判断方法是：如果某个 pass 的输出会被另一个 pass 读取，就在图上画一条箭头；箭头形成环，就必须引入双缓冲或拆分 pass。

代码示例 ​

下面是一段完整的最小 compute 粒子骨架，省略了相机与 GUI：

js
import * as THREE from 'three/webgpu'
import { Fn, uniform, vec3, sin, cos, instancedArray, instanceIndex } from 'three/tsl'

const renderer = new THREE.WebGPURenderer({ antialias: true })
await renderer.init()

const count = 200000
const positions = instancedArray(count, 'vec3')
const velocities = instancedArray(count, 'vec3')

const uTime = uniform(0)
const uDt = uniform(0.016)
const uSwirl = uniform(1.2)
const uGravity = uniform(0.55)
const uDamping = uniform(0.96)

const update = Fn(() => {
  const p = positions.element(instanceIndex).toVar()
  const v = velocities.element(instanceIndex).toVar()

  const force = vec3(
    sin(p.y.mul(0.55).add(uTime)),
    cos(p.z.mul(0.55).add(uTime.mul(0.8))),
    sin(p.x.mul(0.55).add(uTime.mul(0.6)))
  ).mul(uSwirl).toVar()

  force.subAssign(p.mul(uGravity))
  v.addAssign(force.mul(uDt))
  v.mulAssign(uDamping)
  p.addAssign(v.mul(uDt))

  positions.element(instanceIndex).assign(p)
  velocities.element(instanceIndex).assign(v)
})().compute(count)

const material = new THREE.SpriteNodeMaterial()
material.positionNode = positions.toAttribute()
material.scaleNode = uniform(0.08)
material.transparent = true
material.blending = THREE.AdditiveBlending
material.depthWrite = false

const sprite = new THREE.Sprite(material)
sprite.count = count
sprite.frustumCulled = false
scene.add(sprite)

renderer.setAnimationLoop(() => {
  uTime.value += 0.016
  uDt.value = 0.016
  renderer.compute(update)
  renderer.render(scene, camera)
})

初始化位置时，可以直接写 positions.value.array：

js
const array = positions.value.array
for (let i = 0; i < count; i++) {
  array[i * 3] = (Math.random() - 0.5) * 12
  array[i * 3 + 1] = (Math.random() - 0.5) * 12
  array[i * 3 + 2] = (Math.random() - 0.5) * 12
}
positions.value.needsUpdate = true

注意 .value 是 attribute 本身，.array 是底层的 Float32Array。初始化之后必须设 needsUpdate，否则首次上传可能拿不到你填的数据。

运行效果展示 ​

演示默认使用 20 万粒子。每颗粒子有自己的位置与速度，compute 每帧做一次受力积分，渲染阶段直接用 positions.toAttribute() 画成公告板。画面中央是一团会呼吸、会旋转的粒子云：涡旋让它们绕着中心流动，引力把它们往回拉，阻尼让速度逐渐衰减。

左上角显示当前模式、粒子数、FPS 与更新耗时。GPU 模式下，"compute 提交"通常只有零点几毫秒；这个数字是 CPU 把 compute pass 提交给 GPU 的时间，不代表 GPU 真正算完的时间。要评估 GPU 负载，应该看 FPS 是否稳定、是否掉帧，或者使用浏览器的性能面板。CPU 模式下的"CPU 更新"才是实打实的 JS 循环耗时，会随着粒子数线性增长。

右侧面板可以切换更新方式与粒子数。切到 CPU 模式时，每帧都要在 JS 里遍历粒子、更新 Float32Array、标记 needsUpdate，再把整块 attribute 重新上传；粒子数越多，这个循环越慢，FPS 下降越明显。切回 GPU 模式，JS 侧只剩一次提交，数据始终留在显存里。

如果浏览器没有可用的 WebGPU，演示会自动把"更新方式"锁定为 CPU，并显示一条降级提示。这样即使 compute 不可用，仍然有画面、有参数、有对比，不会白屏，也不会抛出未捕获异常。

常见问题解答 ​

compute 里改了值，但渲染画面完全没变，可能是什么原因？

按顺序排查：第一，compute 是否在 render 之前调用；第二，渲染材质引用的 buffer 是否就是 compute 写入的那一块（例如 positions.toAttribute() 用的 positions，不要误用了另一块）；第三，是否在修改 buffer 后重建了材质或节点，导致渲染读的是旧节点；第四，WebGL2 回退后端是否存在自动 ping-pong，让你看到的是上一帧；第五，初始化数据是否真的上传了（needsUpdate）。最常见的是第一和第二条。

为什么每帧读回粒子位置会卡顿？

读回需要等 GPU 把 compute 写完，再把数据从显存拷到可读内存。这是一个同步点：GPU 不写完，CPU 就拿不到；CPU 不读完，GPU 的下一帧可能被阻塞。每帧读回几十万个 vec3，相当于每帧都强制"等 GPU 干完活"，流水线被打断，FPS 自然掉。正确做法是低频采样、按需读回，或者把需要 CPU 知道的信息压缩成很小的统计量（例如只读回一个计数器或包围盒）。

dispatch 的 count 和 workgroup 大小是什么关系？

count 是总线程数（总调用次数），workgroup 大小是每个工作组里有多少线程。底层会计算 ceil(count / workgroupSize) 个工作组。workgroup 越大，调度开销越小，但每个工作组占用的资源也越多，可能降低占用率。默认 64 是一个比较稳妥的起点；真正的调优要看具体算法与 GPU，不要凭感觉乱设。

WebGL2 回退后端能跑 compute 吗？

Three.js 的 WebGL2 回退后端用 transform feedback 近似 compute，能跑一些"每个线程读写自己索引"的简单算法，但不支持共享内存、任意写、原子操作等能力，调度方式也与 WebGPU 不同。写法上尽量保持"一维索引、顺序读写、无跨线程依赖"，这样回退时更不容易出问题。涉及复杂并行算法时，应该把 WebGPU 作为前提，并为 WebGL2 准备 CPU/FBO 降级路径。

Compute 和 FBO GPGPU 应该怎么选？

新项目、目标浏览器支持 WebGPU、算法需要任意写或共享内存，优先 compute。维护老项目、必须兼容 WebGL2、算法本身就是规则网格（图像处理、高度场），FBO GPGPU 更稳妥。还有一类情况是数据量很小，CPU 反而最简单。没有绝对答案，按目标平台、数据规模和算法结构来选。

为什么粒子颜色在 GPU 模式下比 CPU 模式更"纯"？

颜色映射依赖速度，而两种模式的速度积分顺序、初始值、浮点精度可能略有差异；另外 GPU 模式下速度值留在显存里，CPU 模式每帧重算并上传，数值更新频率不同。只要颜色趋势一致（快的地方偏青、慢的地方偏蓝），就不必追求逐像素相同。若差异明显，先检查两边的受力公式与阻尼是否完全一致。

动手小练习 ​

  1. 把引力换成鼠标吸引：在 compute 里增加一个 uMouse uniform，让粒子受到指向鼠标的力。提示：先算 toMouse = uMouse - p，再归一化，注意距离过近时要加一个下限，避免数值爆炸。
  2. 加一个速度上限：在积分之后对速度长度做 clamp，或者用 select 在超过阈值时按比例缩放。观察粒子云在高速时是否还会"炸开"，并解释为什么需要限制。
  3. 做一次低频读回：每 60 帧用 getArrayBufferAsync 读回一次位置，计算粒子云的平均半径并显示在 HUD 上。观察读回那一帧的帧时间是否明显升高，记录数据并解释原因。
