32.3 实战案例：GPU 驱动的可交互粒子场 ​

前置提示：本篇属于战略前瞻内容，不纳入阶段考核；建议先完成基础模块 ⑫ 与 ⑰ 再阅读。

核心概念讲解 ​

接桥：把 ⑰ 的万级粒子洪流升级成"可交互的场" ​

在 ⑰ 粒子 · 万级粒子数据洪流 里，我们已经能把几万颗粒子组织成一条条流动的线、一团团旋转的云。那一版的核心是"预设动画"：粒子按固定轨迹运动，鼠标最多改变相机，粒子本身并不真正"感知"用户。

这一篇要把粒子洪流升级成"场"。场意味着：空间中每个位置都有一股力，粒子的运动由它所在的位置决定；用户移动鼠标，相当于在场上放了一个可以吸引、也可以搅动的源头。粒子不再是"播放动画"，而是在持续响应。要做到这一点，需要把前三节的能力组合起来：

  • 32.1 的节点材质：负责"长什么样"，包括颜色、透明度、尺寸。
  • 32.2 的 compute：负责"怎么动"，包括受力、积分、边界。
  • 本篇新增的交互层：鼠标 uniform、相机控制、参数面板、性能预算与降级。

一个可交互粒子场由哪几层组成 ​

把它拆成四层，结构会清晰很多：

层输入输出负责什么
状态层粒子数、初始分布position / velocity buffer保存每个粒子的位置与速度
受力层时间、鼠标位置、引力、涡旋加速度决定场如何推动粒子
边界层空间范围、是否回绕修正后的位置防止粒子飞散或无限堆积
渲染层position buffer、速度颜色、尺寸、透明度把数据变成可见的粒子

四层都放在 GPU 上，只有参数（uniform）从 CPU 过去。这样每帧的 CPU 工作只剩"更新几个 float 和一次提交"，粒子数可以做到几十万。

鼠标位置作为 uniform 注入 ​

鼠标不是"事件回调里的一个数字"，而是要变成 GPU 能读到的 uniform。流程分三步：

  1. 把屏幕坐标转成归一化设备坐标（NDC）。
  2. 用 Raycaster 从相机发射射线，与一张位于 z = 0 的平面求交，得到世界坐标。
  3. 把命中点写入 uMouse 这个 vec3 uniform，同时用一个 uMouseOn 标记表示"鼠标是否按下"。

核心代码：

js
const raycaster = new THREE.Raycaster()
const pointerNdc = new THREE.Vector2()
const fieldPlane = new THREE.Plane(new THREE.Vector3(0, 0, 1), 0)

function updateMouseWorld(event) {
  const rect = renderer.domElement.getBoundingClientRect()
  pointerNdc.x = ((event.clientX - rect.left) / rect.width) * 2 - 1
  pointerNdc.y = -((event.clientY - rect.top) / rect.height) * 2 + 1

  raycaster.setFromCamera(pointerNdc, camera)

  const hit = new THREE.Vector3()
  if (raycaster.ray.intersectPlane(fieldPlane, hit)) {
    mouseWorld.copy(hit)
  }
}

然后在 compute 里使用它：

js
const toMouse = uMouse.sub(p).toVar()
const dist = toMouse.length().max(0.6).toVar()
const pull = toMouse.normalize().mul(
  uMouseOn.mul(uGravity).div(dist.mul(dist).add(0.9))
)

这里的 .max(0.6) 是安全下限。距离趋近于零时，normalize() 的方向不稳定，力会趋于无穷；加一个下限既避免数值爆炸，也让鼠标中心附近的粒子不会瞬间被吸成一个点。分母用 dist * dist + 0.9 而不是单纯的平方，是为了让力在近处平滑过渡。

如果希望鼠标既能吸引又能排斥，可以再加一个 uMode uniform，用 select 在"指向鼠标"与"背离鼠标"之间切换。注意不要在执行期重建节点图，用 uniform 分支就好。

边界回绕：两种策略与一个常见错误 ​

粒子场最怕"飞出去就再也不回来"。常见处理有两种：

策略一：软边界。 当粒子超出范围时，施加一个指向中心的恢复力，或者直接把位置 clamp 到边界内，同时衰减速度。优点是运动连续、不会瞬移；缺点是粒子会在边界附近堆积，形成一圈不自然的"墙"。

策略二：回绕。 当粒子越过边界时，从对面重新出现，像贪吃蛇从屏幕左边出去、右边进来。优点是粒子密度均匀、视觉上无限延展；缺点是会出现"瞬移"，如果粒子很大或颜色很亮，会看到明显的跳跃。

演示把两种策略做成一个开关。TSL 里可以用 select 做分量级回绕：

js
const wrapAxis = (c) => select(
  c.greaterThan(bound),
  c.sub(bound.mul(2)),
  select(c.lessThan(bound.mul(-1)), c.add(bound.mul(2)), c)
)

const wrapped = vec3(wrapAxis(next.x), wrapAxis(next.y), wrapAxis(next.z))
const clamped = clamp(next, vec3(-BOUND), vec3(BOUND))
const finalPos = select(uWrap.greaterThan(0.5), wrapped, clamped)

常见错误是"只回绕位置，不回绕速度"。位置瞬移了，速度方向却还指着原来的方向，粒子会在边界附近来回抖动。正确做法是位置回绕后保持速度不变（因为速度是"穿过边界"的连续量），但如果你希望粒子在边界处反弹，就应该反转对应分量的速度，而不是回绕位置。两种语义不要混用。

另一个错误是回绕范围与相机视锥不匹配。粒子在 z 方向回绕，但相机是俯视的，视觉上就会突然出现/消失。调试时先把边界画成线框，确认粒子确实在预期的盒子内运动。

颜色按速度映射，以及 ㉔ 的色彩空间提醒 ​

粒子场的"速度感"很大程度上来自颜色。演示用速度长度驱动一个 smoothstep，在蓝色与青色之间插值：

js
const vSpeed = varying(velocities.toAttribute().length())

const material = new THREE.SpriteNodeMaterial()
material.positionNode = positions.toAttribute()
material.colorNode = mix(color(0x1d4ed8), color(0x67e8f9), smoothstep(0, 3.2, vSpeed))

这里有两个细节：

  1. varying 是必要的。 速度来自 storage buffer 的实例属性，在 WebGL 里属性只能在顶点阶段读取；片元阶段要用，必须通过 varying() 显式传下去。TSL 的 varying 会自动生成对应的顶点赋值与片元声明，你不需要手写字符串。
  2. 颜色要用 color()。 模块 ㉔ 讲过，十六进制颜色是 sRGB，渲染工作空间是线性。color(0x1d4ed8) 会按当前色彩管理配置解释；如果你直接写 vec3(0.11, 0.31, 0.85)，得到的是线性值，蓝色会明显偏暗。纹理、颜色常量、renderer.outputColorSpace 三者要统一，否则整个场的色调会"发脏"。

如果粒子使用加法混合（AdditiveBlending），大量粒子重叠时颜色会迅速饱和到白色，速度差异被吃掉。演示把尺寸压小、透明度降低，就是为了保留颜色层次。这个取舍在粒子场里很常见：要"亮"，还是要"看得出速度"。

相机交互与拾取 ​

相机交互和粒子交互会抢鼠标。演示的策略是：

  • 左键按住拖动：更新 uMouse，搅动粒子场。
  • 右键拖动：旋转相机（OrbitControls）。
  • 滚轮：缩放。

实现上把 OrbitControls 的左键动作设为空：

js
controls.mouseButtons = {
  LEFT: null,
  MIDDLE: THREE.MOUSE.DOLLY,
  RIGHT: THREE.MOUSE.ROTATE
}

拾取是另一个话题。CPU 侧拾取可以用 Raycaster 与粒子的包围盒求交，但几十万粒子逐个求交不现实；更常见的做法是 GPU 拾取：渲染一张"ID 缓冲"，每个粒子写入自己的编号，然后读回鼠标位置那一个像素。注意，读回一个像素仍然是一次同步，不能每帧做。更轻量的方案是把拾取做得"近似"：不追求精确命中哪颗粒子，而是把鼠标位置当作场源，这已经足够支撑交互感。

暂停、重置与参数面板 ​

可交互场需要几个基本控制：

  • 暂停：停止累加 simTime 与 uDt，但继续渲染。这样画面静止，相机仍可旋转，方便观察。
  • 重置：重新填充初始位置与速度。GPU 模式下直接重建 storage buffer，或者写一次 init compute；演示选择重建，代码更简单，代价是偶发一次分配开销。
  • 参数面板：粒子数、引力、涡旋、阻尼、是否回绕。粒子数变化需要重建 buffer，其他参数只改 uniform，不应该触发重编译。

这里有个容易忽略的点：暂停时不要把 uDt 设成 0 后继续调用 compute。虽然结果不变，但每帧仍然有一次 dispatch 开销；更好的做法是暂停时直接跳过 compute，只 render。

性能预算与降级：按设备分档 ​

粒子数不是越多越好。它受限于：

  • GPU 的填充率（大量半透明公告板会迅速吃满带宽）。
  • storage buffer 的带宽与 compute 占用。
  • 屏幕分辨率与设备像素比。
  • 是否使用加法混合（overdraw 更贵）。

一个实用的分档策略：

设备档位建议粒子数说明
桌面独显 / 高端核显20 万 - 30 万compute 路径，加法混合，尺寸较小
普通笔记本核显8 万 - 15 万降低尺寸与透明度，必要时关掉加法混合
移动端3 万 - 6 万优先保证 30 FPS，减少 overdraw
无 WebGPU3 万 - 6 万（FBO）回退 FBO GPGPU，纹理尺寸受限

降级不只是"减少数量"，还包括：降低 devicePixelRatio、缩小粒子尺寸、关闭昂贵的混合、把 compute 换成 FBO 或 CPU。演示在无 WebGPU 时自动回退到 FBO GPGPU 版本，并保留画面与提示；在有 WebGPU 时走 compute。两条路径共用同一套参数与相机，用户感知不到"换引擎"，只会看到左上角的后端标签变化。

分档的实现方式有两种：启动时按设备能力选一次，或者在运行中监测 FPS 动态调整。前者简单、可预测，适合演示与工具；后者更灵活，但需要防止"频繁降档又升档"的抖动。一个稳妥的策略是只降不升：当 FPS 连续低于阈值时降低一档，稳定一段时间后再考虑升档，且升档必须有足够的余量。对粒子场来说，粒子数变化意味着重建 buffer，降档本身会有一次卡顿，所以不要在每一帧都做判断。

这也是本模块强调"了解即可、按需采用"的原因：compute 很强大，但它的可用性依赖浏览器与设备。生产项目里，应该先保证有一条能跑的降级路径，再考虑是否启用 GPU 计算。

代码示例 ​

下面给出可交互场的核心骨架，省略 GUI 与相机细节：

js
import * as THREE from 'three/webgpu'
import { Fn, uniform, varying, vec3, color, mix, sin, cos, uv, float,
  smoothstep, select, clamp, instancedArray, instanceIndex } from 'three/tsl'

const uTime = uniform(0)
const uDt = uniform(0.016)
const uMouse = uniform(new THREE.Vector3(0, 0, 0))
const uMouseOn = uniform(0)
const uGravity = uniform(1.4)
const uSwirl = uniform(0.9)
const uDamping = uniform(0.955)
const uWrap = uniform(1)

const count = 147456
const positions = instancedArray(count, 'vec3')
const velocities = instancedArray(count, 'vec3')

const update = Fn(() => {
  const p = positions.element(instanceIndex).toVar()
  const v = velocities.element(instanceIndex).toVar()

  const toMouse = uMouse.sub(p).toVar()
  const dist = toMouse.length().max(0.6).toVar()
  const pull = toMouse.normalize().mul(
    uMouseOn.mul(uGravity).div(dist.mul(dist).add(0.9))
  )

  const force = vec3(
    sin(p.y.mul(0.55).add(uTime)),
    cos(p.z.mul(0.55).add(uTime.mul(0.8))),
    sin(p.x.mul(0.55).add(uTime.mul(0.6)))
  ).mul(uSwirl).toVar()

  force.addAssign(pull)
  force.subAssign(p.mul(0.03))

  v.addAssign(force.mul(uDt))
  v.mulAssign(uDamping)

  const next = p.add(v.mul(uDt)).toVar()
  const bound = float(14)

  const wrapAxis = (c) => select(
    c.greaterThan(bound),
    c.sub(bound.mul(2)),
    select(c.lessThan(bound.mul(-1)), c.add(bound.mul(2)), c)
  )

  const wrapped = vec3(wrapAxis(next.x), wrapAxis(next.y), wrapAxis(next.z))
  const clamped = clamp(next, vec3(-14), vec3(14))
  const finalPos = select(uWrap.greaterThan(0.5), wrapped, clamped)

  positions.element(instanceIndex).assign(finalPos)
  velocities.element(instanceIndex).assign(v)
})().compute(count)

运行效果展示 ​

打开演示后，画面中是一团悬浮的粒子云。默认状态下，涡旋让粒子缓慢绕流，引力把它们拉向中心，阻尼抑制发散。按住左键拖动，鼠标所在位置成为一个力场源：粒子被吸引过去，在附近形成旋臂与空洞；松开后，力场消失，粒子在阻尼作用下慢慢回到流动状态。右键拖动可以旋转相机，从侧面观察场的厚度。

左上角显示后端类型、粒子数、FPS 与 compute 提交耗时。WebGPU 路径显示"WebGPU compute"，无 WebGPU 时显示"FBO GPGPU"，并出现一条橙色提示，说明已经降级。右侧面板可以调整粒子数、引力强度、涡旋强度、阻尼与边界回绕；"暂停"会冻结模拟但保留渲染，"重置"会重新生成初始分布。

颜色按速度映射：慢速粒子偏蓝，快速粒子偏青。由于使用加法混合，粒子密集的区域会更亮；如果你把粒子数调高、尺寸调大，颜色层次会被白色饱和吃掉，这是 overdraw 的直接结果，不是着色器出错。

降级路径的 FBO 版本使用相同的参数与相机，但粒子数受纹理尺寸限制。它不会有 compute 那样的任意写与共享内存能力，只在"每个粒子独立更新"的规则结构下工作。这正是本篇想传达的工程态度：先保证可用的降级路径，再考虑启用更先进的能力。

常见问题解答 ​

compute 里改了值，但渲染完全没变化，怎么排查？

先确认 compute 在 render 之前提交，且只用一次 renderer.compute(update)。然后确认渲染材质引用的就是同一块 storage buffer：material.positionNode = positions.toAttribute()。接着检查 uniform 是否真的更新（uMouse.value.copy(...) 而不是重新赋值）。如果用的是 WebGL2 回退，注意自动乒乓可能让你看到上一帧结果，连续观察几帧再下结论。最后排除"材质已经被替换但节点没重建"的情况。九成的"没变化"都出在顺序或引用错误，而不是 compute 本身。

为什么一读回数据就卡顿，甚至 FPS 直接腰斩？

读回是同步点。GPU 必须把 compute 写完、把 storage buffer 拷贝到可读内存，CPU 才能继续。每帧读回意味着每帧都强制等待 GPU，CPU 与 GPU 的并行被破坏。粒子场的正确做法是"能不读就不读"：位置留在显存，渲染直接用；确实需要 CPU 知道的信息，低频采样，或者只读回一个极小的统计量。调试阶段可以读回，上线前应移除。

鼠标力场在中心附近会把粒子"吸爆"，怎么办？

给距离加下限，并让分母平滑。演示里用 dist.max(0.6) 与 dist * dist + 0.9，避免 normalize() 在零向量附近失去方向，也避免力趋于无穷。还可以给速度设上限，或者对近处的力做衰减。不要用"距离倒数的平方"直接乘一个很大的系数，那在数值上非常危险。

粒子在边界处抖动或突然消失，是什么原因？

先检查位置回绕与速度处理是否匹配。位置瞬移但速度方向不变，会让粒子在边界附近来回穿越；如果你想要"反弹"，应该反转对应分量的速度，而不是回绕位置。其次检查回绕范围与相机视野是否匹配，粒子可能在视锥外回绕，看起来就像"消失"。调试时画出边界线框，能快速定位。

为什么移动端上粒子数一高就掉帧，但 GPU 占用看起来不高？

很可能是填充率而不是计算量。大量半透明公告板会产生严重的 overdraw，移动端 GPU 的带宽与填充率有限，每个像素被重复绘制几十次，帧率就掉了。解决方向：缩小粒子尺寸、降低透明度、减少粒子数、关闭加法混合，或者降低渲染分辨率。compute 耗时低不代表渲染便宜，两者要分开看。

是否应该给这个场加精确的粒子拾取？

看需求。精确拾取通常要 GPU ID 缓冲加读回，成本和"每帧读回"类似，不适合持续交互。更实用的做法是把鼠标位置当作场源，做"近似拾取"；如果确实要选中单个粒子，可以低频（例如点击时）做一次 ID 读回，而不是每帧做。交互体验和性能之间要取平衡。

动手小练习 ​

  1. 把吸引改成排斥：在 compute 里给 pull 乘一个 -1，或者增加一个 uMode uniform 用 select 切换。观察粒子在鼠标附近形成"空洞"而不是"旋臂"，并解释力方向改变后流场结构的变化。
  2. 加入速度上限与颜色阈值联动：给速度长度设一个上限，同时把颜色映射的 smoothstep 上限调到与上限匹配。观察颜色是否还能区分快慢，思考"限速"对视觉信息的影响。
  3. 设计一套分档策略：假设你要同时支持桌面、笔记本、移动端和无 WebGPU 四种环境，写出每档的粒子数、像素比、粒子尺寸与混合方式，并说明优先级。提示：先保证 30 FPS，再谈效果。
