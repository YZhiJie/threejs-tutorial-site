## 知识点拆解

### 1. 国内地图的三套坐标，先认门牌再谈精度

WGS84 是 GPS 的原始经纬度，GCJ-02 是国内互联网底图常用的加密坐标，BD-09 又是在 GCJ-02 上再偏一次。三套坐标描述同一块地，数值却不同，北京地区的差值通常在数百米量级。工程上不存在"哪套更准"的问题，只有"**数据和底图是不是同一套**"的问题。最稳的做法是：入库时统一转到一个约定的坐标系，把 `sourceCrs` 与转换参数写进元数据，渲染层不再做二次判断。

### 2. Web Mercator 负责"切片"，局部 ENU 负责"场景"

Web Mercator（EPSG:3857）用米作单位、经纬线拉直，天生适合切瓦片，所以几乎所有在线底图都用它。但它把高纬度面积拉大，不能当测量平面使用。真正进三维场景时，城市级项目通常再建一个**局部 ENU 切平面**：以城市中心为原点，把经纬度差换算成东向 / 北向的米数，再映射到 Three.js 的 `x = east`、`z = -north`。这一步做完，建筑、道路、地形才共享同一套"米"。

### 3. 原点与 Float32：越远越飘不是玄学

"每个城市一个原点"不只是为了数值好看，更是为了精度。`float32` 的尾数只有 23 位，坐标绝对值越大，可用的最小刻度越粗；再叠加相机近远裁剪面失衡、深度缓冲精度不足，就会出现远处模型边缘闪烁、Z-fighting。解法有优先级：先做浮动原点或按街区 / 瓦片分块，把渲染坐标压到几公里内；再收紧 `near/far`；最后才考虑对数深度缓冲。

### 4. 纠偏属于数据管线，不属于渲染循环

正确的链路是"源数据 → ETL 重投影 / 纠偏 → WGS84 → 城市 ENU → 生成 BufferGeometry → 渲染"。转换要发生在建几何之前，且只做一次。把转换塞进逐帧循环或着色器，既浪费性能，也会让"这份数据到底转没转过"变得无法审计。验收时用控制点抽样比对，把误差写进交付记录。

## 常见误区

- **误区一：把偏移当成"模型建错了"。** 建筑和底图各偏几百米、方向还一致，八成是坐标系混用；先查 `sourceCrs`，再查模型。
- **误区二：用统一常数修 GCJ-02。** 偏移是地域相关的非线性变换，全国加同一个经纬度差只能让某一块区域"看起来对"。
- **误区三：把 Web Mercator 当等距平面。** 在高德 / 百度底图上量出的"米"不是地面真实米，面积统计会系统性偏大。
- **误区四：原点只存在配置里，不进数据。** 只改渲染原点、不改数据转换，会让整城平移；原点必须作为元数据与数据一起交付。

## 自测

<details>
<summary><b>Q1：建筑与底图错位 200 米，第一步该查什么？</b></summary>

先查坐标系，不查模型。取一条道路交叉口，在底图与建筑数据里各取一个点，打印经纬度与 ENU 坐标：差值固定、方向一致，通常是 WGS84 与 GCJ-02 混用；差值随位置变化，通常是原点或投影不一致；差值是个整齐整数，可能是某处多做了一次平移。
</details>

<details>
<summary><b>Q2：为什么局部 ENU 的 z 轴要写成负的 north？</b></summary>

Three.js 的默认视角约定是 -Z 朝北、+X 朝东。若直接把 `north` 赋给 `z`，整座城市会南北翻转——建筑、道路都还在，方向却反了，截图时很难第一眼发现。所以落场景时统一写 `z = -north`，并在坐标工具函数里只做一次映射，避免各模块各写一套。
</details>

<details>
<summary><b>Q3：10 万米外的模型抖动，只开对数深度缓冲够吗？</b></summary>

通常不够。它改善深度分布，但不会修复顶点坐标本身的 float32 精度损失。优先级应是浮动原点 / 分块 → 收紧相机 `near/far` → 对数深度缓冲；共面物体再加微小 Y 偏移或 `polygonOffset`。城市级场景还应把"同屏坐标绝对值"作为一条验收指标。
</details>
