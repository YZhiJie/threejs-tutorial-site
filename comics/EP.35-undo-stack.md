## 知识点拆解

### 1. 编辑器不能只"改"，还要"记得"

直接 `scene.add()`、直接改 `position`、直接 `remove()` 是 Three.js 的日常写法，但它们都有一个共同点：**旧状态当场消失**。渲染不在乎，编辑器却很在乎。撤销的本质不是"时光倒流"，而是"保留足够的信息，把改动反向执行一遍"。

所以在编辑器里，"改"这个动作要升级成"提交一条可逆的命令"。这条命令至少要携带：操作对象是谁、改之前是什么、改之后是什么。没有这三样，撤销就是空谈。

### 2. 命令模式：`do()` 与 `undo()` 是一对逆运算

命令模式把"修改"封装成对象，对外只暴露两个方法：

- `do()`：执行修改，或重做时再次执行；
- `undo()`：把修改精确地反向执行。

现实里的命令不止变换一种。添加物体的 `AddCommand`，撤销是"移除"；删除物体的 `DeleteCommand`，撤销是"按原索引插回"；改颜色的 `MaterialCommand`，撤销是"恢复旧颜色"。每种命令都要单独保证自己的逆运算正确，这是命令式撤销最大的成本，也是它最大的价值。

### 3. 合并与两个栈：历史要"少而准"

一次拖拽会产生上百个 `objectChange`，如果每次都入栈，撤销一次只退一帧。正确做法是按**拖拽生命周期**提交：按下拍"前"快照，松开拍"后"快照，中间的变化只用来实时预览。再叠一层"同对象 + 700ms 时间窗"的合并，连续拖几次也只留一条。

历史由两个数组组成：撤销栈存"已经发生"的命令，重做栈存"被撤销、还能再来一次"的命令。规则只有一条——**任何新操作都要清空重做栈**，否则用户会在"未来"里重放一条不该存在的命令。

### 4. 序列化：只存"可重建的最小信息"

场景 JSON 不是 Three.js 对象的转储。几何的顶点数组、贴图的像素、GPU 的 program，全都不该进 JSON。真正需要保存的只有：id、类型、变换（位置 + 四元数 + 缩放）、材质引用、父子关系，以及少量业务字段。

反序列化时先校验、后清场、再重建：版本号不能高于当前支持、节点数量有上限、未知类型跳过、id 冲突要重映射。坏文件最多导入失败，绝不能让当前场景一起消失。

## 常见误区

- **误区一：把对象引用直接 `JSON.stringify`。** Three.js 对象里有大量循环引用和运行时资源，序列化函数必须显式挑选字段，不能图省事。
- **误区二：命令里的 `before` 存的是可变引用。** `before = obj.position` 会跟着拖拽一起变，撤销时等于"撤销到当前位置"，看起来像没生效。必须克隆。
- **误区三：在 `input` 事件里提交命令。** 颜色选择器拖一下、数字框敲一个字都会产生几十条历史。正确节奏是 `input` 预览、`change` 提交。
- **误区四：新操作忘了清空重做栈。** 表现为撤销两步、新加一个物体，再按重做时场景里冒出旧物体。所有写历史的入口都要清空 `redoStack`。

## 自测

<details>
<summary><b>Q1：一条合格的 `TransformCommand` 至少需要哪三样信息？</b></summary>

操作对象、改之前的 TRS 快照、改之后的 TRS 快照。`do()` 应用 after，`undo()` 应用 before。快照必须是克隆出来的副本，不能引用对象当前的可变属性。
</details>

<details>
<summary><b>Q2：连续拖拽合并成一条，边界条件有哪些？</b></summary>

至少四条：同一对象、同一类命令、在时间窗口内（通常 700ms 左右）、期间没有切换选中或撤销重做。更严谨的做法是给每次操作一个 `mergeKey`，只有 key 相同才合并。
</details>

<details>
<summary><b>Q3：为什么场景 JSON 里不存几何顶点和贴图？</b></summary>

因为它们可以由"类型 + 参数"重建，或者由资源 URL 在运行时加载。把它们写进 JSON 会让体积爆炸、跨端难以复用，而且 GPU 资源本来就无法序列化。JSON 只负责描述"场景里有什么、在哪里、长什么样"。
</details>
