| 格 | 场景 |
| --- | --- |
| ① 困境 | 像素酱给场景加了一层雾效，画面立刻像蒙了层灰、帧率从 55 掉到 24；标签君补刀：粒子一多连鼠标都飘。 |
| ② 揭秘 | 码叔在白板上画了三个叠在一起的半透明方块：同一个像素被着色三次，这就是 overdraw。 |
| ③ 实证 | 打开热力图，红色区域集中在雾效与粒子堆上；读数显示平均 4.2 倍、片元数涨了四倍。 |

## 知识点拆解

### ① "只加了一层雾"，为什么像换了个场景

雾效、光晕、粒子、玻璃，这些"看起来轻"的东西，在 GPU 眼里一点都不轻。它们通常在**同一个屏幕像素上叠了好几层**，而每一层都要跑一次片元着色器、读一次纹理、做一次混合。你看到的是一层薄雾，GPU 干的是三到五倍的活。

更隐蔽的是：这类代价**不体现在 draw calls 上**。雾效可能只是一个全屏 pass，粒子可能只有一个 InstancedMesh——`renderer.info` 的数字很漂亮，帧时间却已经爆了。这正是 [26.1](../guide/26-gpu-profiling/basics.md) 强调"CPU 与 GPU 两条时间线"的原因。

### ② overdraw：同一个像素被画了几次

overdraw 的来源只有三类：

| 来源 | 例子 | 单像素次数 |
| --- | --- | --- |
| 前后遮挡 | 墙后还有一排楼 | 2~5 |
| 半透明叠加 | 雾、玻璃、粒子、光晕 | 5~50 |
| 全屏 Pass | 后处理链 | 每 Pass +1 |

它的总代价 ≈ **像素数 × 每像素指令数 × overdraw 倍数**。像素数又等于宽 × 高 × DPR²，所以"分辨率翻倍、overdraw 不变"时，片元总量仍然变成 4 倍。

可视化方法很直接：把所有物体换成"输出常量 1、开启加法混合、关闭深度测试"的材质，画进一张浮点缓冲；红通道的值就是该像素被着色的次数，再按 黑→蓝→青→黄→红 上色，就是热力图。

```js
renderer.setRenderTarget(countRT)   // 半精度浮点缓冲
renderer.setClearColor(0x000000, 1)
renderer.render(countScene, camera) // 每画一层，红通道 +1
```

### ③ 半透明的两笔账：排序与混合

透明物体每帧要按距离排序（CPU 的 `O(n log n)`），还要从远到近绘制；GPU 侧因为要混合，通常**不能 early-z**，被遮挡的片元也必须真的着色。两层账叠加，让"大面积半透明"成为最不划算的画法之一。

替代方案：能用 `alphaTest` 就别用 `transparent`（可被深度测试裁掉）；能用加法混合就别用普通混合（顺序无关、可关排序）；粒子尽量合图集、降层数。

### ④ 后处理：每个 Pass 都是一次全屏读写

1080p 全屏一次读+写约 16.6MB，五段后处理链就是 83MB/帧，60fps 下约 5GB/s。移动端共享带宽常见只有 10~30GB/s，还要和 CPU、显示抢——所以"多一个 Pass"在手机上不是加一点，而是逼近上限。

优化顺序：能合并的效果合并进同一个 ShaderPass；非必要的 Pass 用半分辨率；能放最后的别拆两段。判断标准：**链上每多一个全屏 Pass，就假设帧时间 +1.5~3ms（移动端）**。

## 坑点清单（FAQ）

- **Q：热力图全红或全蓝，看不出层次？** 色带上限写死了。把 `uMax` 设成"当前平均 overdraw × 1.5~2"，让映射范围跟着场景走。
- **Q：降 DPR 对雾效有用，对别处没用？** 说明瓶颈在片元/带宽；如果降 DPR 完全没反应，瓶颈在 CPU 提交或 JS，回去看 calls 与主线程火焰图。
- **Q：关掉雾效还是卡？** 检查是否还有别的半透明层（粒子、光晕、玻璃）以及后处理链长度；overdraw 是累加的，砍一层不够。
- **Q：`info.memory.textures` 一直涨？** 只 `scene.remove` 不 `dispose` 就会漏；共享纹理被重复 dispose 也会出问题，谁创建谁负责。

## 自测（Quiz）

1. 用一句话定义 overdraw，并写出它的总代价与哪三个量成正比。
2. 为什么后处理每多一个 Pass，代价是"整张图再来一遍"，而不是"只加一点点"？
3. 半透明物体为什么通常享受不到 early-z 优化？给出两个替代方案。

<details>
<summary>答案</summary>

1. overdraw 是同一屏幕像素在一帧里被多个三角形覆盖并着色的次数。总代价 ≈ 像素数 × 每像素指令数 × overdraw 倍数；像素数又等于宽 × 高 × DPR²。
2. 因为每个 Pass 都要把上一张全屏结果读进来、把新结果写出去：1080p 一次读+写约 16.6MB，五段链就是 83MB/帧，是对像素总量的重复劳动，不是加法。
3. 透明物体需要与背景混合，必须保留片元颜色，无法像不透明物体那样先做深度测试直接丢弃。替代方案：用 `alphaTest` 让片元可被裁掉；或改用加法混合并关闭排序与深度写入。
</details>
