## 知识点拆解

### ① 手摆的边界：数量与变化

一栋楼、一棵树，手工摆放没有问题。但城市有两个特征会迅速击穿手工方案：**数量**（几百上千栋楼）与**变化**（改一个密度、换一种风格就要整体重来）。

手工摆放的资产还有一个隐性成本：每一栋楼都是一份独立的顶点数据。40 个楼模型听起来不多，但每个都带完整 UV 与法线，包体很快就到十几 MB。程序化的思路是把"模型"换成"规则"——代码只有几 KB，变体却是无限的。

这一步要先接受一个事实：**程序化不是替代美术，而是接管"数量 + 变化"**。需要设计感的近景主角仍然交给建模软件；需要成片出现、需要按参数整批调整的物体，交给生成器。

### ② 流水线：数据先行，渲染后置

程序化城市的四个阶段各自只做一件事：

| 阶段 | 输入 | 输出 | 实现要点 |
| --- | --- | --- | --- |
| 地块划分 | 城市尺寸、地块尺寸、密度、seed | 地块列表 | 网格 + 格内抖动，保留街区感 |
| 建筑体块 | 地块、风格、最高层数 | 楼块列表 | 覆盖率、退台、屋顶类型 |
| 街道绿化 | 地块网格、空地块 | 合并路带、实例化路灯与树 | 静态的合并，重复的实例化 |
| 合并实例化 | 全部列表 | 少量 draw call | 按"动不动"分层，而不是按数量 |

关键在"**数据先行**"：地块、楼块、窗格先生成成普通数组，渲染层再决定怎么画。这样同一份数据可以换三种输出（逐 Mesh、合并、实例化），也可以在生成完再统计"建筑数 / 体块数 / 三角数"。

生成器本身要遵守纯函数约定：参数进、几何出，不依赖时间、屏幕尺寸与 `Math.random()`。纯函数带来三个直接收益——可单测、可复现、可放进 Web Worker。

### ③ 实证：draw call 才是先掉的那根梁

同一座城，两种画法：

| 指标 | 每楼一 Mesh | 实例 + 合并 |
| --- | --- | --- |
| draw calls | 约等于楼数（300+） | 个位数到十几 |
| 三角形数 | 与楼数成正比 | 几乎相同 |
| CPU 提交 | 每栋一次状态准备 | 每类一次提交 |
| 可编辑性 | 单栋可随意改 | 改单栋要改实例矩阵或重建 |

很多人以为"卡"是三角形太多，实际先撑不住的往往是 CPU 的提交次数。300 栋楼、每栋 12 个三角形，几何量微不足道；但 300 次 draw call 的状态准备足以吃掉半帧预算。先砍 draw call，再谈三角数，这个顺序不能反。

同一 seed 的可复现性也要在实证里验证：刷新页面、换设备、改窗口大小，城市都应该一模一样。做不到，说明随机流里混进了环境量，或者 `Math.random()` 漏在了某个分支里。

### ④ 结案：三条纪律与一份配置

- **种子管复现**：用 `mulberry32` 这类带种子的 PRNG，固定随机调用顺序，禁止 `Math.random()` 参与生成。
- **参数管风格**：密度、层数、地块尺寸、风格各自只影响一件事，互不越权；参数范围要做钳制，防止手改 JSON 把浏览器生成到卡死。
- **预算管性能**：建筑数、窗格数、实例数都要设硬上限；静态物体尽早合并，同构物体尽量实例化。

把 `seed / density / maxFloors / lotSize / style` 收进一份带版本号的 JSON，城市就从"一次性作品"变成"可复现的输入"。分享一座城只需要复制一段配置，重建一座城只需要改一个 seed——这才是程序化建模真正的交付形态。

## 坑点清单（FAQ）

- **Q：每次刷新城市都不一样？** 生成路径里混进了 `Math.random()`，或随机调用顺序被条件分支改变。固定种子 + 固定顺序 + 独立随机流。
- **Q：draw call 比楼数还多？** 楼块、屋顶、窗格、路灯各建一个 Mesh 就会翻倍。同构物体统一交给 InstancedMesh，静态路带合并。
- **Q：窗格一多就卡死？** 单栋楼 8 层 × 3 列 × 两面已接近 50 个实例，200 栋就是一万。设总实例预算，只铺两个立面。
- **Q：合并几何返回 null？** 参与合并的几何体属性结构不一致（缺 uv、索引状态不同）。统一属性后再合并。
- **Q：配置改回读后 GUI 与场景不一致？** 回读参数后没有刷新面板显示。调用 `controllersRecursive().updateDisplay()` 并重新生成。

## 自测（Quiz）

1. 程序化建模相比传统模型资产的四个优势是什么？它不适合替代哪类资产？
2. 城市生成流水线的四个阶段分别产出什么数据？为什么强调"数据先行、渲染后置"？
3. 同一 seed 要得到同一座城，需要遵守哪三条纪律？如果只改密度却导致地标位置变化，问题出在哪？

<details>
<summary>答案</summary>

1. 四个优势：制作成本低（写一次生成器批量产出）、变体多（改一个参数就是新版本）、包体小（只有代码没有大模型数据）、可复现可控（seed + 参数可版本化）。它不适合替代需要设计感的近景主角、精确造型道具这类资产——这些仍然应该由美术建模完成。
2. 四阶段：① 地块划分产出地块列表；② 建筑体块产出楼块列表（位置、尺寸、颜色）；③ 街道绿化产出合并路带与实例化的路灯、树；④ 合并实例化把上述数据压成少量 draw call。强调数据先行，是因为渲染层可以晚一步决定"逐 Mesh / 合并 / 实例化"，同一份数据能换三种输出，也便于统计与导出配置。
3. 三条纪律：不用 `Math.random()` 而用带种子 PRNG；固定随机调用顺序；不依赖时间、屏幕尺寸、设备像素比等环境量。只改密度却导致地标移动，是因为地标与地块共用同一条随机流——密度改变了每个格子的随机消耗数量，后续所有随机值整体错位。修法是给地标用独立种子，或先固定地标格再生成其它地块。
</details>
