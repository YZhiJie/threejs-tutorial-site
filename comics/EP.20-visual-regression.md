## 知识点拆解

### ① 肉眼回归为什么必然失败

3D 页面的输出是一张没有语义的像素画布，回归只能靠"看"。人眼盯 20 个页面，注意力衰减、前后记忆模糊，2 像素级的偏移根本不可靠。更糟的是它**不可规模化**——页面翻倍，凌晨也跟着翻倍。出路是把"看"变成"比"：机器不疲劳、不记得、只看像素差。

### ② 视觉回归流水线

| 环节 | 做什么 | 关键配置 |
| --- | --- | --- |
| 拍基线 | 首次运行存标准截图 | 与 CI 同容器生成，随仓库提交 |
| 拍新图 | 每次 CI 现场截图 | 锁 viewport、deviceScaleFactor |
| 对比 | 逐像素算差异 | `maxDiffPixelRatio: 0.01` 容忍噪声 |
| 出图 | 失败时产 expected/actual/diff 三图 | diff 里差异像素染红 |

抗噪三板斧：**固定种子**（seedrandom 替代 Math.random）、**冻结动画**（测试钩子 freeze 停渲染循环）、**mask 动态区域**（告警列表、时钟不参与对比）。

### ③ 实证：三类门禁的分工

CI 门禁不是一条断言，是三道防线：

- **结构门禁**：InstancedMesh、楼数、draw calls < 500——抓"忘了实例化"；
- **视觉门禁**：默认视角截图 vs 基线——抓"阴影/配色被碰了"；
- **性能门禁**：100 帧采样 P95 < 33ms——抓"这栋楼让中端机跑不动"。

漫画里的实战：阴影偏移 2px，结构与性能断言全绿（它们看不见像素），视觉门禁红灯并产出 diff 图——2341 个差异像素、占比 2%，红块正好圈在楼群阴影区。

### ④ 门禁的运营纪律

- 基线是仓库资产：更新基线单独提交、附 diff 图说明原因；
- 便宜的先跑：单测秒级在前，e2e 分钟级在后，反馈越快红灯越有人看；
- 帧时间在 CI 虚机（SwiftShader 软渲染）放宽阈值 + 趋势告警，33ms 硬门禁留给 GPU runner 与真机夜跑；
- 红灯必须 30 秒能看懂原因，看不懂的红灯迟早被团队绕开。

## 坑点清单（FAQ）

- **Q：截图总有微小差异，阈值放宽又怕漏真回归？** 先固定种子 + freeze 把内容变化降到零；再 mask 掉时钟、告警列表等动态区域；最后用两层参数搭配——threshold 管单像素色差，maxDiffPixelRatio 管差异占比。真回归是成片的红，噪声是零星的点。
- **Q：本地 Mac 生成的基线到 Linux CI 全挂？** 渲染栈跨平台不可能逐像素一致。基线必须在与 CI 相同的容器里生成——本地更新基线也用 Playwright 官方 docker 镜像跑，再把 PNG 提交进仓库。
- **Q：CI 虚机里 P95 帧时间死活过不了 33ms？** SwiftShader 软渲染比真 GPU 慢 10~50 倍，帧时间没有跨机绝对意义。CI 上硬门禁换成结构量（draw calls、三角形数），帧时间放宽阈值并收集趋势做告警；33ms 的精确验收放在带 GPU 的 runner 或真机夜间任务上。

## 自测（Quiz）

1. 为什么视觉回归要求"固定随机种子 + 冻结动画"之后才能截图？
2. draw calls 和 P95 帧时间，哪个更适合做无 GPU CI 环境的硬门禁？为什么？
3. 团队抱怨"门禁老误报，我们直接跳过了"，按本篇的思路应该怎么修？

<details>
<summary>答案</summary>

1. 截图对比的前提是"两次运行的画面本该逐像素一致"。Math.random 每次生成不同布局、动画每帧都在动，差异来自内容本身而非回归，阈值再宽也全是误报。固定种子让内容确定，freeze 让时间确定，剩下的差异才全是渲染层的信号。
2. draw calls。它是结构量——由场景内容决定，与 GPU 快慢无关，SwiftShader 下读数与真机一致，适合硬门禁。P95 帧时间在 CI 虚机上被软渲染拖慢 10~50 倍且受邻居负载影响，硬卡 33ms 必然误伤，应放宽阈值、看趋势，精确验收交给有 GPU 的环境。
3. 门禁的可信度比严格度更重要：① 先降噪——逐个治理偶发失败用例（固定种子、freeze、mask、阈值分层），重试最多 1 次；② 红灯给证据——diff 图、读数要让人 30 秒看懂原因；③ 保留留痕的逃生门——允许 maintainer 豁免但要求写明原因。目标是让团队信门禁，而不是怕门禁。
</details>
